# P4.21 — IM 宿主 `guanlan im`（平台无关核心 + 薄适配器，只读，可选叠加层）

> P4 已有两种宿主传输：**Web**（浏览器里的人）与 **MCP**（Agent 客户端）。P4.21 补**第三种——IM 里的人**：
> 让人在自己已经在的聊天窗口里问 wiki。**同一套只读会话逻辑（`Conversation.turn()`）、同一零写契约、
> 同一零业务智能。**
>
> **形态是「一个平台无关的核心 + 若干薄适配器」，不是「某一个平台的宿主」**（决策P4.21-1）。
>
> **状态：已实现**（实现设计 v12 经十一轮评审修订后落地；实现期的偏离与取舍见 **§15**）。
> **v1 范围 = 个人微信 + 飞书**（§1）。真机联调（§11 第 4/6 步）待各自环境验证。
>
> **平台事实的出处**：本文所有平台行为（端点、字段、错误码、频控、能力位）均**逐条核对过一套
> 已在生产跑的第三方参考实现的源码**（两家适配器合计约一万行），与平台**官方文档**不符处
> **以源码为准并标注**（决策P4.21-24）。该参考实现不公开，故下文只引述**行为结论**、
> 不给文件与行号——结论本身可由真机联调复验（§11 第 4/6 步），那才是最终判据。

### 第四轮复审修订（v4 → v5）

复审再提 3 阻断 + 3 问题，**全部接受**——其中 #24 是我自己在 v4 引入的自相矛盾（sweep 删了记录，却还要求日后
认得出它过期过）。三条引用源码的断言复核属实，**两条比评审说的更严重**：

- `arun` 在收到 `asyncio.CancelledError` 时是 `token.cancel(...)` 后**立刻 re-raise**（`agentao/agent.py:1243-1246`），
  **不等线程**。所以 `task.cancel()` 不只是"停不掉"——它让我们**误以为已经回来了**，而线程还在跑。
  （对照：`request_stop()` 走 token 路径，`await arun` 经 future 返回时**线程确已结束**。两条路径的差别就在这。）
- agentao 的 `arun` 用**自己的 `ThreadPoolExecutor`**（`_get_arun_pool()`，`agent.py:56-62`），其 worker 是
  **非守护线程**，`concurrent.futures.thread` 注册了 `atexit` 钩子在解释器退出时 `join()` 它们——
  **一个卡死的 worker 会让进程卡在退出那一刻**。`sys.exit()` / 从 `asyncio.run()` 返回都救不了。

## 0. 定位

### 0.1 为什么是 P4.21

- **不是 `.1` 子半阶段**：`.1`（P4.6.1/P5.2.1）的定性是「补漏 + 不改任何既有契约」；P4.21 是**新传输 + 新契约**，
  与 P4.17 给 MCP 补 http 同性质——那次也没用 `.1`。
- **不是新里程碑**：仍属「可选宿主层」，与 P4.10/P4.17 兄弟半阶段同性质。
- **不是直接 E2**：**不动数据模型**——所有获准用户看**同一个整库只读视图**，隔离的只是各自的会话历史。这是
  **P4.9 会话分租模型的第二个宿主**，作 E2 前哨。

### 0.2 身份可信度是**分档**的

- **企业系（飞书 / 钉钉 / 企业微信）= 强档**：`user_id` 由企业成员体系认证，可在后台查到是谁、离职即失效。
- **个人微信 = 弱档**：扫码得到的是 **iLink bot 身份**，入站 `from_user_id` 是 iLink 作用域内的标识——
  **稳定、但不可枚举、不可反查、与真实身份无绑定**。

**结论不是「弱档不能用」，是「弱档只适合小圈子」**：几个人的手工授权是一次性成本，200 人的组织不可行。
帮助文案必须写明，不得让弱档冒充强档（决策P4.21-7）。

> **弱档带来的连锁问题**：白名单里的 ID 从哪来？这正是评审 #1 的死锁——由 §9.1 的 `im-identify` 解开。

### 0.3 三条正交的信任线，不可互相顶替

- **P4.11 = 提示词注入面**（`raw/`/wiki 正文是「数据、不是指令」）——纯语义，与网络无关。
- **P4.17 = 网络/传输面**（谁能连、绑哪个地址、要不要 token）。
- **P4.21 = 身份与受众面**（提问者是谁、答案发给谁看见）——**新增**。前两条都不覆盖它：一个零监听端口的进程，
  照样能经**出站**长连把整库答案送进一个 200 人的群。

P4.11 在这里有**新入口**：IM 消息是不可信输入（对方可能贴「忽略以上指令」）。入站文本以「用户提问」身份进
prompt，与 `raw/` 正文同属**数据**；§14 要把这个入口补进 `AGENTAO.md` 措辞。

### 0.4 诚实的前置

`guanlan web` 已有完整问答 UI、SSE 流式、mermaid/KaTeX/flint 渲染——**这些在 IM 通道里一个都用不上**。手机上经
私有网访问 Web 宿主，零新代码，绕开全部平台限制。**本半阶段成立的前提，是「切出 IM、开浏览器、找标签页」的
摩擦足够大**（§13-1）。

> 顺带：Web 宿主绑死 `127.0.0.1`（决策P4-4），私有网虚拟网卡地址不能直接绑。给 `guanlan web` 加 `--host` +
> 按 P4.17 纪律的 token 闸，比整个 IM 宿主小两个数量级。**建议作为独立前置小改动，不并入本半阶段。**

### 3.2 `contract.py` —— 唯一的平台相关面

```python
@dataclass(frozen=True)
class AdapterCaps:
    max_message_length: int
    max_parts: int               # 单次回答最多几片（评审 #4：长答案契约的有界化参数）
    supports_edit: bool
    supports_typing: bool
    supports_late_push: bool
    supports_group: bool
    chunk_delay_s: float         # 分片之间的间隔（防频控）
    batch_delay_s: float         # 入站分片合并的静默期
    batch_split_delay_s: float   # 上一片接近上限时的加长静默期


@dataclass(frozen=True)
class InboundMessage:
    tenant: str          # account_id / tenant_key：防跨租户撞号
    chat_id: str
    chat_type: str       # "dm" | "group"
    user_id: str
    text: str            # msg_kind != "text" 时可能为空
    msg_id: str
    mentioned_me: bool   # 群内是否 @ 了机器人（**平台结构化字段**，绝不靠文本猜）
    msg_kind: str        # "text" | "other"  ← 评审 #9
    has_attachments: bool


@dataclass(frozen=True)
class OutboundRef:
    chat_id: str
    message_id: str      # 供 edit 定位；不支持 edit 的适配器回空串


class IMAdapter(Protocol):
    name: str
    caps: AdapterCaps

    async def start(self) -> None: ...
    async def close(self) -> None: ...
    def inbound(self) -> AsyncIterator[InboundMessage]: ...   # **必须可取消**，见下

    async def send(self, chat_id: str, text: str) -> OutboundRef: ...
    async def edit(self, ref: OutboundRef, text: str, *, finalize: bool = False) -> None: ...
    async def typing(self, chat_id: str, on: bool) -> None: ...
```

**核心永不写 `if platform == "weixin"`**（决策P4.21-3）——只读 `caps` 分派。新增平台 = 实现 Protocol +
填 `AdapterCaps` + 注册一行，核心零改。

**`inbound()` 的可取消义务（评审 #29，决策P4.21-56）**：**不给 Protocol 加 `stop_receiving()`**——那会把停机
责任摊到每个适配器头上，而它们要做的事其实完全一样。改为一条**义务**：`inbound()` 必须**只阻塞在 I/O 等待上**
（socket 读 / `asyncio.Queue.get`），使外部 `task.cancel()` 即可让它干净结束；**取消点上不得留下半提交的状态**
（如"已推进 offset 但事件还没交出去"）。停机时宿主取消收流 task，随后才 `close()` 适配器（§4.4）。

> 微信长轮询被取消在 `getupdates` 半途 → 该批事件的 offset 未推进 → **下次启动会重投**。这是可接受的
> at-least-once：它们本来就没被回答过。（`msg_id` 去重表在内存里、重启即空，故重投**会**再跑一遍——
> 但停机时未回答的消息本就该再跑。）

**`msg_kind` 的分工（评审 #9，决策P4.21-36）**：适配器只做**事实映射**（这条消息是不是纯文本、有没有附件），
**不自行回复**；「见到附件回一句固定提示」是**核心**行为（`intake` 判 `msg_kind != "text"` → 走固定回复路径），
故可在 `test_im.py` 里用 FakeAdapter 决定性地测到。

### 4.1 `serve_im` 装配顺序（**校验全部先于任何副作用**）

`clock` 两边同源（store 与 registry 传同一只）：不是语义依赖——registry 的过期判定只看自己的 `last_seen`
（§4.5）——而是让「注入假时钟」的测试里两边的时间轴一致，日志里的时间读数也对得上。

**`adapter.start()` 失败与信号处理器的收尾**（评审 #40，决策P4.21-67）：`start()` 抛错（凭据失效、
网络不通、飞书 WS 握手被拒）时——

| 动作 | 为什么 |
|---|---|
| `await adapter.close()` 兜底（裹 `suppress`） | `start()` 可能已经建了一半连接；不关就留着一条半死的连接和一个 SDK 线程 |
| **恢复原信号处理器** | `_install_signal_handlers` 换掉的是**进程级**状态。失败路径不恢复，调用方（测试、或将来把 `serve_im` 嵌进别的进程的人）就继承了一对指向已死对象的处理器——其中一个还会 `os._exit` |
| 释放 §8.5 的凭据锁 | 否则下一次 `im-login` 会被一把没有主人的锁挡住 |
| 返回 `EXIT_AGENT_ERROR` | 与 §4.4 的"入站流中断"同类：宿主起不来 |

三件事都放 `finally`，且**顺序无关**（互不依赖）。`_install_signal_handlers` 因此要返回一个可还原的句柄
（`contextlib.ExitStack` 或旧 handler 元组），正常退出路径同样还原。

**④ 能力一致性拒启**（决策P4.21-25）：给了 `--allow-chat` 但 `caps.supports_group=False`（个人微信）→
**拒启并明示**「该平台收不到群消息，`--allow-chat` 不会生效」。替代「静默不生效」——后者让人以为配好了、
实际永远等不到，且无从排查。

### 4.2 一轮问答的生命周期闭合（评审 #10，决策P4.21-37）

`ConversationStore` 的 idle 回收靠 `Conversation.is_idle(now, ttl)` 判定，而它**只在 `begin_turn`/`end_turn`
维护的在飞计数为 0 时才认为空闲**。IM 的一轮可能跑几分钟——**不配对调用就可能被回收并 `close()` 掉正在用的
agent**。故：

```python
conv, status = await registry.acquire(key)     # 慢：内部卸线程
# ┌── 不可分割段：以下三行之间**不得有任何 await**（评审 #25/#31）──┐
if self._closing:                              # 第二道停机闸
    return                                     # 静默返回，一个字也不发
act.conv = conv                                # 登记，使 stop_all 看得见
conv.begin_turn()                              # ★ 必须在同一段内，理由见下
# └──────────────────────────────────────────────────────────────┘
try:
    if caps.supports_typing:
        await adapter.typing(chat_id, True)
    answer = await conv.turn(text, emit)
    ...
finally:
    conv.end_turn()
    if caps.supports_typing:
        with contextlib.suppress(Exception):
            await adapter.typing(chat_id, False)   # typing-off 必须在 finally
```

`begin_turn`/`end_turn` **必须 try/finally 配对**；typing-off 同样入 `finally`（否则异常路径下用户会看到
「正在输入…」永远不消失）。

**为什么 `begin_turn()` 必须挤进那个不可分割段**（评审 #31，决策P4.21-58）：`request_stop()` 是**三态**的
（`conversation.py:745-767`）——有活跃令牌则打断；**无令牌但 `_inflight > 0`** 则记待停；**否则返回 `False`
什么都不做**。而 `act.conv = conv` 之后、`begin_turn()` 之前，恰恰是「令牌没装、`_inflight == 0`」：
停机在这一刻调 `request_stop()` 会**空转**，然后这一轮照常起跑，再也没人叫得停它。
把 `begin_turn()` 拉进同一段，`stop_all()` 看得见 `conv` 的**任何**时刻都至少落在第②态上，
待停会在 `turn` 装令牌时立即兑现（`conversation.py:588-590`）。这条闸才算真正闭合。

### 4.3 卸线程通则（评审 #8，决策P4.21-35）

**一切同步的磁盘 / CPU / 阻塞网络路径都必须 `await anyio.to_thread.run_sync(...)`**，否则一次调用卡住整个
事件循环、**所有人的消息都收不到**。v1 明确的三处：

| 路径 | 为什么 |
|---|---|
| `ConversationStore.create()` / `.restore()` | 其源码注释明写「构造慢、经 `anyio.to_thread` 卸载」 |
| **`ConversationStore.get()`**（评审 #28） | 看着是"字典查一下"，其实**与 `create()` 共用同一把 `threading.Lock`**，而 `create()` 在**慢 Agent 构造期间全程持锁**（`conversation_store.py:114` 注释明写此意图，为的是让上限是硬上限）。于是「新用户建会话」会把「老用户 `get()`」连同整个事件循环一起卡住——**一个同步锁把两条本该无关的路径串了起来** |
| `ConversationStore.delete()`（`drop` 内，决策P4.21-44） | 内部 `conv.close()` 被源码标注「慢，锁外」 |
| `/search`（`CorpusCache` 检索） | 同步磁盘 + CPU；冷启动可全库扫描，后台预热未完成时仍会阻塞 |
| 飞书 `lark-oapi` 的一切调用 | SDK 是同步的（§8.1） |

> 判据不是「这个调用看起来慢不慢」，而是**「它会不会去拿一把别人可能长期持有的锁」**——
> `get()` 正是栽在这一条上。

新增任何同步调用前先问这一条——写进 `guanlan/im/` 的模块 docstring。

### 4.4 任务结构与优雅停

```python
async def _run(...):
    await adapter.start()                            # 抛错 → close() 兜底（§4.1，评审 #40）
    recv = asyncio.create_task(_receive_loop())      # 收流独立成 task（评审 #29）
    stop = asyncio.create_task(stop_event.wait())    # 信号处理器置位
    code = EXIT_OK
    try:
        # ★ 两者**同时等**（评审 #30）：只等 stop_event 的话，收流一死进程就成了活死人
        await asyncio.wait({recv, stop}, return_when=asyncio.FIRST_COMPLETED)
        if recv.done():                              # 收流**非预期**结束
            exc = recv.exception()                   # 读一次——否则 asyncio 报 "never retrieved"
            _logger.error("入站流已中断，宿主无法继续服务", exc_info=exc)
            code = EXIT_AGENT_ERROR                  # 正常返回也算错：长驻宿主没有"收完了"这一说
    finally:
        # ★ 停机序列必须在 finally 里（评审 #35）：无论上面怎么退出的，①~⑥ 都要跑完
        failed = await _shutdown(recv, stop, ...)   # 返回失败步骤列表（评审 #51）
        if failed:
            code = EXIT_AGENT_ERROR                # 清理没干净 → **绝不报 0**
    return code

async def _shutdown(recv, stop, ...) -> list[str]:
    # ★ 每步各自兜异常并**记账**（评审 #45/#51）：后面的照跑，但失败不会被吞成"成功退出"
    failed: list[str] = []

    async def _step(name, coro_fn):
        try:
            await coro_fn()
        except Exception:                            # noqa: BLE001 — 清理不因单步失败中断
            _logger.error("停机步骤 %s 失败", name, exc_info=True)
            failed.append(name)

    async def _cancel_tasks():
        for t in (recv, stop):
            if not t.done():                         # ★ 只取消**未完成**的
                t.cancel()
                with contextlib.suppress(asyncio.CancelledError):
                    await t
            # 已完成的 recv：上面已 exception() 读过，**绝不再 await**（会重抛原异常）

    await _step("cancel-tasks", _cancel_tasks)
    await _step("intake-drain", lambda: intake.drain(flush=False))   # ②
    await _step("stop-all", delivery.stop_all)                       # ③④⑤
    await _step("adapter-close", adapter.close)                      # ⑥
    return failed

async def _receive_loop():
    async for msg in adapter.inbound():
        await intake.offer(msg)        # 五道闸，**不阻塞**（debounce 用独立 task）
    # intake flush → delivery.submit(ready)：**建 task 与登记同一步完成**（评审 #25）
```

- **每一步都要能扛住前一步抛错**（评审 #45，决策P4.21-70）：v7 把三步顺序 `await` 排开，
  `intake.drain()` 或 `stop_all()` 一抛，`adapter.close()` 就没了——而"①~⑥都要跑完"正是上一轮
  刚立的契约。**清理代码自己不能有单点故障。** 信号处理器还原与凭据锁释放在更外层
  （`serve_im` 的 `finally`，§4.1），与 `start()` 失败路径共用同一套兜底。
- **但"继续跑"不等于"没事发生"**（评审 #51，决策P4.21-71）：v8 用 `suppress(Exception)` 兜住
  `adapter.close()`，于是**连接没关干净、进程照样返回 `EXIT_OK`**——这与步骤⑦"只有走完⑤⑥才有资格
  返回 0"直接矛盾，而且是**最坏的一种矛盾**：运维看到 0，以为一切正常。
  故每步各自 `try/except` + **记账**，`_shutdown` 返回失败步骤名列表；**任一步失败 → `EXIT_AGENT_ERROR`**。
  记账用 `list[str]` 而非布尔——日志里要能说清是**哪一步**没干净。

- **收流死了必须让进程知道**（评审 #30，决策P4.21-57）：登录失效、SDK 抛错、连接永久失败都会让
  `inbound()` 返回或抛异常。v5 只 `await stop_event`，于是这些情况下**进程还活着、日志一片安静、
  消息再也收不到**——用户能看到的只有"机器人不理我了"。而 `recv` 的异常若无人 `exception()`，
  asyncio 只会在 task 被 GC 时吐一句 "Task exception was never retrieved"，很可能根本没人看见。
  **正常返回也按错误处理**：长驻宿主不存在"入站流正常结束"这回事。
- **但"读异常"和"等 task"不能同时做**（评审 #35，决策P4.21-62）：v6 在读完 `recv.exception()` 之后，
  停机步骤①又原样写着 `recv.cancel()` + `await recv`——**对已完成的 task，`cancel()` 无效而 `await`
  会把那个异常重新抛出来**，于是 `drain` / `stop_all` / `close` 一个都不跑，正好把"收流出错"变成
  "既没收流又没清理"。故：**按 `done()` 分支**（未完成才取消并 `suppress(CancelledError)`，
  已完成只读一次结果），且**整个停机序列放进 `finally`**。
  > 这是我上一轮改动自己引进的：#30 换掉了主协程的等待方式，却没有回头重读步骤①。
  > **在既有序列上打补丁而不重读整段，就会留下这种"两处各自正确、合起来错"的缝。**

- **入站永不阻塞在应答上**：否则一个 90 秒的问答会堵住整条入站流。
- **task 的创建权归 `Delivery`**（评审 #25，决策P4.21-52）：`server` 不再自己 `create_task` + 维护 `_tasks`。
  原因是 `Activity.conv` 只能在 `registry.acquire()` **之后**才填得上，而 `acquire` 里有一段卸线程的慢构造——
  停机若正好落在这段窗口，`active()` 是**空的**，`stop_all()` 便以为没事可等，`adapter.close()` 之后那个 task
  才拿到会话、继续往已关闭的连接上发。**登记必须早于第一个 `await`**，所以只能由 `submit()` 在建 task 的同一步做掉。
- **`_closing` 双闸**：`handle()` 入口查一次；`acquire()` 返回后**再查一次**，且这次检查与 `act.conv = conv`
  之间**不得有任何 `await`**（与 §5.1 的 cancel-delivery 竞态守卫同一条纪律）。这样才闭合：
  能过第二道闸的 task，其 `conv` 在 `stop_all()` 拍快照前必已登记；过不了的直接静默返回、一个字也不发。
- **单飞**（决策P4.21-13）：`Delivery._inflight: set[session_key]`。命中即回「上一个问题还在处理，请稍候」
  并 return——**必须给显式反馈**而非静默阻塞。沿用 P4.19「单飞 + 并发拒绝、不排队」的姿态。
- **优雅停顺序**（评审 #10/#13/#19，决策P4.21-41/48）：

  | 步 | 动作 | 为什么不能省 / 不能换序 |
  |---|---|---|
  | ① | **未完成才** `recv.cancel()` + `suppress(CancelledError)` 地 `await`；已完成则只读结果（`stop` task 同理） | 收流 task 只阻塞在 I/O 等待上，取消即停（评审 #29）。**"已完成"这一支不可省**（评审 #35）：对已出错的 task `await` 会重抛，把整个停机序列打断在第一步 |
  | ② | `await intake.drain(flush=False)` | **丢弃**未到期的 debounce 缓冲（半条消息不该在关机时触发一轮 LLM 花费） |
  | ③ | 置 `_closing`，再对 `active()` 中**已有 `conv`** 者调 **`conv.request_stop()`** | 顺序不可反：先置闸再拍快照，才轮不到"闸后新登记"的漏网（评审 #25）。而**绝不 `task.cancel()`**——理由见下 |
  | ④ | 置每个 `Activity.writer` 的 `_abort` 并唤醒（见 §6.2） | 否则 writer 可能在关机后继续编辑占位消息 |
  | ⑤ | **无限期** `await` **全部** `Activity.task`（含 `conv` 仍为 `None` 的）与 writer；每 30s 记一条 WARNING（列出还没收尾的 `session_key`） | 见下方「为什么 30 秒不是超时」 |
  | ⑥ | `await adapter.close()` | 必须在所有 turn 真正结束**之后**——否则残留线程的收尾 `send`/`edit` 打在已关闭的连接上 |
  | ⑦ | 返回 `EXIT_OK` | 只有走完 ⑤⑥ 才有资格返回 0 |

  ③④⑤ 封装在 `Delivery.stop_all()` 里（评审 #20），使 `server` 不必伸手进 `Delivery` 的内部集合。

- **两类取消必须分清（评审 #29，决策P4.21-56）**——这是本节最容易被后人揉成一团的地方：

  | | 收流 task（步骤①） | 问答 turn（步骤③） |
  |---|---|---|
  | 阻塞在哪 | **纯 I/O 等待**（socket 读 / `Queue.get`） | **executor 线程**里的 `chat()` |
  | 停法 | `task.cancel()`，**正当且干净** | **只能** `conv.request_stop()` |
  | 取消它会怎样 | 迭代器在 await 点抛 `CancelledError`，无后台残留 | `arun` 只是替我们置了令牌就**立刻 re-raise**（`agentao/agent.py:1243-1246`），**线程还在跑而我们已经"回来了"** |

  换句话说：**`task.cancel()` 在这里不是"没效果"，是"有反效果"**——它把"还没停"伪装成"已经停了"。
  而 `request_stop()` 走令牌路径，`await arun` 经 future 返回时**线程确已结束**。两条路径的差别就在这一点上。

- **为什么 30 秒是 WARNING 而不是超时**（评审 #19，决策P4.21-48）：超时后 `task.cancel()` **恰好重演本设计
  要修的那个错**——外层 task 取消了，executor 线程照跑，然后步骤⑥关掉连接，残留线程的收尾写打在死连接上。
  故超时只用来**告诉用户还在等谁**。

- **优雅停机没有绝对时间上界——这一点必须说明白**（评审 #43，决策P4.21-68）。
  v6/v7 说"真实上界由模型/API 的请求超时保证"，**这句是错的**，两条源码事实：

  1. `openai==2.50.0` 的 `read=600` 由 httpcore 施加在**每一次网络读取**上
     （`httpcore/_sync/http11.py` 的 `_receive_response_body`：`timeout = timeouts.get("read")`
     在**逐块循环内**取用），**不是整次响应的墙钟上界**。服务端只要在 600 秒内持续吐字节
     （SSE 心跳、注释行），这个流可以跑到天荒地老。
  2. agentao 的取消检查在 `for chunk in stream:` 的**每个已解析 chunk** 上（`llm/client.py:717-718`）。
     只有原始心跳、不产出 chunk 时，循环体根本不执行——**`request_stop()` 无处兑现**。
     60 秒重试预算也只在请求**抛异常之后**才检查，中止不了当前请求。

  **所以第 ⑤ 步的"无限期等"字面成立：它可能真的很久。** 结论不是去改这条设计，而是把话说准：

  | 层次 | 谁来保证 | 是不是绝对 |
  |---|---|---|
  | `tools/call` 的**出站写入** | **没有人** | **否**（评审 #57：计时器在 write **之后**才起） |
  | `tools/call` **写完后等响应** | `--mcp-request-timeout` = T（§4.7） | 是，但只管**这一段** |
  | MCP 握手、Streamable HTTP 传输往返 | agentao 的 startup 超时（`wait_for`） | 是，但只管**这一段** |
  | **legacy SSE 传输进入、stdio 传输进入、失败清理、`disconnect()`** | **没有人** | **否**（评审 #55/#56） |
  | 一次完整的 MCP 工具执行 | —— | **否**：含上面那行，故**无严格总墙钟上界** |
  | 模型请求的空闲间隙 | `openai` 的 `read=600` | 是，但只管**空闲**，不管总时长 |
  | 一轮问答的总时长 | **没有人** | **否** |
  | 进程一定退得掉 | **第二次中断信号 → `os._exit(5)`** | **是** |

  **于是硬退出不再是"兜底"，而是唯一的绝对保证**——这反过来让决策P4.21-59/66"凡与保证退出冲突的
  一律让位"更站得住。指南必须照实写：极少数情况下第一次 `Ctrl-C` 会等很久，再按一次即走。
  > 真正的修法（流式消费层的总 deadline + 用持续 trickle 的假服务端验证）**属 agentao**，
  > 记为上游诉求（§13），**不在宿主外层包 `wait_for`**——那只会把"还没停"伪装成"已经停了"。

- **强制退出：只有 `os._exit()` 算数**（评审 #26，决策P4.21-53）。v4 写的「置 `force` → `stop_all()` 返回
  `False` → 从 `asyncio.run()` 返回 → 退出码 5」**根本退不出去**：agentao 的 `arun` 用的是它**自己的**
  `ThreadPoolExecutor`（`agent.py:56-62` 的 `_get_arun_pool`，刻意不用 loop 默认执行器），其 worker 是
  **非守护线程**，而 `concurrent.futures.thread` 注册了 `atexit` 钩子在解释器退出时 `join()` 它们。
  **于是线程真卡死时，进程会卡在"退出"这一步——正是用户按第二次 Ctrl-C 想解决的那个现象。**

  **强退因此完全不走 `stop_all()`**——v4 的 `force: asyncio.Event` 参数与 `bool` 返回值一并删除
  （留着就是两套机制，而其中一套根本不成立）。强制退出必须在**信号处理器里**完成，且是这三步，一步都不能少：

  ```python
  def _on_second_interrupt(n: int) -> NoReturn:   # 第二次 SIGINT/SIGTERM
      # **不碰 logging**（评审 #32），且提示本身也**不许挡路**（评审 #39）
      try:
          os.set_blocking(2, False)               # stderr 可能接在已满的阻塞管道上
          os.write(2, f"强制退出：仍有 {n} 轮未收尾，可能残留后台线程\n".encode())
      except Exception:                           # 写不出去就算了——退出优先级最高
          pass
      os._exit(EXIT_AGENT_ERROR)                  # 绕过 atexit / finally / join
  ```

  - **绝不在这条路上调 `logging`**（评审 #32，决策P4.21-59）：`logging.shutdown()` 会对每个 handler
    `acquire()` + `flush()` + `close()`——**后台线程正持着那把 handler 锁、或它的 flush 正卡在同一个死掉的
    下游上时，主线程就到不了 `os._exit()`**。那样一来"唯一能保证退出的手段"自己先卡住了，
    等于什么都没做。`os.write(2, ...)` 是裸系统调用，不取任何 Python 级的锁。
  - **因此日志完整性只能 best-effort**：缓冲里没刷出去的记录会丢。这是硬退出的**代价**，不是缺陷——
    要的就是"无论如何都退得掉"。**文档与指南都不得承诺"保证日志刷完"**。
  - **那行提示本身也是 best-effort**（评审 #39，决策P4.21-66）：`os.write(2, …)` 在 stderr 接到
    **已满的阻塞管道**时照样会阻塞（`guanlan im 2>| some-full-pipe`）。故先 `set_blocking(2, False)`
    再写、整段裹 `try/except`，**写不出去就直接走**。
    **凡是与"保证退出"冲突的东西，一律让位**——包括我们自己想留下的那句话。
  - **不跑有序 close**：进程即将消失，socket 交给 OS 回收；此时按顺序关反而给残留线程制造"连接还在"的假象。
  - **退出码仍是 `EXIT_AGENT_ERROR`（5），绝不是 0**——把没停干净的退出报成 0，是把运维的判断依据一起骗了。
    不新增退出码（§3.4）。
  - **前提说清楚**：这套信号处理要求**事件循环线程本身还在转**（我们的卡死场景是 agentao 的 worker 线程，
    满足此前提）。若 loop 自身也卡死，任何信号方案都不保证，只剩 `SIGKILL`。**不假装能兜住这种情况。**
  - 这条**必须用子进程测**（§10.1）：在同进程里 `os._exit` 会把测试进程一起带走。

### 4.5 会话状态机：TTL 归 registry，不归 store（评审 #12，决策P4.21-40）

**原设计的「闲置 30 分钟后提示已开始新对话」按现有接口根本不会发生**，两个已核实的源码事实决定了这一点：

1. `ConversationStore.get()` **命中即刷新** `conv.last_active = self._clock()`——且源码注释写明这是**有意的**
   （堵「get 拿到 conv → begin_turn 前被并发 reclaim 误逐」的竞态）。所以 registry 只要先 `get`，闲置两小时
   的会话反而被**复活**。
2. `_reclaim_idle_locked` **只在 `create`/`restore` 里调**，`get` 路径永不触发回收。

**v3 曾想让两套 TTL 分工（registry 判 UX 过期、`store.idle_ttl=2×` 兜内存），第三轮复审证明这条走不通**
（评审 #18，决策P4.21-46）。第三个源码事实是决定性的：

3. `store` **根本没有「因容量逐出」这条路径**——`create()` 顶满时是**抛 `RuntimeError`**
   （`conversation_store.py:122`），它只在此之前顺手回收**超 TTL** 的会话。

三条事实一叠加，两套 TTL 的方案自相矛盾：

- `conv.last_active` 由 `store.get()` 每次刷新，故它**恒不早于** registry 的 `last_seen`；
  凡是 store 判得动的会话（idle > 2×ttl），registry 早在 1×ttl 就判了 `EXPIRED`。**`RECLAIMED` 不可达。**
- 更要命的是**容量并没有人腾**：100 个会话都处在「registry 已过期、但没到 store 的 2×ttl」这段窗口时，
  registry 只在**各自的 key 再次说话时**才清理它们，而第 101 个用户根本没有 key 在表里——他撞上的是
  `RuntimeError`。**「多设一层 TTL 兜底」反而制造了一个谁都不负责的空档。**

**故：TTL 归 `SessionRegistry` 独占，`store.idle_ttl=None`；腾容量的动作也归 registry 主动做。**

```python
async def acquire(self, key):
    now = self._clock()
    rec = self._map.get(key)                      # key -> (cid | None, last_seen)；cid=None 即墓碑
    if rec is not None:
        cid, last_seen = rec
        if cid is None:                           # ⓪ 墓碑：会话已被 sweep 回收，但"过期过"这件事留着
            # expired=True：既把墓碑时间刷成 now，也让本键进 `_creating` 受保护（评审 #50）
            return await self._renew(key, expired=True), EXPIRED
        if now - last_seen <= self._ttl:          # ① 未过期：get（此时刷新 last_active 是对的）
            conv = await anyio.to_thread.run_sync(self._store.get, cid)   # ★ 卸线程，见 §4.3
            if conv is not None:
                self._map[key] = (cid, now)
                return conv, EXISTING
            self._map.pop(key, None)              # ② 不该发生：对象意外没了 → 记 WARNING
            return await self._renew(key, expired=False), LOST   # 悬空映射已弹掉，无墓碑可留
        return await self._renew(key, expired=True), EXPIRED
    return await self._renew(key, expired=False), FIRST

async def _renew(self, key, *, expired):
    self._creating.add(key)          # ★ 同步登记，**早于本路径上的任何 await**（评审 #44）
    try:
        if expired:
            # 墓碑的 last_seen = now（评审 #37）；此刻起本键已在 _creating 里，别人扫不掉它
            await self.drop(key, tombstone=True, seen=self._clock())
        await self._sweep_expired()                              # 腾容量（评审 #18）
        conv = await anyio.to_thread.run_sync(self._store.create)  # 顶满时抛 RuntimeError
        self._map[key] = (conv.id, self._clock())                # 覆盖墓碑（若有）
        return conv
    finally:
        self._creating.discard(key)  # 成功、抛错、被取消，三条路都要摘

async def _sweep_expired(self) -> int:
    now = self._clock()
    doomed = [k for k, (cid, seen) in self._map.items()
              if cid is not None and now - seen > self._ttl and not self._is_busy(k)]
    for k in doomed:
        await self.drop(k, tombstone=True)        # 删会话对象，**留下墓碑**
    self._evict_tombstones(protect=self._creating)  # 保护**整个**在建集合，不只自己
    return len(doomed)
```

- **墓碑：sweep 回收会话对象，但保留「这个键过期过」**（评审 #24，决策P4.21-51）。
  v4 让 sweep 直接 `drop()` 掉整条映射，于是那个用户下次来是 `FIRST`——**既与 §10.1 的用例矛盾，
  也把指南承诺的过期提示变成了"看运气"**（取决于这期间有没有别人来触发过 sweep）。
  **"彻底删除记录"和"日后仍知道它过期过"不可兼得**，故显式选后者：留一条 `(None, last_seen)`。
  - **过期路径也必须 `tombstone=True`**（评审 #34）：`drop` 的默认值是 `False`，若那里漏传，
    `_renew` 里紧随其后的建会话 **一旦抛容量错**（会话数真顶满），这个键的过期身份就一起没了——
    用户重试时收到的是 `FIRST`，"上下文已过期"这句提示在最需要它的那次重试里恰好消失。
  - **光留墓碑还不够，它会被自己淘汰掉**（评审 #37，决策P4.21-64）：过期路径留下的墓碑若沿用**旧**
    `last_seen`，紧接着的 `_sweep_expired` → `_evict_tombstones` 里，**它往往正是最旧的那条**
    ——墓碑满时先被淘汰，然后 `store.create()` 抛容量错，用户重试仍得 `FIRST`。#34 白修了。
    故墓碑的 `last_seen` 记为 **`now`**（用户**确实刚刚发过消息**，这是它的真实语义，不是权宜之计）。
  - **保护不能只保护自己那一个键**（评审 #44，决策P4.21-69）：v7 写的 `_evict_tombstones(protect=key)`
    仍然漏——A、B 两个键**同时**重建时，A 的 sweep 照样淘汰得掉 B 的墓碑，反之亦然；而且 `drop()`
    内部有 `await`，别人完全可能在当前键进保护集之前插进来。
    故改 registry 级 **`_creating: set[str]`**，并把**「标墓碑 → 清理 → 建会话」整条路径**收进
    `_renew()`：进入前**同步** `add`（早于本路径上的任何 `await`）、`finally` 里 `discard`，
    淘汰时保护**整个集合**。
    > **"保护当前操作"和"保护所有正在进行的操作"是两件事**——单机单进程也一样，
    > 因为并发不是来自线程，是来自 `await` 处的交错。上一轮我只想到了前者。
  - **墓碑本身的界**：`_evict_tombstones()` 在墓碑数超过 `tombstone_limit`（由 `serve_im` 传
    `max_conversations`，默认 100）时，按 `last_seen` **最旧优先**淘汰到界内；
    **永不淘汰 `cid is not None` 的活条目**。
    被淘汰的墓碑 = 那个键日后回来时得到 `FIRST` 而非 `EXPIRED`——**这是有意的取舍**：
    半天没说话的人，再被告知"上下文已过期"本就没有信息量。
  - **键空间天然有界**：未授权消息在 §5.2 就被静默丢弃、根本进不到会话层，所以只有白名单内的人能建条目
    （小圈子定位，§0.2）。数量界是防御性的第二道，不是主要依靠。
  - 墓碑只有 `key + float`，百条量级的内存开销可忽略。
- **`_sweep_expired` 才是真正腾容量的机制**。只在**新建**路径上跑（新 key 到达，罕见），
  表长 ≤ `max_conversations` + 墓碑界，一次 O(n) 可忽略。
- **在飞守卫走 `Delivery.busy(session_key)`，不走 `conv.is_idle()`**：少了这道守卫，一轮跑了 30 分钟
  以上的长问答会被别人的新会话顺手 `close()` 掉。之所以**不**借 `is_idle(now, 0.0)`——它内部比较的是
  `store.get()` 刚刷新过的 `last_active`，在注入**冻结时钟**的测试里 `now - last_active > 0` 恒为假，
  sweep 会一个都扫不掉：**一个只在真实时钟下才成立的守卫，等于没有测试**。而单飞集合（§4.4）本就是
  「这个会话键有没有在飞轮」的权威答案，且是纯集合判定、与时钟无关。
  接线：`SessionRegistry` 收一个 `is_busy: Callable[[str], bool]`（默认恒 `False`），
  `serve_im` 在建好 `Delivery` 后 `registry.set_busy(delivery.busy)` ——用 setter 而非构造参数，
  因为 registry 要先于 Delivery 构造（避免循环依赖）。
- **`LOST` 不是「容量回收」**：`idle_ttl=None` 且 registry 独占生命周期后，`store.get()` 返回 `None`
  意味着**不变量被破坏了**（有人绕过 registry 删了会话）。它是防御分支不是正常路径，故**必记 WARNING**。
  用户侧仍要给话：「（会话已重置，已开始新的对话）」——不解释原因，因为对用户没有可行动信息。
- **容量真顶满**（100 个会话都在 TTL 内活跃）：`store.create()` 抛 `RuntimeError`，
  `Delivery` 捕获 → 回一句「当前会话数已满（上限 N），请稍后再试」+ 记 WARNING。
  **必须显式答复**：这是唯一一个"系统忙"而非"你说错了"的拒绝，静默会被当成机器人挂了。
- **`clock` 可注入** → 跨 TTL 的行为可决定性测试，不用真等 30 分钟。
- **提示语按状态分**：`FIRST` **不提示**（第一次说话被告知"上下文已过期"很荒谬）；`EXPIRED` →
  「（上下文已过期，已开始新的对话）」；`LOST` → 「（会话已重置，已开始新的对话）」。
- `/new` 走 `await registry.drop(key)`（**不留墓碑**），下一条消息自然是 `FIRST`（**不提示**）——
  主动重开不该被告知"上下文已过期"。

### 4.6 错误隔离

单条消息的处理异常**绝不**能杀死主循环：`delivery.handle` 整体裹 try/except，出错记日志 + 回一句
「处理出错了，请稍后再试」——**不回传异常文本**（可能含路径/凭据片段）。适配器的重连/退避在适配器内自理。

**但 `AgentCancelledError` 必须先单独接住**（评审 #27，决策P4.21-54）：`request_stop()` 会让 `turn()` 抛它，
而**主动停机不是处理失败**。按 v4 的写法，用户在关机时会收到一句莫名其妙的「处理出错了，请稍后再试」——
更糟的是这会**训练用户去重试**，而此时进程正在退出。

```python
except AgentCancelledError:      # 来自 agentao.cancellation
    await _stop_writer(abort=True)   # 停 writer（§6.2），**不发任何消息**
    _logger.info("会话 %s 的一轮因停机/用户停止而中止", key)
except Exception:
    await _stop_writer(abort=True)
    ... 「处理出错了，请稍后再试」
```

顺序与捕获宽度都不能改：`AgentCancelledError` 的 `except` 必须在通用 `except Exception` **之前**。
`web/app.py:1200` 已有同款先例（Web 端把它与错误帧分开处理），本宿主照同一姿态。

### 4.7 外部 MCP 工具的时间上界（评审 #33，决策P4.21-60）

**优雅停机"等真实收尾"这条契约，此前是悬空的**——两条源码事实：

1. `build_from_environment` 在调用方未传 `mcp_registry` / `mcp_manager` 时，**默认装上**
   `FileBackedMCPRegistry(project_root=wd, user_root=user_root())`（`embedding/factory.py:238-243`）
   ——即**读盘上 `.agentao/mcp.json` 的 MCP 文件发现是默认开的**。`Conversation.__init__` 的 `opts`
   里没有这两个键（`conversation.py:224-243`），所以 IM 宿主会原样继承用户为这个库配的所有 MCP server。
2. MCP 的超时解析：`timeout` 缺省（或显式 `null`）→ `(默认启动超时, request=None)`
   ——**单次工具调用无限等待**（`mcp/config.py:160-163`）。

**于是就算模型 HTTP 请求有超时，一轮也可能永远卡在某个 MCP 工具里。** 这不是"待实证"，是已确诊。

**修法走文档化面**：registry 只需实现 `list_servers() -> dict[str, McpServerConfig]`，
且工厂明写"嵌入宿主要程序化注册就传 `mcp_registry=`"。故包一层：

```python
class BoundedTimeoutRegistry:      # guanlan/im/mcp_bound.py
    """给**每个** MCP server 落一个**不超过 T** 的 request 上界——缺省/非法的补 T，显式值取 min。
    只改这次读到的副本，不动盘上文件。"""
    def list_servers(self):
        out = {}
        for name, cfg in self._inner.list_servers().items():
            out[name] = _with_request_timeout(cfg, self._t)
        return out
```

合并规则**只有一条**（评审 #36/#38 修订后）：

> **看「agentao 解析之后」的 request 是不是有限正数——不是，就用 `T`；是，就取 `min(它, T)`。**

v6 那张按"缺省 / 标量 / 有限值 / null"分四态的表**漏了一整类**：`request` 写成
`0` / `-1` / `"bad"` / `NaN` / `Infinity` 时，`_coerce_timeout` 只打一条 WARNING 就**退回 `default`
——而 request 槽的 default 正是 `None`**（`mcp/config.py:102-122`），于是又变回无限等待。
**"形态"不是判据，"解析结果"才是**：

```python
def _bounded(cfg, T):                     # T 已在入口校验为有限正数
    raw = cfg.get("timeout")
    startup = raw.get("startup") if isinstance(raw, dict) else raw   # 原样保留，不代它做主
    req = raw.get("request") if isinstance(raw, dict) else None
    eff = T if not _finite_positive(req) else min(float(req), T)     # ← 唯一的判定
    if _finite_positive(req) and float(req) > T:
        _logger.warning("MCP %s 的 timeout.request=%s 超过 --mcp-request-timeout=%s，已收紧", ...)
    return {**cfg, "timeout": {"startup": startup, "request": eff}}
```

- **`min()` 而不是"显式值优先"**（评审 #38，决策P4.21-65）：v6 让盘上的显式有限值原样保留，
  于是 `mcp.json` 里写 3600 时，命令行传 60 **什么也没收紧**——而指南把它叫作"上界"。
  **一个任何配置文件都能绕过的上界不是上界**，而这个旋钮存在的唯一理由就是给优雅停机兜住时间。
  故取 `min`，且被收紧时**记 WARNING**——改变用户显式配置的行为不能悄悄发生。
  真需要更长，就把这个旗标调大（它是宿主级天花板，不是每个 server 的默认值）。
- **T 只约束"每次 `tools/call` 请求"；一次完整的 MCP 工具执行没有严格总上界**
  （评审 #52/#55，决策P4.21-72）。`MCPClient.call_tool` 是 `for attempt in range(2)`——
  `SESSION_EXPIRED` / `TRANSPORT_DROPPED` 会**重连并重试一次**（`mcp/client.py:813`，其 docstring
  自称 "bounds each individual tool call"）。而这条链上有**好几段谁都没管**的时间：

  | 子步骤 | 有没有超时 | 出处 |
  |---|---|---|
  | **`tools/call` 的出站写入** | **无** | SDK 先 `await self._write(msg, …)`、**之后**才 `with anyio.fail_after(opts["timeout"])`；其自身注释写明 "`fail_after` arms only after the write"。而 `_write` 就是一句 `await self._write_stream.send(...)`，**没有 deadline**（`mcp/shared/jsonrpc_dispatcher.py:397/401/405/777`，评审 #57） |
  | `tools/call` **写完后等响应** | **有**（T） | `read_timeout_seconds=` → `fail_after(T)` |
  | 握手（`initialize`/`list_tools`） | **有**（startup） | `asyncio.wait_for(self._handshake(), timeout=startup_timeout)` |
  | URL 传输的 **HTTP 连接建立** | **有**（startup 作 connect/write/pool 超时） | `sse_client(url, timeout=startup_timeout, …)` |
  | Streamable HTTP（`type: "http"`）传输进入 | **有** | SDK 的 `streamablehttp_client` **不等服务端事件**就 `yield`，后续往返落在握手的 `wait_for` 内 |
  | **legacy SSE（`type: "sse"`）等 `endpoint` 事件** | **无** | `sse_client` 要 `await tg.start(sse_reader)` 收到 `endpoint` 才 `yield`；而 httpx 的 `read` 被显式改成 `sse_read_timeout`（`Timeout(timeout, read=sse_read_timeout)`）——**服务端只发 keepalive、永不发 `endpoint`，这一等就没有头**（评审 #56） |
  | **stdio 传输建立** | **无** | `await self._connect_stdio()` 不收超时参数——源码注释亦自承"stdio has no transport-level connect bound at all" |
  | **`disconnect()` / exit-stack 清理** | **无** | `await self._exit_stack.__aexit__(...)` 裸等（`mcp/client.py:968`） |

  **所以 v9 那个 `2×(T + startup)` 的公式是错的，已撤回**——它把几段无界的路径当成了零。
  **最终口径（v11 定稿）**：

  > **T 约束的是「请求完成出站写入**之后**、等待 `tools/call` 响应」这一段；出站写入本身不在该计时器内。
  > 握手与 Streamable HTTP 的传输往返有各自的阶段超时；legacy SSE 的传输进入、stdio 传输进入、
  > 出站写入、以及 exit-stack 清理仍可能无界。
  > 因此**完整单次 `tools/call` 请求**与**完整 MCP 执行**都没有严格总墙钟上界。**

  注意"有阶段超时"与"有总上界"是两回事：握手那段确实被 `wait_for(startup)` 包住了，
  但它挡不住**排在它前面**的传输进入——`connect()` 是先裸 `await _connect_sse()`、再进 `wait_for`。
  - **仍然值得设 T**：它把最常见、最长的那一段（工具真正干活、等它回话）收住了，也把"默认无限等待"
    这个最容易踩的坑堵上了。**"不是总上界"不等于"没用"。**
    但也就到此为止：**传输 writer 一旦卡住，后续调用会停在写入阶段，T 连表都没起。**
  - **不顺手把 startup 也收到 T**：stdio server 拉起子进程本来就可能慢，砍它会把好端端的 server 弄挂。
  - 真正的总上界要 agentao 侧补（`disconnect` 加超时、stdio spawn 加界、**legacy SSE 传输进入加界**、
    **出站写入纳入计时**），记为上游诉求（§13-7）。
- **`T` 自身必须校验**（评审 #36）：`--mcp-request-timeout` / `serve_im(mcp_request_timeout=)` 在**入口**
  校验为有限正数，否则 `GuanlanError(EXIT_USAGE)`。否则传 `0` / 负数 / `NaN` 会让上面这条规则算出一个
  没有意义的值，**兜底自己先破了**。
- **测试判据用 agentao 的解析器当"神谕"**（不是运行期依赖它）：对每个畸形配置，断言
  `resolve_timeouts(bounded_cfg)[1]` 是**有限正数且 ≤ T**。这样上游哪天改了解析规则，红的是这条用例，
  而不是线上某一轮悄悄挂死。

- CLI：`--mcp-request-timeout`（默认 **120s**）与 `--no-mcp`（传 `mcp_registry=None`，彻底关掉发现）。
- **为什么不干脆默认关掉 MCP**：P4.19 那半阶段正是围绕"用户已经往这个库里注入的外部 MCP server"做的，
  Web 端答问用得到它们。IM 端一刀关掉会让**同一个库、同一个问题，在手机上和浏览器里答得不一样**，
  而用户无从知道差别从哪来。给上界比砍能力诚实。
- 连带：`Conversation.__init__` 需要一个**可选**的 `mcp_registry` 透传参数（不传则行为与今天逐字节相同，
  Web 零影响），见 §14。

## 5. 入站流水线（`intake.py`，全部平台无关）

### 5.1 五道闸

1. **去重**：`msg_id` + TTL 300s + 上限剪枝。漏则**双倍 LLM 花费**（两家都会重投）。
   > **删除了内容指纹去重**（评审 #7，决策P4.21-34）。原设计照抄参考实现的 `content:{user}:{md5}` 兜底，
   > 但它**无法区分「平台换 id 重投」与「用户合法重复」**，而后者在 IM 里很常见（重复 `/help`、追问同一
   > 问题）。**静默吞掉合法消息比偶尔重跑一次更糟**——前者用户完全无从察觉。若将来实测确认平台会换 id
   > 重投，再加，且必须含 `tenant`/`chat_id`、窗口缩到 ~30s、并排除斜杠命令。
2. **白名单**（默认 deny）：真值表见 §5.2。**不匹配 = 静默丢弃**，不回「你没有权限」——那会把「这里有个
   知识库机器人」泄露给未授权者。
3. **@ 判定**：群聊须 `msg.mentioned_me`（**平台结构化字段**），再剥前缀 `re.sub(r"^@\S+\s*", "", text)`，
   否则 `@bot /search x` 识别不出斜杠命令。
4. **分片合并**：quiet-period 双阈值，**阈值取自 `caps`**（微信 3.0/5.0s——源码实测值，因 iLink 逐条投递）。
   含参考实现那段 **cancel-delivery 竞态守卫**：sleep 定时器与 `cancel()` 同时触发时 `CancelledError` 会延迟到
   下一个 await 才投递，届时本 task 已 pop 走事件、后继 task 看到空桶而静默丢消息——故 sleep 之后**同步**复查
   `_tasks.get(key) is current_task`，中间不得有 await。
5. **分流**：`msg_kind != "text"` 或 `has_attachments` → `command="attachment"`（固定提示，零 LLM）；
   `/search` / `/new` / `/help` → 对应命令（零 LLM，**不建会话、不烧 token**）；其余 → `command=None` 走 LLM。

### 5.2 授权真值表（评审 #6，决策P4.21-33）

| 场景 | 放行条件 |
|---|---|
| 单聊 | `allow_all` **OR** `user_id ∈ allow_users` |
| 群聊 | `chat_id ∈ allow_chats` **AND** (`allow_all` **OR** `user_id ∈ allow_users`) **AND** `mentioned_me` |

**两条都要看清楚：**

**① 群聊里 `user` 与 `chat` 是 AND，不是 OR，也不是只查群**：群成员集合由**群主**控制且随时变化——
只查群等于把授权外包给群主，一次拉人就把整库开给了新成员。

**② `--allow-all-users` 只旁路「用户」名单，永不旁路「群」名单**（评审 #11，决策P4.21-39）。
v2 的写法 `allow_all OR (chat AND user)` 有个安全旁路：一开这个旗标，**机器人所在的所有群**都放行，
与「不给 `--allow-chat` 则群消息一律不理」直接矛盾。两者语义本就不同——

- `allow_chats` = **哪些群能看到整库**（物理受众边界，由部署者决定把机器人放进哪个房间）；
- `allow_users` = **房间里的哪些人能问**（人员边界）。

`--allow-all-users` 表达的是「我不想逐个列人」，**不是**「我不在乎它在哪个群里」。故它只穿透后者。
要真的全开放（含所有群），只能同时给 `--allow-chat`——**没有一个旗标能一次开放所有群**，这是有意的。

启动日志仍必须**大声**打出「⚠️ 全员可问：`--allow-chat` 列出的群里任何人都可读取整库」。

**ID 匹配改为精确、大小写敏感、不剥前缀**（决策P4.21-33）：平台 ID 是**不透明标识**（飞书 `open_id` 是
大小写敏感的编码串），参考实现的 `.lower()` 归一**可能把两个不同主体合并**。只做 `.strip()`，不做 `.lower()`、
不剥 `user:`/`wecom:` 前缀——那些是参考实现的多平台配置遗产，观澜的 ID 直接来自 `im-identify` 的输出，
不需要归一。

## 6. 出站投递（`delivery.py`）

IM 的「秒回期待」 vs LLM 的分钟级时延，是本宿主相对 Web/MCP 的**唯一新问题**：IM 里发出去 30 秒没动静，
用户会**再发一遍**（新 msg_id，去重救不了）。

### 6.1 四档策略由能力位选（v1 用到前两档，决策P4.21-12）

| 条件 | 策略 | v1 覆盖 |
|---|---|---|
| `supports_edit` | 发一条「🔍 正在查阅…」→ **原地改写**（节流）→ 末次 `finalize` | **飞书** |
| `supports_typing and not supports_edit` | **typing on** → 跑 → **off** → 分片发答案 | **个人微信** |
| 都无，但 `supports_late_push` | 占位消息 + 追答 | 企业微信单聊（未实现） |
| `not supports_late_push` | 群内只开零 LLM 命令 | 企业微信群（未实现） |

### 6.2 `emit` 与 edit 的单写者严格有序（评审 #10，决策P4.21-37）

- **非 edit 档**：`emit` **丢弃全部 token**（逐条推会刷屏并撞频控）。
- **edit 档**：`emit` 只更新一个 `_latest: str`（**不**直接发起 edit）。另起**一个 writer task** 循环：
  取 `_latest` 快照 → `await adapter.edit(...)` → `await asyncio.sleep(interval)`。turn 结束时置
  `_final = True`、唤醒 writer 发最后一次（`finalize=True`），主协程 **`await writer_task`** 再返回。

  **这样天然满足三条**：单写者（永不并发两个 edit）、严格有序（同一 task 串行）、final 必在所有中间 edit
  之后（await writer 结束）。**绝不**用「每次节流触发就 `create_task(edit)`」——那正是评审指出的
  「中间 edit 后完成、把 final 覆盖回旧文本」的竞态。

  参数：`interval=2.0s`、`min_chars=200`（两者都满足才发一次中间 edit）；**中间 edit 的文本也必须
  `split_for(...)[0][0]` 限长**，否则超 8000 字的中途快照会被 API 拒。参数归**核心**持有，不下放适配器。

  **writer 的生命周期必须闭合**（评审 #13，决策P4.21-41）——它是 `Delivery` 起的子 task，三条路径都要收干净：

  | 路径 | 处理 |
  |---|---|
  | turn 正常结束 | 置 `_final=True` 唤醒 → writer 发最后一次（`finalize=True`）→ `await writer` |
  | **turn 抛异常** | 置 `_abort=True` 唤醒 → writer **立即退出、不再写**  → `await writer` → **然后**才发错误提示。**顺序不能反**：先发提示再停 writer，writer 会把提示又改回旧的局部文本 |
  | **turn 抛 `AgentCancelledError`** | 同上停 writer，但**一个字也不发**（评审 #27，§4.6）——停机/用户停止不是出错。占位消息就停在最后一次中间 edit 的内容上，这比改成「处理出错了」诚实 |
  | shutdown | 走上一行的 `AgentCancelledError` 路径（`request_stop()` 的必然结果），且在 adapter 关闭**之前**（§4.4 步骤 ④） |

  三条路径统一落在 `try/finally` 里：`finally` 无条件 `_abort or _final` 置位 + `await writer`，
  **绝不允许 writer 活过创建它的 `handle()`**。

> **emit 的线程边界（评审 #21，决策P4.21-49）：`turn()` 内部已经桥好了，宿主侧不要再桥一次。**
> `conversation.py:542` 把调用方传入的 `emit` 包成 `thread_safe_emit`，由它执行
> `loop.call_soon_threadsafe(emit, ...)`——所以**我们传进去的那个 `emit` 已经在事件循环线程上执行**，
> 直接改 `_latest` 即可，不加锁、不再 `call_soon_threadsafe`。
>
> 再桥一次不只是多余：它把每次 token 更新**推迟一个 loop tick**，于是会出现「`turn()` 已返回、writer 已
> `finalize`、迟到的那一跳才改 `_latest`」——终稿被改回中途快照，而且是**偶发**的。
> （v3 这段写反了：把 `Conversation` 内部的实现模式当成了宿主的义务。）

### 6.3 长答案契约：**不静默截断**（评审 #4，决策P4.21-31）

原设计的三条要求（≤5 片 / 每片 ≤ limit / 绝不截断）对超过 `max_parts × limit` 的答案**数学上不可同时满足**，
且「完整版请在 Web 查看」实际暗示已截断。**v2 明确选边**：

**契约 = 「不静默截断」，不是「绝不截断」。**

```python
parts, dropped = split_for(text, limit, max_parts=caps.max_parts)
# dropped == 0  → 无损，全发
# dropped  > 0  → 发 parts（已是 max_parts - 1 片）+ 末片为**显式截断告示**：
#                 「⚠️ 答案还有约 {dropped} 字未发送；请在 Web 端**重新提问**以获取完整回答。」
#                 给了 --web-base-url 时追加一行「Web 入口：{web_base_url}」——**入口，不是本答案的地址**
```

- 告示**自己占一片**，所以用户**永远看得到「这里被截断了」**——这正是「不静默」的含义。
- **文案不能说「完整版：<URL>」**（评审 #23，决策P4.21-50）：IM 会话是 `persist=False`（§3.4），
  被舍弃的那段**没有存在任何地方**；`--web-base-url` 也只是站点入口、不是这一次回答的地址。
  照 v3 的文案，用户点过去只会看到一个空的新会话——**比不给链接更糟，因为它承诺了一个不存在的东西**。
  所以只能诚实地说「要重新问一次」。
- `max_parts` 进 `caps`：微信 **5**（2000×5，约 1 万字）、飞书 **3**（8000×3，约 2.4 万字）。
- **edit 档的超长答案**（原设计未定义）：**首片 `edit` 回占位消息，其余片用 `send` 追发**——占位消息本身
  不可能承载 3 片内容。中间 edit 亦只写首片（§6.2）。
- 片间 `caps.chunk_delay_s` 延迟（微信 1.5s，源码值，防频控丢消息）。

### 6.4 2000 字上限改变主用法（决策P4.21-10）

- **`/search` 是主力**：零 LLM 检索结果天然短，一条装得下，**毫秒级、不烧 token**。
- **LLM 问答是次要**：**分片 + 首片自足**（第一片本身可用，后续是展开）。
- **明确不做**：**不**为 IM 通道改 prompt 让模型「答短点」——那是把判断塞进宿主，破**零业务智能**
  （决策P4.21-16）。要短靠**用户选择用 `/search`**。

### 6.5 markdown 与 wikilink

- **围栏块原样保留**：mermaid（P4.13）/ KaTeX（P4.14）/ flint（P4.20）在 IM 里都无渲染器，沿用那三个半阶段
  一致的**降级契约：保留源码，绝不静默丢弃**。
- **`[[wikilink]]`**（决策P4.21-17）：默认**保留原文**——`[[甲实体]]` 是可读的引用语义，换成
  `http://127.0.0.1:8765/...` 对手机用户**毫无意义且误导**。只有显式给了 `--web-base-url` 才转真链接。

### 7.1 三条必须写进代码注释的口径差（决策P4.21-24）

| 项 | 参考实现**源码** | 平台官方文档 | 取 |
|---|---|---|---|
| `max_message_length` | **2000** | 4000 | **源码** |
| `dm_policy` 默认 | **`pairing`** | `open` | **源码**（安全相关） |
| 分片间隔 | **1.5s** | 0.3s | **源码** |

同一份文档三处与代码不符、两处安全/行为相关。**观澜一律以源码为准，并在适配器里注明取值来源**。

### 7.2 协议细节（全部已核对）

- **Base** `https://ilinkai.weixin.qq.com`；端点 `ilink/bot/{getupdates,sendmessage,sendtyping,getconfig}`。
- **Headers**：`Authorization: Bearer <token>`、`AuthorizationType: ilink_bot_token`、`iLink-App-Id: bot`、
  `iLink-App-ClientVersion: (2<<16)|(2<<8)|0`、`X-WECHAT-UIN: <随机>`、`Content-Type: application/json`。
- **每个请求体都并入** `base_info: {"channel_version": "2.2.0"}`。
- **入站**：`POST getupdates {"get_updates_buf": <游标>}`，长轮询 **35s**；响应
  `{ret, errcode, errmsg, msgs[], get_updates_buf, longpolling_timeout_ms}`。**超时不是错误**——返回空并立即
  重轮询。服务端给了 `longpolling_timeout_ms` 就用它。
- **消息字段**：`from_user_id` / `to_user_id` / `room_id`(或 `chat_room_id`) / `message_id` / `context_token` /
  `item_list[{type:1, text_item:{text}}]`（`ITEM_TEXT=1`）。
- **自消息过滤**：`from_user_id == account_id` **直接丢**——否则回声循环。**这条不能漏。**
- **群消息**：`room_id` 非空即群。`caps.supports_group=False` → 丢弃并计数（debug 级，不刷屏）。
- **出站**：`POST sendmessage {"msg": {from_user_id:"", to_user_id, client_id, message_type:2(BOT),
  message_state:2(FINISH), item_list:[{type:1,text_item:{text}}], context_token?}}`。
- **打字指示**：`POST sendtyping {ilink_user_id, typing_ticket, status}`（`1`=start / `2`=stop）；
  `typing_ticket` 由 `getconfig` 取、**按 user 缓存 10 分钟**。

#### 7.2.1 入站字段映射（评审 #15，与飞书 §8.3 对称，决策P4.21-43）

`InboundMessage` 八个字段逐一给出取值规则——否则「映射正确」这条测试没有标准答案：

| 字段 | 取值 | 说明 |
|---|---|---|
| `tenant` | `account_id`（本机凭据里的，不取自消息） | 防跨账号撞号 |
| `chat_id` | **`from_user_id`** | iLink 单聊没有独立的会话实体，用对端 user id 充当 chat 键 |
| `chat_type` | 恒 `"dm"` | 群消息已在适配器层丢弃（`supports_group=False`），**永不**向核心吐出 `"group"` |
| `user_id` | `from_user_id` | 与 `chat_id` 同值，这是单聊的正常形态，不是 bug |
| `text` | `item_list` 中所有 `type == ITEM_TEXT(1)` 的 `text_item.text`，按顺序拼接（换行分隔） | 无文本 item 则为空串 |
| `msg_id` | `message_id`；缺失则丢弃该条（不自造 id） | 自造 id 会绕过去重 |
| `mentioned_me` | 恒 `False` | 单聊无 @ 概念；核心的群 @ 闸在此永不触发 |
| `msg_kind` | 全部 item 均为 `ITEM_TEXT` → `"text"`；否则 `"other"` | **混合消息（既有文本又有附件）判为 `"other"`** |
| `has_attachments` | 存在任一 `type != ITEM_TEXT` 的 item → `True` | 图片/语音/文件/视频四类都算 |

**混合 item 的取舍**：判 `"other"` 走固定附件提示（§5.1 第 5 道），`text` 字段**仍填**已提取的文本部分但
**不进 LLM**。理由：用户发「这张图什么意思」+ 一张图时，只答文字部分会给出一个**看似回答了、实则没看到图**
的答案——那比明说「暂不处理附件」更糟。宁可少答，不可假答。

### 7.3 跨重启状态（`~/.guanlan/im/weixin/`，决策P4.21-20）

| 文件 | 内容 | 不存会怎样 |
|---|---|---|
| `account.json` | `account_id` / `token` / `base_url`（`chmod 0600`） | 无法连接 |
| `sync.json` | 长轮询游标 `get_updates_buf` | 重启后重放旧消息 |
| `context-tokens.json` | 每 peer 最近一次入站的 `context_token` | 回复投递降级（见 §7.4） |

写盘一律**原子替换**（临时文件 + `os.replace`）。这**不破 KB 零写承诺**（全在 KB 外），但
「零写 ≠ 进程无状态」必须在文档里说清楚。

### 7.4 错误码分流（评审 #3，决策P4.21-30）—— **按请求类型 + errmsg + 是否带 token 三维分**

原设计「`-14` 一律重扫码 + 停 600s；`-2` 一律频控」是**错的**，会在正常的 context token 过期时错误停服 10 分钟
并要求重登录。经参考实现源码复核（其 stale-session 判据与出站发送两处）后的正确分流：

```python
def _is_stale(ret, errcode, errmsg) -> bool:
    if ret == -14 or errcode == -14:
        return True
    # -2 且 errmsg 恰为 "unknown error" 是 stale-session 信号，**不是**频控
    if (ret == -2 or errcode == -2) and (errmsg or "").lower() == "unknown error":
        return True
    return False
```

| 路径 | 信号 | 含义 | 处理 |
|---|---|---|---|
| **入站** `getupdates` | `_is_stale(...)` | **登录会话失效** | ERROR 告警（明示需 `guanlan im-login`）+ 暂停 600s |
| **出站** `sendmessage` | `_is_stale(...)` 且本次**带了** `context_token` 且尚未重试 | **该 peer 的 context_token 陈旧** | 丢弃该 peer 的缓存 token → **去 token 重试一次**（iLink 接受无 token 发送作降级）→ 成功即正常，**不停服、不要求重登录** |
| **出站** | `_is_stale(...)` 但已去 token 重试过 | 真的登录失效 | 抛错，交上层记日志 |
| **出站** | `-2` 且 `errmsg != "unknown error"` | **真频控** | 3× 退避重试（默认 4 次）；累计触发熔断 30s |
| 任一 | 连续失败 ≥3 | — | 退避 30s 后清零计数；否则 2s |

**出站串行化**：适配器内持一把 `asyncio.Lock` 串行所有 `send`（参考实现里同款的出站闸），配
`chunk_delay_s=1.5`——微信频控是真的会丢消息。

### 7.6 扫码登录 `guanlan im-login`（决策P4.21-23）

原设计写「不内建扫码向导」——**推翻**：没有扫码流程，本适配器对**手上没有现成 iLink 凭据的用户**
（即绝大多数人）**完全不可用**，
装了就用不了不叫有界，叫没做完。

流程（端点已核对 `ilink/bot/get_bot_qrcode` / `get_qrcode_status`）：① 请求二维码 → 拿 `qrcode`(hex) 与
`qrcode_img_content`；② **呈现**：用 `qrcode`（纯 Python）**直接把码画在终端里**，缺则打印原始值并给指引；
③ 轮询 `get_qrcode_status?qrcode=<hex>` 直到确认，过期自动刷新（上限 3 次）；④ 落 `account.json`（`chmod 0600`）。

**真机实测修正（§11 第 4 步，2026-08-16）**——首跑即 `{"err_msg":"missing bot_type","ret":1}`，三处与实现不符：

| 观测 | 修正 |
|---|---|
| 不带 `bot_type` 报 missing；**放进请求体照样报 missing**，只有放 query 才被读到 | `bot_type` 是 **query 参数**。逐值试出**合法值只有 `3`**（0/1/2/4…100 及字符串均 `invalid bot_type`，ret=2） |
| `get_qrcode_status` 未扫时**挂满 30s** 才回 `{"ret":0,"status":"wait"}` | 它是**长轮询**。原实现的读超时恰为 30s，每轮都在服务端正要回话时被自己掐断 → 提到 `30+15`s，并容忍 `ReadTimeout` 重来 |
| 「已过期」的响应形态**始终没观测到**（扫掉之前一直 `wait`） | 不能只靠 `status == "expired"` 收场，否则用户扫码前走开就无限静默等待。加 `QRCODE_WAIT_SECONDS = 180` 墙钟兜底 |
| 扫码确认后回 `{"status":"confirmed", "bot_token":"<botid>:<hex>", "ilink_bot_id":"<12字符>@im.bot", "ilink_user_id":"<38字符>", "baseurl":"…"}`——**没有** `token`，**没有** `account_id` | 原实现认的两个字段名（`token` / `account_id`）**全是猜的、一个都不对**。改认 `bot_token` / `ilink_bot_id`，并**以服务端自报的 `baseurl` 为准** |

**`ilink_bot_id` 还是 `ilink_user_id`？——取错会回声循环。** 前者形如 `xxx@im.bot`，正是入站帧里
`to_user_id` 的那个身份；后者是**扫码那个人**的 id。`map_inbound` 的自消息过滤判据是
`from_user == account_id`，取成扫码人则机器人**把自己发的话当成新入站消息**，一路自问自答。
`tests/test_im_weixin.py` 有一条用例把这两种取法的后果并排断言，守着别人日后"顺手改成 user_id"。

**这次的教训比字段名本身重要**：认不出 token 时，原实现的表现是**继续 `wait`**——扫完码一切"正常"，
只是永远等下去；用户看到「扫了没反应」，日志一个字都没有。故新增一条硬错误：`status == "confirmed"`
却取不到 `bot_token` 时**直接抛 `GuanlanError` 并把本次响应的键名列出来**。
**静默失败比崩溃难查一个数量级**，这种地方宁可崩。

§13-3 由此**关闭**：`qrcode_img_content` 是**可扫 URL**（`https://liteapp.weixin.qq.com/q/...?qrcode=…&bot_type=3`），
终端画码分支成立。

**连带推翻一条设计决定**：`qrcode` 原定"可选增强，缺则打印原始值，故不进 extra"——现提为 `[im-weixin]` 的
**正式依赖**。理由是那条退路根本不等价：退回打印的 URL **就是登录凭据本身**，用户要用它只能贴进第三方
二维码生成器（等于把登录链接交给外人）或想办法把 URL 挪到手机上。**这不是"稍差一点的等价路径"，
是把安全成本转嫁给用户**，而代价只是一个纯 Python、非 Windows 无运行时依赖的包。

画法上两个易被忽略的点：

- **`tty=True` 而非只 `invert=True`**：后者靠终端自身的前景/背景色，浅色主题下黑白正好反过来，
  多数扫码器认不出；`tty=True` 让 SDK 显式写死前景白/背景黑的 ANSI 色，**深浅色主题都扫得出**。
  非 tty（重定向 / 被测试捕获）时它会抛 `OSError`，故按 `sys.stdout.isatty()` 降级。
- **窄于码宽的终端一律不画**：折行后是一团**扫不出来的乱码**，而用户看不出哪里不对，只会以为"码坏了"。
  宁可不画并说明原因（版本 6 的码含静默区约需 45 列）。

**这条 bug 是怎么漏到真机的**：`run_qrcode_login` 早就为可测性留了 `transport` 形参，却**从没有一个测试用过它**
——整条扫码登录流零覆盖。补测已入 `tests/test_im_weixin.py`（含一条**反向用例**：服务端回了 `err_msg`
而我们只打「未返回 qrcode 字段」时必须红——把服务端原话吞掉，操作者除了重试无事可做）。
但要如实说：**MockTransport 挡不住这个 bug**，假服务端只会照着我们自己的错误假设写。
真正的判据就是 §11 第 4 步的真机联调，这正是它存在的理由。

## 8. 适配器 B：飞书（`adapters/feishu.py`）

### 8.1 WS 客户端构造：**必传 channel UA tag**（评审 #2，决策P4.21-29）

**已复核参考实现源码属实**（其构造处带显式注释说明这个 tag 的作用）：

```python
lark_oapi.ws.Client(
    # domain：飞书国内站与 Lark 国际站是两套域名，SDK 构造期就要选定
    # （lark_oapi.core.const 的 FEISHU_DOMAIN / LARK_DOMAIN）。由
    # GUANLAN_IM_FEISHU_DOMAIN（feishu|lark，默认 feishu）决定，见 §9.2。
    app_id=..., app_secret=..., domain=domain, event_handler=handler,
    # 不传这个 tag，飞书服务端**不会**经 WebSocket 推送群 @ 事件（只推 P2P 单聊）。
    # 该参数自 lark-oapi **1.6.8** 起才有 —— extra 下限必须 >= 1.6.8。
    extra_ua_tags=["channel"],
)
```

**连锁修正**：extra 从原设计的 `lark-oapi>=1.4` 抬到 **`>=1.6.8`**。旧版本装上去会
`TypeError: unexpected keyword argument`——**这比静默收不到群消息好**，但仍要在 `_check_caps` 阶段先探针
（`inspect.signature` 查 `extra_ua_tags`），缺则拒启并明示「请升级 `lark-oapi>=1.6.8`」。

`lark-oapi` 是**同步 SDK**：WS 客户端跑自己的线程、回调在 SDK 线程触发；HTTP 调用也是阻塞的。故：

- **入站**：SDK 回调里 `loop.call_soon_threadsafe(queue.put_nowait, inbound)`，`inbound()` 从 `asyncio.Queue`
  取——**绝不**在 SDK 线程里直接碰事件循环对象。
- **出站**：`await anyio.to_thread.run_sync(partial(client.im.v1.message.create, req))`（§4.3 通则）。
- **事件**：`EventDispatcherHandler.builder("", "").register_p2_im_message_receive_v1(cb).build()`，
  v1 **只注册 `im.message.receive_v1` 一个事件**。

### 8.2 bot 身份**自动探测**（评审 #2 的连带发现，决策P4.21-29）

原设计要求必填 `GUANLAN_IM_FEISHU_BOT_OPEN_ID`——**多余的**。参考实现在建 WS 前先探一次 bot 身份：
`GET /open-apis/bot/v3/info`（tenant access token，**无需额外权限**）→ 拿 `bot_open_id` + `bot_name`。

故 v2：**启动时总是探测**（不因 env 已设而跳过——陈旧的 env 值会静默破坏群 @ 判定，参考实现对此专门打
WARNING）；env 仅作探测失败时的回退；两者都无且启用了群 → 拒启并明示（否则群内 @ 判定永远 False、
表现为「群里怎么都不理我」）。

### 8.3 入站字段映射

| `InboundMessage` | 飞书事件字段 |
|---|---|
| `tenant` | `header.tenant_key` |
| `chat_id` | `event.message.chat_id` |
| `chat_type` | `event.message.chat_type == "p2p"` → `"dm"`，否则 `"group"` |
| `user_id` | `event.sender.sender_id.open_id` |
| `text` | `json.loads(event.message.content)["text"]`（仅 `msg_type == "text"`） |
| `msg_id` | `event.message.message_id` |
| `mentioned_me` | `event.message.mentions[].id.open_id == <bot_open_id>` ← **结构化字段** |
| `msg_kind` / `has_attachments` | `msg_type == "text"` → `"text"`；其余 → `"other"` + `has_attachments=True` |

### 8.4 出站：`post` 富文本 + 围栏切行

飞书**不直接渲染 markdown**，但 `post` 的 **`md` 元素吃裸 markdown**——转换几乎免费：

```python
{"zh_cn": {"content": [[{"tag": "md", "text": <裸 markdown>}]]}}
```

**唯一的真实逻辑是按围栏块切行**：飞书的 `md` 渲染器在**一个大元素里含围栏块时会吞掉围栏之后的内容**
（参考实现在其分行函数的注释里点明）。故在真围栏行处切开，围栏块独占一 row，前后散文各成一 row。
观澜的答案经常带围栏块（代码/mermaid/flint），**这个坑必踩**。

- `send` → `im.v1.message.create(receive_id_type="chat_id", receive_id=chat_id, msg_type="post", content=…)`，
  返回 `message_id` 装进 `OutboundRef`。
- `edit` → `im.v1.message.update(message_id, body={msg_type, content})`。
- **两处都要「`post` 被拒 → 回退纯文本」的降级路径**：参考实现在 send 与 edit 两侧各写了一遍，说明这是实际
  会发生的（某些 markdown 会被 API 判非法）。

### 8.5 单实例锁：**平台状态目录级**（决策P4.21-26，经评审 #14 修订为决策P4.21-42）

飞书**同一 app_id 起两个 WS 客户端**时消息会被随机分发——表现为「有时不回」且极难排查；微信一个 token 也
只允许一个长轮询实例。v1 做**最简本机锁**：`O_CREAT|O_EXCL` 建锁文件 + 写 `{pid, 子命令名}`；启动时若锁存在
则检查 pid 是否还活着，死进程的陈锁自动清理。抢不到即 `EXIT_USAGE` 拒启并明示 **owner pid + 占用者子命令名**。
不做跨机分布式锁。

**锁键是平台状态目录级，不是租户级**（评审 #14 修订）：

```
~/.guanlan/im/weixin/credential.lock
~/.guanlan/im/feishu/credential.lock
```

原设计写「微信用 `account_id`、飞书用 `app_id`」，**微信那条实现不了**：首次 `im-login` 时 `account_id`
要等扫码成功才拿得到，两个并发的首次登录进程**无法预先互斥**，会同时扫码并互相覆盖 `account.json`。
统一到目录级即消除这个先有鸡还是先有蛋的问题。

**代价说清楚**：同一台机器不能同时跑两个不同飞书 app 的宿主。v1 接受——「一进程一库一平台」本就是既定边界
（§1），要接两个库/两个 app 请用不同的 `HOME` 或等后续按需细化锁键。

## 9. CLI 契约与依赖

### 9.1 三个子命令

```bash
# ① 首次配置：拿到要授权的人的完整 ID（零 LLM、绝不回复、限时）
guanlan im-identify --platform weixin [--seconds 300]

# ② 微信扫码（首次或会话失效后）
guanlan im-login --platform weixin

# ③ 起宿主
guanlan -C <kb> im --platform weixin --allow-user <id> [--allow-user <id>…]
guanlan -C <kb> im --platform feishu --allow-chat <chat_id> --allow-user <open_id>
guanlan -C <kb> im --platform weixin --allow-user-env GUANLAN_IM_USERS   # 逗号分隔
guanlan -C <kb> im --platform feishu --allow-all-users                   # 启动日志大声告警
guanlan -C <kb> im --platform weixin --web-base-url https://kb.internal
guanlan -C <kb> im --platform feishu --mcp-request-timeout 60   # 每次 tools/call 请求的上界（§4.7）
guanlan -C <kb> im --platform feishu --no-mcp                   # 彻底不加载外部 MCP server
```

**`--mcp-request-timeout`（默认 120s）与 `--no-mcp`（评审 #33/#36/#38，决策P4.21-60/63/65）**：
agentao 那边 `tools/call` 的默认是**无限等待**，本旗标默认 120s **把这一段收住**——但它**只收住每次
`tools/call` 请求**，连接、传输进入与断连清理不在其内（§4.7），所以**仍不能保证一轮问答一定等得到头**；
真要立刻脱身只有第二次中断信号。（`--no-mcp` 则连 MCP 都不加载，自然也不会卡在这里。）它是**宿主级天花板**——盘上配了更长的显式值也会被收紧到它（并记 WARNING），
这样它才真的是"上界"。值必须是**有限正数**，否则 `EXIT_USAGE`。默认值 120s 是**有限**而非精确——
真要更长，调大这个旗标（而不是去改每个 server 的配置）。合并规则见 §4.7。

**`im-identify`（评审 #1，决策P4.21-28）—— 解开白名单死锁的那把钥匙。**

原设计的死锁是真的：§0.2 让人「从日志读 ID」，§9 却要求空白名单**拒启**、且日志里 ID **脱敏**——新用户没有
任何安全路径拿到第一个完整 ID。`im-identify` 是一个**独立、有界、不需要白名单**的模式：

| 性质 | 为什么这样设计 |
|---|---|
| **绝不回复任何消息** | 对方只看到「发了没人理」，与机器人不存在无异——不泄露「这里有个知识库机器人」 |
| **不加载 KB、不建会话、不调 LLM** | 零成本、零内容泄露面；连 `-C` 都不接受 |
| **限时**（默认 300s，到点自动退出） | 不会长期敞开一个无鉴权的监听态 |
| **把完整 ID 打到终端 stdout** | 这是它**唯一**的用途；日志脱敏规则在此**不适用**（终端 = 操作者本人） |

输出形如：
```
[im-identify] 收到消息（不会回复）：
  平台=weixin  租户=<account_id>
  用户ID=wxid_xxxxxxxxxxxx   ← 填入 --allow-user
  会话ID=（单聊）             聊天类型=dm
```

`im-identify` / `im-login` 均为**平级子命令、不接受 `-C`**（与知识库无关）——沿 `install-skill` 先例。

#### 三命令互斥：同一平台凭据同时只能有一个进程持有（★ 决策P4.21-38）

**`im-identify`、`im-login`、`im` 三者不能同时跑**——它们抢的是同一份平台凭据：

- **微信**：iLink **一个 token 只允许一个长轮询实例**（参考实现对此有显式的 token lock 与报错）。
- **飞书**：同一 `app_id` 起两个 WS 客户端会让消息**随机分发**到其中一条连接（§8.5 的本机锁正是为此）。

这不是可以绕开的实现细节，是平台语义。故：

- **三个子命令共用同一把 §8.5 的本机锁**，锁键是**平台状态目录级**
  `~/.guanlan/im/<platform>/credential.lock`（评审 #14 修订：**不能**用 `account_id`/`app_id` 作键——微信首次
  `im-login` 时 `account_id` 要扫码成功后才拿得到，两个并发首登进程无法预先互斥，会同时扫码并互相覆盖
  `account.json`）。抢不到即 `EXIT_USAGE` 拒启并**明示 owner pid 与占用者是哪个子命令**——不能只说
  「凭据被占用」，那让人分不清是自己起了两个服，还是忘了关 identify。
- **`im-login` 只对微信有意义**：`--platform feishu` 在 **CLI 解析期**即拒绝（`EXIT_USAGE`，提示「飞书凭据走
  环境变量 `GUANLAN_IM_FEISHU_APP_ID`/`_APP_SECRET`，无需登录」），不进入运行期、不碰锁。
- **`im-identify` 的限时（默认 300s）在此有第二层意义**：它保证一个忘关的 identify 进程最多把宿主挡住 5 分钟，
  而不是永远。

#### 因此：加一个新人到白名单的完整运维流程

```bash
# ① 停服（Ctrl-C 或 kill 宿主进程）—— 必须先停，否则 ② 抢不到凭据
# ② 敞开收集窗口，让新同事发一条消息
guanlan im-identify --platform feishu --seconds 300
# ③ 把输出里的完整 ID 追加进启动参数（或 --allow-user-env 指向的环境变量）
# ④ 重新起服
guanlan -C ~/kb im --platform feishu --allow-chat oc_… --allow-user ou_老张 --allow-user ou_新人
```

**「加人要停服」是「绝不回复未授权者」的必然代价**，不是设计疏漏：要么敞开着收 ID 并回复陌生人（泄露机器人
存在），要么关起来收。v1 选后者。缓解手段是 `--allow-user-env`——把清单收在一个环境变量里，改动集中在一处；
但**改完仍需重启**（进程启动时读一次，不做热重载：热重载白名单意味着运行期改授权，那需要一套配置变更的
审计与原子性保证，属 E2）。

> 这条约束**必须写进 `docs/guide/`**（§14）：第一个用户几乎一定会在起着服的时候跑 `im-identify`，
> 拿到一个"凭据被占用"的错误却不知道是自己的操作顺序问题还是 bug。

### 9.2 其余契约

- **`--platform` 必填、无默认**（决策P4.21-5）：两家能力差别大到没有合理默认值。
- **凭据 env-only / 状态目录**（决策P4.21-6，经决策P4.21-78 补 `.env`）：飞书
  `GUANLAN_IM_FEISHU_APP_ID` / `_APP_SECRET` /
  **`_DOMAIN`**（`feishu`｜`lark`，默认 `feishu`，见 §8.1；`_BOT_OPEN_ID` **已不再必填**，§8.2）；
  微信凭据由 `im-login` 落 `~/.guanlan/im/weixin/account.json`。`_DOMAIN` 取值非法 → `EXIT_USAGE` 拒启并列出
  合法值（替代「用默认值连错域名后报认证失败」这种误导性故障）。
  值经 `.strip()`——空白-only 一律拒启。**绝不**提供明文命令行参数、**绝不**进日志（ID 打前 4 位 + 掩码，
  secret 永不出现；沿用 P4.19「脱敏须覆盖**错误文本**」的教训）。**例外恰好一处**：`im-identify` 的终端输出
  （§9.1）。
- **无 `--mode` / 无 `--reader`**（决策P4.21-8）：**不存在可写分支可切**。
- **白名单是启动前置条件**（决策P4.21-9）：四者全空 → 拒启，报错文案**直接指向 `im-identify`**。
- **无新退出码**：正常停服 `EXIT_OK`；其余用法错 = `EXIT_USAGE`，**就地拒启、不建立任何连接**。
- **凭据独占**（决策P4.21-38）：三个子命令共用一把本机锁，抢不到即 `EXIT_USAGE`，报错须**同时给出 owner pid
  与占用者子命令名**（如「`im-identify` (pid 41822) 正持有 weixin 凭据，等它超时退出或先停掉它」）。
- **依赖门控**：缺对应 extra 时优雅降级提示安装、返 `EXIT_USAGE`、不吐 traceback。探针只探**该平台**的 SDK。

### 10.1 `tests/test_im.py`（核心，`FakeAdapter` 驱动，零网络零 SDK，**不 skip**）

- **核心零平台分支**：`grep -r '== "weixin"\|== "feishu"' guanlan/im/*.py` 应为空——写成断言，守住决策P4.21-3。
- **拒启矩阵**：白名单四者全空（且报错文案含 `im-identify`）/ 凭据缺失或空白 / `--platform` 缺失 / 非知识库根 /
  `--allow-chat` 撞 `supports_group=False` → 各 `EXIT_USAGE` 且**未建立任何连接**（断言 `FakeAdapter.start`
  未被调用）。
- **授权真值表**（评审 #6/#11）：**逐行**测 §5.2 全部组合——必含三条关键正例：
  ① 「群在白名单但人不在 → 拒」（AND 语义）；② 「群内未 @ → 拒」；
  ③ **「开了 `--allow-all-users`，但群不在 `--allow-chat` 里 → 仍拒」**（守住决策P4.21-39：该旗标
  **只旁路用户名单、永不旁路群名单**；这条一旦回归就是把整库开给机器人所在的所有群）。
  另测**大小写敏感**：`allow_users={"Ou_ABC"}` 时 `ou_abc` **被拒**。
- **未授权静默**：断言**没有任何出站调用**（「不回复」本身是契约）。
- **KB 零字节写**（**必测、不得跳过**）：跑完一轮问答后对 `<kb>` 前后快照，断言零字节差异——含**无**
  `agentao.log`、**无** `.agentao/sessions/`；另断言状态目录只写在 `~/.guanlan/im/` 下。
- **去重**：同 `msg_id` 投两次 → 只跑一轮；TTL 过期后可再跑。
  **反向用例（评审 #7）**：同一用户 5 分钟内**两次相同文本、不同 `msg_id`** → **必须都被处理**（守住
  「删掉内容指纹去重」这个决策不被后人好心加回来）。
- **分片合并**：两片（前片接近上限）在阈值内到达 → 合成一条；**含 cancel-delivery 竞态用例**（注入时钟）。
- **生命周期闭合**（评审 #10）：① turn 抛异常时 `end_turn` 仍被调用、typing 被关掉；② **长 turn 期间触发
  idle 回收扫描，断言该会话未被回收**（这是 `begin_turn` 的存在理由）。
- **会话状态机四态**（评审 #12，注入时钟、不真等 30 分钟）：① 首次 → `FIRST` 且**不提示**；② TTL 内再问 →
  `EXISTING`；③ **跨 TTL 再问 → `EXPIRED` 且提示「上下文已过期」，并断言拿到的是新 `cid`**（守住「不会被
  `store.get()` 悄悄复活」）；④ 人为让 `store.get` 返回 `None`（模拟不变量被破坏）→ `LOST`、提示措辞与 ③
  **不同**、记 WARNING、且**无悬空映射残留**；⑤ `/new` 后再问 → `FIRST`（**不提示**）。
- **过期会话真的腾出容量**（评审 #18，**这是修订的核心正例**）：`max_conversations=2` + 注入时钟 →
  两个 key 各建一个会话 → 时钟推过 TTL → **第三个 key** 首次说话 → 断言 ① 拿到会话而**不是**「会话数已满」，
  ② `store.live_count() == 1`（前两个被 `_sweep_expired` 扫掉），③ **前两个 key 再问时仍是 `EXPIRED`**
  （评审 #24：墓碑保住了过期语义——若实现回退成"整条删除"，这里会得到 `FIRST`，用例立刻红）。
  > 反向守卫（守住「不许把 store 的 idle_ttl 加回来」）：断言 `ConversationStore` 是以 `idle_ttl=None` 构造的。
- **墓碑有界且不误伤活条目**（评审 #24）：造 `max_conversations + 10` 个墓碑 → 断言墓碑数被压回界内、
  **淘汰的是最旧的**、且**没有一个 `cid is not None` 的活条目被淘汰**；被淘汰墓碑的键再问 → `FIRST`（可接受）。
- **`/new` 不留墓碑**：`/new` 后再问是 `FIRST`（**不是** `EXPIRED`）——主动重开不该被告知"上下文已过期"。
- **sweep 不误伤在飞轮**（评审 #18）：让 key A 的一轮"卡住"、时钟推过 TTL、key B 首次说话 →
  断言 A 的会话**未被 drop**（`busy()` 守卫生效），且 A 的这一轮仍能正常收尾。
- **容量真顶满**（评审 #18）：`max_conversations=1` + 两个 key **同时活跃**（都在 TTL 内）→
  第二个 key 收到「当前会话数已满」的**显式答复**，且断言**主循环没死**（第三条消息仍被处理）。
- **shutdown 真停**（评审 #13/#19）：起一个"长 turn"的 fake，触发 shutdown，断言 ① 每个在飞会话的
  `request_stop()` **被调用过**；② `adapter.close()` 发生在**所有 turn 真正返回之后**（用调用序列断言，
  不是靠 sleep）；③ edit writer 已退出，且退出后**没有任何出站调用**（停机路径一个字也不发，评审 #27）。
- **异常路径的 writer 顺序**（评审 #10，与上一条分开测）：turn 抛的是**普通异常**时，断言 writer
  **在错误提示发出之前**就停了（不会把提示改回旧的局部文本）。
- **超时只告警、不取消**（评审 #19）：把 `warn_interval` 设为极小值 + 一个要跑很久的 fake turn →
  断言 ① 期间打出了 WARNING（含未收尾的 `session_key`）；② **`task.cancel()` 从未被调用**；
  ③ turn 自然返回后才 `close()`、退出码 `EXIT_OK`。
- **停机不发「处理出错了」**（评审 #27，**必测**）：fake 的 turn 抛 `AgentCancelledError` → 断言
  ① **零出站消息**（尤其不含"出错"字样）；② writer 已停；③ 日志是 INFO 级的"中止"而非 ERROR。
- **停机撞上慢 `acquire`**（评审 #25，**这是修订的核心竞态用例**）：让 `store.create` 卡在卸线程里 →
  此时触发停机 → 待 `create` 放行 → 断言 ① `stop_all()` **等到了**这个 task（不是提前返回）；
  ② 该 task **一个字也没发**（第二道 `_closing` 闸拦住）；③ `adapter.close()` 在它结束**之后**。
- **强制退出真的退得出去**（评审 #26，**必须用子进程**）：`subprocess` 起一个宿主，其 fake turn
  **永不返回**（模拟卡死的 executor 线程）→ 连发两次 `SIGINT` → 断言 ① 进程在数秒内**真的退出**
  （守住"非守护 worker 被 atexit `join()` 会把进程挂住"这条）；② 退出码是 `EXIT_AGENT_ERROR`（**不是 0**）；
  ③ stderr 里有那行提示且写明还剩几轮；④ **断言这条路径没调用 `logging`**（猴补 `logging.shutdown`
  使其一旦被调就挂起，进程仍须退出——直接把评审 #32 的失效模式做成用例）。
  > 同进程测不了：`os._exit` 会把 pytest 一起带走。这也是唯一一条需要子进程的用例。
- **墓碑接线三处**（评审 #34）：① `SessionRegistry` 的 `tombstone_limit` 确实来自 `max_conversations`
  （构造断言）；② **过期后紧接着容量顶满**：让 `store.create` 抛 `RuntimeError` → 用户重试 → 断言仍是
  `EXPIRED` 而**不是** `FIRST`（守住"过期身份不会在最需要它的那次重试里丢失"）；③ `/new` 不留墓碑。
- **墓碑不会自己淘汰自己**（评审 #37，**三条件同时成立的组合用例**）：墓碑**已满** + 当前键刚过期 +
  `store.create()` 抛容量错 → 用户重试 → 断言仍是 `EXPIRED`。
  另断言该墓碑的 `last_seen` 被刷成 `now`（不是沿用旧值）。**上一条用例单独绿不算数——这三个条件凑齐时才暴露问题。**
- **并发重建不会互相淘汰墓碑**（评审 #44，**这是 #37 那条的加强版**）：两个**不同**的键 A、B
  同时进入重建（用可控的慢 `store.create` 制造交错）、墓碑已满、**其中一个创建失败** →
  断言两个键的墓碑都还在，各自重试都拿到 `EXPIRED`。
  再断言 `_creating` 在三条退出路径（成功 / 抛错 / 被取消）后都已清空——**残留一个键就等于永久保护它**。
- **MCP 有限上界**（评审 #33/#36/#38）：
  ① **合并规则按"解析结果"逐例测**：缺省 / `null` / 标量 / `0` / `-1` / `"bad"` / `NaN` / `Infinity` /
  有限但**大于** T / 有限且**小于** T——**判据统一用 agentao 的 `resolve_timeouts(bounded_cfg)[1]`
  是有限正数且 ≤ T**（用上游解析器当神谕，上游改规则时红的是这条用例）；只有最后一例保持原值。
  ② 大于 T 的显式值被收紧时**有 WARNING**（不静默改用户配置）。
  ③ 断言**不改盘上文件**（读两次 `list_servers()`，源 dict 不被就地修改）。
  ④ `--no-mcp` 时传给会话层的是 `mcp_registry=None`；不给旗标时 `request` 是 120s 而非 `None`。
  ⑤ **旗标自身非法**（`0` / 负数 / `NaN` / 非数字）→ `EXIT_USAGE`，且**未建立任何连接**。
- **收流 task 可取消**（评审 #29）：让 `FakeAdapter.inbound()` 阻塞在 `Queue.get` → 停机 → 断言
  ① `recv` task 干净结束（无 `CancelledError` 泄漏为测试失败）；② `adapter.close()` 在其**之后**；
  ③ 取消点上没有半提交状态（fake 记录的"已取出未交付"计数为 0）。
- **收流死亡不留活死人**（评审 #30，**两例**）：① `inbound()` **抛异常** → 断言进程进入停机、
  日志 ERROR 含异常信息、退出码 `EXIT_AGENT_ERROR`、且 `adapter.close()` 被调用；
  ② `inbound()` **正常返回** → 同样按错误处理（长驻宿主没有"收完了"这回事）。
  两例都要断言**没有"永远空等"**（用注入的假时钟/超时守卫，不靠真 sleep）。
  > **①这例必须逐项断言停机四步全跑过**（评审 #35）：`intake.drain` / `stop_all` / `adapter.close`
  > 各被调用一次，且**原异常没有从 `_run` 冒出来**。v6 的写法会在第一步就把它们全跳过——
  > 而"收流抛异常"恰恰是最需要清理跑完的那条路径。
- **清理步骤各自抛错都不影响后续**（评审 #45/#51，**四例**）：分别让 `intake.drain()` /
  `delivery.stop_all()` / `recv` 的取消 / **`adapter.close()` 本身**抛异常 → 每例都断言
  ① 后续步骤**仍被调用**、信号处理器仍被还原、凭据锁仍被释放；
  ② **退出码是 `EXIT_AGENT_ERROR` 而不是 0**（评审 #51：清理没干净却报 0，是最坏的一种矛盾）；
  ③ 日志里点出**是哪一步**失败（记账用列表而非布尔的理由）。
  **清理代码自己不能有单点故障，也不能把失败吞成成功。**
- **三条 acquire 分支都走 `_renew`**（评审 #50）：墓碑 / `LOST` / 首次各一例，断言
  ① 期间该键都在 `_creating` 里（用可控的慢 `store.create` 卡住后检查）；
  ② 三条路径结束后 `_creating` 都已清空。**这条用例存在的理由是：新机制若只接上一半，
  单看 `_renew` 的实现是对的，问题只在调用点——只有从 `acquire` 入口测才发现得了。**
- **`start()` 失败的收尾**（评审 #40）：`FakeAdapter.start()` 抛错 → 断言 ① `close()` 被调用（兜底）；
  ② **原信号处理器已还原**（比对 `signal.getsignal(SIGINT)` 与安装前一致）；③ 凭据锁已释放
  （同平台随即起 `im-login` 能拿到锁）；④ 退出码 `EXIT_AGENT_ERROR`。
- **停机撞在 `acquire` 与 `begin_turn` 之间**（评审 #31，**这是本轮最细的一条**）：卡在
  「`acquire` 已返回、`turn` 尚未装令牌」的窗口触发停机 → 断言 ① `request_stop()` **返回 `True`**
  （证明 `begin_turn()` 已在同一不可分割段内跑过，落到"记待停"那一态，而不是空转的 `False`）；
  ② 该轮起跑后**立即**被兑现的待停停掉，而不是跑完整轮。
- **`store.get()` 不阻塞事件循环**（评审 #28）：让 `store.create` 人为很慢（模拟持锁的 Agent 构造）→
  新用户建会话期间，**老用户**发一条消息 → 断言这条消息在 `create` 完成**之前**就被 `offer` 接收
  （证明 `get()` 走了 `to_thread`，没在 loop 线程上撞那把 `threading.Lock`）。
- **emit 在事件循环线程**（评审 #21）：在 emit 里记 `threading.get_ident()`，断言与 loop 线程一致；
  且断言 emit 内**没有**调用 `call_soon_threadsafe`（猴补探测）；再构造「最后一个 token 紧挨着 turn 返回」
  的场景，断言 `finalize` 后 `_latest` 不再被改（守住终稿不被中途快照覆盖）。
- **`/new` 不阻塞**（评审 #16）：`store.delete` 人为设为慢，断言 `drop` 期间另一条入站仍能被 `offer` 接收
  （证明走了 `to_thread`，没占住事件循环）。
- **edit 严格有序**（评审 #10）：让 fake adapter 的 `edit` 人为延迟，断言**永不并发两个 edit**、且
  `finalize` 的文本是最后落地的（构造「中间 edit 慢于 final」的场景，验证不会被旧文本覆盖）。
- **长答案契约**（评审 #4/#23）：`dropped == 0` 时无损全发；`dropped > 0` 时**末片是截断告示**且含剩余字数；
  **edit 档超长**时首片 edit、余片 send、且**中间 edit 的文本也 ≤ limit**。
  另断言告示文案**不含「完整版」字样**、且无 `--web-base-url` 时**不出现任何 URL**（守住决策P4.21-50：
  不承诺一个不存在的完整答案）。
- **单飞**：在飞时第二条消息得到「请稍候」，且 fake 只被调一次。
- **附件提示归核心**（评审 #9）：`msg_kind="other"` 的入站 → 固定提示、**零 LLM**（断言 fake 未被调用）。
- **`/search` 零 LLM 且卸线程**（评审 #8）：断言走 `search_result_dict` 且 fake 未被调用；并以「检索期间
  另一条消息仍能被 `offer` 接收」证明未阻塞事件循环。
- **优雅停**：shutdown 时未到期的 debounce 缓冲被**丢弃**（不触发 LLM）。
  > **不再断言「在飞 task 被取消并 gather」**——那与上面「等真实收尾、不 cancel」直接矛盾（评审 #19）。
  > 正确契约只有一条：**`request_stop()` → 等 turn 自己返回 → 才 close**。
- **出站形态**：用 2000 / 8000 两个上限各跑一遍（上限是适配器给的数据，不是常量）。

**第 0 步的模型侧结论（v7 写错了，此处更正，评审 #43）**：实测 `openai==2.50.0` 的
`DEFAULT_TIMEOUT = Timeout(connect=5.0, read=600, write=600, pool=600)` 确为有限值——
**但 `read` 是"两次网络读取之间的空闲上限"，不是整次请求的墙钟上界**（httpcore 在逐块接收循环里取用它）。
服务端持续吐字节（心跳）就永不触发；而 agentao 的取消检查只在**解析出 chunk 时**执行，
只有原始心跳时连检查都不会跑。

**所以 v7 那句"模型侧不是无界的一环"是错的，已撤回。** 正确结论：**一轮问答的总时长没有绝对上界**，
优雅停机因此也没有；**唯一的绝对保证是第二次中断信号的 `os._exit`**（§4.4 的分层表）。
这不改设计，改的是我们对外的说法——**一个说错了的保证，比没有保证更危险**。

**第 2 步是大头**（九成代码、完全可测），也是把架构立住的关键。**第 5 步不改核心**是本设计成立与否的判据——
若那时发现核心必须为飞书开分支，说明 `AdapterCaps` 的能力位划错了，应回头改抽象而不是加 `if`。
**第 6 步的群 @ 不能省**：mock 测不出服务端是否真的推群事件（评审 #2 的本质是服务端行为）。

### 第二轮复审新增（★★）

- **★★ 决策P4.21-39（`--allow-all-users` 只旁路用户名单，永不旁路群名单）**：v2 的
  `allow_all OR (chat AND user)` 是安全旁路——一开旗标，机器人所在的**所有群**都放行，与「不给
  `--allow-chat` 群消息一律不理」矛盾。改为 `chat ∈ allow_chats AND (allow_all OR user ∈ allow_users)
  AND mentioned_me`。语义理由：`allow_chats` 是**受众物理边界**（机器人被放进哪个房间），`allow_users`
  是**人员边界**；该旗标表达「不想逐个列人」，不表达「不在乎在哪个群」。**没有任何旗标能一次开放所有群**，
  这是有意的。
- **★★ 决策P4.21-40（会话 TTL 归 `SessionRegistry` 自持，`acquire` 返回四态）**：两条已核实的源码事实使原
  设计的「过期明示」不可能发生——`store.get()` **命中即刷新** `last_active`（源码注释：有意为之，堵 reclaim
  竞态），且 `_reclaim_idle_locked` **只在 `create`/`restore`** 触发。故 registry 自持 `last_seen` + 可注入
  时钟，先判过期再 `get`；`AcquireStatus` 四态，**`FIRST` 不提示**，各态措辞不同。
  > **经决策P4.21-46 修订**：第四态 `RECLAIMED` → `LOST`；`store.idle_ttl` 由「2× 兜底」改为 **`None`**
  > ——两套 TTL 不是分工，是空档（见 §4.5）。
- **★★ 决策P4.21-41（shutdown 先 `request_stop()` 再等真实收尾；edit writer 生命周期闭合）**：
  `task.cancel()` **停不掉** `arun()` 的 executor 线程（`conversation.py` 源码注释明写「不同于 asyncio 取消」），
  只取消外层会出现「进程认为已结束、adapter 已关，残留线程仍在调模型」。七步顺序见 §4.4，`adapter.close()`
  必须在所有 turn 真正返回**之后**。edit writer 三条退出路径（正常/异常/shutdown）统一落 `try/finally`，
  且**异常路径必须先停 writer 再发错误提示**，否则提示会被旧局部文本覆盖。
- **★★ 决策P4.21-42（凭据锁改平台状态目录级）**：原「微信用 `account_id`」实现不了——首次 `im-login` 时
  `account_id` 尚不存在，两个并发首登无法互斥、会互相覆盖 `account.json`。改用
  `~/.guanlan/im/<platform>/credential.lock`。代价：同机不能跑两个不同飞书 app 的宿主（v1 接受，
  「一进程一库一平台」本就是既定边界）。`im-login --platform feishu` 在 CLI 解析期即拒绝。
- **★★ 决策P4.21-43（微信补齐八字段映射表）**：见 §7.2.1。关键取舍：**混合 item（文本 + 附件）判 `"other"`
  走附件提示，文本部分不进 LLM**——只答文字会给出「看似回答了、实则没看到图」的答案，比明说不处理更糟。
- **★★ 决策P4.21-44（`SessionRegistry.drop` 改 async + `to_thread`）**：它最终调 `store.delete()` →
  `conv.close()`，后者被源码标注「慢（可能 MCP 断开等），锁外」；同步调用会让一次 `/new` 卡住整个事件循环、
  所有人收不到消息。
- **★★ 决策P4.21-45（CI 必装并运行 im extras；装了 SDK 时签名缺失应 fail 而非 skip）**：现 CI 只
  `uv sync --extra web --extra mcp`，原「缺 SDK 则整体 skip」等于让最关键的 `extra_ua_tags` 回归**永远不跑**。
  skip 只保留给本地无 extra 的开发机。
  > **经评审 #22 细化**：skip / fail 的分界是「**SDK 导入不到** → skip」「**导入到了但签名缺 tag** → fail」。

### 第三轮复审新增（★★★）

- **★★★ 决策P4.21-46（TTL 归 registry 独占：`store.idle_ttl=None`，registry 建会话前主动 sweep）**：
  v3 的「两套 TTL 分工」不成立。三条源码事实：`store.get()` 刷新 `last_active`、回收只在 `create`/`restore`
  触发、**顶满是抛 `RuntimeError` 而非逐出**（`conversation_store.py:122`）。推论有二：
  ① `conv.last_active` 恒不早于 registry 的 `last_seen`，故 store 判得动的会话 registry 早已判 `EXPIRED`
  ——**旧的 `RECLAIMED` 分支不可达**；② 更要命的是「registry 已过期、未到 store 的 2×ttl」这段窗口里
  **没有任何人腾容量**，100 个这样的会话会把第 101 个用户挡在门外。
  **多一层兜底反而制造了一个谁都不负责的空档**——这是这条决策真正的教训。
  故：`store.idle_ttl=None`，registry 在建会话前 `_sweep_expired()`（今在 `_renew` 内，决策P4.21-69）。
  在飞守卫用 `Delivery.busy(key)` 而**不用** `conv.is_idle(now, 0.0)`：后者比较的是刚被 `get()` 刷新过的
  `last_active`，在冻结时钟的测试里恒为假——**只在真实时钟下才成立的守卫等于没有测试**。
- **★★★ 决策P4.21-47（`RECLAIMED` → `LOST`，窄化为不变量破坏的防御分支；容量顶满给显式答复）**：
  registry 独占生命周期后，`store.get()` 返回 `None` 只可能是有人绕过 registry 删了会话——是 bug 信号，
  故**必记 WARNING**，但用户侧仍要给话（「会话已重置」）。容量真顶满（都活跃）走 `RuntimeError` →
  「当前会话数已满」的**显式**答复：这是唯一一类「系统忙」而非「你说错了」的拒绝，静默会被当成机器人挂了。
- **★★★ 决策P4.21-48（30 秒只告警不超时；强退显式非优雅，返回 `EXIT_AGENT_ERROR`；`Delivery` 补停机面）**：
  v3 的「超时才 cancel」**恰好重演它要修的那个错**——取消外层 task 停不掉 executor 线程，随后 `close()`
  又把连接抽走。宿主不叠第二层超时——叠的那层只能骗自己。
  故 30 秒只用来 WARNING「还在等谁」，然后继续等。
  > **经决策P4.21-68 修订**：本条原写"真实上界由模型/API 请求超时保证"，**该前提不成立**
  > （`read` 是每次读的空闲上限，不是整轮墙钟上界）。30 秒只告警的做法不变，但**不再声称有上界**。强退仅由**第二次中断信号**触发，跳过有序 close、记 ERROR、
  返回 `EXIT_AGENT_ERROR`（5）——**把没停干净的退出报成 0，是把运维的判断依据一起骗了**。
  配套给 `Delivery` 补 `Activity` 登记表 / `active()` / `stop_all()`，否则 server 无从枚举在飞会话与 writer。
  > **经决策P4.21-53 修订**：「从 `asyncio.run()` 返回 5」这个退出动作**本身就退不出去**（agentao 的非守护
  > worker 会被 `atexit` `join()`）。强退改为信号处理器里 `os._exit(5)`，`stop_all()` 的 `force` 参数与
  > `bool` 返回值一并删除。**退出码结论不变。**
- **★★★ 决策P4.21-49（宿主的 `emit` 已在事件循环线程，不得再 `call_soon_threadsafe`）**：
  `conversation.py:542` 已把调用方 `emit` 包成 `thread_safe_emit` 桥回 loop。v3 把 `Conversation` 的**内部
  实现模式**误当成宿主的义务。再桥一次会把每次 token 推迟一个 loop tick，可能在 `finalize` **之后**才改
  `_latest`，把终稿改回中途快照——且是偶发的。
- **★★★ 决策P4.21-50（截断告示不得称「完整版」）**：IM 会话 `persist=False`，被舍弃的内容**没存在任何地方**；
  `--web-base-url` 只是站点入口。改为「请在 Web 端**重新提问**以获取完整回答」，有 URL 时只附入口。
  **承诺一个不存在的东西比不给链接更糟**。

### 第四轮复审新增（★★★★）

- **★★★★ 决策P4.21-51（sweep 留墓碑，`EXPIRED` 语义才成立）**：v4 的 sweep 直接删整条映射，那个键下次来
  必是 `FIRST`——**与用例和指南承诺直接矛盾，且矛盾是我自己在 v4 引入的**。
  「彻底删除记录」和「日后仍知道它过期过」**不可兼得**，显式选后者：`(None, last_seen)` 墓碑。
  界：墓碑数超 `max_conversations` 时按最旧优先淘汰，**永不淘汰活条目**；被淘汰墓碑的键回来时得 `FIRST`
  ——半天没说话的人再被告知"上下文已过期"本就没有信息量。键空间另有白名单这道天然界（§5.2）。
  `/new` 用 `tombstone=False`：主动重开不该被告知"过期"。
- **★★★★ 决策P4.21-52（task 的创建与登记同一步，归 `Delivery.submit()`；`_closing` 双闸）**：
  `Activity.conv` 只能在 `acquire()` 之后填，而 `acquire` 内有卸线程的慢构造——停机若落在这段窗口，
  `active()` 是空的、`stop_all()` 以为无事可等、`close()` 之后那个 task 才拿到会话继续发。
  **登记必须早于第一个 `await`**。第二道闸放在 `acquire` 返回后，且与 `act.conv = conv` 之间**不得有 await**
  ——这样"能过闸者必已登记"才是闭合的。
- **★★★★ 决策P4.21-53（强制退出只能靠 `os._exit`；`arun` 的 `task.cancel()` 有反效果）**：两条源码事实。
  ① agentao 的 `arun` 用**自己的** `ThreadPoolExecutor`（`agent.py:56-62`，刻意不用 loop 默认执行器），
  worker **非守护**，`concurrent.futures.thread` 的 `atexit` 钩子会在解释器退出时 `join()` 它们——
  **卡死的 worker 会把进程卡在退出那一刻**，正是用户按第二次 Ctrl-C 想解决的现象。故强退 =
  信号处理器里 `logging.shutdown()` → `os._exit(5)`，并**用子进程测**。
  > **经决策P4.21-59 修订**：那个 `logging.shutdown()` 自己就可能卡住（handler 锁 / flush），
  > 改为 `os.write(2, ...)` 裸写 + `os._exit(5)`，**不再承诺日志刷完**。
  ② `arun` 收到 `CancelledError` 时是置令牌后**立刻 re-raise**（`agent.py:1243-1246`），**不等线程**——
  所以 `task.cancel()` 不是"没效果"，是**把"还没停"伪装成"已经停了"**。这比 v3/v4 的表述更严重，
  也让"绝不 cancel turn"从偏好升级为硬约束。
  连带：agentao 的请求超时从"待实证"提为**第 0 步前置**。
  > **经决策P4.21-68 修订**：这句"优雅停机的时间上界全押在请求超时上"**不成立**——那个超时管的是
  > 每次读的空闲，不是整轮墙钟。第 0 步已按评审 #53 收窄为"补齐 MCP 上界 + 公开总时长无界"。
- **★★★★ 决策P4.21-54（`AgentCancelledError` 单独接住，静默收尾）**：`request_stop()` 必然使 `turn()` 抛它；
  按 v4 的兜底，用户在关机时会收到「处理出错了，请稍后再试」——**主动停机不是处理失败，而且这句话会训练
  用户去重试一个正在退出的进程**。`except AgentCancelledError` 必须排在通用 `except Exception` **之前**。
  `web/app.py:1200` 已有同款先例。
- **★★★★ 决策P4.21-55（`store.get()` 也必须卸线程）**：它与 `create()` **共用同一把 `threading.Lock`**，
  而 `create()` 在慢 Agent 构造期间**全程持锁**（`conversation_store.py:114`，为的是让上限是硬上限）。
  于是"新用户建会话"会把"老用户 `get()`"连同整个事件循环一起卡住。
  由此把 §4.3 的判据改写为：**不是「这个调用看起来慢不慢」，而是「它会不会去拿一把别人可能长期持有的锁」**。
- **★★★★ 决策P4.21-56（收流独立成 task，停机取消它；两类取消分清）**：Protocol **不加** `stop_receiving()`
  ——那会把同一件事摊给每个适配器实现一遍。改为给适配器一条**可取消义务**：`inbound()` 只阻塞在 I/O 等待上、
  取消点上不留半提交状态。**收流 task 可以 cancel，问答 turn 绝不可以**——前者阻塞在 I/O、取消即净；
  后者阻塞在 executor 线程、取消只会制造假象（见决策P4.21-53②）。这两件事在文档里必须分开写，
  否则"停机不许 cancel"会被后人误读成"任何 task 都不许 cancel"。

### 第五轮复审新增（★★★★★）

- **★★★★★ 决策P4.21-57（主协程同时等收流与停机信号；收流非预期结束＝错误退出）**：v5 只 `await stop_event`，
  于是登录失效 / SDK 抛错 / 连接永久失败之后，**进程活着、日志安静、消息再也收不到**——用户能看到的只有
  "机器人不理我了"，这是最难排查的一类故障。改为 `asyncio.wait({recv, stop}, FIRST_COMPLETED)`，
  且**必须 `recv.exception()` 读一次**（否则只在 GC 时吐一句 "never retrieved"，很可能没人看见）。
  **正常返回也算错**：长驻宿主不存在"入站流正常结束"。
- **★★★★★ 决策P4.21-58（`begin_turn()` 必须与查闸、`act.conv=conv` 同处不可分割段）**：
  `request_stop()` 是三态的（`conversation.py:745-767`），而"已登记 `conv`、`_inflight` 仍为 0、令牌未装"
  这一瞬恰好落在**第三态 → 返回 `False` 空转**，该轮随后照常起跑、再没人叫得停。把 `begin_turn()` 拉进
  同一段，`stop_all()` 能看见 `conv` 的任何时刻都至少落在"记待停"那一态，`turn` 装令牌时立即兑现
  （`conversation.py:588-590`）。**这条闸此前只是"看起来闭合"。**
- **★★★★★ 决策P4.21-59（硬退出路径绝不碰 logging）**：`logging.shutdown()` 逐个 `handler.acquire()` +
  `flush()`——后台线程正持着 handler 锁、或 flush 卡在同一个死掉的下游时，**主线程就到不了 `os._exit()`**，
  "唯一能保证退出的手段"自己先卡住了。改为 `os.write(2, ...)` 裸系统调用 + `os._exit(5)`。
  **代价：日志完整性降为 best-effort，文档与指南都不得再承诺"保证刷完"。**
  同时写明前提——这套信号处理要求事件循环线程还在转（我们的卡死场景是 worker 线程，满足）；
  若 loop 自身卡死，只剩 `SIGKILL`，**不假装能兜住**。
- **★★★★★ 决策P4.21-60（给外部 MCP 调用补有限上界，而不是砍掉 MCP）**：两条源码事实使"等真实收尾"
  此前完全悬空——`build_from_environment` 默认装 `FileBackedMCPRegistry`（`factory.py:238-243`），
  而 `timeout` 缺省解析为 `request=None` ＝ **单次工具调用无限等待**（`config.py:160-163`）。
  修法走文档化面（registry 只需 `list_servers()`）：包一层给未显式配置者注入有限 `request`。
  **不默认关掉 MCP** 的理由：P4.19 那半阶段就是围绕"用户注入到这个库的外部 MCP server"做的，
  一刀关掉会让**同一个库、同一个问题在手机上和浏览器里答得不一样**，而用户无从知道差别从哪来——
  **给上界比砍能力诚实**。
- **★★★★★ 决策P4.21-61（墓碑契约三处接线）**：`tombstone_limit` 显式由 `serve_im` 传
  `max_conversations`；**过期路径必须 `tombstone=True`**——`drop` 默认 `False`，漏传的话紧随其后的
  `_create` 一旦抛容量错，过期身份就一起没了，用户重试时收到 `FIRST`，"上下文已过期"这句提示
  **恰好在最需要它的那次重试里消失**；指南措辞改为与有界淘汰一致（不再绝对承诺"一定提示"）。

### 第六轮复审新增（★★★★★★）

- **★★★★★★ 决策P4.21-62（停机序列整体入 `finally`；对已完成的 task 只读结果、绝不再 `await`）**：
  v6 在 `recv.exception()` 之后仍按老步骤①写 `recv.cancel()` + `await recv`——**对已完成的 task
  取消无效、`await` 会把原异常重新抛出**，于是 `drain`/`stop_all`/`close` 一个都不跑。
  **"收流出错"因此变成"既没收流也没清理"**，而这正是最需要清理跑完的一条路径。
  按 `done()` 分支 + `suppress(CancelledError)` + 整段 `finally`，`stop` task 同样收净。
  > 教训记在这里：这缝是我上一轮改动自己引进的——#30 换了主协程的等待方式，却没回头重读步骤①。
  > **在既有序列上打补丁而不重读整段，就会留下"两处各自正确、合起来错"的缝。**
- **★★★★★★ 决策P4.21-63（MCP 上界的判据是"解析后是否为有限正数"，不是配置形态）**：
  `request` 写成 `0/-1/"bad"/NaN/Infinity` 时，`_coerce_timeout` 只打一条 WARNING 就退回 default，
  而 request 槽的 default 正是 `None` ＝ **又变回无限等待**（`mcp/config.py:102-122`）。
  v6 那张按形态分的四态表整类漏掉了它们。**形态不是判据，解析结果才是。**
  `T` 自身也必须在入口校验为有限正数（否则兜底自己先破）。测试**用 agentao 的 `resolve_timeouts`
  当神谕**——运行期不依赖它，但上游改了解析规则时红的是用例，而不是线上某一轮悄悄挂死。
- **★★★★★★ 决策P4.21-64（墓碑记 `now` + 建会话期间 `protect` 当前键）**：只留墓碑还不够——过期路径
  留下的墓碑若沿用旧 `last_seen`，紧接着的 `_evict_tombstones` 里**它往往正是最旧的那条**，
  墓碑满时先被淘汰，随后 `create` 抛容量错，用户重试仍得 `FIRST`。**#34 会被 #37 完全抵消。**
  两道一起才闭合：① `last_seen = now`（用户确实刚发过消息，这是真实语义）；② 建会话期间受保护。
  > **经决策P4.21-69 修订**：②由 `protect=key` 改为 registry 级 `_creating` **集合**——
  > 只保护自己那个键挡不住 A、B 并发重建时互相淘汰。
- **★★★★★★ 决策P4.21-65（`--mcp-request-timeout` 取 `min`，是真上界不是默认值）**：v6 让盘上显式有限值
  原样保留，于是 `mcp.json` 写 3600 时命令行传 60 **什么也没收紧**，而指南管它叫"上界"。
  **一个任何配置文件都能绕过的上界不是上界**——而这个旋钮存在的唯一理由就是给优雅停机兜住时间。
  故取 `min`；被收紧时记 WARNING，**改变用户显式配置的行为不能悄悄发生**。
- **★★★★★★ 决策P4.21-66（强退提示降为非阻塞 best-effort）**：`os.write(2, …)` 在 stderr 接到已满的
  阻塞管道时照样会阻塞，于是"保证退出"又一次被自己的收尾动作挡住。先 `set_blocking(2, False)`
  再写、整段 `try/except`、无论成败都 `os._exit`。
  **凡与"保证退出"冲突的东西一律让位——包括我们自己想留下的那句话。**
- **★★★★★★ 决策P4.21-67（`start()` 失败要还原进程级状态）**：失败路径除了 `close()` 兜底与释放凭据锁，
  还必须**恢复原信号处理器**——那是**进程级**状态，不还原就让调用方继承一对指向已死对象的处理器，
  其中一个还会 `os._exit`。故 `_install_signal_handlers` 返回可还原句柄，正常与失败两路都还原。

### 第七轮复审新增（★★★★★★★）

- **★★★★★★★ 决策P4.21-68（优雅停机**没有**绝对时间上界；`os._exit` 是唯一的绝对保证）**：
  v6/v7 说"真实上界由模型/API 请求超时保证"——**这句是错的，撤回**。`openai` 的 `read=600` 由 httpcore
  施加在**每次网络读取**上（`_sync/http11.py` 的 `_receive_response_body` 在逐块循环内取用），
  不是整次响应的墙钟上界；持续心跳的流可以无限跑。而 agentao 的取消检查在 `for chunk in stream:` 的
  **每个已解析 chunk** 上（`llm/client.py:717-718`），只有原始心跳而无 chunk 时循环体根本不执行，
  `request_stop()` 无处兑现；60 秒重试预算也只在请求**抛异常后**才查。
  故按分层如实声明（§4.4 的表）：**MCP 的每次 `tools/call` 有界、完整 MCP 执行无界**、
  模型空闲有界、**一轮总时长无界**、**进程退出有界**。
  真正的修法属 agentao（流式消费层的总 deadline + trickle 假服务端验证），记为上游诉求（§13）。
  **一个说错了的保证，比没有保证更危险**——它会让运维在"再等等"和"按第二次"之间做出错误选择。
- **★★★★★★★ 决策P4.21-69（`_creating` 集合级保护，替代 `protect=key`）**：v7 的"保护当前键"仍然漏——
  A、B 同时重建时互相淘汰得掉对方的墓碑，且 `drop()` 内有 `await`，别人可在当前键进保护集前插入。
  改为 registry 级 `_creating: set[str]`，把「标墓碑 → 清理 → 建会话」收进 `_renew()`：
  进入前**同步** `add`（早于本路径上任何 `await`）、`finally` `discard`，淘汰时保护**整个集合**。
  > **"保护当前操作"和"保护所有正在进行的操作"是两件事。** 单进程单线程也一样——
  > 并发不是来自线程，是来自 `await` 处的交错。
- **★★★★★★★ 决策P4.21-70（停机序列嵌套 `try/finally`，清理不得有单点故障）**：v7 把三步顺序 `await`
  排开，`intake.drain()` 或 `stop_all()` 一抛，`adapter.close()` 就被跳过——而"①~⑥都要跑完"正是
  上一轮刚立的契约。按"不跑就出事"的严重度排：adapter 连接 > 信号处理器 > 凭据锁。

### 第八轮复审新增（★★★★★★★★）

- **★★★★★★★★ 决策P4.21-71（`acquire` 三条分支全走 `_renew`；清理失败记账并影响退出码）**：两件事同源——
  **改了机制却没改全部入口**。① v8 加了 `_renew()`，墓碑与 `LOST` 分支却仍指向已删除的 `_create()`，
  于是决策P4.21-69 的集合级保护**一行都没生效**：`_renew` 本身写得对，问题全在调用点——
  **所以用例必须从 `acquire` 入口进，只测 `_renew` 是测不出来的**。
  ② v8 的 `suppress(Exception)` 让 `adapter.close()` 失败被吞，进程照样返回 `EXIT_OK`；
  改为每步记账、任一失败即 `EXIT_AGENT_ERROR`，且记**哪一步**失败。
  **"继续跑"不等于"没事发生"——清理不能有单点故障，也不能把失败吞成成功。**
- **★★★★★★★★ 决策P4.21-72（T 的口径：每次 `tools/call` 请求，而非一次工具执行）**：
  `MCPClient.call_tool` 是 `for attempt in range(2)`——会话过期/传输断开会**重连重试一次**
  （`mcp/client.py:813`，docstring 自称 "bounds each individual tool call"），重连不受 T 约束。
  > **经决策P4.21-73 修订**：本条曾把界写成 `2×(T + startup)`，**那个公式也是错的**——
  > 重试路径上的 **stdio 传输建立**与 **`disconnect()` 清理**根本没有任何超时。见决策 73。
  不顺手把 startup 也收到 T：stdio server 拉子进程本就可能慢，砍它是拿"更小的界"去换"把好 server 弄挂"。

### 第九轮复审新增（★★★★★★★★★）

- **★★★★★★★★★ 决策P4.21-73（撤回 `2×(T + startup)`：完整 MCP 执行无严格总墙钟上界）**：
  上一轮我把"有界"救回来的那个公式**同样不成立**，因为它默认了重试路径上每一段都有人管。实际是：
  `tools/call` 有 T、握手有 `wait_for(startup)`、URL 传输建立有 startup
  （**后半句经决策P4.21-74 修订：legacy SSE 那一支不成立**；T 的口径又经决策P4.21-75 收窄）——但
  **stdio 传输建立没有**（`_connect_stdio()` 不收超时参数，源码注释自承 "stdio has no
  transport-level connect bound at all"），**`disconnect()` / exit-stack 清理也没有**
  （`mcp/client.py:968` 裸 `await __aexit__`）。两段无界被我当成了零。
  故如实声明：**T 仅约束每次 `tools/call` 请求；连接、传输建立、断连清理与重试不在该上界内；
  完整 MCP 执行没有严格总墙钟上界，第二次停止信号仍是最终兜底。**
  - **T 依然值得设**：它收住了最常见也最长的那一段，并堵掉"默认无限等待"这个最容易踩的坑。
    **"不是总上界"不等于"没用"**——但**不能拿它冒充总上界**。
  - 总上界属 agentao 上游能力（`disconnect` 加超时、stdio spawn 加界），单独落实并测试（§13-7）。
  > 连续两轮在同一处栽跟头，教训是一样的：**"有界"这种断言必须逐段核到底**——
  > 只要链条上有一段没人管，整条链就是无界的，中间那些管得很好的段一点也帮不上忙。

- **★★★★★★★★★★ 决策P4.21-74（legacy SSE 传输进入同样无界；MCP 各段逐一钉死）**：
  上一轮我写"URL 传输建立有 startup 上界"时，把 sse 与 http 两支并成了一行——**而 sse 那支不成立**：
  `connect()` 是先裸 `await _connect_sse()`、**再**进握手的 `wait_for`；`sse_client` 要
  `await tg.start(sse_reader)` 收到 `endpoint` 事件才 `yield`，而 SDK 把 httpx 的 read 显式换成了
  `sse_read_timeout`（`Timeout(timeout, read=sse_read_timeout)`）——**服务端持续 keepalive、
  永不发 `endpoint`，这一等就没有头**。（同处核实：`streamablehttp_client` 不等服务端事件就 `yield`，
  故 `type: "http"` 那支的往返落在握手的 `wait_for` 内，是有界的。）
  最终口径见 §4.7 的定稿框。**"有阶段超时"≠"有总上界"**：握手那段确实被包住了，
  但它挡不住排在它**前面**的传输进入——这正是把两支并成一行时看不见的东西。
  > 第三次在同一处返工，根因不再是"没核"，而是**核的粒度不对**：
  > 我核到了"这个函数收了 startup 参数"就停手，没有核"这个参数在被调用方那里到底管住了哪一段"。
  > **参数传进去了，不等于那段时间被管住了。**

- **★★★★★★★★★★★ 决策P4.21-75（T 只管"写完之后等响应"那一段，出站写入不在计时器内）**：
  MCP SDK 的顺序是 `await self._write(msg, …)` **在前**、`with anyio.fail_after(opts["timeout"])`
  **在后**，其自身注释写明 "`fail_after` arms only after the write"；而 `_write` 是一句
  `await self._write_stream.send(...)`，**没有 deadline**（`jsonrpc_dispatcher.py:397/401/405/777`）。
  **于是传输 writer 一旦卡住，后续调用会停在写入阶段，T 连表都还没起。**
  最终口径（§4.7 定稿框）：**T 约束的是"请求完成出站写入之后、等待 `tools/call` 响应"这一段；
  完整单次 `tools/call` 请求与完整 MCP 执行都没有严格总墙钟上界。**
  §13-7 相应补第 ④ 处缺口与"写入端永不排空的假传输"用例。
  > 这是同一条链上的第四次收窄，但根因和上一次又不同：前几次是"某一段没人管"，
  > 这次是**那段时间根本不在计时器覆盖的区间里**——超时存在、也确实生效，只是它开始得太晚。
  > **"这里有个 timeout" 之后必须再问一句：它从哪一刻开始计？**

   **持续发 keepalive、永不发 `endpoint` 的 SSE server**；**写入端永不排空的假传输**（writer 卡死）。
   在此之前本宿主如实声明"完整 MCP 执行无严格总上界"（§4.7）。

### 15.1 两条**在实现期新增**的决策（代码评审逼出来的）

- **★ 决策P4.21-76（`[[wikilink]]` 无条件保留原文，撤回"给了 `--web-base-url` 就转链接"）**：
  原设计（决策P4.21-17）留了这条支线，实现期核实后**不成立**——**Web 宿主根本没有"按页面名打开
  某一页"的路由**：SPA 只认 `?raw=<源文件名>` 与 `?c=<会话 id>`，`/api/page?path=` 要的是**相对
  路径**且返回 JSON（不是可看的页面）。也就是说，任何由页面**名**拼出来的 URL 都是死链，
  而页面**路径**又不能从 wikilink 的**名**推出来。
  **一个 404 比一段可读的 `[[甲实体]]` 更误导**——这与决策P4.21-50「不承诺一个不存在的东西」
  是同一条判据，只不过那次的载体是截断告示、这次是页内引用。
  `--web-base-url` 保留原有的另一半用途：**站点入口**，出现在截断告示里。
  > 这条的教训与 MCP 那四轮是同一类：**"能拼出一个 URL"不等于"那个 URL 打得开"。**
  > 设计阶段写下这条支线时，没有人去核 Web 宿主到底有没有这个路由。

- **★ 决策P4.21-77（`start()` 抛的用法错必须保住自己的退出码，且不吐 traceback）**：
  §4.1 的失败表写的是「`start()` 抛错 → `close()` 兜底 + 恢复信号处理器 + 释放凭据锁 +
  返回 `EXIT_AGENT_ERROR`」，实现时照做，于是**缺凭据也走了这条路**——用户看到的是一屏
  traceback + 退出码 5。但 §9.2 明写「缺凭据 → `EXIT_USAGE`、优雅降级、**不吐 traceback**」。
  两条契约在这里撞了，正确的解法是**按异常类型分**：`GuanlanError`（缺凭据 / 凭据空白 /
  SDK 版本不对 / 域名取值非法）**清理照做、然后原样抛出**，由 CLI 顶层打一行并返回它自己的
  退出码；其余异常才是「宿主起不来」的 `EXIT_AGENT_ERROR`。
  > **退出码 5 和退出码 1 对运维是两件事**：前者说"它坏了"，后者说"你配错了"。
  > 把后者报成前者，等于把人引向查日志、查网络，而真正该做的只是跑一次 `im-login`。

- **★ 决策P4.21-78（IM 的凭据/白名单变量也从 `.env` 读，且沿用 agentao 那一套解析）**：
  §9.2 原文只写「env-only」，实现按字面读 `os.environ`——于是出现一个**没有道理的不一致**：
  同一个 `.env` 文件，模型 API key 读得到，`GUANLAN_IM_FEISHU_APP_ID`/`_APP_SECRET` 读不到。
  根因是时序：进程里确实有人加载 `.env`（`build_from_environment`），但那要等到**第一次建
  `Conversation`**，已在 `adapter.start()` **之后**。
  故在 `serve_im` / `run_identify` 入口各显式加载一次，且**复用 agentao 的
  `safe_load_dotenv`**——要的正是逐字节同一套语义：同样 `find_dotenv(usecwd=True)` 从 cwd
  逐级上溯、同样 `setdefault` 的 **no-override**（真环境变量永远压过 `.env`）、同样剔 NUL 字节。
  **自己再写一遍必然漂移，而漂移的表现会是"某个 key 在这条路上读得到、在那条路上读不到"**
  ——正是本条要消灭的那种 bug。它是私有模块，故留一条 `python-dotenv` 兜底：
  上游改名时该失败的是这一个函数，不是让 `guanlan im` 启动即 ImportError。
  连带：`--allow-user-env` 指向的变量同样可以定义在 `.env` 里（它在同一个入口之后才读）。
  - **同时补上 `.gitignore` 的 `.env` / `.env.*`**（本仓此前**没有**忽略 `.env`）。
    这在本半阶段之前只是卫生习惯，之后变成**必需**：我们刚把 `.env` 写进文档，
    作为存放飞书 App Secret 的推荐位置。**扩大一个文件的用途，就得同时承担它的泄露面。**

### 15.4 一处**既有测试**必须跟着改（惰性化的连带）

`tests/test_web.py::test_web_missing_extra_degrades` 会清空 `sys.modules` 里的 `guanlan.web*`
再打桩 `fastapi=None`。§3.0 惰性化之后，**缺 fastapi 时 `import guanlan.web` 本身是成功的**
（`ImportError` 推迟到取 `serve` 那一刻）——导入成功 ⇒ 导入机制把**父包属性** `guanlan.web`
重绑到本次新建的模块对象，而 `monkeypatch.delitem` 只还原 `sys.modules` 条目，
**两者就此指向两个不同的模块对象**。

后果极隐蔽：后面那条 `monkeypatch.setattr("guanlan.web.serve", …)` 打在**新**对象上，
而 `from .web import serve` 走 `sys.modules` 拿到**旧**对象的**真** `serve`
——于是那条用例真的把 uvicorn 起了起来，整场 pytest 挂死在 84%。

修法是在那条用例里记一次同值 `setattr(guanlan, "web", guanlan.web)`，让 teardown 把父包属性也还原。

> 值得单独记一笔：**这不是惰性化的 bug，是惰性化把一个既有的隐患照亮了**——
> `sys.modules` 条目与父包属性本来就可能分叉，只是此前"子模块导入必失败"恰好掩盖了它。
> 症状（整场 pytest 无输出地挂住）与病因（一次模块对象分叉）之间隔得非常远，
> 这类问题只能靠 `faulthandler` 把线程栈打出来定位，猜是猜不到的。

### 15.5 代码评审（`/code-review --fix`）的收获

一轮 15 项，12 项当场修掉。**其中六项是真实的行为缺陷**，不是风格问题：

| 缺陷 | 后果 | 修法 |
|---|---|---|
| `_clip` 用 `split_for(..., max_parts=1)` | `max_parts=1` 时 `kept = parts[:0]` ＝ **空列表**，于是答案一超上限，中途 `edit` 就**永久停更**——占位消息冻在那一刻 | 未超限直接返回；否则取 `max_parts=2` 的首片 |

| 飞书 WS 线程死掉 | 线程是 daemon，异常被吞；`inbound()` 永远卡在 `Queue.get`，`recv` 永不完成 ⇒ **决策P4.21-57 那个"活死人"检测对飞书结构上不可达** | WS runner 记 ERROR 并投 `_WS_DEAD` 哨兵，`inbound()` 转成异常让 `recv.done()` 真的能触发 |

| 凭据锁把"读不出来"当成"陈锁" | A 刚 `O_CREAT\|O_EXCL` 成功、还没写完 pid，B 读到 0 字节 → `pid=0` → 判定已死 → **删掉 A 的锁**，两个进程同时"独占"同一份凭据 | 只有**读得出 pid 且该 pid 确已死**才回收；读不出来给一条独立的错误 |

另修：`--idle-ttl` 补入口校验（`0` 会让每轮都判过期、`nan` 会让会话永不过期且容量永不释放）；
wikilink 替换改为**围栏内不动**（否则代码块里的 `[[x]]` 被改写，与 §6.5「保留源码」自相矛盾）；
`FENCE_LINE` 提为公开名由 `reply` 与 `feishu` **共用一条判据**（两份正则漂移时，"围栏独占一片"
与"围栏独占一 row"就会对不上，飞书那个吞内容的坑会原样复现）；`intake.drain()` 真的把丢弃计数
打出来（此前那两个计数器**从没有人读**，等于死状态）。

1. **停机不 `close()` 活着的 `Conversation`**：agentao 为每个会话拉起的 MCP stdio 子进程因此留给
   进程退出去回收。**不修是权衡而非疏忽**——`conv.close()` 走的正是决策P4.21-73 核实过**没有任何
   超时**的 `disconnect()`，把它塞进停机路径等于在一条已经声明"没有绝对上界"的链上再加一段无界等待。
   与 Web 宿主的现状也一致。真要修，属 `ConversationStore` 的接口面。
2. `server.py` 跨模块引 `mcp_bound._finite_positive`：它现在同时是三个 CLI 旗标的校验器，
   哪天为 MCP 语义收紧就会顺带改掉那三处。属命名整理，不值当在本 diff 里搅动。

> 这一轮最值得记的不是某一条修法，而是**六项里有四项的失效形态都是"静默"**：
