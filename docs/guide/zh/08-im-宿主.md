# IM 宿主（微信 / 飞书）

> **状态：已实现**（P4.21，设计与决策见 [`docs/P4.21-IM宿主.md`](../../P4.21-IM宿主.md)）。
> 微信扫码登录已真机联调（2026-08-16），二维码**直接画在终端里**；飞书侧仍待各自环境验证。

`guanlan im` 是 **MVP 之后的可选叠加层**：把 wiki 问答搬进你已经在用的 IM。不装、不起，整套东西照旧用 CLI 与
Web 跑通；markdown 仍是唯一事实来源，IM 只是**另一个只读入口**。

## 先明确三件事

1. **只读，且没有可写分支。** 不是"默认只读、可切"——`ingest`/`heal`/上传/`/goal` 一个都不接，`--mode` 参数
   压根不存在。理由不止保护知识库：wiki 内容对所有获准用户**共享**，一旦开写，A 摄入的内容 B 立刻看得到。
2. **不监听任何端口。** 两家都是**出站**连接（微信长轮询、飞书 WebSocket 长连），比 Web 宿主（绑
   `127.0.0.1`）姿态更强——连环回都不绑，不需要公网 IP、不需要反代、NAT 后面照用。
3. **默认拒绝所有人。** 白名单为空**直接拒启**，不存在"先跑起来谁来都答"。这和多数 IM 机器人的默认相反，
   是刻意的：wiki 是共享知识资产，配错一次等于全员可读全库。

## 选哪个平台

| | 个人微信 | 飞书 / Lark |
|---|---|---|
| 单条上限 | **2000 字** | 8000 字 |
| 等待体验 | 显示"正在输入…"，答完一次性发 | 先发占位消息，**原地改写成答案**（接近 Web 流式） |
| 群聊 | ❌ **收不到群消息** | ✅ |
| 身份可信度 | 弱（iLink bot 身份，与真实身份无绑定） | 强（企业成员体系认证） |
| 首次接入 | 扫码 | 在开放平台建应用 |
| 运维脆点 | 登录会话会失效，需**人工重扫码** | 无 |

**结论**：自己一个人或三五个人用、就想在手机上随手问 → 微信。团队/部门共享、要在群里用 → 飞书。

> **微信上 `/search` 应当是主力**：2000 字装不下带引用的完整答案，会被切成好几片轰在手机上；而检索结果天然短、
> 毫秒级返回、不花 token。LLM 问答留给真需要综合的时候。

## 前置

```bash
pip install 'guanlan-wiki[im-weixin]'   # 只用微信
pip install 'guanlan-wiki[im-feishu]'   # 只用飞书
pip install 'guanlan-wiki[im]'          # 两个都要
```

**按平台分开装**是有意的——只用微信的人不该被迫装飞书 SDK。未装对应 extra 时命令优雅降级、提示安装（退出码 `1`）。

另需一台**常开的机器**：两种传输都要求进程持续在线，笔记本合盖就断连。家里的小主机 / NAS / 常开工作站都行。

## 路线 A：个人微信

### 它做不到的三件事（先看，免得白配）

1. **收不到群消息**：扫码得到的是 **iLink bot 身份**（`xxx@im.bot`），不是你的微信号。腾讯通常不向这类身份
   投递普通微信群事件，@ 也不投。所以微信路线**只有单聊**。
2. **身份不可反查**：`wxid_…` 是稳定的，但无法枚举、无法反查到真人。白名单只能靠 `im-identify` 手工收集。
   这在几个人的圈子里是一次性成本，200 人的组织不可行。
3. **登录会话会过期**：过期后宿主会在日志里 ERROR 级明确提示，需要你重跑一次扫码。

### 步骤

```bash
# ① 扫码登录（凭据落 ~/.guanlan/im/weixin/account.json，权限 0600）
# 二维码**直接画在终端里**，用手机微信对着屏幕扫即可，不必打开任何链接。
guanlan im-login --platform weixin

# ② 敞开 5 分钟收集要授权的人的完整 ID —— 让他们各发一条消息
guanlan im-identify --platform weixin

# ③ 起服
guanlan -C ~/my-wiki im --platform weixin \
    --allow-user wxid_8f3k2m9qp0zx \
    --allow-user wxid_2b7d4e1a9c0f
```

`im-identify` 的输出直接粘进 `--allow-user`：

```
[im-identify] 监听中，300s 后自动退出（不会回复任何消息，Ctrl-C 提前结束）

[1] 平台=weixin  租户=wx_acct_a1b2
    用户ID=wxid_8f3k2m9qp0zx        ← 填入 --allow-user
    会话ID=（单聊，无需 --allow-chat）
    聊天类型=dm
```

> **`im-identify` 期间机器人绝不回复任何消息**——对方只看到"发了没人理"。这是有意的：回一句"你没有权限"
> 就等于告诉未授权者"这里有个知识库机器人"。

## 路线 B：飞书 / Lark

### 服务端配置（开放平台后台）

**① 建应用**

| 项 | 值 |
|---|---|
| 应用类型 | **企业自建应用** |
| 后台地址 | 飞书 `open.feishu.cn` / Lark `open.larksuite.com` |
| 必开能力 | **机器人（Bot）** |
| 要复制的 | 「凭证与基础信息」页的 **App ID** 与 **App Secret** |

**② 权限管理——观澜只要两个**

| Scope | 用途 |
|---|---|
| `im:message` | 接收消息、编辑已发消息（用于原地改写答案） |
| `im:message:send_as_bot` | 以机器人身份发消息 |

其他常见于 IM 机器人教程的权限，观澜**一概不需要**：不做媒体所以不要 `im:resource`；不查群信息所以不要
`im:chat*`；不做表情回应所以不要 `im:message.reactions*`；直接用事件里的 `open_id` 精确匹配所以不要
`contact:user.id:readonly`；bot 身份走的 `/open-apis/bot/v3/info` 不需要额外权限，所以**也不要
`admin:app.info:readonly`**（admin 类权限在多数企业要走更高一级审批，能省则省）。

> 勾选事件时控制台会提示该事件需要哪个 scope（飞书把接收消息细分为单聊/群 @ 等更细的权限，`im:message`
> 是覆盖它们的父权限）——**以控制台的提示为准**。

**③ 事件与回调**

1. 连接方式选 **长连接（WebSocket）**，不要配 Webhook URL。
   （观澜只做 WS 模式：webhook 需要一个公网可达的入站端点，与"不监听任何端口"的红线冲突。）
2. 只订阅一个事件：**`im.message.receive_v1`**（接收消息）。

**④ 发布并等审核 ← 最大的坑**

去「版本管理与发布」**创建版本并发布**，企业自建应用通常需要**管理员审批**。

**权限在发布通过前不生效**，表现是：连接建得起来、日志一切正常、就是收不到任何消息。飞书接入最常见的
"看起来配好了但没反应"就是这个，排查时先确认版本状态。

**⑤ 群聊还要一步**：把机器人**拉进目标群**。没进群自然收不到任何事件。

### 步骤

```bash
export GUANLAN_IM_FEISHU_APP_ID=cli_xxxxxxxxxxxx
export GUANLAN_IM_FEISHU_APP_SECRET=xxxxxxxxxxxxxxxx
export GUANLAN_IM_FEISHU_DOMAIN=feishu        # Lark（国际版）填 lark；默认 feishu

guanlan im-identify --platform feishu         # 让人在单聊或群里 @ 机器人发一条
guanlan -C ~/my-wiki im --platform feishu \
    --allow-chat oc_5d2f8a1c9e \
    --allow-user ou_9c4e1a7b2d8f5g3h
```

群场景的 `im-identify` 输出会同时给出用户 ID 和会话 ID：

```
[2] 平台=feishu  租户=abcdef123456
    用户ID=ou_9c4e1a7b2d8f5g3h        ← 填入 --allow-user
    会话ID=oc_5d2f8a1c9e            ← 填入 --allow-chat（群聊才需要）
    聊天类型=group   @了机器人=是
```

`bot_open_id` **不用配**——启动时自动探测。

## 谁能问：授权真值表

| 场景 | 放行条件 |
|---|---|
| 单聊 | `--allow-all-users` **或** 发信人 ∈ `--allow-user` |
| 群聊 | 群 ∈ `--allow-chat` **且**（`--allow-all-users` **或** 发信人 ∈ `--allow-user`）**且** @ 了机器人 |

**群聊是"且"，不是"或"，也不是只查群。** 只白名单群不查人，等于把授权外包给群主——他拉一个人进群，整库
就对新成员开放了。所以群场景 `--allow-chat` 和 `--allow-user` **两个都要给**。

**`--allow-all-users` 只放开"人"，不放开"群"。** 它的意思是「这些群里的人我不想逐个列」，**不是**「机器人
在哪个群都行」。所以即使开了它，**没进 `--allow-chat` 的群依然一律不理**——没有任何一个参数能一次开放所有群，
这是有意的：把机器人拉进哪个房间是部署者的决定，不该被一个"允许所有用户"的开关穿透。

ID 匹配是**精确、区分大小写**的，直接粘 `im-identify` 的原文，别手改。

## 三个命令互斥：加人要停服

`im`、`im-identify`、`im-login` **不能同时跑**——它们抢同一份平台凭据（微信一个 token 只允许一个长轮询实例，
飞书同一 app_id 起两个连接会让消息随机分发）。抢不到会拒启，并告诉你是哪个进程（pid + 子命令名）占着。

**给白名单加一个新人的完整流程**：

```bash
# ① 停服（Ctrl-C）—— 必须先停，否则 ② 抢不到凭据
# ② 敞开收集
guanlan im-identify --platform feishu --seconds 300
# ③ 把新 ID 追加进启动参数
# ④ 重新起服
guanlan -C ~/my-wiki im --platform feishu --allow-chat oc_… --allow-user ou_老张 --allow-user ou_新人
```

**"加人要停服"是"绝不回复未授权者"的必然代价**：要么敞开着收 ID 并回复陌生人，要么关起来收。观澜选后者。
想让改动集中在一处，用 `--allow-user-env` 把清单收进一个环境变量——但**改完仍需重启**（不做白名单热重载）。

## 在 IM 里怎么用

三个斜杠命令，**全部零 LLM、不建会话、不花 token**：

| 命令 | 作用 |
|---|---|
| `/search <关键词>` | 检索，毫秒级返回标题 + 片段 + 页面路径 |
| `/new` | 清空当前会话上下文，重新开始 |
| `/help` | 用法说明 |

不带斜杠的就是 **LLM 问答**（多轮，记得上文）。**群里必须 @ 机器人**；`@机器人 /search 甲实体` 也认。

**答案形态**：

- 超长会**分成几条依次发出**（片间留一点间隔防频控）。超出上限（微信 5 片 / 飞书 3 片）时
  **最后一片是明确的截断告示**，告诉你还剩多少字——不会静默截断，你永远看得到。告示会请你
  **到 Web 端重新问一次**：IM 的会话不落盘，被截掉的那段没有存在任何地方，所以给不出"完整版"的链接
  （给了也打不开）。
- ` ``` ` 围栏块（代码 / mermaid / flint 图表）**原样保留源码**：IM 里没有渲染器，但不会静默丢掉内容，
  你可以到 Web 端看渲染效果。
- `[[wikilink]]` **始终保留原文**，不伪造链接——它是可读的引用语义。**给了 `--web-base-url` 也不会转链接**：
  Web 宿主没有"按页面名开某一页"的路由，凡是照页面名拼出来的地址都是 404，而**一个死链比一段可读的
  `[[甲实体]]` 更误导**。`--web-base-url` 的用途是给截断告示附一个**站点入口**。
- **附件不处理**：发图片/文件会收到一句固定提示，请把要点贴成文字。
- **模型没吐出任何内容**（工具轮空转等）时会明说"本次没有得到任何回答内容"，而不是把占位消息
  「🔍 正在查阅知识库…」永远留在那里。

**进程重启会丢掉全部对话上下文**（会话不落盘，这是"对知识库零字节写入"的代价）。会话闲置 30 分钟也会被回收，
届时下一条消息**通常**会在答案前告诉你"上下文已过期，已开始新的对话"。说"通常"是因为这条提示靠一份有上限的
记录（默认 100 条）——很久没说话、记录已被更新的挤掉时，就直接当新对话开始，不再提示。无论提示与否，
**上下文都已经重置**。

**停机**：`Ctrl-C` 后宿主**不会立刻退**——它会先请求停掉在跑的问答，然后**一直等到那一轮真的结束**才关连接
（每 30 秒告诉你还在等谁）。这是有意的：LLM 那一轮跑在后台线程里，强行取消只会让进程"看起来"退干净了，
实际线程还在跑。被这样中止的那一轮**不会给用户发"处理出错了"**——停机不是出错，消息就停在那里。

**极少数情况下第一次 `Ctrl-C` 会等很久**：模型那一轮的总时长没有硬上界（服务端只要持续送数据，
连接就不会超时），而中止只能在它吐出下一段内容时才生效。等不及就**再按一次 `Ctrl-C`**。

**第二次 `Ctrl-C` 立即强制退出**（退出码 `5`）：**不做任何收尾，日志可能写不全，那行"可能有残留后台线程"
的提示也只是尽力去写、写不出去就直接退**——一切都让位于"无论如何都退得掉"。
它存在的理由是：模型请求若真卡死，普通的退出反而会**卡在退出这一步**（后台线程在进程退出时会被等待）。

## 参数

```bash
guanlan -C <库> im --platform {weixin,feishu} [选项]
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `--platform` | **必填** | `weixin` / `feishu`；无默认值（两家能力差别太大） |
| `--allow-user` | — | 授权用户，**可重复** |
| `--allow-user-env` | — | 从环境变量读逗号分隔清单，与上者取并集 |
| `--allow-chat` | — | 群白名单，**可重复**；不给 = 群消息一律不理。**只给它、不给任何用户 → 拒启**（那样一条消息也过不了闸） |
| `--allow-all-users` | 关 | **只**旁路用户名单，**不**旁路 `--allow-chat`；启动日志会大声告警 |
| `--web-base-url` | — | Web **站点入口**，附在截断告示里。**不**把 `[[链接]]` 转成 URL（拼不出正确地址，见上） |
| `--model` | — | 覆盖问答用的模型 |
| `--max-conversations` | `100` | 内存会话硬上限 |
| `--idle-ttl` | `1800` | 会话闲置回收秒数；须为**有限正数**（`0` 会让每一轮都被判过期） |
| `--mcp-request-timeout` | `120` | 外部 MCP 工具**等一次 `tools/call` 回话**的秒数上界。**它不是一次工具执行的总上界**，甚至也不覆盖完整的一次请求：请求**发出去**那一步不在这个计时器里；握手等阶段有各自的超时但不受这个值约束；SSE/stdio 方式的连接建立与断连清理则**没有超时保护**。这是**宿主级天花板**：`mcp.json` 里配了更长的值也会被收紧到它（日志有告警）。需要更长就调大这里。必须是正数 |
| `--no-mcp` | 关 | 完全不加载这个库配的外部 MCP server（答问只用知识库本身） |

```bash
guanlan im-login    --platform weixin          # 扫码，不接受 -C
guanlan im-identify --platform {weixin,feishu} [--seconds 300]   # 收集 ID，不接受 -C
```

**环境变量**：`GUANLAN_IM_FEISHU_APP_ID` / `_APP_SECRET` / `_DOMAIN`（`feishu`｜`lark`，默认 `feishu`）。
微信凭据由 `im-login` 落盘，不走环境变量。凭据**绝不**接受命令行明文传入，也不会出现在日志里。

**这些变量可以写在 `.env` 里**（与模型 API key 同一个文件、同一套规则）：

```dotenv
# .env —— 从当前目录逐级上溯查找，与 agentao 读模型 key 的是同一个文件
GUANLAN_IM_FEISHU_APP_ID=cli_xxxxxxxxxxxx
GUANLAN_IM_FEISHU_APP_SECRET=xxxxxxxxxxxxxxxx
GUANLAN_IM_FEISHU_DOMAIN=feishu
GUANLAN_IM_USERS=ou_9c4e1a7b2d8f5g3h,ou_2b7d4e1a9c0f     # 配 --allow-user-env 用
```

三点要记住：

1. **真环境变量优先**：`export` 过的值**压过** `.env`（no-override）。改了 `export` 却没生效，
   多半是反了——不会出现"`.env` 里的旧值偷偷盖掉你刚设的新值"。
2. **查找方式是从当前工作目录逐级往上**，不是"知识库根目录下的 `.env`"。
   `im-identify` 不接 `-C`，也照这条规则找。
3. **`.env` 一定不要提交**——本仓库的 `.gitignore` 已覆盖 `.env` / `.env.*`；
   放进别的仓库时请自己确认一遍。

## 故障排查

| 现象 | 原因与修法 |
|---|---|
| 拒启，提示白名单为空 | 先跑 `guanlan im-identify` 拿 ID，再填 `--allow-user` |
| 拒启，提示凭据被占用 | 三命令互斥。报错里有 pid 和子命令名——停掉它，或等 `im-identify` 超时退出 |
| 拒启，提示 `--allow-chat` 不会生效 | 微信收不到群消息。去掉该参数，或改用飞书 |
| 拒启，提示"只给了 `--allow-chat`" | 群聊放行是「群 **且** 人 **且** @我」。补 `--allow-user`，或用 `--allow-all-users` 表示"这些群里谁都能问" |
| 拒启，提示凭据锁"读不出来" | 极少见：另一个进程正在建锁，或锁文件损坏。确认没有别的 `guanlan im*` 在跑后，手动删掉 `~/.guanlan/im/<平台>/credential.lock` |
| 飞书：跑着跑着突然全员不理 | WS 线程死了。宿主会记 ERROR 并以退出码 `5` 退出（不会装作还活着）——查凭据是否被吊销、网络是否中断 |
| 回一句"当前会话数已满" | `--max-conversations`（默认 100）个会话**同时活跃**。等闲置的自动回收，或调大该值 |
| 某一轮迟迟不回，`Ctrl-C` 也停不下来 | 多半卡在某个外部 MCP 工具上。用 `--mcp-request-timeout` 收紧每次请求的上界，或先 `--no-mcp` 确认是不是它。注意 SSE/stdio 方式的**连接建立**与**断连清理**没有超时保护，所以收紧这个值也不保证一定能等到头——等不及就再按一次 `Ctrl-C` |
| 机器人突然全员不理，日志里有 `入站流已中断` | 连接或登录已失效，进程会以退出码 `5` 退出。微信重跑 `im-login`；飞书查应用状态与网络 |
| **飞书：起服时报「WS 首次连接失败」/「在 30 秒内没有连上」** | 长连没建起来，宿主**拒绝装作启动成功**。三个常见原因：网络不通、`app_id`/`app_secret` 不对、本机 TLS 根证书库为空（macOS 官方版 Python 要跑一次 `Install Certificates.command`，否则报 `CERTIFICATE_VERIFY_FAILED`）。上面几行 `[Lark] ... connect failed` 里有服务端原话 |
| **飞书：连上了但收不到任何消息** | **十有八九是应用版本没发布/没通过审核**——权限在那之前不生效。其次检查是否订阅了 `im.message.receive_v1` |
| 飞书：单聊正常、群里 @ 没反应 | 两个独立原因，分开确认：① 机器人**没被拉进群**；② `lark-oapi` 版本低于 `1.6.8`（低版本收不到群 @ 事件，启动时会明确报错） |
| 飞书：Lark 国际版连不上 | `GUANLAN_IM_FEISHU_DOMAIN=lark` |
| 微信：日志报会话失效 | 重跑 `guanlan im-login --platform weixin` 扫码 |
| 微信：偶尔某条回复发不出去 | 正常，宿主会自动重试；持续失败才看日志 |
| 开了 `--allow-all-users`，群里还是不理 | 正常：该参数不放开群名单。把群 ID 加进 `--allow-chat` |
| 未授权的人发消息，机器人完全没反应 | **这是设计如此**，不是故障 |
| 答案被切成好几条 | 超过单条上限。微信 2000 字容易触发——改用 `/search`，或到 Web 端看 |

---

## 明确不做的事

写入知识库（任何形式）、媒体收发、主动推送 / 定时播报、`/goal` 长任务续跑、用户管理与分租、
一个进程同时接两个平台（要都接就起两个进程）。

飞书的 webhook 模式与企业微信的 callback 模式也不做——它们需要公网可达的入站端点，与"不监听任何端口"冲突。
