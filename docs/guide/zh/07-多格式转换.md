# 多格式转换

`guanlan convert` 补的是一个 CLI 缺口:`ingest` 只接受 `.md`,而很多资料是 PDF/DOCX/PPTX/XLSX/HTML/图片。`convert` 把它们经 **`pdf-to-markdown` 技能**(MinerU → marker → pypdf 分层回退)转成 `raw/<slug>.md` 源,再走原样的 `.md` ingest。

> 它**不是新的主流程**,也**不替代** Web 端的「上传→解析→人审→晋级」(那条更强)。它补的是 CLI 用户「PDF/DOCX → raw → ingest」的官方入口。

## 用法

```bash
guanlan -C my-wiki convert 报告.pdf                 # 转换并落 raw/报告.md
guanlan -C my-wiki convert 报告.pdf --dry-run        # 只打到 stdout,raw/ 零写(人审预览)
guanlan -C my-wiki convert 报告.pdf --ingest         # 转换成功后串联 ingest
guanlan -C my-wiki convert 报告.pdf --name notes     # 覆盖目标 slug → raw/notes.md
guanlan -C my-wiki convert a.pdf --backend marker    # 指定后端
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `src` | — | 待转换的文件(PDF/DOCX/PPTX/XLSX/HTML/图片…) |
| `--name` | 原件 stem | 覆盖目标 slug |
| `--origin` | 转换前原始 `src` 路径 | 显式出处(写入 `origin` provenance) |
| `--overwrite` | 关 | 同名 `raw/` 已存在时显式覆盖(默认不覆盖) |
| `--dry-run` | 关 | 只把结果打到 stdout,`raw/` 零写 |
| `--ingest` | 关 | 转换成功后串联 `ingest raw/<slug>.md` |
| `--backend` | `auto` | 转换后端:`auto`/`mineru`/`marker`/`python`(透传技能 `convert.py`) |

## 行为契约

- **两步默认,不自动 ingest**:`convert` 只做「转换 + 落源」(确定性宿主写 `raw/`,无 Agentao、无门禁、无快照、无 `log.md`)。建页是另一步 `guanlan ingest`(或加 `--ingest` 串联)。
- **脚本零 LLM**:观澜不带 LLM 客户端/密钥,只外调转换器。marker 是否用 Gemini 由**用户环境**决定(无 `--model`、无 env 擦除、无模型透传)。
- **记下是谁解析的**(决策P5.2-13):落源时 frontmatter 多一个 `parsed_by` 键,值是**实际生效**的后端(`mineru` / `marker` / `python`;MinerU 4 还带上实际档位,如 `mineru/standard`,见下文「核对实际档位」)。`--backend auto` 是分层兜底,三档质量差一个数量级,而 `raw/` 不可变、wiki 层从它长出来——不记下来,事后没有任何字段能回答「这库里哪些页建在降级文本上」。它与 `origin`(来自哪个文件)同属 provenance:一个管来自哪里,一个管怎么来的。只记最终后端(不记降级链路),读不到后端标记就不写该字段。Web 的「解析 → 晋级」这条路同样记,晋级后仍在。
- **图片随源落盘**(P5.2.1):转换器抽出的图片落到 `raw/images/<slug>/<slug>-N.ext`,并重写 markdown 图片引用指向新相对路径,使 `raw/<slug>.md` **自洽**。容量三道闸:单图 20 MiB / 累计 200 MiB / 张数 500,超限报错(非静默丢图)。`--dry-run` 连图一并零落盘。
- **无新运行依赖、无新 extra**:复用技能的分层后端,任一可用即可;全不可用时优雅降级报错(退出码 `1`)。

> 真正跑一次转换需至少装好一个后端(MinerU / marker / pypdf)。MCP **不做 convert**(写 `raw/` 与只读姿态冲突)。

## MinerU 解析档位

`convert`、`import` 和 Web「导入」里的解析走的都是同一个技能脚本,下面说的对三处都适用。本节的档位与硬件数据取自 MinerU 4.0.12 随包说明(`mineru-4.0.12.dist-info/METADATA`)和官方文档 [Tiers and runtimes](https://opendatalab.github.io/MinerU/usage/tiers/);MinerU 升级后以官方文档为准。

### 观澜与 MinerU 的关系

- 安装观澜**不会**装 MinerU。MinerU 是外部命令行工具,要自己装(`uv tool install -U mineru`);`PATH` 上找不到 `mineru` 时,`--backend auto` 直接退到 marker、再退到 pypdf。
- MinerU 4 自身的默认安装带 ONNX + llama.cpp,但**本地解析引擎默认关闭**(`parse_server.local.mode = disabled`)。这时本地只能跑 `flash`,PDF 只取文本层,扫描件取不出字。
- 要 `basic`/`standard`/`advanced`,得先下载模型、再打开托管引擎(见下文)。观澜不替你下模型、不改 MinerU 配置。

### 四个档位

| 档位 | 质量与速度 | 适用 |
|---|---|---|
| `flash` 极速解析 | 质量最低、最快;不用模型 | 预览、建索引。Office/HTML/EPUB/CSV 等非 PDF 格式一律用它 |
| `basic` 基础解析 | 基础质量、中等速度 | 资源有限的本地解析 |
| `standard` 标准解析 | 标准高质量;合适硬件上与 `basic` 速度相近 | 日常阅读和复杂文档的默认档 |
| `advanced` 高级解析 | 普通文档同 `standard`,难文档更好;最慢 | 难文档、要最高质量且能接受更长等待 |

不指定 `--tier` 时,MinerU 先选 `standard`、再选 `basic`;`advanced` 不会被自动选中。

### 硬件与模型

| 档位 | 模型引擎 | 模型下载 | 最低内存 | 加速器 |
|---|---|---|---|---|
| `basic` | ONNX | 约 0.8 GB | 2 GB | 不需要(CPU 可跑) |
| `basic` | PyTorch | 约 0.8 GB | 8 GB | 建议 GPU/MPS |
| `standard`/`advanced` | ONNX + llama.cpp | 约 2 GB | 8 GB | CPU 可跑,建议 Vulkan |
| `standard`/`advanced` | PyTorch + llama.cpp | 约 2 GB | 16 GB | 需要 GPU/MPS,8 GB+ 显存 |
| `standard`/`advanced` | PyTorch + vLLM/lmdeploy/mlx | 约 3 GB | 16 GB | 需要 GPU/MPS,8 GB+ 显存 |

MinerU 官方按硬件推荐的托管档位:Apple Silicon 的 macOS 用 `standard`(默认安装已带 PyTorch);Intel 的 macOS 用 `basic`;8 GB+ 显存的 NVIDIA 用 `standard` 并装 `mineru[full]`;4 GB+ 显存的 NVIDIA 用 `basic` 并装 `mineru[torch]`;有较新核显的 Linux/Windows 用 `standard`;没有加速器的用 `basic`。托管档位只有 `basic` 和 `standard` 两种,`standard` 托管引擎同时提供 `basic`、`standard`、`advanced` 三个请求档位。

### 打开托管引擎

```bash
mineru-kit models download --tier standard      # 先下模型(basic 或 standard)
mineru-kit models verify --tier standard
mineru config set parse_server.local.managed_tier standard   # 先设档位
mineru config set parse_server.local.mode managed            # 再打开托管模式
mineru server status --json                                  # 等引擎健康后再解析
```

已有自己部署的解析服务时,也可以用 `parse_server.local.mode self_hosted` 配 `parse_server.local.self_hosted_url`。远端解析(mineru.net)要显式加 `--remote`,会**上传文件**;观澜的 `convert`/`import`/Web 解析都不会加 `--remote`。

### 启动等待与回退

`mineru parse` 依赖后台服务。服务没起时,技能脚本会自动 `mineru server start`。服务起来后,托管引擎还要加载模型,这期间提交解析会得到 `quality_tier_unavailable`。所以脚本会先等引擎就绪,再提交解析:

- 轮询 `mineru server status --json`,看 `parse_server.local` 的 `mode`、`healthy`、`starting`、`supported_tiers`、`error_code`/`error_msg`。
- 引擎健康:日志打 `[mineru] engine ready: supported tiers=…`,按原档位解析。
- 本地引擎关闭(`mode=disabled`):不等,直接说明只能跑 flash。
- 超时(默认 180 秒,技能脚本参数 `--engine-wait`,`0` 表示不等)或托管引擎重启次数用完:日志打 `[mineru] engine not ready (原因)`。
- 没指定档位时,引擎不可用就回退到 `flash`,日志打 `[mineru] fallback: retrying with --tier flash`;显式指定了 `basic`/`standard`/`advanced` 则不回退,直接报错。
- 服务原本就在跑、但引擎还在加载时,同样会等一次再重试。

### 核对实际档位

- 解析成功后,脚本打一行 `[mineru] tier=<档位>`;`import` 的任务日志和 Web 解析进度里都能看到。
- 落盘时 `parsed_by` 记成 `mineru/<档位>`,例如 `mineru/standard`、`mineru/flash`。旧版本落的源只有 `mineru`。要查哪些源是 flash 解析的:`grep -l "parsed_by: mineru/flash" raw/*.md`。
- MinerU 自己的状态:`mineru server status`(人读)或 `mineru server status --json`(机读)。
