## 1. 现状盘点

| 已有 | 位置 | 用法 |
|---|---|---|
| 单写者 FIFO 作业队列：ingest/heal/backfill/audit/投喂 都 `enqueue` 进同一条 worker，持 `write_lock`（含库级 OS 锁） | `guanlan/web/jobs.py` | 执行层保留不改 |
| 心跳进度 `job.progress`、增量日志 `emit`、heal/audit 结构化回执 | 同上 | 直接复用 |
| 只读问答不取 `write_lock`，跑在各自 `conv.lock` 上 | `app.py /api/chat` | 读路径已不被写阻塞 |
| 一键入库清单 `workspace/tasks/<id>.json` + `.log`；暂停（篇间）/续跑/放弃/`recover_stale` | `guanlan/oneclick.py` | 只读取用于展示；**清单兼作 raw 文件归属依据**（`_owned_by_other_tasks`），不能当作可清理的历史 |
| 子进程整组结束：`stopscope.stop_scope`（0.2 s 轮询）+ `kill_group` | `guanlan/stopscope.py` | 运行中取消复用 |
| 原子写回 `rawio.atomic_write_bytes`；`.trash/` 软删先例（P3.9） | `rawio.py`、`remove.py` | 回滚复用 |

写门禁只保存 frontmatter 指纹（`snapshot_page_meta`）与 `raw/` 哈希（`snapshot_raw`），**不保存 wiki 页字节**，回滚需要自己的前像（§4）。

**缺口**：
1. 作业表只在内存：刷新或重启后，ingest/heal/backfill/audit 的进度与结果都丢；没有列表接口。
2. 监测绑在浮层上：关掉浮层就看不到进度，打开别的浮层会互相覆盖；没有全局入口。
3. 除一键入库外不能取消。
4. 库被 CLI 占用时直接失败，而不是等待。
5. 可写会话的 turn 在等 `write_lock` 时**没有任何提示**——后台 ingest 跑 10 分钟，这轮对话就无声卡 10 分钟。

## 2. 目标与红线

**目标**
- G1 提交即返回；任意时刻都能看到全部任务及其最终结果。
- G2 能取消（排队中直接撤回；运行中停止并**回滚当前步骤**）、能重试。
- G3 只读问答永不等写锁（现状，保持）；可写会话等待后台任务时**看得见**在等什么。
- G4 重启后记录仍在，未完成的标为「中断」，其前像保留到用户处理。

**红线**
- 单写者不变，写任务串行；每个写任务照旧走写门禁。
- 任务记录与前像都是派生物，放 `workspace/` 下（不进 zip、索引、图谱）；markdown 仍是唯一权威。
- 回滚覆盖或移除的任何当前文件先进 `.trash/`，不直接删除。
- 重启不自动续跑、不自动回滚：只标「中断」，由用户决定。
- 层③ 423 保留：可写 turn 活跃期间拒绝写任务提交。
- `--reader` 部署不注册任何任务写端点。
- **不碰一键入库清单的生命周期**：不改、不删 `workspace/tasks/` 下任何文件。

## 3. 总体结构

```
浏览器 ── 顶栏徽标 + 任务中心抽屉 ── GET /api/tasks（活跃 + 最近完成）
   │ 提交：补录/沉淀/heal/audit 原入口 → 返回 task_id 后关闭浮层
   ▼
TaskStore（新，web/tasks.py）── workspace/jobs/<id>.json 信封 + <id>.log
   │                         └─ 只读合并 workspace/tasks/*.json（一键入库清单）用于展示
   ▼
JobQueue（既有）── ① 拍前像 workspace/jobs/<id>/before/ → ② stop_scope 内跑 fn(emit) → ③ 门禁
   │ 取消：停止标志 → 子进程整组结束 → 按前像回滚
   ▼
Agentao 子进程
```

**D1 不重写执行层**，在 `JobQueue` 上加信封层：入队、状态翻转、完成处各回调一次 TaskStore。

**D2 两类记录分目录**：
- 通用任务（ingest/backfill/heal/audit）的信封写在 **`workspace/jobs/`**，由本期管理，适用保留策略。
- 一键入库仍只在 `workspace/tasks/`，任务中心**只读**它的清单来展示（状态、进度、日志尾），操作按钮跳回暂存区现有的任务卡。
  这样 `oneclick.iter_tasks()` 扫描的目录里不会混进别的 JSON，历史清单也不会被通用保留策略删掉。

## 4. 通用任务

### 4.1 信封（`workspace/jobs/<id>.json`）

```jsonc
{
  "id": "20261113-1530-ingest-a1b2",
  "kind": "ingest | backfill | heal | audit",
  "title": "补录：raw/某报告.md",
  "params": { "raw": "raw/某报告.md" },   // 重试用
  "state": "queued",
  "created": "…", "started": null, "finished": null,
  "exit_code": null,
  "summary": null,                        // heal/audit 结构化回执的序列化
  "preimage": null,                       // "workspace/jobs/<id>/before"，有前像时才有
  "pgid": null,                           // 当前 Agentao 子进程组号；每次起子进程前后更新，见 4.6
  "rollback": null,                       // 回滚回执，见 4.4
  "retry_of": null,
  "error": null
}
```

日志 `workspace/jobs/<id>.log` 追加写；接口按字节偏移增量取尾部。运行中的 `progress` 心跳行仍从内存 `Job` 读，不落盘。

### 4.2 状态

```
queued ──► waiting_lock ──► running ──► succeeded | failed
  │            │               └──► cancelling ──► cancelled（已回滚）
  │            │                                └─► rollback_failed（前像保留）
  └── cancel ──┴──► cancelled
重启时：running / cancelling ──► interrupted（前像保留）；queued / waiting_lock ──► cancelled（未开始，无写入）
        running 但前像未就绪（无 READY）──► cancelled（Agent 未启动，无写入；删除残缺的 before/）
```

- `waiting_lock`：拿不到库级锁（CLI 在写）时等待，退避 5 s 起翻倍、封顶 60 s，累计 30 分钟转 `failed`；可随时取消。等锁期间不拍前像。
- 重启后 `queued` 记为 `cancelled` 而非重新入队：符合「重启不自动花钱」，用户点重试即可。
- 本期**没有暂停**；一键入库的篇间暂停沿用其现有入口。

### 4.3 前像：按任务隔离的普通文件副本

- **何时拍**：任务开始执行、已持写锁之后，调 Agent 之前。
- **范围**：`wiki/` 全部文件 + 库根 `SCHEMA.md`、`AGENTAO.md`。不含 `raw/`（门禁哈希守）、`workspace/`、`graph/`、`.trash/`。
- **形式**：原样复制到 `workspace/jobs/<id>/before/files/`（保持相对路径）。不做内容寻址、不跨任务去重、不做 GC。
  量级按单份约 15 MB 估（3000 页 × 5 KB），落地时在真实库实测，超过 2 s 在任务日志记一行耗时。
- **恢复所需的全部信息一起落盘**——重启后内存里什么都没有，回滚只能依赖这些文件：

  | 文件 | 内容 | 回滚时用于 |
  |---|---|---|
  | `before/manifest.json` | 范围内每个文件的相对路径 → SHA256 | 4.4 步骤 2 比对 |
  | `before/raw.json` | 任务开始时的 `snapshot_raw`（`raw/` 相对路径 → SHA256） | 4.4 步骤 3 核对 `raw/` |
  | `before/baseline.json` | 任务开始时的 `check_baseline`（阻断违规身份键列表） | 4.4 步骤 4 复核 |
  | `before/READY` | 空文件，**最后**写入 | 就绪判定 |

- **就绪标记**：依次写 `files/` → `manifest.json` → `raw.json` → `baseline.json`（各自原子写并 `fsync`），全部成功后才写 `READY`。
  - **没有 `READY` 不启动 Agent**：拍前像失败 → 任务直接 `failed`，库未被动过。
  - **没有 `READY` 的前像不能用于恢复**：由上一条，它对应的任务一定没启动过 Agent，库没被写过；重启时把任务记 `cancelled`、删除残缺的 `before/`。
  - 回滚前校验 `files/` 中每个文件的 SHA256 与 `manifest.json` 一致；不一致（前像本身损坏）→ 拒绝回滚，记 `rollback_failed`。
- `raw.json` / `baseline.json` 由任务层拍一次，与写门禁内部各自再拍的快照**互不复用**（多一次 `raw/` 哈希与一次 `check`，换来与门禁实现解耦）。
- **何时删**：
  - `succeeded` / `failed` / 已完成回滚的 `cancelled` → 任务结束即删除整个 `before/`。
  - `interrupted` / `rollback_failed` → **保留**，直到用户在任务中心选择处理方式（4.5）。
- **为什么不怕被下一任务覆盖**：每个任务一个独立目录，下一任务只写自己的目录、不清理别人的。

### 4.4 取消与回滚

| 任务所处阶段 | 处理 |
|---|---|
| `queued` / `waiting_lock` | 直接记 `cancelled`；worker 取到时跳过。无前像、无回滚 |
| `running` | 记 `cancelling`、置停止标志。Agent 子进程在跑 → `stop_scope` 在 ≤0.2 s 内整组结束它；处于确定性阶段（门禁、确定性修复）→ 跑完当前这一步，下一次起子进程时立即停止；若 `fn` 已正常返回，worker 见标志已置同样回滚。即：**任务完成前发出的取消，结果都是回滚** |
| 终态 | 409 |

回滚步骤（worker 线程内，仍持写锁；**幂等**，中途崩溃后可整段重跑）：

1. 确认子进程组已无残留成员（4.6 的探测）；仍存活则不回滚，进入 4.6 的写入阻止。
2. 按 `manifest.json` 比对范围内文件：内容不同 → 当前版本移入 `.trash/job-<id>@<ts>/`，再用 `atomic_write_bytes` 写回前像；缺失 → 写回前像；前像中没有的新文件 → 移入 `.trash/`。之后删除新出现的空目录。`.trash/job-<id>@<ts>/manifest.json` 记录每一项动作。
3. `raw/` 与 `before/raw.json` 比对；被改则**不恢复**（与门禁一致），记 `rollback_failed`。
4. 跑 `check`，阻断违规应 ⊆ `before/baseline.json`；否则 `rollback_failed`。
5. `bump_wiki_generation()`；写回执：

```jsonc
"rollback": { "restored": ["wiki/entities/甲.md"], "removed": ["wiki/concepts/乙.md"],
              "trash": ".trash/job-…@20261113T153012", "raw_ok": true, "check_ok": true }
```

**能力上限**：只回滚范围内文件；分不清 Agent 写的与外部编辑器同时改的（后者也会被回滚，可从 `.trash/` 找回）；自行 `setsid` 脱离进程组的孙进程不受 `killpg` 影响。

### 4.5 中断任务的处理

`interrupted` 与 `rollback_failed` 任务在任务中心置顶，给两个按钮：

- **回滚到任务开始前**：作为一个普通写作业入队（持写锁），执行 4.4 的步骤 2–5。提示语：「以任务开始前为准，之后库里的所有改动（包括本任务之后的其它写入）都会移入 `.trash/`」。
- **保留现状**：确认后删除前像，任务记为 `abandoned`。

两者之一完成前，前像不删，也不会被任何其它任务清理。**不做**自动恢复。中断任务本身不阻止新任务（每个前像独立，新任务不影响它的可用性；代价只是上面提示语里说的「之后的改动也会被移走」）——**前提是它的 Agent 已经确认退出**，否则按 4.6 处理。两个按钮都要求 4.6 的探测结果为「已退出」。

### 4.6 残留 Agent：确认退出前拦住一切新的写执行

**问题**：Agentao 子进程跑在独立会话里（为了能整组结束）。Web 进程崩溃后，库级 OS 锁随 Web 进程释放，但子进程组可能还活着、还在写 `wiki/`。
新 Web 起来后若照常开写，就同时有两个写者，违反单写者红线；此时回滚也会被残留进程的后续写入破坏。

**记录**：每次起 Agentao 子进程前，信封写 `pgid: "spawning"`；`Popen` 返回后立即写入真实组号。
主进程结束后**探测整个进程组**；确认无成员才清空 `pgid`（写回 `null`）。仍存活或无法确认时保留组号，进入下面的写入阻止流程；
**解除前不启动下一子进程**（自愈轮等后续调用一并暂停）。Agentao 主进程退出不代表它派生的 shell / 后台进程都已退出，
`communicate()` / `wait()` 只等主进程，所以不能以它们返回作为清空依据。各写路径的多次子进程调用（自愈轮等）逐次按此更新。实现上通过 `runtime` 的子进程启动处加一个可选回调完成，不改 `run_agent_task` 的签名语义。

**探测**（Web 启动时，对每个 `interrupted` / `cancelling` / `rollback_failed` 信封）：

| `pgid` 字段 | 判定 |
|---|---|
| `null` | 已退出（崩溃时没有子进程在跑） |
| 整数，POSIX `killpg(pgid, 0)` 抛 `ProcessLookupError`，或开机时间晚于任务的 `started` | 已退出 |
| 整数，`killpg(pgid, 0)` 成功 | **存活** |
| `"spawning"`（崩溃落在启动与记录之间），或平台无法探测（Windows 首版） | **未知**，按存活处理 |

判定方向偏保守：误判「存活」只会多拦一会儿写入；误判「已退出」才会造成双写者。

**存活 / 未知时的「写入阻止」**（只在本 Web 进程内，状态不落盘，每次启动重新探测）：
- **拦住**：JobQueue worker 不再取新作业执行（新提交照常进 `queued`，不丢）；可写会话的 turn 在 `enter_writable` 之前直接以错误帧结束（「后台残留进程未退出，暂不能写入」），不进入写锁等待；所有宿主写端点（`/api/raw`、上传、删除、一键入库、`GET /graph` 写盘等）返回 423；4.5 的「回滚 / 保留现状」按钮不可用。
- **不拦**：只读问答、页面浏览、检索、零 LLM 只读报告。
- **解除**：任务中心置顶一条「残留进程」提示，显示 `pgid` 与供用户自查的命令（`ps -g <pgid>` / `ps -o pid,command -g <pgid>`），给两个操作：
  - **重新检测**：再探测一次，已退出则自动解除；
  - **我已确认，解除阻止**：二次确认后解除（用于组号已被无关进程复用、或 `spawning` / Windows 无法判定的情况）。
- 不提供「一键结束该进程组」：组号可能已被无关进程复用，宿主无法可靠区分，误杀代价高；用户确认后可自行在终端结束。
- **CLI 不感知**这个阻止（它看不到 Web 的内存状态），提示文案里写明「解除前请勿在命令行执行写命令」。

### 4.7 提交、去重、保留

- 原有提交端点（`/api/ingest`、`/api/heal`、`/api/backfill`、`/api/audit`）签名不变，响应在 `job_id` 外加 `task_id`；`GET /api/jobs/{id}` 保留一个版本作兼容。
- 去重：同 kind + 同 params 已有非终态任务 → 返回已有 task_id。非终态任务上限 50，超出 429。
- 保留：`workspace/jobs/` 中终态任务保留最近 200 条，超出时删最旧的信封与日志；`interrupted` / `rollback_failed` 不参与。清理在任务结束时顺手做。**只作用于 `workspace/jobs/`。**

## 5. 不影响问答

- **只读问答**：现状不取写锁，保持。
- **可写会话等待**：可写 turn 在 `acquire_thunk` 之前，若有写任务 running，先推一帧 `waiting_for_task {task_id, title}`；前端在气泡里显示「正在等待后台任务『…』完成」，并给一个打开任务中心的链接。**只显示，不提供改只读**：等待时 turn 已持 `conv.lock` 且已计入可写计数，现有 `/mode` 既要这把锁、又会被层③ 拒绝；要支持就得新增「撤回锁等待」机制，本期不做。
  **等待期间点「停止」不会立即结束这一轮**：此时 turn 还没装上取消令牌，`request_stop()` 只记待停标志，要等阻塞中的 `acquire_thunk` 返回、取得写锁后才兑现（`conversation.py` 取锁后检查 `_stop_requested`）。
  所以等待帧的文案写明「停止请求将在后台任务结束、取得写锁后生效」，前端点停止后显示「已请求停止，等待后台任务结束」，不承诺即时停止。
  想尽快结束，可在任务中心取消那个后台任务。
- **423**：可写 turn 活跃时提交写任务仍被拒；前端把 423 翻成「可写会话进行中，结束后再提交」，表单内容保留。
- **检索缓存**：`CorpusCache` 按 `(mtime_ns,size)` 增量重建，无需改动；任务完成或回滚后前端 `loadPages()`。

## 6. API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/tasks` | 三部分：**全部「需要处理」**（`interrupted` / `rollback_failed`，不限条数、不限时间）+ **全部活跃** + **最近完成 20 条**；另带 `write_blocked`（4.6 的阻止状态与 `pgid`）。含一键入库（`kind="import"`、`source="oneclick"`）。每条带 `updated` 时间 |
| GET | `/api/tasks/{id}?log_after=<offset>` | 详情、日志增量、回执 |
| POST | `/api/tasks/{id}/cancel` | 见 4.4；import 任务 409（用暂存区原入口） |
| POST | `/api/tasks/{id}/retry` | 终态任务按 `params` 新建任务，`retry_of` 指回原任务 |
| POST | `/api/tasks/{id}/rollback` · `/abandon` | 仅 `interrupted` / `rollback_failed`，见 4.5；写入阻止期间 423 |
| POST | `/api/tasks/write-block/recheck` · `/release` | 4.6：重新探测；确认后解除阻止 |
| DELETE | `/api/tasks/{id}` | 仅通用任务的终态记录；有未处理前像时 409 |

## 7. 前端

- **顶栏徽标**：`运行 1 · 排队 3`；有失败、中断时变色。点击打开**任务中心抽屉**（非模态，不遮挡聊天区）。
- **任务中心**：置顶「需要处理」（中断 / 回滚失败），然后「进行中 / 排队 / 最近完成」。每行：图标、标题、状态、心跳行、耗时、按状态显示的按钮。展开看日志尾、复用现有 heal/audit 回执渲染、回滚回执。import 行显示总体进度，点击跳到暂存区的任务卡。
- **取消确认**：「将停止并把本任务的写入回滚到开始前（被覆盖的内容进 .trash/）」。
- **提交即关浮层**：toast「已加入后台任务」，不再在浮层内 `pollJob`。
- **单一轮询**：一个定时器拉 `/api/tasks`（有活跃任务 1 s，否则 10 s）。前端按 id 维护本地表，对比上一次状态发现「→终态」的变化，据此弹 toast、`loadPages()`。
  - 「需要处理」的任务不论多旧都在响应里，不会被「最近 20 条」挤掉。
  - 本地表里还在跟踪（上次看到时非终态）、这次却不在响应里的 id——例如浏览器在后台停了轮询、期间完成了超过 20 个任务——逐个调 `GET /api/tasks/{id}` 补查终态；返回 404（已被保留策略清掉）则从本地表移除，不报错。
- **写入阻止横幅**：`write_blocked` 为真时，顶栏下方显示常驻横幅（4.6 的说明 + 「重新检测」「我已确认，解除阻止」），写入口按钮置灰并提示原因。

### 8.1 推后项：对话中提议后台任务（方案 A）

**场景**：用户在对话里说「创建 Concept『XXConcept』」。按本期设计，对话轮次不是任务：只读会话里 Agent 写不了，
可写会话里 Agent 在前台直接写（P4.5 守卫与撤销覆盖），都不进任务中心。本项让 Agent 能把这类请求**提议**成后台任务。

**做法：工具只提议，用户点击提交。**
- 宿主给对话 Agent 注册一个工具（暂名 `propose_task`），参数只含意图：`{kind, type, name, note?}`，例如
  `{kind: "create_page", type: "concept", name: "XXConcept"}`。
- 工具**不写盘、不入队**，只经 SSE 推一帧 `task_proposal`；前端在气泡里渲染卡片「建议创建后台任务：建立 Concept『XXConcept』 [提交]」。
- 用户点「提交」→ 前端调普通的任务提交端点 → 进任务中心（§4 全套：排队、取消回滚、中断处理）。
- 工具 `is_read_only=True` 名副其实（它确实不写），所以**只读会话也能用**——agentao 在只读姿态会拒绝非只读工具（同 `guanlan_search` 的约束）。
  需声明 `copies_to_subagents`，理由同 `guanlan_search`。

**为什么不让工具直接入队（方案 B，不采用）**：直接入队的工具不能标只读，只能在可写会话里用；它等于在进程内绕过层③ 423，安全只剩 P4.15 确认一道；
IM 没有确认 UI 会直接拒绝；而可写会话里 Agent 本来就能前台写，转后台收益小。

**守住的边界**
- **层③ 不变**：提交者是人，走普通端点；可写 turn 活跃时点提交照样 423，卡片保留，turn 结束后可再点。
- **防注入**：Agent 读到资料里的诱导指令而提议，也只是出一张卡，不点就不发生任何事。
- **读写分线（同 P4.8 决策P4.8-3）**：卡片只带意图参数，**不带 Agent 在对话里写的正文**；页面内容由后台任务在写门禁下重新生成。
- 去重沿用 4.7：同一提议重复点提交，返回已有 task_id。
- `--reader` 部署不注册该工具（卡片指向的写端点本就不存在）。

**前提：要有能「建指定页」的任务类型。** 现有入口都做不到——heal 只物化「被引用但缺页」的 worklist 条目（选择范围限于 worklist），
沉淀只写 `syntheses/`。倾向**扩展 heal 支持显式目标**，而不是另起一个 `create_page` 工作流：
- 复用 heal 的写入契约与回执；证据来源从「引用它的页面」放宽为「检索库内 source 页」。
- **库内找不到依据时拒绝建页**，回执说明原因，不凭空生成（页面须有来源的约定）。
- 需改 `skills/guanlan-wiki/references/heal.md`（STE 英文），改后按既有做法在库内 `skills/` 做 A/B，确认不拉低 heal 的逐字引语率。

**依赖与归属**：依赖 T1 的任务中心与提交端点；新增工具、卡片、heal 显式目标三块，作为 T1/T2 之后独立的一期评估，不并入 T2。

非目标：写任务并行；读快照隔离；撤销已成功的任务；`raw/` 被改后的自动恢复；定时/自动任务；reader 部署下的任务。

## 9. 决策

| # | 决策 |
|---|---|
| D1 | 不重写执行层，在 `JobQueue` 上加信封层 |
| D2 | 通用任务信封在 `workspace/jobs/`；一键入库清单留在 `workspace/tasks/`、只读展示，不受保留策略影响 |
| D3 | 运行中取消 = 回滚到任务开始前；被覆盖/移除的当前文件进 `.trash/`；回滚幂等 |
| D4 | 前像 = 按任务隔离的普通文件副本 + SHA256 清单；正常结束即删；`interrupted` / `rollback_failed` 保留到用户选「回滚」或「保留现状」 |
| D5 | 重启：运行中的记 `interrupted`，排队中的记 `cancelled`；不自动续跑、不自动回滚 |
| D6 | 可写会话等待后台任务：只推等待帧显示，不提供改只读；等待期间的「停止」在取得写锁后才生效，文案如实说明 |
| D7 | `/api/tasks` 返回全部「需要处理」+ 全部活跃 + 最近完成 20 条；前端对消失的已跟踪 id 用详情接口补查 |
| D8 | 通用任务终态保留最近 200 条，只清 `workspace/jobs/`，不清有未处理前像的任务 |
| D9 | 前像与 `raw/` 快照、`check` 基线一起落盘，最后写 `READY`；未就绪不启动 Agent、不用于恢复 |
| D10 | 残留 Agent 进程组存活或无法判定时，拦住 Web 内一切新的写执行（作业、可写会话、宿主写端点、回滚），不拦只读；用户「重新检测」或确认后解除；不提供一键结束进程组 |
| D11 | `pgid` 只在探测到整个进程组无成员后才清空；主进程退出不算。未确认前保留组号、进入写入阻止，不启动下一子进程 |

## 10. 分期

| 期 | 内容 | 风险 |
|---|---|---|
| **T1 可见** | TaskStore（信封、日志、列表/详情、合并只读 import 清单）、徽标、抽屉、提交即关浮层、单一轮询、重启标记、保留策略、可写会话等待帧 | 低：执行路径不变；等待帧只在取锁前多推一帧，不改锁序 |
| **T2 控制** | 排队取消、重试、去重/上限、`waiting_lock` 退避；前像（新 `guanlan/preimage.py`，零 LLM，含 `raw.json` / `baseline.json` / `READY`）+ 运行中取消回滚 + 中断任务的回滚/保留现状；`pgid` 记录与残留进程写入阻止 | 中：取消 × 门禁 × 回滚 × 崩溃恢复交叉；`preimage.py` 先脱离 Web 单测扎实再接入 |

T1 的「重启标 `interrupted`」只改状态、不涉及前像与写入阻止（与现状相同：今天 Web 崩溃同样可能留下残留子进程）；残留进程的防护随 T2 的 `pgid` 记录一起上线。

## 11. 测试要点

**T1**
- 重启：`running` → `interrupted`，`queued` → `cancelled`；坏 JSON 不拖垮列表。
- `/api/tasks` 中任务从 running 变 done 后仍在响应里（最近完成），前端能见到终态与回执。
- 造 1 条较早的 `interrupted` + 30 条更新的终态任务：`interrupted` 仍在响应里。
- 前端本地跟踪的 running 任务，在一次轮询间隔内完成并被 20 条以上新任务挤出列表：前端经详情接口拿到其终态；详情 404 时静默移除。
- 等待写锁期间点停止：前端显示「已请求停止，等待后台任务结束」；后台任务结束、turn 取得锁后立即以停止收尾，不调用模型。
- 保留策略只删 `workspace/jobs/` 里最旧的终态信封；**`workspace/tasks/` 里的一键入库清单一个都不动**，`_owned_by_other_tasks` 结果不变。
- `oneclick.iter_tasks()` 不会读到 `workspace/jobs/` 的信封。
- 可写 turn 在有后台任务时先收到 `waiting_for_task` 帧，取得锁后正常继续；无后台任务时不发该帧。
- `--reader` 下 `/api/tasks*` 全 404。

**T2**
- `preimage` 单测：新建 / 修改 / 删除 / 改名 / 空目录残留 / CJK 长文件名（Linux 按字节）后回滚，范围内逐字节一致；被覆盖版本都在 `.trash/`。
- 回滚幂等：在步骤 2 中途模拟崩溃后重跑，结果与一次跑完相同。
- 取消落在：排队 / 等锁 / Agent 运行中 / 确定性修复中 / `fn` 刚返回 / 终态（409）。
- 取消后：无残留进程、`raw/` 未变、`check` ⊆ 基线、`before/` 已删。
- 回滚失败（模拟 OSError）→ `rollback_failed`、前像保留、写锁释放、后续任务照常运行。
- 中断任务：重启后前像仍在；期间跑完另一个任务，中断任务的前像不受影响；「回滚」恢复到其开始前、「保留现状」删前像；进程组仍存活时拒绝回滚。
- 去重、50 上限（429）、CLI 持锁时 `waiting_lock` 并在释放后开跑。
- 就绪标记：在写 `files/`、`manifest.json`、`raw.json`、`baseline.json` 各步之后模拟崩溃 → 无 `READY`、Agent runner 未被调用；重启后任务为 `cancelled`、残缺 `before/` 已删。
- 重启后回滚只用落盘数据：新进程里对 `interrupted` 任务回滚，`raw/` 核对与 `check` 复核分别读 `raw.json` / `baseline.json`（构造「基线里已有的违规」验证不被误判为回滚失败）。
- 前像文件被篡改（哈希与 manifest 不符）→ 拒绝回滚、`rollback_failed`。
- 写入阻止：用一个真实的 `sleep` 子进程组模拟残留 Agent，`pgid` 写进 `interrupted` 信封后启动 app → `write_blocked` 为真；新作业停在 `queued`、可写 turn 收到错误帧且未进入写锁等待、宿主写端点 423、回滚 423；只读问答、页面、检索正常。结束该进程组后「重新检测」→ 解除，排队作业开始执行。
- `pgid: "spawning"` → 判为未知、阻止；「我已确认，解除阻止」后解除。`null` → 不阻止。
- 主进程退出、同组子进程仍存活：Agentao 替身主进程派生一个同组的后台 `sleep` 后自行退出 → `pgid` **不被清空**、进入写入阻止、下一子进程（如自愈轮）不启动；结束该后台进程后「重新检测」→ `pgid` 清空、阻止解除。
