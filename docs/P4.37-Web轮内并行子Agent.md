# P4.37 — Web 轮内并行子 Agent

> **状态**：已实现（2026-11-24，第三版定稿，经两轮设计评审、六轮代码审查）。实机验收见 §5.4，实现记录见 §7。
> 范围：Web 对话（嵌入式 agentao）里打开后台子 Agent，让同一轮派出的多个子 Agent 真正同时运行。宿主用「收尾屏障」保证所有子 Agent 都在本轮写日志关闭、库写锁释放之前结束。IM、CLI 子进程路径、P4.33 后台任务不在本期。
> 目标：长流程（如库内 长篇审查任务的 5 组核查）墙钟时间从「各组之和」降到接近「最慢一组」。不放松确定性写门禁。
> 本文改写 P4.23 §3.4 的一条结论：后台子 Agent 不必关死，只要不让它活过本轮。
>
> **第二版变更**（按第一轮评审）：删去自动续跑与起跑屏障。停止超过 30 秒只提示，继续持锁等到写入结束。屏障移到所有退出路径共用的收尾段。审查 skill 改为按空位补派。验收用例按 agentao 0.5.23 后台工具的真实行为重写。第 6 节待定问题改为已定。
>
> **第三版变更**（按复审）：屏障期间收到停止，排空收尾后返回 `stopped`（§2.4 第 6 步）。写明屏障计数的契约，记账锁由 `begin_journal`、`end_journal` 与记账写共用（§2.3、§2.5）。审查 skill 保留逐个等待，删去耗时估算，验收按预期表清单核对，等待超时交给宿主屏障排空（§2.7）。改正删除会话的口径（§2.4）。

## 1. 现状

### 1.1 为什么现在不能并行

agentao 0.5.23 有两条子 Agent 执行路径：

| 路径 | 同一批多个调用 | 观澜 Web 现状 |
|---|---|---|
| 前台（`agent_<name>`，不带 `run_in_background`） | 可写会话里**整批串行**：`runtime/tool_planning.py::is_foreground_subagent_call` 判为「返回前可能写文件」，`tool_executor._all_read_only` 因此退回串行。只读会话里并行 | 可用，但审查任务要写文件，只能串行 |
| 后台（`run_in_background=true`） | 立即返回任务 ID，子 Agent 在独立线程运行，同时运行数受 `max_concurrent` 限制（默认 6，`agents/bg_store.py`）。主 Agent 用 `check_background_agent(agent_id, wait_seconds≤1800)` 取结果 | **关闭**：`guanlan/web/conversation.py` 构造期传 `bg_store=None` |

2026-11-24 一个真实知识库（下称样例库）实测：库内审查 skill 一轮派出 5 个 `agent_generalist`，日志里只有一个子 Agent 在跑，5 组逐个完成。

### 1.2 关掉后台的理由（P4.23 §3.4）

后台子 Agent 能活过父轮收尾。那时本轮写日志已 `end_journal()`、写锁已释放，于是它的写：

1. 拿不到撤销 token；
2. 混进下一轮的 per-turn 写日志；
3. 脱离本轮 check 范围（可能没有下一轮、下一轮可能只读、或被收进 `before_check` 基线从此静默）。

库写锁释放后，它还会与其他会话的可写轮、P4.33 后台入库任务并发写库。

这些风险的共同前提是**子 Agent 活过了本轮**。只要宿主保证「本轮关日志、释写锁之前所有子 Agent 已结束」，它们都不成立。这就是本方案。

### 1.3 已有的零件与约束（agentao 0.5.23）

| 事实 | 位置 | 对本方案的意义 |
|---|---|---|
| 子 Agent 继承父的 `filesystem` | `agents/tools/_wrapper.py`（子 Agent 构造传 `filesystem=self._filesystem`） | 子 Agent 的结构化写经同一个 `PolicyFileSystem`：`raw/`、`AGENTAO.md` 不可变判定照常生效；写日志打开期间，它的 `wiki/`、`SCHEMA.md` 写也进日志 |
| 子 Agent 不能再派子 Agent | `_wrapper.py::_narrow_tools`（agent tool 一律剔除） | 只有一层后台任务，`count_in_flight()` 就是全部 |
| 后台子 Agent 拒绝一切需确认的调用 | `_wrapper.py::_child_transport`（`suppress_output` 时 `confirm_tool=lambda *_: False`） | 不会弹确认，也不向父会话发事件。只能做权限规则直接允许的事。`workspace-write` 预设下，库内普通路径的 `write_file` 直接允许（`permissions.py` `_PRESET_RULES`） |
| 达到上限拒绝启动，不排队 | `bg_store.py::register` 抛 `BackgroundCapacityError` | 第 N+1 个启动失败，模型须等空位再派（§2.6） |
| `check_background_agent` 超时返回时任务可能仍在运行 | `agents/tools/_bg_tools.py::_wait_and_report` | 超时 ≠ 失败，不能据此补做同一张表 |
| 子任务各有一枚取消令牌，不链到父轮 | `_launch_background` | 停止时宿主必须逐个 `cancel` |
| `count_in_flight()`、`list_current()`、`cancel(id)` | `bg_store.py` | 屏障条件与停止手段 |
| `persistence_dir=None` | `BackgroundTaskStore.__init__` | 宿主自建纯内存 store：不写 `.agentao/background_tasks.json`，没有跨进程 `recover()` |

## 2. 方案

### 2.1 一句话

Web 会话改传一个宿主自建的内存 `BackgroundTaskStore`。`turn()` 的收尾段（所有退出路径都经过）在关写日志之前加一道**收尾屏障**：等本会话的后台子 Agent 全部结束，期间一直持有库写锁。

主 Agent 负责显式取结果（`check_background_agent`），宿主只负责守住写入边界，不替模型续跑。

### 2.2 一轮的时序

```text
取 self.lock → 取库写锁 → begin_journal
  → arun（主 Agent 派出后台子 Agent，用 check_background_agent 等结果）
  → finally：
       [收尾屏障] 等 count_in_flight()==0   ← arun 正常返回、抛错、被停止都经过这里
       → _finalize_writable（end_journal、撤销 token、写后 check）
       → 释库写锁
       → 屏障期间收到过停止 → 抛 AgentCancelledError（走现有 stopped 路径）
```

子 Agent 的写全部落在 `begin_journal` 与 `end_journal` 之间，且全程在库写锁之内。撤销、check、日志归属都与前台写一致，其他写者也插不进来。

### 2.3 收尾屏障

位置：`turn()` 的 `finally` 收尾段，在 `_finalize_writable` 之前。现有收尾段已覆盖正常返回、`arun` 抛错、停止三条路径，屏障放在这里就一并覆盖，包括「主 Agent 派发后抛异常」这种情况。只读轮同样执行（只读轮没有写日志，但子 Agent 仍在运行，等它结束让「一轮」的边界在两种姿态下一致）。

逻辑（在线程池里跑，不堵事件循环）：

1. `count_in_flight()==0`：直接通过。正常情况下主 Agent 已逐个取过结果，屏障是零成本的兜底。

   计数的契约：`count_in_flight()==0` 表示本会话的每个后台任务都已结束工具执行、记录已进入终态（`_wrapper.py::_launch_background` 先跑完子 Agent、再 `bg_store.update(status=…)`）。agentao 此后还可能发终态事件、关闭子 Agent，但这些都不写库。首版用这个计数守住写入边界，不等子 Agent 对象关闭。
2. 否则推一帧 `bg_agents {running: n}`，每 0.5 s 复查一次，数量变化时再推一帧。
3. 等待期间轮询本轮 `CancellationToken`。用户按停止 → 转 §2.4。
4. 没有总时限。子 Agent 自身受 `max_iterations` 约束。停止只发出取消请求，屏障仍等到计数归零。设固定上限只会在长审查任务中途把正常任务砍掉。

主 Agent 没取结果就收尾时，结果不会自动回到模型。完成通知留在 agentao 队列里，随用户下一条消息注入。首版接受这一点（§4 P4.37-5）。

### 2.4 停止

1. 用户按停止：父轮令牌被 cancel。`arun` 返回 cancelled，或屏障在轮询中看到令牌已 cancel。
2. 宿主对 `list_current()` 中 pending/running 的每个任务调 `store.cancel(id)`。不用 `close_owner`：它会把 owner 永久标记为关闭，本会话以后再也派不出后台任务。
3. 继续等待。agentao 0.5.23 起取消能打断卡在网络上的模型请求，正常情况下几秒内结束。
4. 30 s 后仍有未结束的：推 `bg_agents {running: n, stopping: true}`，前端显示「仍有 N 个子 Agent 正在停止」。**不放行**，继续等。
5. 全部结束后照常 `_finalize_writable`（关日志、生成撤销 token、跑 check），再释库写锁。
6. **返回 `stopped`，不返回 `done`。** 现有 `turn()` 在进入 `finally` 之前已按 `arun` 的结果决定正常返回（`conversation.py` 中 `outcome["status"] == "cancelled"` 才抛 `AgentCancelledError`）。若 `arun` 已正常返回、停止是在屏障期间才到的，屏障记下「本轮被停止」。收尾段做完排空、关日志、check、释锁之后，抛 `AgentCancelledError`，走现有停止路径：Web 发 `stopped` 帧，目标模式按暂停处理，不把这一轮当成正常完成。`stopped` 帧照常带本轮的撤销与检查结果（`meta_out` 已在 `_finalize_writable` 中写好）。`arun` 本身已是 cancelled 或已抛错时，沿用原有的异常，不另抛。

30 s 只是提示阈值，不是放行阈值。理由：放行后残留任务继续写，即使隐藏撤销按钮，写后 check 也会漏报；同会话的起跑屏障挡不住其他会话、后台入库任务或 CLI 写库。一直持锁等到写入结束，就不存在跨轮残留，也不需要残留管理。

代价：一个卡在不响应取消的阻塞调用里的子 Agent，会让本轮一直不结束、库写锁一直被占。这种情况下用户能看到「正在停止」的提示，其他写者显示已有的等锁状态。删除会话也要先拿会话锁（`app.py` `delete_conversation` 的 `async with conv.lock`），所以卡在屏障时，删除请求会等本轮收尾后才执行，不能用来打断屏障。

### 2.5 写日志加锁

`PolicyFileSystem.write_text` 的记账现在只在单线程里跑，后台子 Agent 会从多个线程同时写。加一把 `threading.Lock`，由以下三处共用：

1. `begin_journal()`；
2. `end_journal()`；
3. 撤销范围内的 `write_text()`：从「判断写日志是否开启」开始，覆盖写前字节、实际写入、写后哈希和更新日志。

三处共用一把锁，开关日志与记账写才互斥：一次写要么完整进本轮日志，要么完全不进。屏障保证收尾时已无在飞写，这把锁是第二道防线。

不在撤销范围内的写（如 `workspace/reports/`）不取锁，不影响并发写。撤销范围按目标路径判定，与日志是否开启无关，所以这个判断可以放在锁外。

shell 直写不经 `PolicyFileSystem`，不进日志。这是 Web 路径既有的边界（P4.23 §3.4 订正第三条），本方案不扩大也不缩小它。

### 2.6 开关

默认**关**。`guanlan web --background-agents[=N]` 打开，`N` 为同时运行上限，缺省 4（低于 agentao 默认 6：多数国内模型服务的并发与限流更紧）。

- 关：构造期仍传 `bg_store=None`，行为与现在逐字相同，屏障短路。
- 开：每个 `Conversation` 构造一个 `BackgroundTaskStore(persistence_dir=None, max_concurrent=N)`。每会话一个，`count_in_flight()` 天然只算本会话。只读与可写会话都给：Web 同一会话可切换姿态，store 在构造期定下。只读姿态下子 Agent 继承只读限制（`_wrapper.py` `readonly_mode_getter`）。

默认关的理由：多出一条并发写路径，长等待也让一轮持写锁更久，期间 P4.33 后台任务要排队。

### 2.7 技能侧：按空位补派

样例库内审查 skill 的 `SKILL.md` 步骤 4 的派发说明改为：

1. 有 `run_in_background` 参数时：
   1. 派发前，按 `references/subagent-task.md` 的分组列出本次的**预期表清单**（每组可产出多张表，如第 1 组产出两张）。
   2. 先派出不超过上限的组数，每组 `run_in_background=true`。启动被拒（提示已达上限）时，不重试，记下该组待派。
   3. 对已派任务逐个调 `check_background_agent(agent_id, wait_seconds=1800)`。看到一个任务结束，就补派一个待派组。
   4. 所有已派任务都到终态后，按预期表清单核对 各组结果文件。缺哪张表，主 Agent 就自己补做哪张，**即使对应任务报告 `completed`**。
   5. 等待超时、任务仍在运行时：不补写该组的表，不重派，也不重复同一个等待。记下任务 ID 与「未完成」状态，结束本轮。宿主屏障会等它写完再收尾，下一条消息再接着核对清单（与 agentao 超时提示「end this turn」一致）。
   6. 不用 shell `sleep` 或反复无等待的 check 去等。
2. 没有该参数时：沿用现有前台派发（串行，只换上下文隔离）。
3. 子 Agent 任务模板（`references/subagent-task.md`）写明：产物用 `write_file` 写。后台子 Agent 的需确认调用会被直接拒绝，写入只能走权限规则直接允许的工具。

逐个阻塞等待时，主 Agent 只有**看到**某个任务结束才会补派。正在等一个慢组时，其他组先空出的席位会闲置。所以上限小于组数时不做耗时估算，验收记录实际补派时点。上限 6 时 5 组一次派完，没有这个问题。

同一批里的多次 `check_background_agent` 按工具实例锁逐个执行（agentao `docs/design/background-subagent-wake.md` §6.2「As implemented」），但等待期间子 Agent 都在跑，不影响并行。

## 3. 前端

只加一种 SSE 帧 `bg_agents`：

```json
{"running": 3, "finished": 1, "stopping": false, "tasks": [{"id": "8dc52bec", "status": "running"}]}
```

- **运行期轮询**：后台子 Agent 不向父会话发事件（`suppress_output`），P4.26 的子 Agent 进度行接不到它们。`turn()` 在 `arun` 起跑时起一个只读轮询协程，每 `_BG_WATCH_INTERVAL`（1 s）看一次本会话任务表，内容变化才推帧。所以从派出那一刻起就能看到派发与完成情况，不必等到收尾屏障。
- **只算本轮**：起跑时已有的任务 ID（之前各轮的，已全部结束）记为基线，不计入本轮帧。
- **屏障也推同一帧**：轮询在屏障前停掉，屏障接着推（带 `stopping`），归零时补一帧终态，前端据此收起。
- 帧只带 ID 与状态，不带任务原文（同 P4.26 决策4）。
- 前端在当前气泡下显示一行「后台子 Agent：3 个运行中，1 个已结束」，`stopping` 为真时改为「仍有 3 个子 Agent 正在停止」，`running` 为 0 时收起。任务中心不加会话占用详情，其他写者沿用已有的等锁状态。子 Agent 的逐步进度不在本期。

### 3.1 任务标签与进展（2026-11-24 补）

`bg_agents.tasks[]` 每项在 `id`、`status` 之外，按有无附带：

| 字段 | 来源 | 说明 |
|---|---|---|
| `label` | 任务表 `task`（agentao 存任务原文前 80 字）行首的 `【…】` | 截到 40 字。没有标签就不带，前端显示 ID |
| `tools` | host 事件 `tool_lifecycle` `started` 计数 | 子 Agent 至今发起的工具调用次数 |
| `tool` | 最近一次 `started` 的工具名 | 只在运行中带，工具结束或任务结束即不带 |
| `started_at` / `finished_at` | 任务表 | 秒级时间戳，前端算已运行时长 |

- **进展从哪来**：构造期传 `relay_subagent_events=True`（agentao 0.5.17 起），子 Agent 的 host 事件以子会话 ID 转到父事件流。宿主挂一个 `add_host_event_observer`：`subagent_lifecycle` 的 `spawned` 带 `parent_task_id`（后台启动才有，等于任务表 ID）时登记「子会话 → 任务」，之后该会话的 `tool_lifecycle` 计数。前台子 Agent 的 `spawned` 不带 `parent_task_id`，不登记，它的进展照旧走 P4.26 的 transport 帧。
- 观察者在子 Agent 线程内联执行，只在锁内更新两张小表；显示由运行期轮询读取。只记工具名与计数，不记参数、摘要、错误原文。
- **任务原文仍不上线（P4.26 决策4）**：只认行首 `【…】`。标签由派发方写在任务第一行，例如 `【第 2 组：A.2】`。模型没写就只显示 ID。
- 前端：汇总行下每个子 Agent 一行「标签或 ID · 状态 · N 次工具 · 当前工具 · 已运行秒数」，全部 `textContent`。
- 不显示轮次：host 工具事件不带轮次（前台的「第 n/max 轮」来自 transport 标签，后台没有）。

## 4. 决策

| 编号 | 决策 | 理由 |
|---|---|---|
| P4.37-1 | 后台子 Agent 可开，但必须在本轮关写日志、释库写锁之前结束 | P4.23 §3.4 的风险都以「活过本轮」为前提 |
| P4.37-2 | 屏障由宿主执行，放在所有退出路径共用的收尾段 | 写门禁是确定性的，不能押在模型自觉等上；`arun` 抛错时也要等 |
| P4.37-3 | 屏障无总时限；停止发出取消请求，屏障继续等到计数归零；屏障期间被停止的轮排空后返回 `stopped` | 固定上限会砍断长审查任务；停止不能被当成正常完成 |
| P4.37-4 | 停止用逐个 `cancel`，不用 `close_owner`；30 s 只提示，继续持锁等到全部结束 | `close_owner` 永久封住后台启动；放行会让残留写逃过 check 并与其他写者并发 |
| P4.37-5 | 首版不做自动续跑，由主 Agent 用工具显式取结果 | 判定「未读通知」只有私有接口；实测确实需要再推动上游提供公开信号 |
| P4.37-6 | 每会话一个内存 store，`persistence_dir=None`，跟随 Web 开关，只读会话也给 | 不落盘、无跨会话 `recover()`、计数天然隔离；会话可切换姿态 |
| P4.37-7 | 默认关，`--background-agents[=N]` 打开，缺省 N=4 | 新增并发写路径与更长的持锁时间，先实测 |
| P4.37-8 | 任务中心不加会话占用详情；IM 继续 `bg_store=None` | 不扩大本期范围；IM 只读、无确认 UI |
| P4.37-9 | 显示后台子 Agent 的工具进展（relay + host 事件观察者）；任务只显示行首 `【…】` 标签（A 方案），不显示原文 | 有进展才知道各组跑到哪；标签由派发方写，任务正文不上屏，守 P4.26 决策4 |

### 5.2 用例（`tests/test_web_bg_agents.py`，假工厂）

1. 开关关：构造参数里 `bg_store is None`，与现状一致。
2. 收尾屏障：假子任务 2 s 后写 `wiki/x.md`。断言 `_finalize_writable` 晚于该写，写日志含 `wiki/x.md`，撤销能还原它，写后 check 看得到它。
3. **派发后抛错**：主 Agent 派出子任务后 `arun` 抛异常。断言晚到的写仍进入本轮日志与 check，屏障结束前未释库写锁。
4. 停止：`arun` 已正常返回、屏障等待中 `request_stop()`。断言每个在飞任务都被 `cancel`，`close_owner` 未被调用；排空后 `turn()` 抛 `AgentCancelledError`，端点发 `stopped` 帧而非 `done`，帧内带本轮撤销 token 与写后检查结果；目标模式按暂停处理，`turns_used` 不加 1。
5. **停止超过 30 s**：一个任务忽略取消（测试中阈值缩短）。断言推出 `stopping: true` 帧；其间另一会话的可写轮与一个后台任务都拿不到库写锁；该任务结束后才关日志、生成撤销 token、释锁。
6. 写日志并发：多线程同时写同一 `wiki/` 路径，日志的首条写前字节等于起跑时的内容。
7. 写日志开关竞态：写线程持记账锁、停在「判断日志开启」之后时，另一线程调 `end_journal()`。断言 `end_journal()` 阻塞到该写记账完毕，取走的日志含这条写；`begin_journal()` 同理。
8. 只读轮：同样经过屏障。

### 5.3 真 agentao 契约用例（`tests/test_agentao_contract.py`，离线死端点）

### 5.4 实机验收

用样例库跑一次 5 组的审查任务，三组对照：开关关（串行）、N=4、N=6。

- 先核对：按预期表清单，每张 各组结果文件 都写出；没有一张表被主 Agent 与子 Agent 重复写；工作目录无临时文件。
- 再比较：总墙钟、各组起止时刻、N=4 时第 5 组的实际补派时点、模型服务限流报错数。
- 跑一次中途停止：确认 `bg_agents` 帧、停止提示、撤销结果，以及停止期间后台入库任务处于等锁状态。

## 6.1 已知限制（代码审查后记录，本期不处理）

1. **多个子 Agent 改同一个文件会丢改动。** 记账锁只保证撤销日志一致，不保证文件内容：编辑工具是「读→改→写回」，两个子 Agent 同时改同一页时后写的会盖掉先写的，不报错。彻底解决要在编辑工具层按路径加锁，超出本期范围。派发时让每个子 Agent 只写自己的文件（样例库的审查 skill 每组写各自的结果文件），不要让多个子 Agent 改同一页。
2. **停止按在 `arun` 最后一个检查点之后。** 本轮有后台子 Agent 时，屏障看到令牌已取消，会取消子 Agent，并按停止收尾（`stopped`）；本轮没有后台子 Agent 时，同样的停止照旧得到 `done`。前者有子 Agent 被中断，报停止是如实的。
3. **asyncio 取消（停服）后前台线程还会再跑一小段。** 取消 `await arun` 不会立即停掉它的工作线程；屏障会打本轮令牌，线程在下一个检查点停。屏障放行与线程真正停下之间若它又发起后台启动，这个窗口没有被封住。
4. **任务记录在一个会话内只增不减。** agentao 只清理更早代际的记录，Web 不调用 `start_new_conversation`（会清掉下一轮还要看的完成通知）。运行期轮询每秒扫一次本会话记录，常规规模下开销可以忽略。
5. **屏障自身出错时照常收尾。** 不收尾会让库写锁永不释放；收尾前先逐个取消子 Agent 并记 error 日志，但仍在跑的子 Agent 可能在锁外再写一小段。只在屏障代码本身抛异常（如 agentao 任务表接口变化）时发生。
6. **主 Agent 没取的完成通知不跨重启。** 任务表只在内存里。主 Agent 派出后没用 `check_background_agent` 取结果就收尾时，完成通知留在任务表的队列里，随下一条消息注入；Web 重启或会话懒恢复会新建任务表，这些通知随之丢失，模型不知道子 Agent 写了什么（文件本身已在盘上）。按 §2.7 让主 Agent 显式取结果可避免。
