# P4.35 — Web 撤回源

> **状态**：定稿（2026-11-23，经六轮评审），未实现。
> 范围：Web 首版支持单源撤回和按原件撤回全部分卷，均经预览、确认、执行，结果进入任务中心。
> 目标：误收录、已撤稿的源可以从摘要页撤回。单源撤回沿用 CLI 的计划和回收区留档，整批复用同一套撤回原语。
> `restore`、`--purge`、`--cascade` 仍属 P3.9 的后续项（决策P3.9-10）。

## 1. 现状

- `guanlan remove <源>`（P3.9）：零 LLM、人发起的宿主确定性写。默认预览，`--yes` 才执行；把 raw 文件、同级图片目录、摘要页移入
  `.trash/<slug>@<ts>/`，先写 `manifest.json`；多源页摘 slug、删 index 行；独源页与入链只提示。执行序「manifest 先写 → 摘 slug →
  删 index 行 → 最后移源」，每步幂等，中断后重跑向前收敛，不承诺回滚。移源一步内部也是 raw 最后移（图片目录 → 摘要页 → raw，PR #234 已合并），
  刚移走 raw 就中断时重跑不会漏掉分卷图片目录。
- Web 当前没有任何入口（`docs/P3.9-源撤回.md` §184：Web 侧「属 P4.x 机会性优化、单独评估」）。Web 能删的只有 `workspace/` 下的上传与解析中间物。
- 已有可复用件：
  - `run_remove_result(root, slug) -> RemovePlan`：纯函数、只读，当初就是为 Web 复用拆的（P3.9 §139）。
  - P4.34 §6.2 索引修复：「预览浮层 → 确认 → 进任务中心」的同类先例（`reindex` 任务类型）。
  - P4.33 任务中心：写锁排队、层③ 423、查重、上限、重启恢复、§4.6 残留进程写入阻止。

## 2. 关键冲突：前像回滚不适用于撤回

任务中心对每个写任务拍前像（P4.33 §4.3），取消或中断时按前像回滚。这套机制**不能直接套在撤回上**：

| 前像机制的假设 | 撤回的实际 |
|---|---|
| 范围是 `wiki/` + `SCHEMA.md` + `AGENTAO.md`，**不含 `raw/`** | 撤回的核心动作就是把 `raw/<slug>.md` 移走 |
| 回滚第 ⑤ 步：`raw/` 与前像快照不一致 → `rollback_failed` | 撤回执行到「移源」后，`raw/` 必然不一致 |
| 回滚把 wiki 恢复到任务开始前 | 摘要页、`sources`、index 行回来了，raw 却还在 `.trash/`——库处于「有摘要页、无原文」的不一致态 |

即：一个被取消或中断的撤回任务，按现有流程回滚**必然**记 `rollback_failed`，而且回滚到一半的状态比不回滚更糟。

可选做法：

- **A（推荐）：撤回任务不拍前像。** 只允许在开始前取消；执行中不可取消（只是移动几个文件、改几页 frontmatter，预计毫秒到秒级，取消窗口本来就很小；落地时在真实库实测）；中断后的处理是「重新预览并再提交一次」，
  即 CLI 的「重跑向前收敛」。撤销靠 `.trash/` + manifest 人工恢复，与 CLI 完全相同。
- B：把 `raw/` 纳入撤回任务的前像。要改 `preimage` 的范围与第 ⑤ 步判定，并让「回滚」第一次具备恢复 `raw/` 的能力——这违背
  P4.33 的设计（`raw/` 只核对不恢复，与写门禁 `raw_mutated` 判死一致），等于在 Web 里偷偷做了一个 `restore`，排除。
- C：不进任务中心，端点同步执行。拿不到写锁排队——撤回可能和在途 ingest 同写 `index.md`、同一页的 `sources`；也没有记录可查。排除。

本稿按 A 展开。

## 3. 方案

### 3.1 入口

- **摘要页**：浏览 `wiki/sources/*.md` 时，页头（`.page-meta`，与「在图中查看」同一行）加「撤回此源」按钮。分卷摘要页的浮层同时提供「撤回此卷」和「撤回原件的全部分卷」两种范围，默认此卷，切换范围后重新加载清单。只在可写部署出现（reader 判定沿用体检按钮）。
- 首版只此一个入口。体检「待入库」项（raw 已在、还没有摘要页——上传错了还没收录的情况）加「撤回」入口列为推后项（§8），因为那一栏的语义是「该收录」，
  在旁边放删除按钮容易误点，需要单独想交互。

### 3.2 预览

`GET /api/remove/preview?source=<源>&scope=one|all`（或 `?task=<撤回任务 id>`，见 §3.5），零 LLM、不写盘。先解析摘要页及真实 raw 路径，`one` 默认采用 CLI 的单源计划，`all` 按下述规则生成整批计划。两种范围都返回 `plan_digest`（§3.4）。

- **分卷身份**以目标 raw 所在目录与 frontmatter 的 `split.parent` 组成原件键。只枚举同目录且 `split.parent` 相同的 raw 分卷，按 `split.index` 排序。成员身份来自元数据，slug 及摘要页按每卷真实 raw 路径解析。所选源没有可核实的分卷元数据，或成员缺少有效序号、序号重复、摘要页身份冲突时，拒绝 `scope=all` 并说明原因。
- **导入冲突**：预览和锁内复核都检查 `workspace/tasks/` 中的未完成一键导入任务，状态集直接引用 `oneclick.ACTIVE_STATES`，不另写一份。通过已生成条目的目标 raw 路径判断是否为同一原件；拆分结果尚未生成时，用单份清单的 `sample` 或多份清单中的 `docs[].sample` 与原件键匹配。命中则拒绝整批撤回，预览返回 409 并提示先完成或放弃导入。暂停任务续跑会跳过已标为 `written` 的卷，也可能继续写尚未落盘的卷。
- **整批影响面**：先得到整批的待移动路径集合（raw、图片目录、摘要页），再扫一次衍生页、index 和入链。排除同批待移动的摘要页。保留页的 `sources` 按下面两步处理（仅 `scope=all`）：
  1. **找失效引用**：用同一份「路径 ↔ 源身份」关系分别算撤回前、撤回后能否解析。撤回前能解析、撤回后解析不到的 slug，就是因本批移动而失效的引用——不论它是不是字面上的批内 slug。撤回前就解析不到的悬空引用不是本批造成的，不算、也不动。
  2. **看剩余来源**：有失效引用的页，若还有撤回后仍能解析的来源，一次摘净全部失效引用；没有则列入 `orphans`、原样保留并告警。
  入链只报告批外保留页到待移动摘要页的链接，批内摘要页互链不报警。index 只列实际要删的登记行。
- **路径 ↔ 源身份关系**：预览时扫一遍 `raw/`，经 `rawio.source_identity_keys` 得每份 raw 的全部身份键，再并上 `wiki/sources/` 现存摘要页的名字；重开预览时，经 §3.5 核实后复用的旧身份也并入。撤回前用全部条目，撤回后去掉 `relocate` 里的路径。按源身份认，不按同名文件是否存在认；只看当前盘面与信封，不读 `.trash/`。
  同一份 raw 可以有两个身份键：旧名摘要页 `re-sume` 存在时，`source_identity_keys` 对这份 raw 同时返回 `re-sume` 与 `résumé`。这份 raw 在本批时，`re-sume` 与 `résumé` 都是失效引用：`[résumé]` 列为失源告警；`[re-sume, résumé]` 列为失源；`[re-sume, résumé, C]` 两个一起摘掉、只剩 `[C]`。
  旧名摘要页已归档、raw 仍在时，盘面上已认不出 `re-sume` 指向这份 raw；若不把复用的旧身份并入「撤回前」，`re-sume` 会被当成原本就悬空而漏摘，所以重开预览必须并入。
  例：A、B 同批，A 已在上一轮移走、B 待撤，保留页 `sources: [A, B]` 的批外来源 A 已无效，列为失源、原样保留，不会摘成只剩 `[A]`。
  `scope=one` 不用这条，继续与 CLI 口径逐项一致（只按「是否只剩本源」分多源页与独源页）。因此单源撤回 `re-sume` 时，上面那页仍会按 CLI 摘成 `[résumé]`——这是 P3.9 的既有问题，记为 P3.9 待修项，另行处理：届时用同一套「撤回前后能否解析」规则修 CLI，Web 单源随之一致，P4.35 不单独偏离 CLI。

浮层逐项列出（不截断——撤回是低频操作，清单通常很短）：

- **将移入回收区**：`relocate`，整批按卷分组并显示原件及卷数
- **将从这些页的 sources 中移除的来源**（正文不改）：`drop_slug`，每项显示将摘的 slug 和剩余源数
- **将删除的 index 行**：`index_lines`
- ⚠ **撤回后失去有效来源的保留页**（页面保留原样）：`orphans`
- ⚠ **撤回后会出现悬链的保留页**：`backlinks`
- 旧名页提示（`requested != slug`，#203）

确认按钮文案：「撤回（开始执行前可取消；完成后没有撤销，可从 .trash/ 手动找回）」。没有二次输入 slug 之类的额外确认——预览本身就是确认面，与 CLI 默认预览同级。

错误：解析不出 slug、raw 下同名多份、范围参数非法或无法可靠识别分卷组 → 400；源不存在 → 404；同原件导入未完成 → 409。

### 3.3 执行

`POST /api/remove {source, scope, plan_digest}`（或 `{from_task, scope: "all", plan_digest}`，见 §3.5）→ 任务类型 `remove`，走 `_submit_task`（层③ 423、查重、上限、写锁排队、§4.6 写入阻止、重启恢复），撤回作业直接执行，无前像。

**信封必须建成才入队。** `_submit_task` 现有的降级（任务存储不可用或建信封抛 `OSError` 时 `task_id = None`、作业照跑）对 `remove` 不适用：整批重开依赖信封里的原件身份，没有信封还意味着不查重、运行中拿不到 409 的取消保护。两种范围都一样——任务存储不可用或信封落盘失败 → 503，作业不入队，库与 `.trash/` 零改动。

作业取得写锁后：

1. 在同一把写锁里复查导入冲突、重算整份计划和内容摘要。任何成员检查失败或整份摘要不匹配，作业以 `EXIT_USAGE` 结束，库和回收区零写入。摘要不匹配时回执「预览之后库有变化，没有执行任何改动，请重新预览」。
2. 核对通过后先写 manifest，再按计划一次摘净每页的批内来源并删除相关 index 行。单源沿用 CLI 的 `.trash/<slug>@<ts>/`；整批每次执行只建一个 `.trash/<sample>@<ts>/`、写一份 manifest（§3.6）。
   `<sample>` 取这批 raw 实际所在目录 `raw/<sample>/` 的目录名（盘上已存在的单级目录名，命名规则同导入落盘），**不用** frontmatter 的 `split.parent`——那是可手改的文本，只用于判定成员、不进入任何路径。建目录前再校验：名字是单个路径成分，`resolve` 后仍在 `.trash/` 之内，否则拒绝执行。
3. 逐卷移入同一个回收目录（`_move_into_trash` 保留库内相对路径，`raw/<sample>/…` 与 `wiki/sources/…` 可同处一目录），每卷依序移动图片目录、摘要页、raw。全程沿用已核对的计划，不在卷与卷之间重算或逐卷比较摘要（同一把写锁内盘面不变）。单源回执沿用 CLI 文案，整批回执列出已处理卷和回收目录。
4. 完工回调按写 wiki/ 处理（bump 代际），已打开的页面、图谱据此刷新。

### 3.4 为什么执行前要核对预览（与 reindex 不同）

reindex 执行时重算、不核对（P4.34 D13）：它只做加法与删悬空行，排队期间库变了，按新状态做反而更对。撤回是删除性操作，用户确认的是**具体清单**：
排在一个长时间 ingest 后面时，ingest 可能新建了引用本源的页（`drop_slug` / `orphans` 变长），用户没看过这些就不该被改。

- `plan_digest` 为规范 JSON 的 SHA-256。`scope=one`：范围、撤回计划的全部字段（含 `orphans` 与 `backlinks`），以及每个 `relocate` 文件的相对路径和内容 SHA-256。`scope=all`：只含与入口无关的内容——范围、原件键、有序成员（raw 路径、源身份、raw sha256）、`relocate` 及文件哈希、`drop_slug`、`orphans`、`index_lines`、`backlinks`；`slug`、`requested`、任务 id 只在展示与追踪层，不进摘要。目录以按相对路径排序的递归文件哈希清单表示。JSON 键排序，计划列表按稳定顺序生成。
- 因此实际操作和影响面相同时，从 A 卷、B 卷或任务入口预览得到同一个摘要，提交合并为一个在途任务。任务入口若复用了旧身份、多出旧名引用的摘除，清单已经不同，摘要随之不同。
- 单源与整批都核对内容。同名 raw 被覆盖、摘要页被换成新内容、图片目录的文件增删或改写，均使旧确认失效。读取失败或计算时发现清单变化，返回重新预览原因，待锁内重新核对通过才可写。
- 摘要只用于「是否同一份清单」，不防篡改（提交者本来就能直接提交新预览的摘要）。

### 3.5 取消、中断、重试

| 阶段 | 处理 |
|---|---|
| `queued` / `waiting_lock` | 照常取消（P4.33 §4.4 第一行），库未改动 |
| `running` | **不可取消**，取消端点返回 409「撤回执行中，不能取消；完成后可从 .trash/ 找回」。前端对 `remove` 任务在运行态不显示取消按钮 |
| 服务在执行中退出 | 重启恢复记 `interrupted`（无前像分支），但错误文案按 kind 改写：「撤回执行中服务退出，可能已部分执行。重新预览并提交一次即可完成剩余步骤；回收区 `.trash/<slug>@…/`（整批为 `.trash/<sample>@…/`）里可能已有本次的 manifest。」不给「回滚 / 保留现状」按钮 |
| 重试 | 任务中心按任务信封里的范围和原件身份（§4）打开预览浮层，用户确认后提交新任务。直接调用 `POST /api/tasks/{id}/retry` 对任一范围的 `remove` 一律返回 409「请重新预览」，不生成新任务。判定顺序：信封不存在 404 → `remove` 409 → 层③ 423 → 其余状态与参数校验。`remove` 的重试无论何时都不会生成任务，先说「请重新预览」比先让用户等层③ 释放更直接；之后重新预览再提交时照常受 423 约束 |

**整批中断后重开**：`scope=all` 的任务信封保存原件键（raw 目录 + `split.parent`）和提交时核实过的成员，每个成员记 raw 路径、源身份与 raw 的 sha256。

- **请求形状**：任务中心用 `GET /api/remove/preview?task=<id>` 预览、`POST /api/remove {from_task, scope: "all", plan_digest}` 提交，与 `source` 二选一，只接受 `scope=all` 的撤回任务。服务端两次都从旧信封读原件键，锁内复核同样走这条路径；新任务信封记 `retry_of` 并沿用同一原件键。原发起卷整卷移走后，`source` 已无法表达这个原件，`task` / `from_task` 是唯一入口。
- **两个入口的等价**：用 `source` 发起 `scope=all` 时，先查同一原件有没有**待续的撤回任务**；有则返回 409 并附该任务 id，前端改走任务入口。这样旧身份只有任务入口一条读取路径，两个入口不会给出不同清单；没有待续任务时两个入口都只看盘面，结果天然一致。
  **待续任务**须同时满足：① `scope=all`、状态为 `interrupted` 或 `failed`；② 信封带 `remove_writes_began`（见下）；③ 按当前盘面仍有待处理成员；④ 信封没有 `superseded_by`。多条符合时取 `remove_writes_began` 最晚的一条。`task` / `from_task` 引用旧任务时核对同一组资格，不符合返回 409 并说明原因（如「该任务未进入执行，请从摘要页重新发起」），免得直接引用旧任务绕过入口筛选。
  - **`remove_writes_began`**：撤回专用的持久化标记（时间戳）。锁内复核（导入冲突、成员、摘要）全部通过、写第一份 manifest 之前落盘；落盘失败则不写库、作业失败退出。不复用任务中心的 `started`——它在作业进入 `running` 时就写（`web/tasks.py` `on_start`），那时锁内复核还没跑，摘要失配、导入冲突等零写入的失败也会带上它。
  - **`supersedes`**：与 `remove_writes_began` 同一次落盘，记下本次执行将覆盖的旧任务 id——同一原件、此刻符合待续资格 ①②③④ 的全部旧记录。名单在写锁内、移动文件之前确定：这时旧任务的剩余成员还在盘上，③ 才判得准。
  - **`superseded_by`**：整批撤回成功完成时，按本任务信封里的 `supersedes` 名单，在这些旧记录上写 `superseded_by: <新任务 id>`。**不在成功后重新按 ③ 筛**——正常成功时本批成员已移空，③ 恰好不成立，会漏写；之后同一原件重新导入，旧失败记录又满足 ③，会重新触发 409 引导。资格靠旧记录自身的标记判断，不靠查找成功记录：历史清理（`_prune_locked`）可能先清掉成功那条。写标记失败只影响引导、不影响库，记一行日志；本任务若中断，`supersedes` 留在信封里，下一次续跑成功时一并补写。
- **成员**：一律按原件键从**当前盘面**枚举，保存的成员列表不作执行清单，只用于显示「已完成 k 卷、剩 m 卷」；盘面上出现提交时没有的同原件新卷，进入新预览，由新的确认与摘要把关。剩余成员为空时，提示本批已无剩余文件可撤回。
- **身份**：默认用当前归属，区分明确认领与待核实线索。`locate_source_page` 按文件名命中就立即返回，看不到同时存在的改名认领页，不能用来判断「唯一」；P4.35 新增一个**不提前返回**的收集函数，列出这份 raw 的全部明确认领：文件名命中、`raw_digest`、单篇原始资料声明、多篇原始资料声明（含本篇）。
  - **恰好一张认领页**：按当前归属生成清单，这张页就是该卷的摘要页，一并移走，不复用旧身份。
  - **共享摘要页**（一张页认领了多份 raw）：所认领的 raw 全在本批 → 随本批移走，清单注明它对应多卷；同时认领了批外 raw → 阻止整批撤回（预览 409），列出该页与依据。移走它会让批外资料失去摘要页，留着又会多一条指向已撤回原文的声明，都需要人判断。口径与 P3.9 续跑保护把多篇声明算作认领一致（PR #235）。
  - **两张及以上认领页**（包括同名页与改名页同时认领）：归属无法确定，暂停整批撤回——预览返回 409，列出这些页及各自依据（文件名 / `raw_digest` / 原始资料声明），请人先处理。只停用旧身份仍可能移走 raw、留下认领页，所以不能只停用。
  - **只在正文提到路径**的候选是待核实线索，在预览里单列提示，不算认领、不阻止撤回。
  - **没有任何认领页**时，才考虑复用信封里该成员的 `raw 路径 → 源身份`，且须同时满足：① 旧名摘要页已归档；② 该路径上 raw 的 sha256 与信封记录一致。P3.9 `_pending_legacy_raw` 的续跑保护用同一判据（PR #235）。
- **失源判断**：按 §3.2 的两步规则；复用的旧身份并入「撤回前」。

两个断点的预期不同：来源编辑做到一半中断，重开预览仍列出未摘的页；来源与 index 都已改完、尚未移卷时中断，重开预览只剩移动。

每次执行各建一个回收目录，前一次的 manifest 继续留档，回执提示保留前后两次回收记录。

### 3.6 整批 manifest

一次整批执行写一份 `manifest.json`，字段与 CLI manifest 同名同义，另加批信息：

- `group`：原件键、回收目录所用的 raw 目录名，以及按 `split.index` 排序的成员（raw 路径、本次确认的全部身份键 `identity_keys`——含复用的旧身份、摘要页、raw sha256）。共享摘要页在 `group.shared_pages` 里单列：页路径及其认领的全部本批 raw。
- `moved`：**计划**移动的文件。与 CLI 相同，manifest 先于移动落盘，中断时可能只移了一部分；人工恢复以回收目录里实际存在的文件为准。不改字段名，免得将来 `restore` 要认两种格式。
- `slug_dropped_from`：沿用 CLI 的条目格式 `{page, dropped_slug, before_sources}`，另加 `resolved_to`：这条引用**撤回前解析到的落点**，`{page?: 摘要页路径, raws: [raw 路径, …]}`。
  - 引用经源身份解析到某份 raw（如双身份的 `re-sume` 与 `résumé`）：`{raws: [该 raw]}`，同一卷的多个身份键各成一条、`raws` 相同。
  - 引用解析到摘要页：`{page, raws: [该页认领的全部 raw]}`。共享摘要页 `S` 认领本批 A、B 时，保留页 `[S, C]` 摘掉 `S` 的条目记 `{page: wiki/sources/S.md, raws: [A, B]}`，不随便归给其中一卷。
  一页摘了几个 slug 就写几条，`before_sources` 都记这次编辑前的完整列表。恢复时按 `resolved_to` 回补：单卷恢复回补 `raws` 只含该卷的条目；`raws` 含多卷的条目（共享摘要页）须相关各卷与该页都恢复后才回补，由恢复方判断。`resolved_to` 是新增字段，CLI 单源条目不变，将来 `restore` 只需认一种格式（多出的字段可忽略）。
- `orphaned`、`backlinks`、`index_lines_removed`：同 CLI。

manifest 只用于留档与人工恢复，不是重开预览的输入（§3.5）。

## 4. 接口

| 端点 | 说明 | reader |
|---|---|---|
| `GET /api/remove/preview?source=&scope=one\|all` 或 `?task=<id>` | 预览（`task` 只接受 `scope=all` 的撤回任务，与 `source` 二选一），返回 `{ok, slug, requested, scope, relocate, drop_slug, orphans, index_lines, backlinks, plan_digest}`；`all` 另含 `group`（raw 目录、parent、按 index 排序的成员及各卷移动路径） | 不注册 |
| `POST /api/remove` `{source, scope, plan_digest}` 或 `{from_task, scope: "all", plan_digest}` | 提交任务，返回 `{job_id, task_id}` / 查重时 `{deduplicated: true}`；任务存储不可用或信封落盘失败 → 503 | 不注册 |

- 预览端点 reader 下也不注册：它暴露的是「撤回会动哪些文件」，只对能撤回的部署有意义；reader 已有页面浏览与 lint 能看到同样的信息。
- 任务参数为 `{source: <规范化后的 slug>, scope: "one" | "all", plan_digest}`，`scope=one` 按这三者查重；`scope=all` 的查重键见下条。同一源的单卷和整批是不同任务。
- `scope=all` 的信封另存 `group`：原件键与提交时核实的成员（raw 路径、源身份、raw sha256），供任务中心重开预览（§3.5）。`scope=all` 的查重键为「原件键 + scope + plan_digest」，`source` 不同但指向同一原件、同一清单的提交合并；`from_task` 提交同样按此查重。

## 5. 代码改动

- `remove.py`：抽出单源与整批共用的计划、来源编辑、manifest 和移源原语，提供接收库根和计划的摘要计算与执行入口。执行入口复用 P3.9 的 raw 最后移动顺序；整批的有效来源判断用 `rawio.source_identity_keys` 建身份表（扣掉待移动路径）；整批回收目录名取 raw 目录名并做越界校验。CLI 保持当前参数和输出契约。
- `web/app.py`：`RemoveBody`、`_TASK_BODIES["remove"]`、`_task_spec` 分支和两个端点；`_submit_task` 为撤回选择无前像流程，且对 `remove` 关掉「建不成信封照跑」的降级（→ 503）；`task` / `from_task` 两种请求形状；`task_retry` 在信封 404 之后、层③ 423 之前对 `remove` 返回 409。
- `web/tasks.py`：`TASK_KINDS` 加 `remove`；新增 `NO_PREIMAGE_KINDS = ("remove",)`：运行态取消 → 409；重启恢复的无前像分支按 kind 选文案。
  这是给任务中心的统一流程加一个分支——P4.34 §6.2 评审里「轻量前像要改统一流程，等真遇到再说」，撤回就是那个真遇到的情况，但这里只做「不拍」，不做「轻量拍」。
- 前端：`wiki.js` 页头按钮；新预览浮层（参考 `openReindexPreview`），支持切换单卷及原件范围；`tasks.js` 对 `remove` 隐藏运行态取消、用原范围打开重试预览；i18n 中英文案。

## 6. 能力上限与失效规则

- **撤销**：Web 不提供。与 CLI 相同，靠 `.trash/` + manifest 人工恢复；自动 `restore` 是 P3.9 后续项，落地后 Web 再接。
- **失源页正文**：有剩余来源的页只摘 `sources`；撤回后失去全部来源的页原样保留。回执提示通过 ingest 或审计复核正文。
- **与 CLI 并发**：CLI `remove --yes` 经 `cli.run_locked` 取库级锁（`kblock.needs_kb_lock`），Web 写作业持同一把锁，两者互斥；CLI 预览不取锁，可随时运行。
  （P4.34 §6.2 记的「CLI `reindex` 不取锁」已过时：`needs_kb_lock` 现在对非 `--dry-run` 的 `reindex` 同样取锁。）
- **排在撤回之后的同源 ingest**：raw 已移走，ingest 在目标解析处以 `EXIT_USAGE` 失败，任务中心可见。不做跨任务联动取消。
- **执行函数中途 IO 失败**：作业以非零码结束，回执写明「可能已部分执行」，处理同 §3.5 的中断。
- **失效规则**：影响范围、来源归属、移动路径或内容核对规则变更时，同步检查 §3.4 的摘要输入。任务中心的前像若覆盖 `raw/`，重评 §2。

## 7. 决策（草案）

| # | 决策 | 理由 |
|---|---|---|
| D1 | 进任务中心，但不拍前像；运行中不可取消 | 前像不含 `raw/`，回滚撤回必然 `rollback_failed` 且留下更糟的半态（§2）；撤回只做少量文件移动与 frontmatter 改写，取消窗口很小 |
| D2 | 执行前核对预览摘要，不一致不执行 | 删除性操作，用户确认的是具体清单；排队期间库可能变化（§3.4）。与 reindex D13 的取舍相反 |
| D3 | 撤回任务重试须重新预览，通用重试接口返回 409 | 让前后端统一要求重新确认，避免提交携带过期摘要的任务 |
| D4 | 首版只在摘要页提供入口 | 「待入库」旁放删除按钮易误点，交互另议 |
| D5 | 不写 `log.md`、不过写门禁 | 与 CLI 一致（P3.9：manifest 即审计轨迹；人发起的宿主写） |
| D6 | 预览与执行端点 reader 下都不注册 | 沿用决策P4.9-2 |
| D7 | 首版支持按原件撤回全部分卷 | 一键导入可能生成许多卷，误导入时用一份整批清单确认；同原件未完成的导入会阻止整批撤回 |
| D8 | 整批失源按有效来源判断，只看当前盘面 | 中断后重开时已移走的批内卷不能算批外来源；不读 `.trash/`，单源不用此规则 |
| D9 | 整批每次执行一个回收目录、一份 manifest | 统一记录一次跨卷编辑，中断后不留下逐卷的空回收目录 |
| D10 | 任务信封保存原件键与成员，重开按盘面复核；任务中心经 `task` / `from_task` 引用旧任务 | 旧名摘要页先移走后旧 slug 未必能定位 raw；原发起卷整卷移走后 `source` 无法表达原件 |
| D11 | `remove` 必须信封建成才入队，否则 503 | 整批重开、查重、运行中取消保护都依赖信封；不沿用 `_submit_task` 的降级 |
| D12 | 保存的身份只在「无任何归属页 ∧ 旧名页已归档 ∧ raw 未变」时复用 | 成员看盘面、身份默认看当前归属；与 P3.9 `_pending_legacy_raw` 同一判据（PR #235） |
| D13 | 有效来源按「扣掉整批待移动路径后能否解析」判；P3.9 单源的同类问题另修 CLI | 同一 raw 有两个身份键时，按「现在能否解析」会把同卷另一个名字当成批外来源 |
| D14 | 整批回收目录名取 raw 目录名，不用 frontmatter 的 `split.parent` | frontmatter 可手改；路径须是单个成分且在 `.trash/` 内 |
| D15 | 整批失源按撤回前后能否解析找失效引用，再看剩余来源；复用的旧身份并入撤回前 | 同一 raw 的另一个身份键不是字面上的批内 slug，按交集判会漏掉 |
| D16 | 归属按 `locate_source_page` 分三档：唯一归属按当前归属，多张归属暂停整批，仅提及只提示 | 只按文件名认不出改名页；把仅提及也叫冲突会误导人 |
| D17 | 摘要页入口遇到待续撤回任务返回 409 转任务入口；待续 = 进入过执行 ∧ 仍有待处理成员 ∧ 未被后续成功覆盖，多条取最晚 | 旧身份只在信封里，两个入口须走同一读取路径；零写入的失败不该拦人 |
| D18 | `scope=all` 的摘要不含 `slug`、`requested`、任务 id | 同一批从不同入口进入须得到同一摘要，才能合并成一个任务 |
| D19 | 归属用不提前返回的收集函数判唯一；共享摘要页全在本批则随批移走，含批外 raw 则阻止整批 | `locate_source_page` 文件名命中即返回，看不到同时存在的改名认领页 |
| D20 | 待续用专用标记 `remove_writes_began`（锁内复核通过、首写前落盘）与 `superseded_by`；`task` / `from_task` 核对同一资格；覆盖名单 `supersedes` 在移动前确定、成功后按名单写标记 | 任务中心的 `started` 在复核前就写；成功记录可能被历史清理；成功后成员已移空，重新按「仍有待处理成员」筛会漏写 |
| D21 | 整批 manifest 成员记 `identity_keys`、共享摘要页单列，摘除条目加 `resolved_to`（撤回前解析到的摘要页与 raw 列表） | 双身份同时摘除、引用指向共享摘要页时，恢复须知道引用属于哪一卷或哪几卷 |

## 8. 推后 / 非目标

## 10. 测试要点

- 单源预览的既有计划字段与 CLI `remove --json` 逐项一致；旧名页、分卷 `raw/<sample>/<slug>.md`、raw 同名多份（400）、不存在（404）。
- 单源执行后比较 CLI `remove --yes` 的盘面，核对 `.trash/` 结构与 manifest、多源页 `sources`、index、空分卷目录清理。
- 分卷按目录、`split.parent` 和 `split.index` 识别。文件名形似但元数据不同者不进入本批。
- 撤回 A、B 时，保留页 `sources: [A, B]` 列为失去有效来源并保持原样，`[A, B, C]` 一次摘掉 A、B。A、B 的摘要页互链无告警，批外页面指向任一摘要页的链接有告警。
- 预览后修改批内靠后的卷，锁内核对失败，以 `EXIT_USAGE` 结束。逐项比对所有卷、wiki 和 index，确认文件零改动、`.trash/` 无新增。
- 单源及整批都测试同路径换 raw 内容、换摘要页内容或改图片文件，旧摘要失效并要求重新确认。
- 同原件导入未完成时预览返回 409。预览后、撤回取锁前出现同原件的未完成导入时，作业退出且零写入。覆盖暂停续跑、多原件清单和无关原件的情况。
- 中断后从任务中心重开预览并提交，剩余卷全部撤回，已移卷不重复归档。覆盖：发起卷摘要已移但 raw 尚在；raw 刚移走就中断；旧名摘要页已归档；发起卷已被另一轮执行整卷移走、仍有其他卷待撤；从非发起卷的摘要页发起 `scope=all` 得到同一份清单。
- 有效来源：A 已移走、B 待撤时 `sources: [A, B]` 列为失源并原样保留；批外来源是旧名页的、不在本批的 raw 时仍算有效；`scope=one` 对同一盘面的结果与 CLI 一致。
- 同一 raw 两个身份键（整批）：`[résumé]` 列为失源告警；`[re-sume, résumé]` 列为失源；`[re-sume, résumé, C]` 摘成 `[C]`；原本就悬空的引用原样保留。单源时 `[re-sume, résumé]` 按 CLI 现状摘成 `[résumé]`（先断言现状，P3.9 修复后翻转）。
- 重开时旧名页已归档、raw 仍在：复用的旧身份并入撤回前，`[re-sume, X]` 摘掉 `re-sume`，不当成原本悬空而漏摘。
- 任务中心重开全链路：`?task=` 预览 → `from_task` 提交 → 锁内复核 → 执行。覆盖发起卷已整卷移走；旧名页已归档且 raw 未变（复用身份）；raw 内容已变（不复用）；`task` 指向单源任务或非撤回任务 → 400。
- 归属：任意改名页经 `raw_digest` 认领 → 按当前归属，该页随卷移走；同名页与改名页同时认领 → 预览 409 列出两页与依据、零写入；只在正文提到路径的页 → 单列提示、照常撤回；共享摘要页只认领本批卷 → 随批移走并注明多卷；共享摘要页同时认领批外 raw → 409 列出依据。
- 入口等价与待续资格：有待续任务时用 `source` 发起返回 409 与任务 id，改走任务入口后清单与直接从任务进入一致。摘要失配零写入的失败任务没有 `remove_writes_began`，不触发引导，`task=` / `from_task` 引用它返回 409；`remove_writes_began` 落盘失败时作业不写库；多条待续任务时取 `remove_writes_began` 最晚的一条。
- 覆盖标记：中断 → 续跑成功后，旧记录按 `supersedes` 名单带上 `superseded_by`；「恢复成功 → 清理成功记录 → 同原件重新导入 → 新预览」不再被旧任务拦截；续跑任务本身又中断时，`supersedes` 留在信封里，下一次成功时补写。
- 摘要与查重：A 卷、B 卷、任务入口在操作与影响面相同时得到同一摘要，三次提交只产生一个任务；任务入口复用旧身份多出摘除时摘要不同。
- 信封必须建成：建信封抛 `OSError`、任务存储为 None 两种情况均 503，作业不入队，库与 `.trash/` 零改动。
- 回收目录名：手改 raw 的 `split.parent` 为 `../x` 或含 `/` 的值，整批回收目录仍按 raw 目录名建在 `.trash/` 内；目录名校验不过时拒绝执行、零写入。
