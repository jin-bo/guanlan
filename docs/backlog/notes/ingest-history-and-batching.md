# 入库性能：历史携带成本与下一轮实验

日期：2026-10-18。承接[已有对照](ingest-performance-research.md)和[下一步方案](ingest-next-optimizations.md)。本次只读既有实验日志、核对当前代码及 Agentao 0.5.14、查官方文档；没有调用模型、修改知识库或调整默认配置。

## 结论

候选方向有两个：**同主题短资料的小批摄入**，以及**运行时稳定上下文的组织方式**。前者尝试减少重复综合与登记，后者尝试改善缓存复用。二者均未实测提速，不能给收益承诺。

同日补做的零模型盈亏核算（见〈方向二〉）显示，小批摄入的门槛很高：放进同一会话依次处理，总输入约为独立两篇的 1.6 倍；共同摄入要打平，请求数须比两篇之和少 26%–42%，且几乎必然触发上下文压缩。因此小批不宜直接做模型实验。稳定上下文一线需要改 Agentao 运行时，归 Agentao 侧的修订，发版后再测。

单篇需要立即加速时，已有 `high/low` 对照仍是最直接的证据：low 耗时均值从 6m22s 降至 3m54s，但区间重叠，且有一次覆盖偏窄；保留为用户侧选项，不改默认。不要再把 index 登记、首包附资料、入库检索接入、换一种收尾措辞作为主要优化项；前三项的零模型评估均显示收益上限小，见调研笔记〈index 登记交给 wrapper 的收益上限〉〈短资料首包附 raw 与 SCHEMA 的收益上限〉〈入库检索接入的召回评估〉。

## 本次新增测量

复用上一轮同一篇 E 资料的 12 次真实模型运行：收尾措辞对照 6 次，推理档位对照 6 次。它们是重复样本，**不是跨资料泛化评估，也不是本次新方案的对照实验**。

其中 high2、low2、low3 已触发 Agentao microcompaction，排除出连续历史估算；余下 **9 次、309 个请求**可分析。新增只读脚本 [`scripts/analyze_ingest_history.py`](../../../scripts/analyze_ingest_history.py)，输出聚合计数，不输出正文或资料路径。

复现方式：

```sh
.venv/bin/python scripts/analyze_ingest_history.py <一次完整运行的agentao.log> [...]
```

脚本针对 Agentao 0.5.14 的秒级时间格式、增量消息日志与单次无压缩运行；检测到压缩、自愈、多次运行或不适用格式时拒绝估算。实验日志在本机临时目录，不纳入仓库；需要这些原始日志才能复现下表，脚本本身不产生新模型实验。

### 请求区间占满主循环

按日志的 `LLM REQUEST` 到对应 `LLM RESPONSE` 为请求区间，前一个 RESPONSE 到后一个 REQUEST 为请求间隔，9 次请求区间占比 **99.6%–100%，中位 99.7%**。

这不是“纯模型计算占比”：区间含请求日志、序列化、网络、服务排队、prefill 和生成。日志只有秒级精度，亚秒工具开销无法可靠拆分；也不包括首请求前的启动、Web 排队和门禁。它支持的结论只是：**这些样本中，文件工具执行本身不是主循环的主要时长来源**。把文件读写改为真正并行，不等于会获得明显端到端收益。

### 历史里最多的是读取结果，其次是写入参数

口径：初始任务和 system 按出现请求数累计；每个工具结果按其首次出现在请求日志起、到最后一次请求的次数累计；响应中的工具参数按剩余请求数累计。每次临时追加的 skills/todos/recall 尾部只算当次，**不当成每轮重复累积的持久消息**。

下表为“字符 × 携带请求次数”的构成，分母仅含列出的字段。不含 assistant 普通文本、历史 reasoning、工具 schema、协议字段与 tokenizer 差异，**不是实际 token/费用占比，更不是可节省时延**。

| 字段 | 中位占比 | 9 次范围 |
|---|---:|---:|
| 文件读取结果 | 52.4% | 47.9%–54.5% |
| `write_file` / `replace` 参数 | 15.0% | 12.1%–16.6% |
| system 文本 | 14.5% | 13.9%–17.1% |
| skills/todos/recall 临时尾部 | 9.6% | 9.2%–11.2% |
| 其他工具结果 | 4.0% | 1.6%–11.8% |
| 其他工具参数 | 2.6% | 1.6%–3.2% |
| 初始任务 | 1.9% | 1.8%–2.3% |

读取结果再按内容拆分，以同一分母计：既有内容页中位 16.9%，raw 13.7%，SCHEMA/conventions 12.5%，overview 4.6%，index 3.9%。各项单独取中位，不能要求加和恰好等于总中位数。

两条有用的反证：

- **把 `replace` 换成“行号 + hash”并不一定值得。** 所有 `replace.old_text` 累计仅占上述字段的 0.6%–1.6%，中位 1.0%。写入参数主要是必须生成的新内容，不能把整个 15% 当成可消除的重复旧文。多补丁工具若有价值，应证明它减少了请求往返；replace 有多少已与其他调用同轮发出，需先从日志核实。
- **提前触发通用压缩不能直接算收益。** 12 次中已有 3 次触发 microcompaction。当前实现超过有效窗口 55% 才尝试缩短旧工具结果、最近 5 个结果保留全文、其他长结果保留约 3,000 字符；完整摘要阈值为 80%。这些是容量保护，不是针对入库的最优策略。提前压缩会丢失旧论断与修改锚点，也会改写缓存前缀并可能引起重读，需独立对照。3 次压缩都发生在 prompt 约 106k–110k tokens、第 28–34 次请求之后；其中一次压缩截掉了 raw 中段，模型随后发现并补读。

## 方向一：稳定上下文与重复任务

代码核对发现一个此前未单独拆出的重复：Agentao `cli/run.py` 激活 skill 时把整个 `spec.prompt` 作为 `task_description`，`skills/manager.py:get_skills_context` 又将它写进 `Task:`；`prompts/builder.py` 每次在请求尾部追加激活的 skill 内容。

因此，wrapper 的任务（包括注入的页面名录）既在初始 user 消息里，又在动态尾部的 `Task:` 里。high1 首请求去掉日期提醒后的任务为 2,505 字符，完整尾部 12,757 字符，前者逐字包含于后者。high1 用的是 #106 之前的 skill；#106 把 heal/audit 移入 `references/` 后，同一尾部实测降到 9,998 字符，任务在尾部中的占比相应升高。这个重复在小名录样本里不大；非 source 名录很大时会同比放大，不能沿用本次百分比预测。

以下两个实验都要改 Agentao 运行时，归 Agentao 侧修订；GuanLan 侧等其发版后，按本节口径重测：

1. **去除重复长任务**：激活 skill 只给简短任务描述，完整 prompt 继续保留在用户消息。需要运行时接缝；GuanLan 当前通过 CLI spec 的 `skills` 列表激活，没有独立的 skill-task 参数。不能直接把原任务删掉或用未经说明的环境变量代替。
2. **把固定 skill 规则放到历史前面**：ingest 开始即固定激活一个本地 skill，可实验将其不变正文放在稳定前部；任务描述、todos、recall 留在动态尾部。保留指令来源和角色，不能擅自提升成 system。需上游支持固定任务场景，并保留中途激活/撤销 skill 的现有契约。

当前尾部放在历史之后，新请求在此前尾部所在位置变成 assistant 历史，完整 skill 会再次落到新后缀。前移稳定正文有机会延长可复用前缀，但收益取决于提供方缓存行为；**不能说目前完全没有缓存**。DeepSeek 官方说明按前缀匹配、尽力缓存，并提供 hit/miss token 计数；缓存只影响输入处理，生成仍然执行。[官方 Context Caching 文档](https://api-docs.deepseek.com/guides/kv_cache/)（2026-10-18 核对）

这条线先做不调用模型的请求构造比较，确认最早差异位置、固定规则体积与没有丢规则；再在独立库副本上做重复模型对照，记录实际 cache hit/miss、首 token、生成时间和质量。当前普通 `agentao.log` 只记录 prompt/completion/total，无法从本次日志算缓存收益，也不能用输入减少量直接折算时长。

## 方向二：同主题短资料小批摄入

单篇成本主要处于请求区间；小批的目标应是**共享语义工作**：相关资料读一次共同既有页，合并一次正文，批量更新 index/log，最后综合一次 overview。只把几个独立 ingest 串在同一进程里，省掉几秒启动与门禁，预期收益有限；让单个会话机械连续完成若干篇还可能因历史增长更慢。

### 盈亏核算（零模型，只读日志）

用上文 9 次无压缩运行的逐请求 prompt tokens 估算两篇资料的三种做法，9 次两两组合共 72 对。同一篇资料的重复运行代替两篇不同资料，只能给量级。

- **独立两篇**：两次运行的总输入之和，作为基准。
- **同会话依次**：第二篇的每次请求，多带第一篇结束时的历史（末次 prompt 减首次 prompt）。
- **共同摄入**：一次会话，上下文从首次 prompt 涨到「第一篇末次 + 第二篇增量 ×（1 − s）」；s 是第二篇增量中与第一篇共享、不必再进历史的比例。曲线形状按单篇实测校准（总输入 ÷ 线性估计，中位 1.19），求与基准打平时的请求数。

| 量 | 结果 |
|---|---|
| 单篇首次 / 末次 prompt | 约 16k / 77k–107k tokens |
| 单篇请求数 | 22–49 |
| 同会话依次的总输入 | 独立两篇的 1.59 倍（1.38–1.82） |
| 同会话依次时，第二篇超过压缩线的请求 | 中位 97% |
| 共同摄入打平的请求数（s = 0 / 0.25 / 0.5） | 两篇之和的 58% / 65% / 74% |
| 共同摄入末次上下文（同上） | 约 187k / 166k / 145k tokens |

- **同会话依次不可取。** 只省启动与门禁，第二篇却全程背着第一篇的历史，几乎每次请求都越过压缩线。
- **共同摄入的门槛高。** 即使第二篇一半的增量可共享，请求数也要比两篇之和少约四分之一才打平；不共享时要少四成以上。
- **压缩几乎必然。** 单篇末次 prompt 已贴近约 106k 的压缩线，两篇共同摄入的末次上下文为 145k–187k，越过压缩线，s 较小时还接近完整摘要阈值（80%）。压缩截掉旧结果后的补读会继续抵消收益。
- 本核算未计压缩后的重读、输出量变化与缓存，只说明不改运行时的前提下，小批收益依赖大幅减少请求，目前没有证据表明能做到。

若仍要探索，较可行的形态不是共享一个长会话，而是逐篇独立摄入、把 overview 综合与 index/log 收尾合并成一次独立的短任务，避免历史携带。这同样未经验证，需先从日志估出收尾段可合并的请求数。

### 若做模型实验

实验起点：从两篇短资料开始，比较“逐篇独立摄入”和“同一任务共同摄入”；另选低相关资料作负对照。长度与预计触及页数限制整批预算，不给所有资料无差别拼接。预算和 2 篇只是实验参数，不是默认配置。

必须保持每篇独立 source 页、来源归属、日志和 digest；预检批内/批外 slug 冲突，完整保护 raw。若整批只做最终门禁，则只有整批成功才能 stamp digest；失败残留和重试语义要明确，不能凭已有 source 页宣称部分摄入完成。当前 `run_ingest` 只接一个目标，批量需要独立编排设计，不是改 prompt 后绕开它。

验收按**每篇**核心事实、冲突、已有论断/来源保留和查重判断，报告整批与每篇摊销耗时、请求数、输入/输出、失败重试成本。两组从相同备份开始、交替重复；不能以少建页或略写正文作为提速。

## 执行优先级

1. **先做便宜的零模型核查**：大名录场景中重复 `Task:` 的实际体积、稳定前缀差异，以及请求级 hit/miss 和时延字段的可观测接缝。
2. **小批摄入暂不做模型实验**：盈亏核算显示门槛高、几乎必然压缩。若继续，先从日志估出「逐篇摄入 + 合并收尾」能省的请求数，有余量再设计对照。
3. **稳定 skill 前置/任务去重等 Agentao 侧修订发版后再测**：衡量缓存与端到端时延，不能只看字符数。
4. **历史压缩放后面**：先识别哪些旧结果确实被新版取代，再讨论定向移除；保留合并证据与版本信息，不删除提供方要求的 reasoning。DeepSeek 带 tools 时要求回传历史 reasoning，[官方 Thinking Mode 文档](https://api-docs.deepseek.com/guides/thinking_mode/)仍如此说明（2026-10-18 核对）。

不增加同库写 worker，不优先改门禁扫描、向量索引或文件工具线程池。本次发现支持继续研究模型请求的组织方式，没有证明某项新改动已经提速。
