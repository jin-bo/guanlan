# GuanLan 入库性能调研

日期：2026-10-17。代码基线：`5229bc9`（Agentao 0.5.12）。本次只增加调研笔记和合成基准脚本，未改入库行为。

## 结论与优先级

**合成库上，一次无自愈 `run_ingest` 的宿主成本（raw 快照 + 页面元数据快照 + check，前后各一次）约为 1,000 页 0.81 秒、5,000 页 4.12 秒**，尚不含 Agentao 执行。如果实际一篇入库需要数分钟，应先量 Agentao 初始化、模型请求、读写工具轮次和自愈，而不是先重构存储。

这个结论是**本机本次测量**，不代表冷盘、远程挂载、更大库或更大附件；raw 文件数多、附件大的库，本地成本会更多落在 raw 遍历与哈希上（见下文 128 MiB 附件场景）。

建议顺序（已按〈评审修订〉调整，原排序见该节）：

1. **增加阶段计时、token/工具调用/自愈计数**，定位实际慢任务。——**已落地**（#92：写入口收尾的「ℹ 用量」行）。
2. **对齐 overview 的更新条件**：`INGEST_PROMPT` 与 skill 口径不一，改 prompt 一句即可。——**已落地**（#92）。
3. **上下文瘦身**：以确定性「页名 + aliases 名录」+ P5.0 检索候选替代每次整读 `index.md`；给 overview 体积加 health 提示；调整读文件顺序以利 prompt 缓存。
4. 资料积压且度量证明固定开销占比高时，再设计**小批串行入库**。
5. **暂缓**：门禁扫描复用、进程内 Agentao、并发——收益相对模型耗时过小，或架构代价过高。

## 现有入库链路与已做优化

入口是 `guanlan/ingest.py:run_ingest`，写编排归口 `guanlan/gate.py:run_guarded_write_result`：

```text
校验源路径、全 raw 目录查 source slug 冲突
  → raw 全内容 SHA256 快照
  → wiki 全页元数据快照 + check 阻断违规基线
  → agentao run 子进程：发现 skill/配置/外部 MCP、模型与文件工具读写
  → raw 全内容快照 + check + 页面来源回退/正文骤缩检测
  → 必要时确定性修引号、重新门禁
  → 必要时启动新的 agentao run 自愈（最多 2 次），每次重新门禁
  → 成功后只对当前源摘要页 stamp raw_digest
```

自愈调用传回的是违规 prompt；本 wrapper **未传 session resume 参数**。不能把它当成廉价的同会话续写。实际启动/MCP/模型成本尚未测量。

以下能力**已经存在**，不能重复列为待实现收益：

- `fmrepair.py` 在 LLM 自愈前确定性修复部分引号错误，真门禁复验，必要时回滚；见 [已有设计](../../ingest-frontmatter-自愈消除.md)。该文对错误频率的历史判断，本次未用真实任务日志重新验证。
- 容错页面解析优先 `CSafeLoader`；严格校验仍使用 `SafeLoader`。
- `run_check` 已把读入的文本用于严格/容错两档解析，避免内部再读全库一遍；但**不是只解析一次**。
- skill 已要求偶现术语只留前向引用、不建空桩，overview 仅在有新角度/论断/矛盾时修改。
- ingest prompt 已禁止 Agent 自行跑 shell/check，wrapper 统一校验。
- 检索预热已经落地，但 ingest 仍走自己的子进程，不能据此声称入库已复用 Web 检索缓存。

## 实测

环境：macOS 27.0.1 arm64、Python 3.12.0、PyYAML 6.0.3（带 libyaml）、Agentao 0.5.12。未调用真实模型。

### 合成库：完整 run_ingest 的宿主成本

使用 [`scripts/bench_ingest.py`](../../../scripts/bench_ingest.py)：临时库、约 1:9 source/concept、唯一 aliases、跨页链接、每页 32 行重复中文正文；每个源约 4 KiB。先预热一次，再取 3 次中位数。注入立即返回的 fake runner，因此**不含 Agentao 冷启动、模型请求、真实语义写入和终端心跳**。无额外二进制附件时，raw Markdown 的体积仍计入快照。

| content 页数 / 场景 | 总耗时 | raw 快照累计 | 页面元数据快照累计 | check 累计 | runner 次数 |
|---|---:|---:|---:|---:|---:|
| 100 页，无自愈 | 0.079 s | 0.0008 s | 0.0127 s | 0.0653 s | 1 |
| 1,000 页，无自愈 | 0.808 s | 0.0076 s | 0.1339 s | 0.6656 s | 1 |
| 5,000 页，无自愈 | 4.119 s | 0.0380 s | 0.6751 s | 3.4016 s | 1 |
| 1,000 页，额外 128 MiB raw 附件 | 0.926 s | 0.1081 s | 0.1346 s | 0.6808 s | 1 |
| 1,000 页，2 次自愈 | 1.640 s | 0.0152 s | 0.2662 s | 1.3556 s | 3 |

各列分别取中位数，故不要求严格相加等于总耗时。无自愈三种扫描各 2 次；两次自愈时各 4 次。自愈用非法 `type` 注入，避免被确定性引号修复提前消掉。

无自愈合成测试中，两次 `check` 约占宿主耗时的 82%。1,000 页的 cProfile 观察到 6,000 次 `_load_yaml_mapping`：2N 次严格解析、4N 次容错解析，分别来自前后两次 check 与前后两次页面元数据快照。profile 有明显额外开销，**其耗时不与上表直接比较**。

复现：

```bash
uv run python scripts/bench_ingest.py
uv run python scripts/bench_ingest.py --pages 1000 --raw-mib 128
uv run python scripts/bench_ingest.py --pages 1000 --repairs 2
uv run python scripts/bench_ingest.py --pages 1000 --repeat 1 --profile
```

## 具体优化方案

### 1. 先补观测：区分排队、初始化、模型与门禁

记录 `queue_wait_ms`、前置/快照/基线 check/首次 Agent/每次修复/每次门禁/stamp 耗时，同时记源字节数、content 页数、raw 文件数与总字节数、变更页数、自愈次数及其 violation kind。Web `Job` 当前没有入队/开始/结束时间字段，只有状态和进度提示，不能把排队时间归给模型。

`AgentRunResult.raw` 已保存 Agentao JSON 信封。已核对安装的 Agentao `cli/run.py`：包含 `usage.prompt_tokens/completion_tokens/cache_read_tokens/cache_creation_tokens` 和 `tool_calls`，可先消费这些现成数据。**tool_calls 不等于模型请求次数**；细分首 token、每轮模型等待、工具耗时、重试退避和 MCP 初始化需上游事件/trace 支持，不能从 wrapper 总耗时反推。

至少分短文、长论文、更新既有实体三类任务，比较 p50/p95、成功率、每篇 token、修复率及每分钟成功入库篇数。只记录指标，不把原文、prompt、模型密钥写进新日志。

### 2. Agent 轮次与上下文：最应先验证的用户体感杠杆

- **消除 prompt/skill 不一致**：`INGEST_PROMPT` 要求“更新 index 与 overview”，skill 却要求 overview 有新观点才改。统一为条件更新，可减少无价值读写与生成。
- **把独立文件读取放同一模型工具调用轮次**：源、index、overview、SCHEMA，以及已知相关页可以按依赖批次读取。目标是省模型往返；Agentao 的同工具实例调用受锁串行，不能声称同批 `read_file` 已实现并行 I/O。
- **先给确定性目录/别名路由，再读正文**：复用既有 owner/alias 解析口径，让 Agent 找到应合并的页，避免为核对别名反复读大量正文。目录应紧凑、按需提供，不能把全库正文塞进 prompt。
- **给 ingest 提供可用的确定性检索接缝**：当前 prompt 禁 shell，Web 专用 `guanlan_search` 也不会自动进入 CLI 子进程。需要显式接入工具或由 wrapper 提供候选路径。来源术语选择与是否合并仍由 Agent 判断；检索未命中须有目录/别名回退，不能静默漏合并。
- **保持必要自查**：skill 规定返回前回扫修改页的链接。可让运行时提供最终文件内容，避免额外读轮次，但不能仅靠 prompt 把这道质量检查删掉。

模型选择、推理预算与缓存策略需在实际提供方上做 A/B；先比较同质量下的成功篇/分钟，不能凭型号名称承诺倍数收益，也不能只看首轮延迟而忽略修复率。

### 3. 门禁：共享数据，保留校验语义

**第一步：阶段内复用。** 让完整校验扫描内部产出可复用的容错 metadata/body 长度；基线 check 与写前 `snapshot_page_meta`、写后 check 与写后页面快照分别共享同一阶段读入的数据。保留严格档与容错档的独立解析，避免误用严格结果构造链接解析表。

当前无自愈路径约 4N 次 content 正文读取、6N 次 YAML 解析；阶段内复用有机会省去 2N 次正文读取与 2N 次容错解析。**这不是整体提速倍数承诺**；合成库中独立页面快照累计约占 16%，还需承担共享结果构造成本。真正 Agent 总耗时中的比例可能更小。

**第二步：按内容复用页面解析。** 在单次受保护写流程中读取页面、按完整内容指纹缓存严格/容错解析及链接扫描结果，前后及修复轮只重算变更内容。仍重新枚举路径，重新做全局别名唯一性、stem/fold owner 和 sources/断链解析，因为新增页或改别名会影响未改正文的旧页。基线违规集、原始 `page_before` 仍固定于写前，不能被中途新状态替换。

跨任务长驻缓存要额外解决外部编辑与失效。仅依赖 `(mtime,size)` 或 Web 代际不足以保证门禁正确；可先局限于单次受保护写流程，避免引入持久化派生状态。

**禁止直接把严格 `SafeLoader` 改成 `CSafeLoader`。** 不只是错误文案不同：本机验证 `aliases: [a<TAB>b]` 被 C loader 接受、Python loader 报 `ScannerError`。把 C 结果直接当严格成功，即使“C 报错才回退 Python”，仍会漏掉这个例子。必须保持严格语义，或另做明确的兼容性设计和验证。

### 4. raw 快照：保留全内容保护，降低实现成本

`snapshot_raw` 覆盖所有附件、空目录和符号链接关系；不能只保护当前 `.md` 或用 mtime/size 快照替代。大量 raw 文件/附件的库，优先 profile 遍历、系统调用和哈希各自占比。

可评估 `os.scandir` 复用 stat 信息、普通文件流式 SHA256，保持现有符号链接跟随/环保护/空目录语义。当前 `read_bytes()` 会按单文件大小分配临时内存；分块哈希首先改善峰值内存，吞吐是否提高要测。项目支持 Python 3.10，使用 3.11+ `hashlib.file_digest` 时须兼容回退。

仅因“刚才检查过”就跨模型运行窗口复用 raw 哈希，会削弱发现内容改写的能力。要去掉全量哈希，需先有覆盖所有写入口的实际不可变保证，属于单独的权限/存储方案。

### 5. 小批入库、进程复用与并发

**小批串行入库**适合大量短文积压：一个 Agent 处理小批资料，共享上下文、首尾各一次门禁，每个源仍独立摘要/日志/digest，overview 可按整批综合。先按 token/预计触及页数限批，再试 2–5 篇短文；这是实验起点，不是固定默认值。批次内外 slug 冲突均须预检。

批处理降低的是固定开销和重复上下文，不会自动消除逐篇理解/合并成本。现有门禁不是 wiki 全量事务回滚；一批失败后修改可能留盘，重试需识别已处理源和部分完成状态。批次越大，失败影响面与模型截断风险越高。

**进程内 Agentao**可复用初始化资源、接收细粒度事件，但不自动缩短模型推理。需维护每篇任务隔离、close/cancel、MCP 生命周期、权限及首轮/修复语义。已有 Web 嵌入经验可参考，待启动耗时证明值得后再迁移。

**不要直接增加 JobQueue worker 或并行运行多个 ingest 写同一库**：实体页合并、index/log/overview 都共享，当前写协调是进程级，CLI 间也无全局事务锁；`redirect_stdout/stderr` 还是进程级捕获。若未来需要并发，可并行只读分析形成提案，再在单写者下重新核对版本并串行合并。多库并行应隔离进程及输出，并遵守提供方限流。

## 评审修订（2026-10-17）

对上文初稿逐条对照代码复核后的修订。初稿的建议顺序是「计时 → 减模型往返 → 门禁复用 → 小批串行 → 进程内 Agentao」，〈结论与优先级〉已按本节改排。

### 已复核成立

- **prompt/skill 的 overview 口径不一致**：`guanlan/ingest.py` 的 `INGEST_PROMPT` 写「更新 `index.md` 与 `overview.md`」，`SKILL.md` ingest 第 4 步却规定 overview「仅当本次引入新角度、新论断或新矛盾时才改」。prompt 是每次必达的直接指令，实际会压过 skill 的条件——改 prompt 一句即可对齐，成本最低，排第 2。
- **自愈轮是冷启动**：`gate.py` 的自愈循环重新调用 `run_agent_task`，未带会话续接，每轮都是新的 `agentao run` 子进程（重新发现 skill/配置/外部 MCP）。`MAX_REPAIR_ATTEMPTS` 上方注释「把违规回喂同一 agent」与实现不符，宜顺手改成「回喂新一轮 agent」。自愈 prompt 本身窄，成本中等，但第 1 步的计数应单列每轮自愈的 token 与耗时。
- **严格档不得换 `CSafeLoader`**：复核 `aliases: [a<TAB>b]`，C loader 接受、Python `SafeLoader` 报 `ScannerError`，与 `check.py` 既有注释（决策P3.8-2/P3-6）一致。

### 降级：门禁扫描复用（原第 3 条 → 暂缓）

按上文自己的数据，阶段内复用最多省掉独立页面快照那一份，合成库中约占宿主耗时的 16%；而宿主成本整体在 1,000 页约 0.8 秒，每篇入库可省约 0.1–0.2 秒，对比数分钟的模型耗时可以忽略。代价却落在门禁这块安全关键代码上：要保证严格/容错两档结果不混用、`page_before` 与基线固定于写前、跨页 aliases/stem 变化照常重判。收益与风险不成比例，除非第 1 步度量显示某类库的门禁成本异常高，否则不做。新增共享状态本身也有维护成本，不能因为「零 LLM」就当作便宜。

### 补充：上下文体积是最大的杠杆（原稿未给数据、未排首位）

skill ingest 第 1 步要求每次完整读 `wiki/index.md` 与 `wiki/overview.md`，两者都随库线性增长：

- **`index.md`**：每个 content 页一行 `- [标题](dir/stem.md) — 一句话（别名：…）`，按行格式估算每页约百余字符；千页级的库单此一文件即达十余万字符，自愈轮还可能再读。而去重决定树真正需要的只是「页名 + aliases」，每页约二十字符，**按此估算约为 index 体积的 1/5**。这一项的量级远大于门禁里任何可优化的部分。
- **`overview.md`**：定位是「活体综述」，但没有任何体积约束；若 prompt 一直要求「更新 overview」（见上），它会随每次入库只增不减，长期膨胀到与 index 同量级。

修订方案（均为每次现算、不落盘的确定性派生，不新增持久状态）：

1. **名录替代整读 index**：wrapper 用既有 `iter_pages` + `load_page` 生成「stem | aliases」紧凑名录拼进 prompt，skill 第 1 步改为「读名录，按需看 index 相关分区」。index 本身不动——它仍是 query 的 CJK 召回面（conventions：index 行可附别名补召回）。
2. **检索候选**：wrapper 以源文本为查询跑 P5.0 `search` 取 top-K 既有页路径作为「可能需合并的页」注入 prompt。ingest 子进程禁 shell、拿不到 Web 的 `guanlan_search`，由 wrapper 预算是唯一不引 Tool 注入的接缝。候选只是提示，合并与否仍由 Agent 判断；名录兜底，检索未命中不会静默漏合并。
3. **overview 体积提示**：`health` 加一条 advisory（不阻断），并让 skill 只在打算改 overview 时才读全文。
4. **读文件顺序利于 prompt 缓存**：现行顺序是先读 raw 源、再读 index/overview/SCHEMA，请求前缀每次都不同。改为先读稳定文件、最后读 raw，可使跨篇入库前缀一致。agentao 已支持 `cache_control`，但默认关闭、须由用户在 endpoint 上开启，观澜不碰这项配置；收益以第 1 步的 `cache_read_tokens` 验证。

上述体积数字是按格式估算，落地前须以第 1 步度量在实际库上复核（统计 prompt tokens 中 index/overview 的占比）。

### 其余条目维持

- 小批串行入库：维持原设计，但前置条件改为「度量证明固定开销（启动 + 上下文重读）占比高」。
- 进程内 Agentao、并发：维持暂缓。并发另有既定裁决——P2 §11 单写者假设，`llm_wiki-反向评审-v0.6.11.md` §3 已记为「有架构理由的不做」。唯一可安全并行的是零 LLM 的 `convert`，可在批量 ingest 之前把多份 PDF 并行转完，但不得与 ingest 的快照窗口重叠。

## 真实模型实测（2026-10-17）

用 #92 的用量行在一个数十页的小库上实跑入库（Agentao 0.5.12，未开 `LLM_PROMPT_CACHE`；每次失败后从同一份入库前备份还原）。资料甲约 9 KB、资料乙约 7.7 KB，均为同一类讲话稿。逐迭代数据取自 agentao 日志。

**以下数字都是单次运行的观察值**：样本是一个小库、两篇同类资料、每个配置一次，不能推广为各类入库任务的一般比例。

### 成功运行

| 配置 | 资料 | 耗时 | Agent 执行 / 内部迭代 | 输入 tokens（缓存命中） | 输出 | 工具调用 |
|---|---|---:|---:|---:|---:|---:|
| DeepSeek 官方 API，`deepseek-flash` | 乙 | 6 m 14 s | 1 / 51 | 2,982,057（2,641,664，89%） | 37,659 | 102 |

门禁一次通过、无自愈；新建 5 页、合并更新 3 页，`index.md` / `log.md` / `overview.md` 与 `raw_digest` 齐全。按阶段拆分（阶段边界按工具序列人工划分，前后可差一次迭代）：

| 阶段 | 迭代 | 输入 tokens | 占比 | 耗时 |
|---|---|---:|---:|---:|
| 读源 + 检索既有页 | 1–9 | 258k | 9% | 71 s |
| 新建 5 页 | 10–13 | 173k | 6% | 26 s |

### 观察

- **收尾自查是这次成功运行的最大成本**（观察值；**下文第一轮对照未复现**，见〈收尾措辞对照：第一轮结果〉）。skill 写工作流收尾要求「返回前回扫你写/改的每页正文」补漏链；模型的执行方式是「发现一处、改一处、再读全文」：后 24 次迭代里 source 页被 `replace` 15 次、重读 5 次，`overview.md` 重读 6 次。全程 50 次 `replace`，每次迭代只改一两处却要重发 6–8 万 tokens 的上下文。
- **高缓存命中未消除反复迭代的开销。** 本次 89% 的缓存命中降低了输入计费（按全价计的输入约 34 万 tokens），但整体仍耗时 6 分 14 秒。现有数据没有无缓存对照，无法判断缓存对延迟贡献多少。
- **模型的工具调用风格决定输入量级。** Gemini 除首次迭代外每次只调一个工具，并重复读未变文件（单请求输入 1.3 万 → 7.8 万，缓存只命中 15%）；DashScope 上的 DeepSeek 一次迭代并行 5–8 个工具，但把时间花在长推理上；DeepSeek 官方 API 每次迭代 1–4 个工具、平均约 7 秒。同一份 prompt，开销形态差异很大。
- **额外读 raw 未经要求。** 成功运行在第 9 次迭代自行读了另外两篇相关 raw 用于对比综述。对质量可能有益，但不在 prompt 要求内，并拉长此后每次迭代的上下文。
- **失败不回滚，留下半成品。** agent 失败走 `agent_error` 分支，不跑 check 也不回滚（`gate.py` 既有语义）；Gemini 那次留下已建页但未登记的状态，只能靠 `health` 的 `index_missing_page` 发现。
- **服务商侧审核是独立的失败类别**，发生在读完、想完、开始输出之后，已花的读与推理开销全部作废，重试不一定能过。
- **上下文瘦身在小库上测不出收益。** 该库 `index.md`、`overview.md` 各约 8 KB，单请求输入最高 8.5 万里它们占比很小；〈评审修订〉的名录方案须在千页级库上另行验证。
- **用量行措辞易误读。** 「Agent 1 轮」指一次 Agent 执行（首轮 + 自愈轮的计数），不是内部迭代数；本次那「1 轮」内部有 51 次迭代。agentao 信封不含迭代数，宜改称「Agent 执行 N 次（其中自愈 M 次）」，取不到迭代数就不列。

### 对优化排序的影响

1. **先收紧收尾自查**（第一轮对照后**暂缓改 skill**，见下文），排在上下文瘦身与门禁性能之前。采用温和措辞，约束的是「发现一处、改一处、再读全文」的循环，而**不硬限每页 `replace` 次数**——工具调用次数不等于迭代次数，机械限次还可能迫使模型整页重写，反而增加覆盖旧内容的风险。拟定 skill 文案：

   > 写页时完成必要的 wikilink。全部内容写完后，对本次修改页做一遍集中自查；按页汇总遗漏并一次性修正，修正后只核对受影响片段。除非发现明确错误，不重复整页扫描，也不扩展到未修改页面。

2. **确定性补链工具暂不作为替代。** 现有 `lint.missing_entity` 识别的是已写成 `[[X]]` 但无目标页的引用，识别不了「该链而未链」的术语——那需要语义判断。确定性工具至多对已知页名 / 别名给匹配建议，且须处理代码块、已有链接、歧义与重复出现，裁定仍归 Agent。可在收尾措辞的对照有结论后再评估。
3. **额外读 raw 改为按需**：只有当前源与相关 wiki 页不足以解决具体问题时才扩展读取其他 raw，并把新增依据如实记入 `sources`。
4. **模型选择进前列**：按 provider 实测「同质量下的成功篇/分钟与每篇 token」。
5. **半成品问题单独评估**：低成本选项是在 `agent_error` 报告里提示跑 `guanlan health` / `reindex`；是否要更强的回滚另需权衡。

**含义**（下文第二轮显示同一 skill 的建页数在运行间波动很大，以下分类仍成立，但组间建页差异不宜归因于措辞）：多出的页面**既非全无价值，也非都值得独立维护**——约 4 张有较强的独立建页依据（复用频率支持建页，但不能证明必须建），约 4 张是偶现术语的薄页，1 张是命名分歧。据此：

1. 若要压成本，应针对「非本篇核心、且只能从当前资料提炼少量重复性描述」的术语收紧建页标准，而非一刀切少建页；字数短本身不是判据，也不设固定建页数上限。高复用概念提前建页可能在后续入库里摊回成本。
2. 「raw 库中被多少篇提及」是零 LLM 的复用信号，可保留为建页判断的辅助输入；术语须先由 Agent 提出，接法另议，不预设。真要实现须按文档去重、归并明确别名，并警惕字符串误命中、否定语境与同源转载——「出现得多」不直接等于「值得独立维护」。下一轮先不接入，免得同时改变规则与可用信息。
3. 收尾措辞若仍要验证，补重复运行时须**同时记录新建页数**，并固定、记录完整 skill 哈希；全局 skill 更新前先留存旧版，实验继续显式加载固定副本。

- 据此**搁置「建页范围」这条线**，skill 不改；转回确定性的上下文瘦身（名录 / 检索候选），它的收益不依赖模型行为，可以用合成基准与 token 计数直接验证。

## 验收边界

下一步最小实现宜为**计时指标 + prompt 条件更新 + 名录/检索候选的上下文瘦身**，按实测占比分别交付（阶段内扫描复用已按〈评审修订〉暂缓）。若日后仍做门禁优化，比较优化前后完整违规列表、顺序和退出码；特别覆盖历史违规基线、跨页 aliases/stem/fold 变化、sources.dropped、确定性修复回滚、坏 YAML、CRLF、raw 同大小/同 mtime 改写、符号链接与空目录。

对 Agent/批处理优化，除耗时与 token 外，还要检查重复实体、遗漏旧来源、正文覆盖、冲突保留与 source 摘要完整性。目前只有一轮单次的探索性对照（见〈收尾措辞对照：第一轮结果〉），**没有证据承诺端到端提升多少倍**。
