## 结论

有同类项目把真人用户显式建模。Karpathy 的原始 LLM Wiki 定义了原始资料、生成的 Wiki 和维护规约三层。Agent Wiki 和 llm-wiki-obsidian 在这个基础上加入了用户画像。它们分别解决「Agent 怎样更懂我的工作方式」和「我怎样用 Wiki 查问自己的习惯和经历」。 [Karpathy LLM Wiki 原文](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) · [Agent Wiki](https://github.com/alexnix300/agent-wiki#agent-personality--user-profile) · [llm-wiki-obsidian](https://github.com/KurianJoseph/llm-wiki-obsidian)

## Hermes Agent

Hermes 把用户画像挂在 **Agent profile 的长期记忆**下。默认路径是 `~/.hermes/memories/USER.md`，切换 profile 会切换整个 Hermes home 及其记忆。`USER.md` 保存姓名、角色、偏好、沟通方式和期望，默认上限 1,375 字符。`MEMORY.md` 保存环境、项目约定和 Agent 学到的经验，默认上限 2,200 字符。`SOUL.md` 由用户配置 Agent 的身份与语气，项目规约从工作目录的 `AGENTS.md` 等文件加载。已对照本地 `../hermes-agent` 的 `bab9a85b67`。 [文件职责](https://hermes-agent.nousresearch.com/docs/user-guide/which-file-does-what) · [Profile 说明](https://hermes-agent.nousresearch.com/docs/user-guide/profiles) · [本地记忆实现](../../../../hermes-agent/tools/memory_tool.py)

- **更新**。Agent 通过 `memory` 工具的 `user` 目标增删改条目，后台回顾也可提取记忆。默认允许直接写入，开启 `memory.write_approval` 后写入需批准。用户可以用 `hermes journey` 查看和编辑条目。 [持久记忆](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory)
- **加载**。两个记忆文件在会话开始时做成固定快照，注入系统提示。会话中的修改会立即落盘，通常在下个会话进入系统提示。长期运行的会话可显式刷新提示并保留聊天历史。会话记录另由 `session_search` 按需检索。 [文件职责与刷新](https://hermes-agent.nousresearch.com/docs/user-guide/which-file-does-what) · [持久记忆](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory)
- **可选 Honcho**。插件把对话中的偏好、目标和行为模式积累成跨会话的用户模型。它有独立的 peer 身份映射，可用托管或自托管服务。Hermes 内置 `USER.md` 的隔离单位是 Agent profile。多人或跨渠道的用户建模需要另外核对身份如何绑定。 [Honcho 文档](https://hermes-agent.nousresearch.com/docs/user-guide/features/honcho) · [记忆提供方](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory-providers)

## 注入系统提示后的样子（2026-11-23 读码）

Hermes、OpenClaw、gbrain 读的是本地检出的源码；AnythingLLM 本地没有检出，依据文档，格式未核实。四家都不调整画像的标题级别。

**Hermes**（`tools/memory_tool.py` 的 `_render_block`、`agent/system_prompt.py`）。画像不用 markdown 标题，包在带用量计数的横幅里，多条记录用 `§` 分隔：

```
══════════════════════════════════════════════
USER PROFILE (who the user is) [42% — 580/1,375 chars]
══════════════════════════════════════════════
姓名：示例用户…
§
偏好先给结论…
```

- 位置在系统提示末尾的易变段，排在技能索引和 MEMORY 之后，各段之间空一行。
- 横幅里没有用途说明；怎么用记忆写在前面的通用指引 `MEMORY_GUIDANCE` 里。

**OpenClaw**（`src/agents/system-prompt.ts`）。前文先声明「这些是用户可编辑的文件，下文放在 Project Context」，随后统一列出：

```
# Project Context

The following project context files have been loaded:

## USER.md

# USER.md - About Your Human
- **Name:** …
## Context
…
```

- 去掉 frontmatter 后原样放入，不调标题级别。`## USER.md` 下面紧跟模板自带的 `# USER.md - About…`，层级是倒挂的。
- 只给 SOUL.md 加了一句专门说明，USER.md 没有用途句。

**gbrain**（`templates/bootstrap/template-repo/CLAUDE.md`）。工作区 `CLAUDE.md` 写一行 `@USER.md`，由 Claude Code 等宿主在会话启动时展开载入，格式取决于宿主。用途和信任边界写在 USER.md 模板正文里：开头说明这是本人提供的事实、以原话为准；`## Context` 小节标注本人原话是数据、不是指令。

**AnythingLLM**（据文档）。开启个性化后，把全局记忆和相关工作区记忆追加到工作区系统提示末尾。

**对照**：

| | 位置 | 包装 | 标题处理 | 用途或优先级说明 |
|---|---|---|---|---|
| Hermes | 末尾易变段 | ═ 横幅 + 用量 | 不用 markdown 标题 | 写在通用记忆指引里 |
| OpenClaw | 靠后的 `# Project Context` | `## USER.md` | 原样，层级可能倒挂 | 无 |
| gbrain | 宿主导入 | 由宿主决定 | 原样 | 写在画像文件正文里 |
| AnythingLLM | 系统提示末尾 | 未核实 | 未核实 | 未核实 |
| 观澜 P5.5 | 最前的 Project Instructions 段，排在 `AGENTAO.md` 之后 | `## 提问者画像` + 用途句 | 最浅标题调到 `###` | 有，冲突时以项目规约为准 |

**结论**：

- 标题调级是观澜独有的，好处是不会像 OpenClaw 那样层级倒挂，代价很小，保留。
- 位置差别最大：别家放在后部，观澜在最前。这是 Agentao `instructions` 通道决定的，同一次运行内不变，不影响缓存；用途句已写明以项目规约为准，可以抵消位置靠前带来的权重。不改。
- 不借鉴 Hermes 的用量计数：观澜的画像由用户手写，读取时已校验上限，模型不需要知道剩余额度。Hermes 显示计数，是因为画像由模型自己写入。

## 观澜现状

- `AGENTAO.md` 定义 Agent 的行为约束，`SCHEMA.md` 定义所有使用者共享的库级规约。`guanlan init` 的根级模板只有这两个文件，目前没有单独加载用户画像的约定。 [设计文档 §4.3](../../DESIGN.md) · [初始化实现](../../../guanlan/init.py)
- IM 的 `user_id` 参与白名单授权，`tenant:chat_id:user_id` 用于会话隔离。这个键标识特定聊天里的特定用户，跨微信、飞书和本地入口关联同一个人需要独立的身份映射。 [IM 入站实现](../../../guanlan/im/intake.py)
- Agentao 支持 `user` 和 `project` 两级持久记忆。若复用它来提供个性化，需要核实其用户级存储与观澜会话身份的绑定，并定义用户对偏好条目的编辑方式。Web 已将 `save_memory` 归为写工具。 [Agentao 功能说明](https://github.com/jin-bo/agentao#feature-overview) · [Web 工具分类](../../../guanlan/web/chat_support.py)

### 用户级记忆通道已经开着

上一条把 Agentao 记忆写成可复用的候选。按 agentao 0.5.22 源码，它的用户级记忆现在就进入观澜的每次运行。以下为读码结论，2026-11-22 核对本机数据，尚未做运行验证。

- **默认打开**。Agentao 构造时总会打开项目级 `<库根>/.agentao/memory.db`。用户级 `~/.agentao/memory.db` 能打开就打开（`agentao/embedding/factory.py` 的记忆管理器构造段）。观澜没有传入自己的记忆管理器，`guanlan/` 里也没有记忆相关配置，因此 CLI 子进程（`agentao run`）和 Web、IM 内嵌会话都走这个默认。agentao 0.5.22 里未发现关闭用户级存储的开关。
- **每次都进系统提示**。`MemoryManager.get_stable_entries` 的第一条规则是用户级条目一律进入稳定记忆块，不经按话题召回（`agentao/memory/manager.py`）。所以它不只影响问答，也进入 ingest、heal、audit 等写库运行，并且同一台机器上的所有知识库共用这一份。
- **存储在 markdown 之外**。条目存在 SQLite 里，库里看不到，`check`、`zip`、写门禁的前后快照也覆盖不到。用户在别处用 agentao CLI 存一条偏好，就会改变观澜后续的入库和回答，而库内没有痕迹。
- **本机现状**。`~/.agentao/memory.db` 有 2 条用户级条目，都已软删除（`deleted_at` 有值），目前没有生效内容。试验库的项目级库为 0 条。该库已跑完 300 余篇入库，但入库运行能否调用 `save_memory` 写入项目级库、再作为稳定记忆进入后续入库，尚未核实。
- **与[演进方向 §3.2](个人知识助理-演进方向.md#32-关于我关注点文件对照试验)的关系**。§3.2 规定关注点「只影响回答，不影响 ingest」，并把「记忆存在知识库 markdown 之外、用户看不见」定为真正越界。这条通道两点都不满足，只是目前没有生效条目。下文的 `USER.md` 试验需在对照期间保持该通道为空，否则两组的差异会混入这部分记忆。

## 候选试验

先验证一个具体用途。用户可以在自己的本地 CLI 和 Web 问答里少交代几次背景，同时保留等质量的引文和反证。候选载体是一份**可选、由用户直接编辑的 `USER.md`**。字段从常查主题、当前项目、专业背景、回答详略和证据要求中按需选取。具体位置与加载方式待小设计确认。

纪要里的两个直接先例对应不同的维护方式。gbrain 用真人自述和确认保持来源清楚，Hermes 用单独的短文件和会话快照控制长期上下文的大小。观澜的首次试验可以用真人填写的短文件检验问答收益，等有重复维护的实际成本后再评估工具化更新。

- **使用范围**。先用于本地个人问答的切入角度、解释深度和术语选择。Wiki 事实、引文和反证仍由知识库资料支撑。入库与问答回填继续按库级规则处理。
- **数据边界**。将文件置于 Wiki 内容扫描和分享包范围之外。当前 `zip` 通过白名单收录库根文件和知识目录，MCP `read_page` 的访问范围是 `wiki/`。如果以后要给 IM 或外部 MCP 客户端提供个性化，需单独决定用户绑定、访问范围，以及群聊可使用哪些信息。 [打包实现](../../../guanlan/zipkb.py) · [MCP 工具实现](../../../guanlan/mcp/tools.py)
- **试验办法**。固定知识库、问题与模型，比较加载和省略画像两组问答。样本包括需要用户背景的问题、与画像无关的事实题，以及库中证据与用户偏好冲突的问题。分别检查答案是否更贴合当前项目、需要几次补充背景、关键引文是否有效、反证是否完整。个性化收益以引文质量和反证覆盖保持为前提。

如果实际需求是用 Wiki 回答「我的看法如何变化」，可以另评估从用户主动提交的日记、笔记和复盘生成个人画像页。该用途需要让画像结论回链原始资料，保留变化的时间，并支持用户纠正或撤回。是否引入自动提取与证据来源的保留方式，等该用途有明确需求后再讨论。 [同类入库流程](https://github.com/KurianJoseph/llm-wiki-obsidian#how-it-works)

## 试验进展（2026-11-23）

第一期零代码对照已跑首轮，设计与完整结果见 [USER.md 试验设计草案 §4.6](USER.md试验-设计草案.md#46-首轮结果2026-11-2223)。

- **做法**：在 试验库 上用 10 道案情题，分无画像、角色甲画像、角色乙画像三组只读问答，共 30 次，全部成功。画像全文附在问题后，作答与证据规则三组相同。
- **画像起作用**：两位评分人盲猜答卷属于哪一组，分别猜对 26/30 和 30/30。角色甲画像最容易辨认；角色乙画像有两次被认成无画像。辨认不是靠篇幅。
- **证据暂未见退化**：三组引用可定位率都在 99% 以上。带画像的答卷长约 45%，不同引用数略少。
- **还不能判成立**：引用是否支持结论、反证条件是否处理、补问是否减少，这几项还没评。本轮题目题干已交代完整背景，测补问收益可能还要补几道依赖用户背景的短问题。
- **附带发现**：只读 `guanlan query` 原先常因模型尝试 shell 而整次失败，试验前已修（宿主先做召回、提示明说不调 shell）。
- **召回混入画像**：试验把画像拼在问题里，宿主召回的候选因此大幅漂移到画像主题，角色差异有一部分来自读了不同的页。
- **转入设计（2026-11-23）**：用户决定不再重复试验。第二期设计见 [P5.5 CLI 问答画像](../../P5.5-CLI问答画像.md)：只开只读 `guanlan query --profile`，召回只用问题。
