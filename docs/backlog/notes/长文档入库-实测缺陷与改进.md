# 长文档入库：一次真实批量入库的实测缺陷与改进（backlog）

> 状态：**实测笔记，不立阶段**；P1-2/3 已实现（见 CHANGELOG〔未发布〕）。日期 2026-11-04，观澜基线 `be9d85b`。只读统计本机一个真实库的 `raw/`、`wiki/`、agentao 会话与日志；不调用模型、不改库。库名、资料标题、正文内容与本机路径都不入本笔记，下文称「库 X」「长文子目录」。
>
> 关联：[`index-overview-log与混合检索-参考项目对照.md`](index-overview-log与混合检索-参考项目对照.md)（参考项目的长文处理对照见会话结论，待并入）、[`ingest-history-and-batching.md`](ingest-history-and-batching.md)（小批摄入的盈亏核算：单会话连续处理多篇，历史增长、必然压缩）、[`ingest-performance-research.md`](ingest-performance-research.md)（已有实测只覆盖 1.7–3.3 万字资料）、[`openkb-反向评审结论.md`](openkb-反向评审结论.md) §9（标题树零 LLM 重建候选）、`SKILL.md` ingest〈长资料〉指引。

## 0. 一句话

库 X 的长文子目录有 56 份资料（合计约 1,844 万字，中位 9.3 万字），其中 53 份是在**一个 agentao 交互会话里一次性「批量入库」**的，没有经过 `guanlan ingest`。结果是：**每份资料只读了开头 10–25 行**，source 页中位不到 800 字，引用到的最大行号中位只占原文 1.6%，53 页里 168 条链接断链，全程却累计消耗约 3,200 万 prompt tokens、9 小时。同目录另 3 份走 `guanlan ingest` 逐篇入库，覆盖到原文末尾、合并进既有概念页，质量正常。**根因不是模型读不动长文，而是批量需求没有受控通道，用户只能绕开 wrapper**；长文本身的工具限制（行数上限、超长行截断、上下文压缩）是第二层问题。

## 1. 样本

| 项 | 数 |
|---|---:|
| 长文子目录资料 | 56 份 |
| 合计 / 中位 | 18,443,570 字 / 93,187 字 |
| 超过 4 万字（agentao 单工具结果落盘阈值） | 52 |
| 超过 10 万 / 20 万 / 100 万字 | 25 / 13 / 2 |

## 2. 两条路径对比

| | 路径 A：`guanlan ingest` 逐篇 | 路径 B：agentao 交互会话批量 |
|---|---|---|
| 份数 | 3 | 53 |
| 入口 | wrapper：raw 快照、写门禁、`raw_digest` | 直接在库内起 agentao 交互会话，用 goal 模式下达「把今天新增的 raw 全部入库」（同批共 86 份，长文子目录占 65 份，其中若干为重复版本，后被清理） |
| 读原文 | 分段读到末尾；日志自述「六处读取被工具压缩，已全部重读补齐后再引用」 | **每份 1 次 `read_file`，offset 1，limit 10–25** |
| source 页 | 5.9k–7.8k 字，按专题列结构并带行号 | 中位 797 字，以书名、编者、目录为主 |
| 引用覆盖（最大引用行号 / 原文行数） | 接近 100% | 中位 1.6%；超过 10% 的只有 4 页 |
| 合并既有页 | 每篇合并 1 个既有概念页，并做锚点前移、冲突标注 | 整批只新建 2 个概念页 |
| 断链 | 少量 | 547 条链接中 168 条断链（31%） |
| `raw_digest` | 有 | 53 页全无 |
| 页面命名 | wrapper 给出的 `raw_slug` | 直接用 raw 文件名（含空格、括号等） |

路径 B 会话的运行指标（来自 agentao 日志与 goal 记录）：

- 一个 goal、一轮用户输入，**360 次 LLM 迭代**；goal 时间预算 2 小时，实际运行约 **8.9 小时**才因超限停下。
- 各次请求的 prompt tokens 累计约 **3,200 万**；单次最高约 15.9 万。
- 会话历史涨到约 **21 万 tokens 时触发整体压缩**（321 条消息被摘要），此前多次触发 microcompact，截断大工具结果。
- 收尾时 overview 依据这批薄 source 页做了「系统更新」。

## 3. 缺陷（按影响排序）

### D1 批量没有受控通道，用户只能绕开 wrapper（根因）

- `guanlan ingest` 只接一个 `target`（`guanlan/cli.py` / `run_ingest`）。86 份资料要逐条敲命令，用户自然转向 agentao 的 goal 模式。
- 绕开之后，wrapper 保证的东西全部失效：raw 只读快照、逐篇写门禁（断链、`sources` 不回退等）、`raw_digest`、`raw_slug` 命名、log 格式。
- `ingest-history-and-batching.md` §方向二 的零模型核算已经预言了这种做法的代价：单会话连续处理多篇，历史线性增长、必然压缩，「让单个会话机械连续完成若干篇还可能因历史增长更慢」。本次是这个结论在 86 份规模上的实证。

### D2 长文只读开头，产出名不副实

- 读 10–25 行只能拿到书名、版权页、目录。source 页的「要点」实际是对目录的复述，其余论断无法溯源。
- 原因有二：会话需要在有限上下文里塞下 86 份资料，模型主动压缩了每份的读取量；SKILL 的〈长资料〉指引（按语义边界切块、逐块处理）是软约束，没有执行，也没有任何检测。
- **成本与产出倒挂**：读得极少，却因为单会话历史累积，累计输入是路径 A 单篇的数十倍。

### D3 现有检查发现不了「薄」

- `check` 只报出断链（全库 2,569 条中有 168 条来自本批），对「source 页只覆盖原文 1.6%」毫无信号。
- `health` 的 source 页无原文检查以「文件名 / `raw_digest` / 原始资料声明」任一路指向现存 raw 为准；本批 source 页文件名与 raw 同名，因此全部通过。**「没有 `raw_digest`」这个明确的「未经 wrapper 入库」信号目前没有被利用。**

### D4 overview 被薄证据改写

批量会话收尾时依据 53 篇薄 source 页「系统更新」了 overview。overview 是全库综述，基于目录级证据改写，会把薄弱结论扩散到后续所有 ingest 和 query。

### D5 工具硬限制：即使走路径 A 也只能靠模型自觉

- 52/56 份超过 4 万字，单次整读必然落盘截断（只保留首 8k + 尾 32k）；20 份超过 2,000 行，不带 limit 读不全。
- 12 份含超过 2,000 字的单行，`read_file` 会截断这些行。按行号分段读也读不到被截掉的部分，模型未必察觉。
- 路径 A 的日志显示，约 7 万字的资料也会被 microcompact 截断六段，靠模型主动重读补齐。100 万字级资料（本目录有 2 份）在单轮 agentao 会话里没有可行的读完方式，从未实测。

### D6 命名与去重残留

- 本批 source 页用 raw 文件名而非 `raw_slug`。之后若对同一 raw 运行 `guanlan ingest`，`locate_source_page` 先按文件名 stem 找页（`guanlan/sourcepage.py:46-48`），能否认出带空格、括号的旧页，需要先验证再补跑。
- 同批出现多个重复或扫描版本，会话里建了「转向页」，后来又手工删除 9 页并 `reindex --prune`。批量入库前缺少确定性的重复预检。

## 4. 改进建议

### P0 止血（不需要新机制）

1. **补跑这 53 篇**：按篇调用 `guanlan ingest`。补跑前先抽一篇验证 D6（是否认出旧 source 页、是否合并而非新建），并确认长文在路径 A 下的实际表现（D5）。overview 待补跑完成后再统一修订。
2. **在 `AGENTAO.md` 模板与 SKILL 中写明**：多篇资料入库必须逐篇走 `guanlan ingest`；会话内不得自行批量创建 source 页。这是软约束，只能降低再次发生的概率，所以需要配合 P1 的检测。

### P1 确定性、零 LLM（符合「wrapper 只做编排与检测」）

1. **`health` advisory：source 页缺 `raw_digest`**（建议码如 `health.source_unstamped`）。信号明确：没有 `raw_digest` 就等于没有经过写门禁。本库会立刻报出 53 + 历史若干页，可作为补跑清单。需要配一条「本该报出却可能被吞掉」的用例（见扫描器过滤的既有教训）。
2. **ingest prompt 附〈资料结构〉**（**已实现**，`catalog.raw_outline`；页码标记统计未做——它是转换工具的约定而非观澜约定）：wrapper 提取 raw 的标题行与行号，附在 prompt 末尾，并写明资料规模（字数、行数、超长行数）。实现可复用 `overview_outline`（`guanlan/catalog.py:133`，已处理行号口径与代码围栏）。效果是让「按章节分段读」从软指引变成有现成目录可循；代价是 prompt 多几百到几千字（大书目录较长时需设上限，超出时只给前两级标题）。
3. **ingest 前的规模提示**（**已实现**，与第 2 条同一处）：raw 超过阈值（如 4 万字或 2,000 行）时 stderr 提示一行，并在 prompt 里明确要求分块处理；含超过 2,000 字单行时单独提示，因为这些行用 `read_file` 读不全。
4. **`convert` 时处理超长行**：`convert` 是 raw 的唯一写入口（`rawio`），可在写入时把超过阈值的单行按句末标点折行。raw 写入后不可变，因此这只对新转换的资料生效；已有资料只能靠第 3 条提示。

### P2 受控批量通道（需要单独设计）

1. **`guanlan ingest` 接受多个目标或一个目录**，wrapper 逐篇串行，**每篇一次独立的 agentao 运行**：独立上下文、独立门禁、独立 `raw_digest`，失败只影响当篇并可续跑。这不是 `ingest-history-and-batching.md` 否定的「同会话小批共享语义」，而是把用户手工敲 86 次命令的动作确定性化；不节省模型成本，但消除 D1 的绕行动机。
   - 需要定义：批内重复预检（同名、同 slug、同内容哈希），失败与续跑语义，批次进度输出，批末是否统一跑一次 overview。
2. **超长资料的分章入库**（单篇 100 万字级）：两种形状待选——`convert` 时按一、二级标题拆成多份 raw，每章作为独立资料入库，再用确定性约定挂回同一本书；或 wrapper 按章多轮编排，传递滚动摘要（参考项目里 llm_wiki 的做法）。前者更贴合 raw 不可变、逐篇门禁的不变量，后者状态更多。先用 P1 的〈资料结构〉和规模提示，在中等长度资料上实测路径 A 的覆盖度，再决定是否需要这一步。

### 不建议

- 让单个 agentao 会话连续处理多篇（本次已实证：历史增长、压缩、读取被主动压缩）。
- 在 wrapper 里为长文自带 LLM 调用做摘要（违反「LLM 只经 agentao」）。
- 用截断原文的方式「适配」上下文（参考项目 swarmvault 只嵌前 1,200 字的反面教材）。

## 5. 复现

- **规模统计**：遍历长文子目录 `*.md`，统计字数、行数、超过 2,000 字的行数。
- **source 页质量**：按 raw 文件名找同名 source 页，统计页长、`[[链接]]` 数、`check` 输出中该页的 `wikilink.broken` 条数、页内 `:N` 行号引用的最大值与 raw 行数之比、是否含 `raw_digest`。
- **读取行为**：解析 agentao 日志的 `Tool: read_file` + `Arguments` 块，筛出目标在长文子目录下的调用，按文件聚合 offset / limit。
- **运行指标**：日志中的 `LLM iteration`、各次 prompt tokens、`Compaction triggered`；goal 记录中的时间预算与实际用时；会话 JSON 首条的压缩边界（`tokens_before`、`messages_summarized`）。
- 统计脚本只输出聚合数，不打印正文。
