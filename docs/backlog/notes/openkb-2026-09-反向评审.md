## 1. 发现（3 项）

### A. `SCHEMA.md` 模板承诺了机器不支持的东西（**改模板即可消除，不需要新机制**）

**触发**：OpenKB `#200` 把 `entity_types`（实体抽取词表）从编译期常量提升为 `global.yaml` → 每库 `config.yaml` 的分层配置（库级列表整体覆盖、`null` 与空列表都表示继承、读接口同时给生效值和它来自哪一层）。按它复核观澜的对应面时，发现问题不在"我们缺分层配置"，而在**模板和机器契约不一致**。

**事实**：[`examples/SCHEMA.md`](../../../examples/SCHEMA.md) §启用的页面类型 的表下写着「删掉本库用不到的类型；**新增类型也在此声明**」，而机器侧的分类法硬编码在三处：[`pages.py:80/86`](../../../guanlan/pages.py)（`DIR_TO_TYPE` / `VALID_TYPES`）、[`check.py:47`](../../../guanlan/check.py)（`_VALID_TYPES = VALID_TYPES`）、[`reindex.py:47/108`](../../../guanlan/reindex.py)（`_DIR_TO_SECTION` / `_section_for`）。`SCHEMA.md` **从不被 Python 解析**（决策P3.10-1）。照模板声明一个新页型，得到的是下面这些。

实测（`guanlan init` 空库 + 两张 `type: 'case'` 页：`wiki/cases/TestCase.md` 落新目录、`wiki/concepts/TestCase2.md` 复用既有目录；三条命令同一状态下连续跑）：

```
$ guanlan check
✗ check 失败：2 页，2 条违规：
    [frontmatter.bad_type] wiki/cases/TestCase.md: type 须 ∈ ['concept', 'entity', 'source', 'synthesis']，实为 'case'
    [frontmatter.bad_type] wiki/concepts/TestCase2.md: type 须 ∈ ['concept', 'entity', 'source', 'synthesis']，实为 'case'

$ guanlan health
· health 体检：2 页，5 条建议：
    [health.index_missing_page] wiki/cases/TestCase.md: 磁盘存在但未收录进 index.md
    [health.index_missing_page] wiki/concepts/TestCase2.md: 磁盘存在但未收录进 index.md
    [health.uncharted_page]     wiki/cases/TestCase.md: 页不在 sources/entities/concepts/syntheses 任一目录，无法按约定归类
    （另两条 stub_page 与本节无关，略）

$ guanlan reindex --dry-run
  跳过 wiki/cases/TestCase.md：不在 sources/entities/concepts/syntheses 任一目录下，无法归区。
· reindex（dry-run，未写盘）：将登记 1 页：
    + [Concepts] - [测试案例](concepts/TestCase2.md)
```

**证据支持的三条结论**（不多于此）：

1. **自定义 `type` 被 `check` 阻断**，且 `bad_type` 不在 [`gate.py:51`](../../../guanlan/gate.py) 的 `_WARNING_KINDS` 里，故在写门禁里属 blocking。
2. **落规范目录之外的页 `reindex` 不登记**（它不猜分区），于是 `health.index_missing_page` 不会因跑 `reindex` 而消解——这类页要么手改 `index.md`，要么挪回四目录。两条命令各自的行为都正确，**这是能力边界，不是互相矛盾**。
3. **复用既有目录时 `reindex` 按目录登记**：一张自称 `type: case` 的页被登记进 `[Concepts]` 分区，index 分区与页自称的 type 不一致，且**无 advisory 兜底**（`health.type_dir_mismatch` 按决策P3.10-6 对非法 type 主动跳过、交 `check`）。

**一条风险（未验证，勿当事实）**：写门禁对 blocking 违规会走 `gate.REPAIR_PROMPT` 自愈轮。**推断**上，一次真实 ingest 若产出自定义页型，自愈轮会被指示去"修正"该 `type`；**但本篇没有跑真实 ingest 去验证 LLM 实际改了什么**。记为风险，排期前应先复现。

**最便宜的修复 = 改模板措辞，不是造配置机制**：把 `examples/SCHEMA.md` 那句「新增类型也在此声明」改掉，明确**只支持四种内置页型**（`source`/`entity`/`concept`/`synthesis`），领域细分走 `tags` 或正文小节约定。这一步**零代码改动、零新机制**，且立刻消除误导。[`examples/` 是 init 模板的单一事实源](../../DESIGN.md)（wheel 的 `force-include` 从它生成 `guanlan/_templates/`），改一处即生效；**已 init 出的老库不会自动更新**，如在意可在 CHANGELOG 提一句。

**明确不在本篇设计的**：自定义页型的配置格式。理由三条——① 决策P3.10-1 拒绝解析散文表的理由没被推翻；② 机读围栏块 + 人读表镜像会**新增同步负担**，为一个未排期能力提前付代价；③ 三处常量收敛与"是否支持自定义"**是两件事**，收敛后仍可以只支持四型。E 轨后置的裁决不变，本节只把限制记清楚。

### B. `remove` 预览不告诉你「谁链向它」（**只借预览**）

**OpenKB 形状（`#198`）**：`page_ops.pages_linking_to` 在锁内算出反链页清单，`dry_run` 只报"哪些页的入链会受影响"、不动盘。

**观澜现状**：[`remove.py`](../../../guanlan/remove.py) 预览已列 `.trash/` 移入项、摘 slug 的多源页、删除的 index 行、独源孤儿，但"谁 `[[链向]]` 这张被撤的源页"要事后另跑 `lint` 才看得见（`remove.py:301`）——而这正是决定撤不撤的主要信息。

**最小实现（不要造通用反链框架）**：[`graph.py:188`](../../../guanlan/graph.py) 的 `compute_backlinks` **只返回入链计数**（`dict[str, int]`），拿不到页面清单。正确做法是复用 `build_graph` **已解析的边**，筛出指向待撤源页、且来源不是它自己的边，去重列出。只读、零 LLM、只改预览文案，不新增写语义。

**删页本体不借，三条理由**：① OpenKB 自己的 docstring 写着 "a recompile can still regenerate them"——照抄进观澜得到的是**会复活的删除**（源还在 `raw/`，下次 ingest/heal 可能再造）；② 观澜已有两条更对的路——源级 `remove`（决策P3.9-1）与 P4.5 可写 turn（带写日志 + 撤销本轮写）；③ 它删页时用 `fix_broken_links` 把悬链降级成纯文本，直接撞决策8（断链只报不改）。

### C. 子进程 import 守卫**覆盖不完整**（不是"没有"）

**观澜已有两条同款守卫**，都在 [`tests/test_cli.py`](../../../tests/test_cli.py)：`test_mcp_defaults_module_is_a_dependency_free_leaf`（:374，断言建 parser 不拉官方 MCP SDK）、`test_web_defaults_module_is_a_dependency_free_leaf`（:396，断言不拉 fastapi/uvicorn）。**缺口是两条：**

1. **IM extra 没有同款叶子守卫**。[`cli.py:625`](../../../guanlan/cli.py) 的注释记着 IM 子命令惰性导入、实测模块数 `177 → 242`，但没有用例守住它——这恰好是三个可选 extra 里唯一没守的那个。**该用例必须同时断言两条**：建 parser 后 `lark_oapi` **与** `guanlan.im.server` 都不在 `sys.modules`。只断言前者挡不住本要防的那件事：实测 `import guanlan.im.server` **本身也不会**拉起 `lark_oapi`（适配器是惰性的），所以宿主模块被提前导入时 `lark_oapi` 那条断言照样绿。这正是既有 MCP 守卫的形状——`test_mcp_defaults_module_is_a_dependency_free_leaf` 就同时断了 `guanlan.mcp.server` 不在 `sys.modules`，照抄即可，不增加机制。
2. **`search` 的 graph-free 约束没有守卫**。[`search.py:382/597`](../../../guanlan/search.py) 两处函数级导入的注释写着"保核 import 面 graph-free"，独立进程实测 `import guanlan.search` 后确实没有 `guanlan.graph`——但没有用例锁住。

**不要为测试重构 CLI**：`import guanlan.cli` **会**加载 `guanlan.graph`，因为 [`cli.py:19`](../../../guanlan/cli.py) 顶层就是 `from .graph import graph_entrypoint`——`graph` 是 CLI 的正经依赖，graph-free 是 **`search` 的**约束，两者不可混为一条断言。CLI 侧该断言的是"**不加载可选 extra**"（实测 `fastapi`/`uvicorn`/`mcp`/`lark_oapi`/`markdown` 均不在 `sys.modules`），`search` 侧才断言 graph-free。
