# 入库性能：名录落地后的下一步

日期：2026-10-17。代码基线：`193d8d0`（#96 已合并）。承接[入库性能调研](ingest-performance-research.md)。本次只做代码核对、真实库只读统计、临时合成库实验与官方文档核查；不调用模型、不改用户库、不调整运行配置。

## 判断

不再按原方式重复试验收尾措辞或建页数量限制；现有对照没有证明稳定收益。名录已排除 sources，不宜再为缩短 prompt 删别名。

**同日后续**：固定版本的多资料实验（见调研笔记〈固定版本、多份资料各一次〉）中，写 `log.md` 之后的输入占比为 20–43%，并有两次运行因「改后复读」被 agentao doom-loop 检测误判而失败。收尾仍值得研究，但先按「必要更新 / 写后核对 / 补链 / 重复空转」拆分轨迹再设计对照，不重复原措辞实验；doom-loop 误判已提交 Agentao（[jin-bo/agentao#543](https://github.com/jin-bo/agentao/issues/543)，0.5.14 已修复），观澜侧不放宽检测。

下一步分两条线：

1. **低成本核查推理预算与输出构成**：数万 completion tokens 不等于数万正文 tokens。若实际启用了高强度思考，先比较低强度对同等语义质量的影响。
2. **减少 index 维护的模型往返**：先提供 index 标题定位；若运行轨迹仍显示登记占明显成本，再做有范围约束的批量登记能力。

检索接缝、批量文件操作和历史内容压缩均有潜力，但需要分别解决召回与运行时契约，不应一起塞入一个 PR。

## 1. 推理预算：本次新增的重要核查点

已核对 [DeepSeek 官方 Thinking Mode 文档](https://api-docs.deepseek.com/guides/thinking_mode/)：当前默认开启 thinking，默认 effort 为 `high`；支持 `low/high/max`；携带 tools 的后续请求须保留历史 `reasoning_content`，这些内容会进入上下文。文档查询日期为本笔记日期，提供方行为以后可能变化。

**不能据此认定既有实验实际使用了 high**：实验可能显式配置过 thinking/effort，仍需检查运行时解析后的非敏感参数，不能从模型名称推断。也不能把历史输出与最终文件体积的差直接算成推理 token。

本地 Agentao `cli/run_models.py:RunUsage` 目前只有 prompt/completion/cache 计数，未细分 reasoning。建议从每次响应的 usage（提供方有该字段时）增加推理计数；没有时只统计推理文本字符数，明确不是 token。日志只输出数量，不输出推理文本。

若确认 high，先做 **high 对 low** 的探索，而不是直接关闭思考；保持模型、wire、skill、工具集合与源备份一致。检查核心知识覆盖、已有页合并、来源保留、冲突记录和链接，不能仅以门禁通过判质量相等。配置仍归 Agentao/用户端点，GuanLan wrapper 不直接持模型客户端。

重要区别：降低推理预算可能同时减少生成量和后续请求携带的历史量；**不得为了省上下文擅自删除 API 要求回传的 reasoning_content**。`temperature` 也不能当作可靠的省时旋钮：官方文档说明 thinking 模式下该参数不起作用。

**同日后续**：已核实此前实验未设 `LLM_EXTRA_BODY`、实际为默认 `high`；high 对 low 三对交替的结果见调研笔记〈推理档位对照：high 对 low〉——low 均值快约四成但区间重叠，且有一次覆盖偏窄，默认不改，仅作用户侧可选开关。

## 2. index 登记：从定位摘要到确定性批量操作

最新冒烟（名录不列 sources 一组）仍有 6 次 index 局部读取，另有 4 次在 index 内搜索定位。**这 10 次工具调用不等于 10 次模型请求**，需从轨迹确认哪些调用分布在不同请求中。

### 只读统计

以当前工作区四个真实库为对象，运行 `overview_outline(wiki / 'index.md')`，只记录体积；库内容不写入本笔记。函数对 ATX 标题的提取可用于本次统计，不代表已经做成专用 index API。

| content 页数 | index 字符 | 标题数 | 标题行号摘要字符 | 非 source 名录字符 |
|---|---:|---:|---:|---:|
| 1,531 | 185,028 | 6 | 126 | 1,664 |
| 845 | 63,114 | 6 | 120 | 9,951 |
| 116 | 9,524 | 6 | 119 | 1,791 |
| 45 | 3,973 | 6 | 116 | 1,039 |

**第一步可只附这百余字定位信息**，减少重复搜索“Entities/Concepts/Sources 分区在哪里”。它不能替代条目查重，也不能免掉修改前读取；插入后行号会变，应批量规划或重新定位，不可把开场行号当永久锚点。

### 更完整的方向：批量登记

`guanlan/reindex.py:run_reindex` 已能零 LLM 计算缺失页的分区和登记行，且不写盘。对临时合成库新增 5 页后测量：

| 原有 content 页 | 新增登记 | 登记行累计字符 | 单次计算时间 |
|---|---:|---:|---:|
| 1,000 | 5 | 205 | 31 ms |
| 5,000 | 5 | 205 | 155 ms |

两次均保留原有全部登记行。以上是单次离线计算，不是入库提速数据，不含文件写入。使用 `scripts/bench_context.py:make_kb` 建临时库、添加 5 张合法 concept 页，再调用 `run_reindex` 计算；未修改任何真实 index。

但**不能直接在每次 ingest 后自动调用全库 reindex**：

- 它会把历史未登记页一并补入，超出本次写集。
- 现有 `_format_entry` 没有语义“一句话摘要”；直接替代 Agent 登记会改变 index 内容。
- 它主要补缺失行，不等于刷新既有条目的标题、别名和摘要。
- 失败与自愈期间的页增删、index 写入时点及幂等重试，需要与现有门禁编排协调。

合理设计是**仅本次页面集合的批量 upsert**：确定性代码负责路径、分区、唯一登记及保留既有描述；新的语义描述仍由 Agent 提供。先查明前后写集如何可信取得，不能把未经核对的最终自然语言说明当作写集。可做宿主工具或门禁编排中的受限收尾能力，但两者都不是“改一句 skill”能完成的。

**同日后续**：从 22 次真实运行日志估算，只处理 index 的轮次每次 0–4 轮，可省输入中位数 3.5%、最大 12.1%，多数 index 操作已与其他工作同轮发出。暂不做批量登记，详见调研笔记〈index 登记交给 wrapper 的收益上限〉。

## 3. 批量文件操作：省模型往返，不是放开同库并发

已核对安装的 Agentao：

- `tools/file_ops.py:WriteFileTool` 已有 `append=True`，返回简短成功回执。log 追加无需新工具；只有轨迹显示模型为追加而整读/整写日志时，这才是优化点。
- `replace` 每次接收一对 old/new 文本，没有多补丁参数。
- `runtime/tool_executor.py` 对同一工具实例有锁，不同工具实例才可在线程池并行。因此同轮多个 read/replace 的潜在价值是减少模型请求次数，不能声称文件 I/O 已并行。

先量：重复读同一路径的次数与字符、工具报错后的重试、每请求工具数，以及生成量中正文/工具参数/推理各占多少。已有重复读若发生在写入之后，可能是必要核对，不应一律消掉。

若瓶颈确实是同页多处编辑，可向 Agentao 提出 `edit_file(patches=[...], expected_hash=...)`：先验证所有补丁与文件版本，再整体应用，任一不匹配则保持该文件原样。这个方向能避免半页改完再让模型处理旧锚点，但需要运行时实现和协议测试。不能用整页覆盖替代它来“省调用”。

另一个低成本实验是短资料首包提供 raw 与 SCHEMA，省去独立取文件的一轮；需有明确体积预算、原文数据边界、与 raw 快照一致的读取时点。已有名录初次注入过大的教训在前，不能对长源和巨大 SCHEMA 无条件内联。

## 4. 检索工具：让 Agent 查询，而不是 wrapper 替它作语义判断

当前 ingest CLI 子进程不能自动使用 Web 的 `guanlan_search`，但已有 search 核心和只读 MCP search/read_page 可复用。应比较三种接法的初始化成本：显式配置现有只读 MCP、Agentao 宿主注入、wrapper 给初始候选；不要为了一个工具立刻迁移整个 ingest 到嵌入式运行时。

更合适的第一版是 Agent 自己用关键词查候选，只返回少量路径、标题和命中片段，需要时再读正文。完整非 source 名录继续兜底命名/别名检查；候选不是可读页白名单，空结果也不能证明库内没有相关页。sources 仍按需可查，不能从全部检索域永久删除。

**不要把全文 raw 不加限制地丢给现有 BM25**：`search.score` 对每个 query 词遍历语料统计 df，再逐文档累加；整篇源的去重词数会显著增加计算，宽主题还可能稀释候选相关性。先用标题/小组关键词做离线召回评估，再决定是否预取。`search_pages` 冷算还会额外全库建 graph 做 backlink，不能把它误认为只有轻量字符串查询。

## 5. 缓存、工具集合与历史内容

- **稳定前缀**：`build_ingest_prompt` 的源路径在首段；本次固定库、两个合成源路径的 user prompt 仅前 56 字相同。此数字**不包括** system、AGENTAO、工具 schema 等，不能据此说服务器完全没有前缀缓存。仅把稳定文件先读、raw 后读，不会修复更早已经不同的 user 消息。要优化跨篇缓存，需要比较实际 wire 消息中最早变化的位置，稳定模板/工具顺序与动态任务分离，并用缓存计数验证，收益首先是输入处理/计费，不保证端到端时延。
- **不必要的外部 MCP**：`web/mcpdiag.py` 已明确 CLI 默认发现用户/项目 MCP。若初始化或工具 schema 占比明显，可建立实验专用的最小工具配置；不自动禁用用户所需工具，也不把权限 deny 误当成 schema 已从请求中移除。
- **历史压缩**：老的搜索结果、重复文件快照会累积，但移除历史可能损失证据、破坏缓存前缀，且 reasoning 有提供方要求。不建议先做通用压缩；优先让检索与文件读取本身少返回无关内容，保留范围/截断/版本信息。
- **不自动跳过同 digest 源**：raw 未变不等于 wiki/SCHEMA/skill 未变；重摄可能就是为了按新规则补全知识，digest 不足以证明该任务无须执行。

## 推荐执行顺序

1. **不改默认行为**，先补每请求的时延、推理/普通输出构成、重复文件读取及 index 操作分布。把实验配置中的 thinking/effort 明确记录。
2. 若实际为 high，做 high/low 小规模质量对照；同时离线验证 index 定位摘要，二者分开评估。
3. 若 index 维护仍占明显请求数，设计本次写集的批量登记；保持语义描述与修改前读取要求。
4. 再按日志选择检索接缝或批量编辑能力，不重复做无收益证据的 skill 限次实验。

暂不优先做全库门禁加速、持久化向量索引、进程内迁移或同库多写者。现有数据尚未证明这些改动值得。真实模型实验仍需独立副本、固定代码/完整 skill/模型配置、交替执行并重复运行，报告覆盖与完整性，不能以减少建页数量替代同等质量。
