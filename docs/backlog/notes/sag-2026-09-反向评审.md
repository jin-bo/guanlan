## 1. 借鉴项（收敛后：A + B′ 已落地，C 暂缓，**D 已建已关**）

> 评审意见（2026-09-12）：本节首版把「值得注意的线索」过早升级成了「确定要借的机制」。下面逐项标注收敛后的档位，**降级的理由写在原处、不删证据**。

### A. 上传端点：**先收全再校验大小** → 改成只读 `limit+1` 字节

**SAG 的实现**（`api/v1/documents.py:103-108`）：

```python
max_upload_bytes = settings.max_upload_mb * 1024 * 1024
data = await file.read(max_upload_bytes + 1)   # 只读上限加一字节
if not data:              raise ValidationError("文件内容为空")
if len(data) > max_upload_bytes: raise ValidationError(f"文件超过 {settings.max_upload_mb}MB 上限")
```

配套测试（`tests/test_upload_limits.py`，59 行）**不测"能否拒绝"**，测的是**读了多少**：假 `UploadFile` 把每次 `read(size)` 的实参记进 `read_sizes`，把上限打成 0，断言 `upload.read_sizes == [1]`——**证明它从没读过更多**。文档上传与附件上传各一条。

**观澜的现状（已核实）**：[`web/app.py:709`](../../../guanlan/web/app.py)

```python
data = await file.read()          # 网络接收不持锁（大文件不阻塞队列）
if not data: ...
if len(data) > MAX_UPLOAD_BYTES:  # 50 MiB —— 校验发生在全量读入之后
```

**这个小修的作用域必须说准**（评审修正）：进入端点处理函数之前，multipart **已经接收完毕并暂存**（Starlette 的 `UploadFile` 超过 1 MiB 即转存临时文件）。因此 `read(limit+1)` **不限制此前的网络接收，也不限制临时磁盘占用**——它只消除**端点内的一次性全量内存读取**。拖一个 5 GB 的 PDF 进来，改完之后磁盘照样先落 5 GB，省下的是那 5 GB 常驻内存。

**诚实分档**：Web 宿主只听 127.0.0.1、单用户，**这不是攻击面，是手滑面**；作用域也只有内存那一段。但修法是**一个参数 + 一条测试**，仍值得做。测试断言**限定为"端点读取尺寸"**（照 SAG 的记录读取尺寸范式），不要顺带断言内存或磁盘峰值——那不是这一改能保证的。这与 [[scanner-filter-underreport-test]] 同一条纪律：**只断言结果的用例证明不了"没多读"**。

**明确不做**：ASGI 层限体。`/api/raw` 投喂走 JSON body、`MAX_RAW_BYTES` 判在 [`rawio.py:158`](../../../guanlan/rawio.py)，FastAPI 解析 JSON 时同样已全量入内存——**同类但非同形**，本项不含它，也不借本项顺势去建一套请求体上限方案。

### B. 实际解析用了哪个 backend **没有落进 provenance**（🟢 **近期保留**，收敛为 B′：只记最终 backend）

**SAG 的实现比 CHANGELOG 写的重得多**。`parsing/service.py` 开篇就把解析结果定义成一个**带出身的类型化值**：

```python
@dataclass(frozen=True, slots=True)
class PreparedDocument:
    path: str
    provider: Literal["original", "markitdown", "mineru"]   # 谁解析的
    cached: bool = False                                     # 是否复用了缓存
    fallback_from: Literal["mineru"] | None = None           # 从哪一档降下来的
    fallback_error: str | None = None                        # 为什么降
```

围着它的三件事都值得看清楚：

1. **降级是可恢复的状态机，不是一条日志**：`status ∈ {running, done, fallback_running, fallback_done, fallback_failed}`，`fallback` 子状态带 `provider/signature/status/mineru_error/mineru_error_code/markitdown_error`。进程重启后从 state 恢复，**不重跑已完成的那一档**。
2. **降级也失败时，可重试性取上游那一段**：两段错误合并成一条消息，但抛出的异常类型**按 MinerU 那一档的 `mineru_error_code` 决定**（`ServiceUnavailable`→`ServiceUnavailable`、`Upstream`→`Upstream`、否则 `Validation`）。这与 §2.A 的 #177 是同一条纪律：**包装不得吞掉可重试性**。
3. **产物按签名缓存 + 旁路 marker**：`f"{path}.parsed.{signature}.md"`，`signature = f(provider, settings)`（改解析配置即自然失效）；降级产物有自己的签名与缓存路径，外加一个 `_write_fallback_marker(marker_path)` **在磁盘上留下"这份是降级来的"**。同一 `cache_path` 上一把 `asyncio.Lock`，注释写明目的是"避免并发重新处理**重复创建付费任务**"。

**观澜的现状（已核实）**：分层兜底是 MinerU→marker→pypdf，质量差一个数量级。skill 侧**早就知道用了谁**——[`skills/pdf-to-markdown/scripts/convert.py:340`](../../../skills/pdf-to-markdown/scripts/convert.py) 打 `[done] backend={name}`，但走 stderr；宿主侧 [`convert.py:183`](../../../guanlan/convert.py) **只在失败时用 stderr**，成功路径整条丢弃。于是 `raw/<slug>.md` 上有 `origin`、`source` 页上有 `raw_digest`（P3.7），**唯独没有"被谁解析成这些字"**。Web 解析面板经 `progress=emit` 把它**流式显示过一次**（[`web/parsefeed.py:57`](../../../guanlan/web/parsefeed.py)），窗口一关即失；[`web/parsefeed.py` 模块 docstring](../../../guanlan/web/parsefeed.py) 更是明写「**不落 `raw/`、不加 provenance**」，且 parsed 是 scratch、`overwrite=True` **整盘替换、无任何缓存**。

**为什么这条对观澜比对 SAG 更重**：观澜的价值链是 `raw/ → wiki/`，而 **`raw/` 不可变**。一次静默降级到 pypdf 的版面错乱文本会被当作正典源，往上长出摘要页、实体页、综述；**事后没有任何字段能回答"这库里哪些页建在降级文本上"**。这不是新机制，是**补齐既有 provenance 家族的第三个字段**。

**收敛后的落法（B′，评审采纳）——只记最终 backend，其余全部暂缓**：成功路径解析 stderr 末条 `[done] backend=<name>`，经 [`rawio.apply_origin`](../../../guanlan/rawio.py) 同款 **YAML-safe** 写法落**一个标量**。三条边界：

① **只记最终 backend**，不记 `fallback_from` / 失败原因 / 状态机——SAG 那套（可恢复状态机、签名缓存、fallback marker、降级失败时按上游错误码决定异常类型）**整体暂缓**。暂缓的理由是**尚无重复转换成本的实际证据，也没有跨重启续跑的需求**；**不是"观澜的转换不花钱"**——[`skills/pdf-to-markdown/scripts/convert.py:176-189`](../../../skills/pdf-to-markdown/scripts/convert.py) 在 `GEMINI_API_KEY` 存在时会给 marker 开 `--use_llm`，外部调用成本无法排除（评审修正）。真出现重复转换的实测成本，再回来谈缓存。
② **缺标记 = 不写该字段，绝不猜**：`[done] backend=` 是**宿主与随包脚本之间的输出约定**，按"读不到就不写"处理即可，**不需要额外的版本兼容机制**——[`convert.py:79`](../../../guanlan/convert.py) 经 `bundled_skill_dir("pdf-to-markdown")` 只解析**安装态 `guanlan/_skill/` 或开发期仓库根 `skills/`**，从不读用户全局安装的 `~/.agentao/skills/`，两者随同一个 wheel 发布（评审修正：首版"跨仓契约 / 用户可能装着老版 skill"的说法不符合实际调用路径）。
③ **对 `check` 不可见**（同决策P3.7-3b：源上的元数据不该让合法页判失败）。

**还须钉死一件（评审补）**：观澜有**两个写点**——CLI `convert` 直接写 `raw/`，Web 走 `workspace/parsed/` 再**晋级**。晋级时 [`web/promote.py:78`](../../../guanlan/web/promote.py) 会对解析产物 `_apply_origin` 写 `origin`；若 `parsed_by` 是在解析期写进 parsed 文件的，**必须有用例钉死它晋级后仍在**（`_apply_origin` 是 split→set→dump，理应保留其他键，但"理应"不是证据）。两个写点要么都记、要么都不记，不能只覆盖 CLI 那条。

### C. 检索分词**切碎复合标识符**（🟠 **暂缓**——证据成立，方案过重；先走 D）

**SAG 的实现**（`services/query_analysis.py`）比 CHANGELOG 那句"避免英文数字组合被错误拆分"细得多，是**两件相反的事同时做**：

```python
_LEXICAL_PART_RE   = re.compile(r"[a-z0-9][a-z0-9_.+-]{1,31}|[\u3400-\u9fff]+")  # 复合标识符整体保留
_ALNUM_SUBTOKEN_RE = re.compile(r"[a-z]+|[0-9]+")                                 # 粘连的字母+数字再拆开
```

- **带 `. - _ +` 的复合标识符整体是一个 token**：`bge-m3`、`gpt-4o`、`v0.1.23` 不被切开。
- **粘连的字母数字（`ai2027`/`gpt4`）反而拆开**，源码注释讲了理由：确定性 grep 路径按字面子串匹配，粘连的 query 跨不到分开写的正文（`AI 2027`/`GPT-4`），**这是中文分词在英文数字侧的对应物**。
- **关键纪律：拆出来的词被标记为 `expanded_terms`**，检索时（`retrieval_service.py:_lexical_sections`）命中若来自扩展词则**不计入 `exact_keys`**，而 `exact` 在重排里值 **+0.15**。即**扩展召回的命中天生比原词命中弱一档**。
- 另有两条边界：查询词**最多 4 个**（`if len(terms) >= 4: break`），jieba 分词**包在 try 里**（`retrieval must survive tokenizer failure`）回退到 legacy 词项。

**观澜的现状（已核实）**：[`search.py:72`](../../../guanlan/search.py) `_WORD_RE = re.compile(r"[a-z0-9]+")`——`bge-m3`→`bge`+`m3`，`claude-opus-5`→三段，`P4.22`→`p4`+`22`，`v0.1.23`→`v0`+`1`+`23`。**召回不丢**（query 与文档同一 `tokenize`，决策P5.0-3），丢的是**精度**，且损失形状是可说清的：**一条标识符查询实际退化成"其中最稀有的那一段"**，数字段（`4`/`22`/`23`）在真实库里是高频噪声，被 IDF 压到近乎无贡献。观澜自己的语料**恰恰塞满这种标识符**（决策编号、阶段号、版本号、模型名）。

**⚠️ 修正首轮判断**：首轮写"落地前必须先有黄金集回归闸"——**闸已经有了**。[`tests/test_search_quality.py`](../../../tests/test_search_quality.py)（445 行）是完整的确定性回放闸：16 页领域语料 + `GOLDEN` 黄金集，断言 P@1 / 聚合不回退 / 字节稳定 / config 页永不召回。**但它现在抓不到本节的问题**：`GOLDEN` 里已有 `Case("GPT-4", "entities/gpt-4.md", …)`，而该页标题就是 `GPT-4`（标题 3× 加权），语料只有 16 页、没有第二页含裸 `4`，**这条用例在修与不修下都是绿的**。所以落地要配的不是"建闸"，而是**一条本该被稀释的用例**：语料里加几页含高频数字段的页，断言标识符 query 的 primary 不被挤下去。这正是 [[scanner-filter-underreport-test]] 那条纪律的检索版。

**⚠️ 为什么暂缓（评审意见，已回代码核实）**：首版把三件事捆成"改一个分词正则"——复合 token + 拆分片段 + 扩展词降权。**第三件根本不是分词改动**：观澜的打分数据流是 `tokenize(text) → list[str]` → `DocBag.tf: dict[str, int]`，[`search.py:324`](../../../guanlan/search.py) 的 query 侧同样只拿到一个扁平 `list[str]`——**词项来源在数据结构里根本不存在**。要支持 SAG 那种"扩展词命中不计 `exact`、少 +0.15"，得改 `tf`/query 词项的表示、改 `score()` 的累加，波及 P5.3 backlink 重排与所有黄金集。而前两件也给不出"原查询排名不退化"的保证：合并 token 抬高 `|d|`，BM25 长度归一化让**全库分数整体漂移**。

**因此本节降级为线索**：证据（`[a-z0-9]+` 切碎标识符、数字段变高频噪声）成立且已记录在案，但**不排期、不动 `tokenize`**。若出现**真实失败样例**（用户实际搜不到、且 agentao 的 `search_file_content` / `rg` 也答不了的 query），再回来评估 BM25 改造，**届时先补那条"本该被稀释"的黄金集用例**。不必同时推进两套解法。归 [`cjk-retrieval-enhancements.md`](cjk-retrieval-enhancements.md) 检索增强线存档。

## 2. 宿主面（3 项：一条按需新增、一条从简、一条只记不排）

### A. 错误**归因维度**（layer / stage），不借它的错误码枚举

`core/error_taxonomy.py` 开篇写的动机**逐字命中观澜现状**：

> 历史上错误码只有 HTTP 语义，一个 `UpstreamError` 同时装了「引擎内部错」「LLM 厂商错」「DB 存储错」，用户上报日志时无法判断问题出在哪一环、该找谁排查。

解法是三个正交维度：`code` × `layer`（责任归属）× `stage`（链路环节），随响应带 `request_id`。本轮**最后一个 commit（#177，09-11）**补的是这套的漏网之鱼——引擎已判 `retryable=False` 的错被包成可重试的 `UpstreamError`，于是**一个注定失败的操作被反复重试**。深审看到它的重试判据是**两层**（`jobs/inproc.py:53`）：

```python
def _is_retryable(exc) -> bool:          # ① 可重试性是"错误"的属性
    return bool(getattr(exc, "retryable", False)) or isinstance(
        exc, (ServiceUnavailableError, UpstreamError, OperationalError))
...
if _is_retryable(error) and job.attempts < settings.job_max_attempts:   # ② 轮数是"任务"的属性
```

**观澜的现状（已核实）**：[`errors.py:11`](../../../guanlan/errors.py) 自己写着 `EXIT_AGENT_ERROR` = 「子进程非零退出 / `status==error` / stdout 解析失败」——**模型厂商 401、agentao 崩了、输出解析不了，是同一个码**。CLI 用户还能看 stderr；IM 用户拿到的是 [`im/delivery.py:48`](../../../guanlan/im/delivery.py) 那一句 `处理出错了，请稍后再试。`——"该找谁排查"的信息量为零，而"稍后再试"对一个缺 API key 的库是**误导**。

**借什么 / 不借什么**：借**维度**（一次失败至少说清"卡在哪一环、根子在谁"）与**两层判据**（§3.A 用得上）；**不借** `ErrorCode` 枚举、HTTP 语义、`request_id` 中间件——观澜是 CLI + 三个薄宿主，退出码是对外契约、**不可动**（P2 §9）。最小形是**在既有退出码之上加一层归因**，不新增退出码、不改 CLI 契约。这块判断有多少属 agentao、有多少属观澜，本篇**不裁**。

### B. 诊断日志：缺的是 **sink**，不是脱敏纪律

**⚠️ 修正首轮判断**：首轮写"照抄 SAG 那条脱敏纪律"——**判反了**。深审对照下来，**观澜的脱敏归口强于 SAG**：[`web/mcpdiag.py`](../../../guanlan/web/mcpdiag.py) 遮 userinfo、query **和路径段**（理由写得很清楚：Zapier/Composio/Smithery 这类托管 MCP 就是把 key 放在 `/s/<token>/mcp` 路径里），解析不出结构的串**整串遮掉**，且**刻意保住可诊断性**（`url` 遮成同一条 URL 而非 `***`，读者仍看得出打到哪个 host 的哪条路径失败）；IM 启动横幅 [`im/server.py:320`](../../../guanlan/im/server.py) **只打数量、绝不打 ID**，理由写明 stdout 常被重定向进 journal。而 SAG 这一轮（#173）才刚学会 `llm_base_url` 这种"非密钥字段"也会夹带凭据（`https://user:pass@host/v1?token=…`），修法是**干脆不打值**，测试断言连 `https://` 都不出现。

所以**该借的只有 sink**：SAG 的 `core/logging.py` 配了 `request_id` 过滤器 + 统一格式，并**显式压低 httpx/openai/LiteLLM 等噪音源到 WARNING**，理由是**禁止模型客户端在 DEBUG 模式打印完整提示词/正文**。

**观澜的现状（已核实）**：`guanlan/im/` 全模块用 `logging.getLogger("guanlan.im")` 打了相当细的事件（丢弃未授权消息、越权合成消息、发送失败、会话超限…），但 [`im/server.py:390`](../../../guanlan/im/server.py) 自己注明「**宿主不配置 logging**，INFO 级没有任何 handler 接（`logging.lastResort` 只兜 WARNING+）」——**这些事件默认一个字也不出现**，且没有 `--log-level` / `--diag-log`。

**为什么现在提**：[`P4.22-IM可点引用.md`](../../P4.22-IM可点引用.md) §9 挂着的真机未决项——**飞书把卡片回调投在哪种 WS 帧上**（代码两种都收，垫片因此留着）、未授权点击路径、转发卡片路径——**正是诊断日志该回答的**。现在要答，只能改代码插 print 再跑一次真机。

**收敛后的最小形（评审采纳）**：只给 `guanlan.im` 配一个 **stderr handler + 级别控制**，并照 SAG 压低第三方 logger（`httpx` / `lark_oapi` 的 DEBUG 会打完整消息体）。**暂不加 `--diag-log <file>`**——落文件是另一档承诺（轮转、留存、误传风险），真机排障有 stderr 重定向就够。

**⚠️ 一条不能顺手做的事（评审修正）**：`mcpdiag` 的脱敏是**为 MCP 配置写的**——它遮的是 URL 的 userinfo / query / 路径段，对象是**结构化配置里的已知字段**。IM 日志要处理的是**任意用户消息文本**，两者不同构，**不能把 `mcpdiag` 直接当通用脱敏器**。本项的姿态应是**不打消息正文**（只打事件、ID 形状、长度、结果），而不是"打了再遮"。

#### 以下为原文（结论已作废，事实仍有效）

**SAG 的形状**：写协调活在**共享持久状态**里——`source_document_mutation(SessionLocal, source_id, "document-upload")` 是一个**按信源命名的互斥窗口**，配 `_source_maintenance_jobs` 租约与 per-source 停止信号，`jobs` 表持久化 `attempts/status/error`。谁起的进程都受同一把约束。

**观澜的现状（已核实）**：[`web/jobs.py:47`](../../../guanlan/web/jobs.py) 写明是「**进程级**单写者协调（一把 `write_lock` + `active_writable_turns` 计数）」，[`web/server.py:158`](../../../guanlan/web/server.py) 硬编码 `workers=1` 的理由也是"单进程单事件循环"。全仓搜 `flock` / `fcntl` / 锁文件 **零命中**——**观澜没有任何跨进程写互斥**。

**为什么这条比听起来严重**：观澜的写门禁靠 **`raw/` 前后快照**判红线（`snapshot_raw` → agent → `diff_raw`）。若 Web 宿主开着、用户同时在另一个终端跑 `guanlan ingest`，两条写路径会交错：**CLI 的快照窗口里出现了 Web 投喂写进 `raw/` 的文件 → CLI 报 `raw_mutated`（退出 4）**，即**在最严重的那条红线上冤枉 agent**；反向也成立（Web 的窗口里混进 CLI 的写）。观澜是单用户本地宿主，这不是并发服务问题，但"把 web 开着、顺手在终端跑一条命令"**恰恰是本项目最自然的用法**。

**收敛后的提法（评审采纳）——只规定一条原则，不规定实现规模**：

> **一库一锁；锁覆盖"影响写门禁的完整操作窗口"；由最外层操作持有。**

**不**引入租约、锁管理服务、陈旧锁清理机制（进程被 kill 后 advisory 文件锁由 OS 自动释放，这正是不需要清理器的理由）。

**⚠️ 首版的入口清单是错的（评审修正，已回代码核实）**，排期前必须先出**完整入口盘点**，至少含这三处首版判错/漏掉的：

- **`reindex` 是写命令**——[`reindex.py:9`](../../../guanlan/reindex.py) 写明「只写 `wiki/index.md`，不碰 `raw/`、不起 Agentao、**无写门禁**」。首版把它按"`--dry-run` 才是读"处理，等于漏了默认写路径，而它改的恰是 `index.md`。
- **`graph` 不是读命令**——[`graph.py:432-437`](../../../guanlan/graph.py) 写 `graph/graph.json` + `graph.html`。首版把它列进"不取锁"的读命令，判错。（它写的是派生物、不影响 `raw/` 快照，但要不要取锁是**盘点后的裁决**，不能靠首版那句想当然。）
- **嵌套调用会重复取锁**——[`convert.py:49`](../../../guanlan/convert.py) `from .ingest import run_ingest`，`convert --ingest` 是"落源 + 摄入"两段；Web 的写作业与可写 turn 也可能层层嵌套。**"由最外层持有"正是为这个写的**，实现上要么可重入、要么在内层显式跳过。

**"约二十行"那句删掉**：那只描述锁原语本身，不代表接入成本。**另须先议**：Windows 无 `flock`（观澜是否承诺 Windows？）、锁文件落点与是否进 `.gitignore`。

### A. 自愈轮：`wiki.missing` 这一类是否该直接判死（🟠 **须先补复现用例**）

SAG #177 的形状是"**已知不可重试就别再重试**"，且判据分两层（错误的属性 + 任务的轮数，见 §2.A）。观澜只有第二层：[`gate.py:496`](../../../guanlan/gate.py) 的自愈循环**只看轮数上界**。

深审注意到一条违规：`wiki.missing`。[`check.py:210`](../../../guanlan/check.py) 在 `wiki/` 不存在或不是目录时返回单条 `Violation("wiki", "wiki.missing", "wiki/ 不存在或不是目录")`，它**不在** [`gate.py:51`](../../../guanlan/gate.py) 的 `_WARNING_KINDS` 里，故属 blocking，会进自愈轮。

**⚠️ 触发条件要写全（评审修正，首版漏了）**，三条同时成立才会走到那一步：① `run_result.ok` 为真——agent 失败走 `agent_error`，根本不跑 check（[`gate.py:389`](../../../guanlan/gate.py)）；② `wiki/` 在**写前存在**——写前就缺的会进 [`check_baseline`](../../../guanlan/gate.py)，属既有违规、**不算新增**，不触发自愈；③ 本轮运行后 `wiki/` 消失。即这是"**本轮新发生的整个生成层丢失**"，不是常态路径。

**并且"必然失败"是过头话**：`REPAIR_PROMPT` 是 `"…以下问题…{violations}…"`，**实际违规文本会带进去**，agent 看得到"wiki/ 不存在或不是目录"。它多半修不好，但断言"两轮必败"**没有证据**，本篇也没跑过复现。

**收敛后的提法**：可以主张「**本轮新发生的整个目录丢失应直接判死、不进自愈**」，作为一条**明确的保护策略**——理由不是"重试必然无效"，而是"在生成层已被删除的状态下让 agent 自由行动，风险不对称"。**先决条件：补一条复现用例**（构造 agent 删 `wiki/` 的假 runner，断言当前行为，再断言修后行为）。**不扩展成通用重试分类框架**——"两轮违规集全等即停"那条同族启发（身份键 [`_vkey`](../../../guanlan/gate.py) 现成）**一并搁置**，它的前提是确定性信号，而观澜的自愈轮是随机的。

### B. 抽取上限防**实体膨胀**

**⚠️ 修正首轮判断**：首轮按 CHANGELOG 记为"SAG 每块最多 20 事项 / 每事项 20 实体、精简档 8"。**深审在本仓没找到这组常量**——`generation/prompt.py` 里没有，它应在引擎包 `zleap-sag`（独立发布、不在此仓）或 profile 配置里。故本条**只能按变更日志记载，无法按实现核实**，降级为线索。

观澜的对应面**一半有一半没有**：`heal` 侧有 [`heal.py:59`](../../../guanlan/heal.py) 的 `DEFAULT_LIMIT` + `--min-refs`，**有界且会声明推迟项**；`ingest` 侧**没有任何上限**——一次摄入建多少张实体页，全靠 [`SKILL.md`](../../../skills/guanlan-wiki/SKILL.md) 的决定树与模型判断（全文搜"上限/最多/不超过"只命中自愈轮那一处）。

**张力**：给 skill 加数字上限与"判断归 skill、wrapper 不携带业务智能"**不冲突**（上限是写给 skill 的约定，不是 wrapper 的检查），但与"实体耐久增量维护、不重抽"的基调有轻微不合——SAG 每次重抽，膨胀会**累积放大**；观澜只增不重写，单次膨胀的长期危害小一档。**不裁**：先看真实库里单次 ingest 的建页分布。

## 6. 🔵 情报两条（agentao 面 / 契约面，不是观澜的借鉴项）

- **fake-ip 代理会被 SSRF 守卫误拦（只作排障线索，不作放行建议）**：Clash/mihomo 的 fake-ip 模式把域名解析到 `198.18.0.0/15`，由 TUN 网关按映射表转发。任何"拒绝非全局地址"的守卫（`if not address.is_global`）都会把**正常站点**一起拒——`ipaddress` 判该段 `is_global` 为假。**排障时先想到这一层**：域名没问题、代理没问题，拒绝发生在守卫里。
  **⚠️ 明确不采纳 SAG 的放行做法**（评审修正，首版把上游注释当成了安全保证）：SAG 源码注释称该段"不属于任何真实内网服务、非 TUN 环境不可路由"，**这不成立**——`198.18.0.0/15` 是 [RFC 2544](https://www.rfc-editor.org/rfc/rfc2544.html#section-C.2.2.1) 的基准测试段，该 RFC 本身就把这些地址分配给**被测设备端口**；"保留作基准测试"不等于"本地不可路由"。因此这里**只保留排障线索，不建议默认放行整个网段**。观澜自身不发起网络取数，这条落在 agentao 的 fetch 白名单上，与 [[agentao-local-editable-uv-no-sync]] 记的 `AGENTAO_WEB_FETCH_ALLOW_CIDRS` 同源——真要放行，也该是**按需放行具体目标**，不是整段。
- **两个薄契约换整个客户端生态**：SAG 用 `api/v1/openai.py`（181 行，把任意 agent 包成 OpenAI Chat Completions 端点）+ `api/v1/dify.py`（109 行，Dify 外部知识库 `POST /retrieval`）接进了一大片现成客户端。观澜已为 IM 付了 per-platform 适配器的钱（P4.21），**本条不推翻 P4.21**，只记一笔：若将来还要接第四类宿主，"实现一个别人已经在用的薄契约"可能比"再写一个适配器"便宜一个量级。两者都薄到可以**直接架在 P5.0 `search_pages` / P5.1 既有内核**上。
