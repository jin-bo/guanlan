## 0. 一句话

「跨助理」「markdown 存储」「AI 维护知识库」三点，同类里都已有人做（Mem 的聊天能直接建、改、整理笔记；Basic Memory 让多个助手经 MCP 读写同一份 markdown），**单凭它们区分不了观澜**。值得验证的差异是：**写入经过确定性检查、原文受保护、知识变更可追溯——以及这些约束是否真的让答案更可信**。据此保留一个定位假设：**可审计的个人知识编译层，助理当前端**（§3.1）。它成不成立，先用 §5 的三个验收问题实测，再决定后面几项的投入。

## 2. 观澜现有的差异点（需实测证明其价值，不是已证明的优势）

- **写入门禁 + `raw/` 不可变**：每次写作业前后对 `raw/` 做快照比对（`EXIT_RAW_MUTATED`），写入经 `check` 等确定性校验。**本次调研未确认同类有等价机制**——这是「没查到」，不是「确认没有」。
- **变更可追溯**：source 页带 `raw_digest`，`audit`（P3.7）能找出原文变了之后受影响的页；`remove`（P3.9）撤回进 `.trash/` 留档。
- **零 LLM 的体检 / 图谱 / 检索**、**markdown 唯一真相**、**中文优先**。
- **入口已经不少**：Web、MCP（只读，P4.24 发布 `guanlan-query` 技能）、IM（微信、飞书）、网址导入（P4.31）、一键入库与目录批量入库（P4.30 / P4.32）、图谱可视化（P4.27）。

这些机制是否**实际提升了答案可信度**，目前没有数据。§5 的验收问题就是为此设的。

## 3. 演进方向

### 3.1 定位假设：可审计的个人知识编译层，助理当前端

- **依据**：各家助手的记忆互不相通；Gemini 做「导入别家记忆」，说明用户需要一份跨助理的长期知识。但跨助理本身不是观澜独有（Basic Memory 已做），观澜要证明的是「可审计」带来的可信度。
- **现状**：MCP 宿主（P4.10 stdio / P4.17 Streamable HTTP / P4.18 SDK v2）+ P4.24 技能发布已是这条路的底子；IM 宿主复用同一只读会话。
- **形状**：后续投入优先放在「被挂载时好不好用」——外部助理会不会先查库、读证据、正确引用——而不是另做一个聊天前端。
- **不变的边界**：MCP 仍只读（P4.10）；写入只走 CLI / Web 的门禁路径。
- **第一步就是实测**（§5 第 1 项），不是开发。

### 3.2 关于「我」：关注点文件对照试验

- **同类怎么做**：ChatGPT 后台自动合成；Claude 是透明、可编辑的条目，按项目分开。
- **现状（查过两面）**：wiki 记的是世界，没有「我」。**能力面**：agentao 自带记忆系统（`agentao/memory/`，含把会话里的偏好、约束自动提成长期记忆的 `crystallizer`）；Web 对话把 `save_memory` 归为写工具（`guanlan/web/chat_support.py` 的 `_WRITE_TOOL_NAMES`），只读会话里用不上。**决策面**：未见显式推后，也未见讨论。
- **形状**：一份用户自己写的关注点文件（关注的主题、在做的项目、偏好的回答方式），属于**配置，不是内容**，不进 index / graph / lint 扫描。**只影响回答的关注角度与表达方式，不影响 ingest 对知识事实的整理。**
- **两个边界**：
  - **外部助理读不到**：MCP `read_page` 经 `_safe_wiki_file` 限定在 `wiki/` 内（`guanlan/mcp/tools.py`），放在库根的文件外部助理取不到；只改 `guanlan-query` 提示词不够。要跨助理生效，须另议 MCP 暴露方式（新工具或资源），属另一项决策。
  - **不整读 index**：查询提示词已规定 `wiki/index.md` 只当目录、不整读（`guanlan/query.py` 的 `QUERY_PROMPT`）。关注点文件是单独一份小文件，按需读，不与 index 捆绑。
- **试验办法**：先只在本地问答入口（CLI `query` / Web 对话）接入；用同一组真实问题有无对照，看三项：
  1. 是否更贴合当前项目；
  2. 是否减少重复交代背景；
  3. **是否因迎合偏好而忽略反证**（这一项变差就不做）。
- **自动提取**：不在这一步做。不是原则上禁止——只要结果落在 markdown、经门禁、留记录就不破架构——而是在手写版没证明价值前，自动提取只会增加一份要维护的状态。真正越界的是把记忆存在知识库 markdown 之外、用户看不见。

### 3.3 收集：IM「收件箱」（按使用障碍决定）

- **同类怎么做**：手机上转发一篇文章就算收进来（ima、Khoj 的 WhatsApp、Mem）。
- **现状（查过两面）**：IM 宿主只读，P4.21 规定对知识库**零写**——这是明确决策，不是遗漏。网址导入（P4.31）与一键入库确认关口（P4.30）已有，只在 Web / CLI 发起。
- **形状**：IM 收到链接或文件时，只落到 `workspace/` 下的收件箱（不碰 `raw/`、`wiki/`），回一条「已收，回到 Web / CLI 确认入库」；Web 暂存区列出收件箱条目，复用 P4.30 / P4.31 的确认关口入库。
- **须重开的决策**：P4.21 的「零写」要收窄成「不写 `raw/` 与 `wiki/`」，须在新小设计里单独拍板。
- **新增状态与失效**：收件箱条目（文件 + 出处记录）；入库或丢弃后移除；长期不处理的条目要有清理或提示规则。
- **触发条件**：先确认真实使用里**确实因为手机收集麻烦而漏掉资料**，再做。
- **能力上限**：只解决「随手收」，不解决「收了不看」。

### 3.4 离线维护简报

- **同类怎么做**：Khoj 有定时任务；ChatGPT 后台合成。
- **现状（查过两面）**：`heal` / `audit` / `check` / `health` 全部手动发起；E3「夜间自动富化」在 DESIGN §7 与 [`未来工作计划-反向评审收口.md`](未来工作计划-反向评审收口.md) §2 轨 C 明确推后。
- **能可靠承诺的内容**：断链、缺失实体、结构异常（`check` / `health` / `lint` / `heal --dry-run`）、**原文漂移**（`audit --dry-run`），以及**汇总页面上已有的待核标记**（`## ⚠️ 资料冲突与待核`）。
- **不能承诺的**：自动发现语义矛盾或论断过期。`audit` 粗筛（`guanlan/audit.py` 的 `_scan_drifted_sources`）比的是原文 sha256 指纹，**原文没变就不会报任何东西**——不会因时间流逝识别过期，也找不出所有跨页矛盾。简报里**「没有候选」不能表述为「知识仍然正确」**。
- **定位**：它解决的是**维护**，对「收了不看」帮助有限。要验证助理价值，看的是用户是否因此重新用上某条知识、完成某个判断，而不是看了体检数字。
- **新增状态与失效**：「上次报到哪儿」的游标（用于算「本周新增」）；游标丢了就退化为全量报告，不影响正确性。
- **先离线、后推送**：先在真实库上离线看一段时间的简报，确认产生值得处理的行动、重复噪音可控，再考虑推到 IM 或 Web 首页。需要 LLM 的修复仍由人批准后才跑，守住零 LLM 与 LLM 分档。

### 3.5 产出与找资料（需求明确后）

- **产出**：NotebookLM 强在产出形式。观澜对应的是 **P6 技能蒸馏**：设计已自洽，工作法归属已拍板为扩既有 `guanlan-wiki` skill（主草案决策 D9；[`p6-技能蒸馏-工作法归属未决.md`](p6-技能蒸馏-工作法归属未决.md) 已归档），**当前状态是暂缓实现、等真实需求**，不再有待拍的决策。按 wiki 生成简报 / 讲义一类能力，可以像 `pdf-to-markdown`、`flint-chart-author` 那样做成辅助技能。
- **从问题出发找资料**：网址导入（P4.31）已有；缺的是「Agent 先提出候选资料 → 人确认 → 入库」这一步，可复用 P4.30 的确认关口；Agent 侧联网检索走 agentao 已有工具，不自带客户端。

### 3.6 降低单机版上手门槛（需求明确后，先验证）

- **同类怎么做**：桌面产品「下载即用」；Obsidian 方案、Khoj 自托管都能接本地模型。
- **现状**：需要 uv / Python 环境与自配模型。本地模型能否经由 agentao 顺畅接入（OpenAI 兼容端点、工具调用质量）**未验证**。
- **形状**：若单机版要面向非开发者，打包好的桌面安装 + 模型配置引导可能比新功能更关键。先做一次本地模型跑通 ingest / query 的实测，再决定投入。

## 4. 暂不跟进（投入取舍，不是原则冲突）

- **自动整理知识或记忆**：只要 markdown 仍是权威、写入走门禁、留有记录，就不破架构——`heal` / `audit` 本身就是这个形状。暂不扩展，是因为 §3.2 的手写版还没证明价值。**真正越界的**只有一种：把记忆存在知识库 markdown 之外、用户看不见（ChatGPT 式的后台记忆）。
- **向量检索**（E1）：暂不上，依据应是**观澜自己真实问题上的召回表现**，不是别人知识库的规模经验。现有 `tests/test_search_quality.py` 的黄金集可以扩成真实库的召回实测；出现漏召回实证再评估（DESIGN §8）。
- **音频产出**：不违背本地与可审计，推后是因为需求未出现、成本较高。
- **云同步、多租户**：属企业版 E2，与单机版方向无关。

## 5. 顺序与验收

### 5.1 定位成立的验收问题

这组结果比功能数量更能说明观澜是否已经成为个人知识助理的底座：

1. **换一个助理还能否稳定使用**：同一份库，经 MCP 挂到不同助理（如 Claude、Cursor、IM），是否都会先查库、读证据再答。
2. **答案能否回到证据**：答案里的 `[[页]]` 引用是否真实存在、是否支持对应论断，能否从页追到 `raw/` 原文。
3. **知识更新后能否可靠纠正旧结论**：原文更新或新资料入库后，旧结论是否被标注或纠正。设计用例时要注意 §3.4 的能力上限——`audit` 只覆盖原文漂移，**新资料与旧页矛盾、原文未变但论断过期**这两类要专门测，看现有路径（ingest 时的冲突标注）能覆盖到哪里。

### 5.2 顺序

| 顺序 | 工作 | 验证重点 |
|---|---|---|
| 先做 | 外部助理接入实测（§3.1，按 §5.1 三问） | 是否会查库、读证据、正确引用；是否比直接给原文更有用 |
| 随后 | 关注点文件对照试验（§3.2） | 个性化是否带来可见改善，且不因迎合偏好而忽略反证 |
| 按使用障碍决定 | IM 收件箱（§3.3） | 是否确实因为手机收集麻烦而漏掉资料 |
| 再做 | 离线维护简报（§3.4） | 是否产生值得处理的行动，重复噪音是否可控 |
| 需求明确后 | P6、桌面打包、本地模型完善（§3.5 / §3.6） | 是否解决已出现的使用障碍 |
