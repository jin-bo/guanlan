# USER.md 个人画像试验 · 设计草案

> **状态**：已结束（2026-11-23）。第一期首轮已跑（§4.6）：画像让回答随角色变化，可稳定辨认；证据列与补问次数未评。用户决定不再重复试验，第二期转入设计：[P5.5 CLI 问答画像](../../P5.5-CLI问答画像.md)。
> **来源**：[用户画像 · 同类项目调研](用户画像-同类项目调研.md)「候选试验」，[个人知识助理演进方向 §3.2](个人知识助理-演进方向.md#32-关于我关注点文件对照试验)。
> **目标**：用一份用户自己写的短文件，验证本地问答能否更贴合用户、少交代背景，同时引文和反证不变差。
> **分两期**：
> - **第一期**：零代码对照，回答「值不值得做」。
> - **第二期**：仅在第一期成立后实施，只接 CLI 只读 `query`。
>
> 第一期不成立就到此为止，结论写回调研笔记。Web 等有实际需求时再议（§6）。
> **不做**：自动提取画像、画像实体页、跨渠道身份映射；Web、IM、MCP 的个性化；改 Agentao 用户级记忆通道（只作为试验前提，见 §7）。

## 1. 现状（2026-11-22 读码）

| 事项 | 现状 | 位置 |
|---|---|---|
| CLI 问答 | 固定 `QUERY_PROMPT`，以 `read-only` 姿态、库根为工作目录运行；`--backfill` 改走完整写门禁 | `guanlan/query.py` |
| Agent 读文件 | 只读运行也能读工作目录（库根）内任意文件 | Agentao 文件工具 |
| CLI 写门禁 | 写前、写后对 `raw/` 取指纹，核对有无改动；发现改动判违规，**不恢复**原内容 | `guanlan/gate.py` |
| 前像回滚 | 只属于 Web 任务中心（P4.33）：覆盖 `wiki/`、`SCHEMA.md`、`AGENTAO.md`，取消或中断时恢复 | `guanlan/preimage.py`、`guanlan/web/tasks.py` |
| Web 对话 | 会话构造时激活 skill；运行中可在只读与可写之间切换姿态 | `guanlan/web/conversation.py` |

## 2. 要回答的问题与判定

**问题**：附上一份用户手写的画像后，本地问答是否更少需要补问，且引文和反证不变差？

**判定**（第一期按顺序判断）：

1. 任一证据指标比对照组差（§4.4）→ **不成立，停止**。这是 §3.2 定下的底线。
2. 证据指标都不差，且**至少两道背景题少一次补问** → **复跑这些题**，收益再次出现才算**成立**，进入第二期。
3. 其余情况，或复跑时收益没有再出现 → **不成立**。

## 3. 画像文件

- **位置**：**放在知识库目录之外**。第一期放在试验目录里（§4.1）。第二期由 CLI 显式指定路径（§5）。

  放在库外，这样 Agent 读不到；Web reader 与 IM 会话也读不到。画像不会进 `zip`、扫描类命令和 MCP，也不需要写保护、快照或回滚。
- **写者**：只由用户本人编辑。
- **格式**：普通 markdown，不要 frontmatter。建议小节，按需选用，不强制：
  - `## 关注的主题`
  - `## 在做的项目`
  - `## 专业背景`（决定术语和解释深度）
  - `## 回答方式`（详略、结构、语言）
  - `## 证据要求`（例如「规范类问题要给条款号」）
- **上限**：1,500 字。参照 Hermes `USER.md` 的 1,375 字符，按中文略放宽。

## 4. 第一期：零代码对照

### 4.1 前提与目录

- 试验库 全量入库完成，题目来自真实领域。
- `~/.agentao/memory.db` 与 `<试验库>/.agentao/memory.db` 均无生效条目。每轮开跑前用 `sqlite3` 核对，并在结果表里记录条数（§7）。
- 两组同一模型、同一推理档位；期间不改 skill，不跑 `install-skill`。
- **试验目录在知识库之外**，例如 `~/.guanlan/trials/user-md/`，存放：
  - 画像：`USER.md`
  - 题目与反证基准：`questions.md`
  - 原始答卷：`answers/`
  - 评分表：`score.md`

  **不放在 `<试验库>/workspace/` 下**：只读 query 也能读库根内的文件，模型可能自行读到画像或前一组答卷。

### 4.2 两组的提示

两组用**同一套**作答和证据规则，即现有 `QUERY_PROMPT`，不另加任何指令。唯一差别是试验组在问题后附上画像全文：

- **对照组 B**：`guanlan -C <试验库> query "<问题>"`
- **试验组 A**：`guanlan -C <试验库> query "<问题>\n\n附：提问者画像\n<USER.md 全文>"`

不加「画像不是证据」「照常写反证」之类的说明。那些说明本身会影响引文和反证，会让判定分不清是画像起的作用，还是说明起的作用。

画像全文直接放进提示，不让 Agent 去读文件，这样两组只差这一段文字。

### 4.3 题目

共 9 题，三类各 3 题，由用户出题：

| 类别 | 用途 | 例 |
|---|---|---|
| 背景题 | 测收益 | 「这条对我们手上的项目有什么影响」 |
| 与画像无关的事实题 | 测有无副作用 | 「某标准规定的步骤是什么」 |
| 冲突题 | 测是否迎合 | 画像写了某种倾向，库里有反例 |

- 每题两组各跑一次，共 18 次运行。每题只记一次结果。
- **冲突题在出题时预先列出应出现的反证**（页名与要点），作为评分基准。

### 4.4 评分

18 份答卷去掉组别、打乱顺序后放在一张表里，由用户人工评分，评完再揭盲。不写评分脚本，不算平均分。

| 列 | 怎么判 |
|---|---|
| 关键引用可定位 | 关键结论引用的 `[[页]]` 能否找到对应页面 |
| 关键引用支持结论 | 页面内容是否确实支持该结论 |
| 反证覆盖（仅冲突题） | 预先列出的反证写出了几条 |
| 需要补问（仅背景题） | 拿到这份答案后，是否还得补一次背景再问才能用；记补问次数 |

- **证据指标**：前三列。任一列试验组比对照组差，即判退化。
- **收益指标**：第四列，按 §2 判定。

### 4.5 复跑与成本

- **复跑**：只有证据过关、且至少两道背景题少一次补问时才做。复跑那几道背景题，两组各一次，同样盲评，收益再次出现才算成立。
- **成本**：
  - 机时：首轮 18 次只读 query，按每次 1–3 分钟估，约 0.5–1 小时。
  - 用户：出题、列反证基准、评分，约 1–2 小时。
- **结论**：摘要写回调研笔记；原始答卷留在试验目录，不进仓库。

### 4.6 首轮结果（2026-11-22～23）

**与本节设计的偏离**（如实记录，判定时一并考虑）：

- **题目与分组**：改用用户事先准备的两份角色画像（角色甲、角色乙）和 10 道共用测试题，分三组：无画像、角色甲画像、角色乙画像，共 30 次运行，而不是 9 题 × 2 组。题目都是带反证条件的完整案情题，没有按背景题、事实题、冲突题三类出；反证条件写在题干里，应出现的处理写在出题对照中。
- **入库未完成**：试验库 入库仍在进行，题目只取已入库部分。每题三组同时启动，面对同一库状态。
- **画像与题目文件原在库内**。试验期间移到试验目录，跑完原样移回；答卷里没有出现画像目录、出题对照等字样。
- **记忆库**：开跑前两个 `memory.db` 的生效条目均为 0。
- **先修了 query 缺陷**：首次开跑时只读 `query` 因模型尝试 shell 而整次 `permission_denied`。修复后（宿主先做召回、提示明说不调 shell）30 次运行全部成功。两组走同一份修复后的提示，不影响组间比较。

**客观统计**（按组汇总）：

| 组 | 平均长度 | 每份不同引用数 | 引用可定位 |
|---|---|---|---|
| 无画像 | 约 4,200 字 | 16.1 | 160/161 |
| 角色甲画像 | 约 6,100 字 | 13.6 | 135/136 |
| 角色乙画像 | 约 6,200 字 | 14.4 | 144/144 |

**角色辨认**（两位评分人盲猜每份答卷属于哪一组，揭盲对照）：

| 评分人 | 单份猜对 | 一题三份全对 |
|---|---|---|
| 甲 | 26/30 | 8/10（错的两题都是角色乙画像与无画像互换） |
| 乙 | 30/30 | 10/10 |

**结论与未完成项**：

- **画像起作用，且角色差异可稳定辨认。** 随机猜一题三份全对的概率是 1/6，10 题全对约 1.7×10⁻⁸。角色甲画像一次都没被认错，角色乙画像有两次被认成无画像。
- **不是靠篇幅辨认。** 有三题的无画像答卷比某个画像组更长，这三题仍大多认对。
- **证据方面**：「引用可定位」三组都在 99% 以上，没有退化。带画像的两组篇幅长约 45%，不同引用数略少。
- **§2 判定还没出。** 「引用支持结论」「反证条件处理」两列和补问次数还没评。评分人揭盲后再补这几列已经不是盲评，评分表里要注明。
- **补问次数不太适用。** 本轮题目都是完整案情题，题干已经交代了背景，可能需要补出几道依赖用户背景的短问题再评收益。
- **召回混入了画像（设计时零 LLM 复核发现）**：本轮把画像拼在问题后面，宿主召回也用「问题 + 画像」检索。重算 10 题的前 8 个候选，与只用题干相比，角色甲每题只重合 0–2 个，角色乙重合 2–7 个。所以上面的角色差异有一部分来自读了不同的页，不只是写法不同。P5.5 因此改为召回只用问题（决策 D2）。
- 原始答卷、评分表与揭盲记录在 `~/.guanlan/trials/user-md/`，不进仓库。

## 5. 第二期：CLI 只读 query 接入（仅在第一期成立后实施）

- **入口**：只有 `guanlan query` 的只读分支，用一个显式参数指定库外画像文件，例如 `--profile <路径>`。参数名实施时定。
- **提示格式**：复用第一期试验组的格式，即问题后附「附：提问者画像」+ 全文，不另加指令，保证上线行为就是验证过的行为。
- **与 `--backfill` 同时给**：报用法错误退出，不悄悄忽略。回填写进 `syntheses/`，画像不应进入共享内容。
- **路径在知识库目录内**：报错退出。否则 Agent 能读到它，§3 的边界就不成立了。
- **超过上限**：报错退出，不截断，因为截断会悄悄丢掉用户写的后半段。
- **加载成功**：stderr 打一行 `ℹ 已附上画像（N 字）`。
- **不给参数**：行为与现在逐字相同。

**否决的做法**：

- 放在库根，由宿主或 skill 读取：Agent、reader 与 IM 会话都能读到。还要为它补写保护，而 CLI 门禁只能核对、不能恢复（§1）。
- 写进 `AGENTAO.md` 或 skill：所有运行都会加载，包括 ingest。
- 用 Agentao `save_memory` 存画像：存在 SQLite 里，用户看不见，违反 §3.2 的红线。

## 6. Web 接入：留待有实际需求时

本草案不设计 Web 接入。本节记录将来要解决的边界、参考项目的做法和初步倾向，不作为本期实施内容。

### 6.1 要先解决的边界

- **会话姿态会切换**：Web 会话可以从只读切到可写。构造时注入的画像会随会话进入写入轮次，与「只影响回答，不影响整理」冲突。
- **历史残留**：即使只在只读轮带画像，只读轮里生成的回答也会留在会话历史里，切到可写后模型仍看得到。Web 回填（P4.8）会把对话中的答案写进 `syntheses/`，画像的影响就会由此进入共享内容。
- **文件位置**：若为方便改放库根，就要同时解决 reader 与 IM 会话的读暴露，以及 Agent 写入后的恢复问题。

### 6.2 参考项目的注入方式

| 项目 | 注入位置 | 时机 | 依据 |
|---|---|---|---|
| Hermes `bab9a85b67` | 系统提示的 `USER PROFILE` 小节 | 会话开始时冻结快照；会话中修改立即落盘，下个会话才进提示 | 读码：`tools/memory_tool.py`、`agent/system_prompt.py` |
| gbrain `23b28ebe45` | 工作区 `CLAUDE.md` 以 `@USER.md` 导入，由宿主在会话开始时载入；钩子每轮注入的是知识库召回内容，不是画像 | 会话开始 | 读模板：`templates/bootstrap/template-repo/CLAUDE.md` |
| Agentao（观澜运行时） | 用户级记忆进系统提示的稳定记忆块 | 每轮重新生成系统提示，内容取自 SQLite | 读码：`agentao/memory/manager.py` |
| OpenClaw | `USER.md` 在会话启动时加载；共享网关按已认证身份选择对应文件 | 会话开始 | 文档 |
| AnythingLLM | 开启个性化后，问答加载全局记忆与当前工作区的相关记忆 | 每次问答，按相关度召回 | 文档 |
| Agent Wiki、llm-wiki-obsidian | 画像是 wiki 中的一页，按规约由 Agent 读取 | 由 Agent 决定 | README |

**Hermes 的几处细节：**

- **默认关闭**：由配置 `user_profile_enabled` 开启，默认 `False`，上限 1,375 字符。
- **冻结快照**：只在会话开始时生成一次，保持系统提示稳定，提示缓存不失效。
- **防注入扫描**：生成快照时扫描注入模式，命中的条目在快照里换成占位符。注释给出的理由是：冻结快照会让有问题的条目在整个会话乃至跨会话持续生效。
- **放在易变区**：位于系统提示的易变区，排在 skill 索引之后，画像变化时不会让前面的固定部分缓存失效。

**归纳：**

1. **主流是系统提示加会话开始时冻结**，没有项目把画像附在每条用户消息后面。
2. **第一期「附在问题后面」的格式不同于所有参考项目。** 它能回答画像内容有没有用，回答不了放进系统提示后效果是否相同。所以 Web 接入时须用第一期的同一组题再验一次放置位置（§6.3）。
3. **画像冻结在系统提示里，一条写坏的指令会影响整个会话**，例如「不要提反证」。观澜的画像由用户手写、放在库外，投毒风险远低于 Hermes 这种由 Agent 写入的记忆，但影响面相同。第一期的冲突题能量出这类影响；Web 接入时可考虑在长度之外再加内容检查。
4. **没有先例在写入轮去掉画像。** Hermes 的画像全程都在，因为它没有「只影响回答，不影响整理」的约束。这条边界须由观澜自己定。

### 6.3 初步倾向（待 Web 有需求时评审）

- **带画像的会话锁定只读**：创建会话时选择是否带画像；带画像就不提供切到可写和回填，要写入另开会话。这样 §6.1 的姿态切换与历史残留两条一并消除。
- **注入位置**：会话构造时经 `build_from_environment(project_instructions=...)` 写进系统提示，内容为 `AGENTAO.md` 原文加画像小节，`AGENTAO.md` 用 Agentao 的 `load_project_instructions` 读取。整个会话不变，相当于 Hermes 的冻结快照，压缩也不会裁掉。

  不采用逐轮改写 `agent.project_instructions`。Agentao 每轮都会重新生成系统提示，技术上做得到，但中途改写不是上游承诺的用法，而且每切换一次，整段提示缓存都会失效。
- **文件仍在库外**：由 Web 启动参数指定路径，与 CLI `--profile` 对应。
- **reader 部署与 IM 一律不加载**。
- **画像修改只对新会话生效**；会话信息里显示「已附画像（N 字）」。
- **上线前验证放置位置**：用第一期的同一组题，对比「系统提示」与「附在问题后」两组，收益与证据指标都不变差才上线。

## 7. 与 Agentao 用户级记忆通道的关系

调研笔记已记录：Agentao 的用户级记忆（`~/.agentao/memory.db`）默认进入观澜所有运行的系统提示。本草案**不改这条通道**，只把「对照期间通道为空」列为第一期前提（§4.1），避免两组差异混入这部分记忆。通道本身怎么处理另行讨论。

## 8. 测试计划（第二期）

- **不给参数**：提示词与现状逐字相同。
- **给参数**：提示词末尾为「附：提问者画像」+ 全文，问题部分与不给参数时相同。
- **报错退出**：`--backfill` 同时给参数、路径在库内（含经符号链接解析后落在库内）、文件超限、文件不存在，各一条用例。
- **stderr**：加载成功时有提示行，stdout 不受影响。

## 9. 修订记录

**2026-11-22 首轮评审**。结论：第一期零代码试验通过；第二期先收敛到 CLI 只读 `query`，等试验看到可复现的收益再决定是否接入 Web。采纳的意见：

1. **A/B 只差画像内容**：删去试验组多出的「画像不是证据」「照常写反证」两条指令，两组同一套规则（§4.2）。画像与原始答卷移到知识库目录之外（§4.1）。
2. **缩小首轮规模**：从 15 题 × 2 次改为 9 题各一次，共 18 次；一张表人工盲评，删去评分脚本与平均分阈值。关键引用同时核对可定位和是否支持结论；任一证据指标退化即停；收益须复跑确认（§2、§4）。
