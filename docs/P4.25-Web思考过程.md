# P4.25 Web 思考过程显示（只读表现层）· **已实现**（落点见 §10）

> P4 Web 宿主的**表现层增强**：把模型在一轮问答里的推理文本（reasoning / thinking）随流显示在对话气泡上方，
> 默认折叠。零新增 LLM 调用、零新增 token 花费、零写、不改会话存档。
>
> **背景（本相位存在的理由）**：agentao 早已把推理发成 `EventType.THINKING`（`runtime/llm_call.py`
> 的 `_emit_reasoning`，数据 `{"text": ...}`），它自己的 CLI 与 ACP transport 都在消费。观澜 Web 的嵌入
> transport 也收到了这些事件——`build_compat_transport` 只接 `llm_text_callback`（`conversation.py:282`），
> 旁听口 `_on_agent_event`（`conversation.py:377`）只转压缩起止——于是**推理到了进程里、在 Web 这一跳被扔掉**。
> 结果有三：① 思考型模型首 token 前常有几十秒空白，用户只看到「处理中 Ns」心跳；② P4.23 的
> `reasoning_only`（「模型只产生了推理过程，没有给出答案」，`chat.js:855`）只给结论、不给证据；
> ③ 用户无从判断模型是「在想」「在绕圈」还是「卡住了」。

## 1. 范围

**v1 恰好是**：一个文本事件、一个折叠块、64 K 尾部上限、一个前端开关，普通流与 `/goal` 续跑流共用一个处理函数；
`reasoning_only` 时自动展开。**无独立计时、无调用分段、无重试标记。**

**不做**：见 §6 非目标。要点：不落盘、不回放、不进 IM / MCP、不改推理档位、不显示工具步骤。

**归 P4.25 而非补丁**：新增一种 SSE 帧（`thinking`）、一条前端偏好，属 Web 宿主同位阶的表现层半阶段，
与 P4.13/P4.14/P4.20 的「内容渲染器」及 agentao 0.5.12 的 `compaction` 帧同类；不引入数据模型、不新增
退出码、不碰任何写路径，P4.5 层①②③与写锁原样不动。

## 2. 上游事件语义（实现的前提，已读源码核对）

以 `agentao/runtime/llm_call.py`（当前锁定版本）为准：

1. **两条发射路径，相对正文的顺序不同**：
   - **流式**：客户端调用 `on_reasoning_chunk` 时，每片经**每次调用一个**的 `StreamTextSanitizer` 清洗后发 `THINKING`。
     `_on_text_chunk` 首行即 `_flush_reasoning()`，故**在这条路径上**，同一次调用的推理先于正文。
   - **整段回退**：客户端从未调用 `on_reasoning_chunk`（`reasoning_streamed` 为假）时，`chat_stream()` **返回之后**
     才读 `message.reasoning_content` 整段发一次 `THINKING`（`llm_call.py:275-284`）。此时这次调用的正文 token
     **可能已经全部发完**——推理排在正文之后。

   故**不能假定推理先于正文**，任何前端规则都不得依赖「首个 token 到达 = 推理结束」（决策P4.25-3）。
2. **帧边界 ≠ 模型分片边界**：清洗器可能把半截片扣住，到下一片或 flush 时才放出。前端只能拼接。
3. **一轮 ≠ 一次调用**：工具循环里每次 LLM 调用都可能各有一段推理，跨调用会与正文交错。
4. **重试**：`_on_retry` 重置清洗器并发 `LLM_RETRY`；失败那次已显示的推理不会被上游撤回，下一次的推理接着发。
5. **是否有、有多少，取决于提供方**：有的模型完全不发（推理不出 API）；有的发摘要；有的发原文、可长达数万字。

上游的 `THINKING` 与 `LLM_TEXT` 同属 transport 事件面，**并非稳定的 HostEvent 契约**（P4.23 已就 `LLM_TEXT` 记下此点并要求契约测试，
`THINKING` 同理）。故须配一条走**真实调用路径**的契约用例（§5），上游改载荷键或改回退路径时在 CI 里炸，而不是静默变成「再也不显示」。

## 3. 设计

### 3.1 服务端：旁听口加一个分支

在既有 `_on_agent_event`（`transport.subscribe` 旁听，与 token 流回调并行、互不替换）里加一个分支：

`THINKING` → SSE 帧 `thinking`，载荷 `{"text": <str>}`；空串不发。**只此一个**——`LLM_CALL_STARTED` / `LLM_RETRY` v1 不接（决策P4.25-6）。

- **不改 `build_compat_transport` 的构造参数**（决策P4.25-1）：那里冻结了 token 流的语义（注释：「事后改属性是死代码」），
  而 `subscribe` 是 0.5.12 起的公开旁听口，`compaction` 帧已走这条路。同一个 `self._emit` 通道 → 与 `token` 帧按**实际发射顺序**到达。
- **只转 `text`**（决策P4.25-2）：沿 `compaction` 白名单口径。
- **IM 零影响**：IM 的 `emit` 只认 `kind == "token"`（`im/delivery.py:493`），未知 kind 原样丢弃——本相位不改 IM 一个字节，
  另加一条用例钉住。

### 3.2 前端：折叠块

`handleThinking(botEl, payload)` 一个函数，普通流 `handleSSE` 与续跑流（每个内层轮的 `ctx.botEl`）两处调用，共用 `parseSSE`
（沿评审 #11 的归口做法）。规则：

- **建块**：本轮首个非空 `thinking` 帧到达时，在当轮 bot 气泡**之前**插一个 `<details>`（与 `chat-compact` 结果行同一插法
  `botEl.before(...)`）；整轮没有推理就不建块。**默认折叠**（决策P4.25-4）。
- **摘要**：`<summary>` 只显示「思考过程 · N 字」，随追加实时更新。**不显示秒数**（决策P4.25-3）：推理可能在正文之后才到
  （§2.1 整段回退），不存在可靠的「思考结束」时刻；且秒数会把网络等待、重试退避都算成「思考」。
- **纯文本**（决策P4.25-5）：只用 `textContent` 追加，**绝不**走 `render_markdown` / `enhanceContent`。理由两条：
  ① 安全——推理里可能复述页面原文、引入 HTML 或 ` ```mermaid ` 等可执行渲染的载体，不应获得答案同等的渲染权；
  ② 语义——推理里出现的 `[[某页]]` 是模型「考虑过」的页面，不是它**引用**的来源，渲染成可点链接会把二者混淆。
- **心跳**：`thinking` 帧与 `token` 帧一样**撤掉**「处理中 Ns」行；之后若再静默满一个心跳间隔，服务端照常发 `heartbeat`、
  前端照常重建该行。不新增任何计时器，也就没有需要在 `done` / `turn_done` / `stopped` / `error` / 断流时额外清理的状态。
  （必须撤：`thinking` 帧会重置服务端 `queue.get` 的心跳等待，推理流动期间不再有心跳帧，不撤则旧秒数会冻在屏上，看着像卡死。）
- **长度上限**：块内只保留**最后 64 K 字符**，超出时块首显示「前面 N 字已省略显示」（决策P4.25-7）。只截显示、不影响答案；
  64 K 取 P4.20 块源上限同值。
- **收尾**：块一律保留原状。唯一例外：`done` / `turn_done` 帧带 `incomplete.reason == "reasoning_only"` 时**自动展开**——
  这轮唯一的产出就是推理，`appendIncompleteNote` 的提示后面紧跟证据。
- **偏好开关**：顶栏一个「思考」开关按钮（Web 没有设置面板，故与语言切换并列；`aria-pressed` 表状态），默认开，
  存 `localStorage` 键 `guanlan.thinking`（读写都 try/catch，读不到按默认）。关掉时 `handleThinking` 直接返回、不建块——
  但调用方**仍撤心跳**（理由同上）；已有的块经 `body.hide-thinking` 即时隐藏，再打开即显出。服务端照发（决策P4.25-8）。
  reader 模式（P4.9）下按钮保留。
- **i18n**：新增 `thinking.title`（含字数）/ `thinking.elided` / `btn.thinking` / `tip.thinking` 中英两套（P4.7）。

**v1 已知的显示局限（接受，不修）**：没有调用分段，多次调用的推理首尾相接；重试时失败那次的推理与下一次的推理也直接相接。
二者都只影响阅读，不影响正确性。要分段须接 `LLM_CALL_STARTED`，而那会带来「已有推理后又来一次无推理调用 → 空分隔」等问题
（决策P4.25-6），留待有真实需求再议。

### 3.3 不落盘、不回放

- 观澜**不新增**任何推理存储（决策P4.25-9）：`thinking` 帧只活在当次 SSE 流与当前页面 DOM 里，刷新即无。
- `GET /api/chat/{id}/messages` 的回放**不显示**推理，即便盘上消息里带着推理载体（如 `reasoning_content`）：
  ① 该字段是否存在因提供方而异；② `ConversationStore.restore` 在恢复边界会 `purge_model_specific` 清掉这些载体（P4.23 §3.2），
  显示一个会自己消失的东西不诚实；③ 推理不是知识库的事实来源，不应在任何持久界面上与答案并列。
- 注意区分：观澜「不新增存储」**不等于**「盘上没有推理」。agentao 序列化的消息里本就可能带推理载体，那是 P4.2 会话落盘的既有行为、
  本相位不改；文档与 UI 文案不得写「推理不会被保存」。

## 4. 信任与成本

- **不新增信任面**：Web 只绑 `127.0.0.1`（决策P4-4）；推理来自同一模型、读的是同一个库，信息量不超过答案 + 工具结果。
  reader 模式（P4.9）同样显示——它限制的是写，不是看。
- **不新增 LLM 花费**：推理是否生成由模型端与推理档位决定，观澜只是不再丢弃它。
- **带宽**：推理可能是答案的数倍长，都经同一条 SSE。本机回环，可接受；因此 v1 不做服务端开关（决策P4.25-8）。
  若日后 Web 走出本机（目前无此计划），再议。
- **清洗**：上游已对推理做清洗（`StreamTextSanitizer` / `sanitize_text_field`），前端只用 `textContent`，观澜不另做一套。

## 5. 测试面

`tests/test_web.py`（fake factory，沿 `test_compaction_events_become_whitelisted_frames` 写法）——**只断言帧序与上游发射序一致，
不断言推理在 token 之前**：

1. `THINKING` → `thinking{text}` 帧；载荷只有 `text` 一个键。
2. 空串 `THINKING` 不发帧。
3. 交错保序：按「推理 → token → 推理 → token」与「token → 推理」（模拟整段回退）两种顺序发射，SSE 帧序逐一一致。
4. `/goal` 续跑流里同样出现 `thinking` 帧，且落在对应内层轮的 `turn_start` 与 `turn_done` 之间。
5. `GET /messages` 回放：盘上 assistant 消息带 `reasoning_content` 时，回放项**不含**它（反向用例，防日后有人「顺手」加上）。
6. reader 模式下照样有 `thinking` 帧。

`tests/test_im.py`：IM 的 `emit` 收到 `thinking` 帧不抛、不改 `latest`、不触发发送。

`tests/test_agentao_contract.py`（**真 Agentao**，P4.23 约定的唯一上游行为观测点）。**不得**手工构造 `AgentEvent(THINKING, …)` 再 emit——
那只验接线，上游生产端把 `text` 改名照样全绿。改为替换 `real_conv.agent.llm.chat_stream`，经真实 `agent.chat()` 调用路径驱动，
用 `real_conv._emit` 收帧，两条用例：

- **流式**：fake 先调 `on_reasoning_chunk("推理")` 再调 `on_text_chunk("答")` → 收到 `("thinking", {"text": "推理"})`，且在 `("token", "答")` 之前。
- **整段回退**：fake 只调 `on_text_chunk`，返回的响应 `choices[0].message.reasoning_content = "推理"` → 收到同样的 `thinking` 帧，且在 token **之后**。

fake 的签名须**显式写出**上游传入的关键字（`on_text_chunk`、`on_reasoning_chunk`、`on_retry`、`cancellation_token`……），不写 `**kw`：
上游改名关键字时显式签名会 `TypeError` 而失败，`**kw` 则会吞掉（同 `test_arun_forwards_cancellation_token_and_images` 的教训）。
响应对象的形状照 agentao 自身测试构造 `chat_stream` 返回值的方式，不自创。无需请求真实模型。

前端：新增 `scripts/smoke_p425.py` 真浏览器冒烟（Playwright，沿 `smoke_p420.py`；不进 pytest；注入 fake 帧，不打真 LLM）：
折叠默认态、`reasoning_only` 自动展开、字数摘要更新、64 K 截断提示、推理后再来 `heartbeat` 能重建心跳行、偏好关掉后不建块但心跳照撤、
推理里的 `[[页]]` / `<b>` 以字面显示。

## 6. 非目标

- **调用分段 / 重试标记 / 思考计时**：见 §3.2 末段与决策P4.25-3/6。
- **工具步骤时间线**（读了哪页、跑了哪条检索）：价值更高也更大，涉及 `TOOL_START`/`TOOL_COMPLETE` 载荷脱敏，另案。
- **推理档位调节**：CLI `ingest --thinking` 已透传 agentao；Web 侧加入口会牵动会话构造与成本口径，另案。
- **持久化与回放推理**：见 §3.3。
- **IM / MCP**：IM 的消息是整条/编辑式送达，推理只会刷屏且进群即公开；MCP 只返回工具结果，客户端自有推理展示。
- **子 Agent 推理**：上游本就不转发给父级（§7），不显示。

## 8. 决策表

| 编号 | 决策 | 理由 |
|---|---|---|
| P4.25-1 | 走 `transport.subscribe` 旁听口，不改 compat 构造参数 | 构造期冻结的回调事后不可改；与 `compaction` 同路、同通道保序 |
| P4.25-2 | 载荷只转 `text` | 沿 `compaction` 白名单口径 |
| P4.25-3 | 不显示思考秒数，不以首 token 判定推理结束 | 整段回退时推理在正文之后；秒数会混入网络等待与重试退避 |
| P4.25-4 | 默认折叠 | 推理是诊断信息，不与答案争主位 |
| P4.25-5 | 纯文本显示，不渲染 markdown、不解析 `[[链接]]` | 安全（不给推理渲染权）+ 语义（考虑过 ≠ 引用） |
| P4.25-6 | v1 只接 `THINKING`，不接 `LLM_CALL_STARTED` / `LLM_RETRY` | 分段带来空分隔、重试尾片顺序等问题，收益只是阅读便利 |
| P4.25-7 | 显示上限 64 K 字符，保留尾部 | 防 DOM 卡顿；离答案最近的推理最有用 |
| P4.25-8 | v1 只有前端开关，无服务端旗标 | 本机回环带宽可忽略；不扩配置面 |
| P4.25-9 | 观澜不新增推理存储，回放不显示 | 载体因提供方而异、恢复时被清；推理不是事实来源 |

## 9. v2 修订记录（第三方评审，2026-10-24）

1. **推理先于正文的假设撤回**：整段回退在 `chat_stream()` 返回后才发，此时正文可能已发完（§2.1）。连带删掉「首 token 停表」规则，
   测试改为只断言保序（§5）。
2. **删掉思考计时**：v1 计时器的收尾出口（`done` / `turn_done` / 错误 / 断流，尤其没有 token 的 `reasoning_only`）未闭合，
   且与 `heartbeat` 重建行冲突。改为摘要只显示字数、保留既有心跳（决策P4.25-3）。顺带补上「`thinking` 帧须撤心跳」——
   它会重置服务端心跳等待，不撤则旧秒数冻屏（§3.2）。
3. **契约用例改走真实调用路径**：替换 `chat_stream`、覆盖流式与整段回退两种情况，显式签名防关键字改名被吞（§5）。
4. **删掉调用分段与重试标记**：不接 `LLM_CALL_STARTED` / `LLM_RETRY`；v1「块内无字不插分隔」挡不住「已有推理后又来一次无推理调用」
   的空分隔。原 §7 待核项①③随之作废，决策重新编号。
