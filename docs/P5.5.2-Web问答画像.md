# P5.5.2 — Web 问答画像

> **状态**：草案（2026-11-23），经一轮评审（§6），§5 已由用户拍板，未实现。
> **前置**：[P5.5 CLI 问答画像](P5.5-CLI问答画像.md)（注入通道、校验、隐私）、[P5.5.1 画像默认路径](P5.5.1-画像默认路径.md)（`~/.guanlan/USER.md`、文件存在即使用、坏了降级）。本稿回答 P5.5.1 §6 列出的五个问题。
> **目标**：本机 `guanlan web` 的对话会话也能带上用户画像。界面上始终看得到本会话是否带了画像，也能在单个会话里关掉。
> **不做**：`--reader` 部署的画像；IM、MCP 的画像；在浏览器里编辑画像；按会话选不同画像文件；把画像写进库内任何文件。

## 2. 决策

### W1 范围：只有本机 `guanlan web`，不含 `--reader`，不含 IM

- 画像来源只在 `cli.py::_cmd_web` 里解析，结果以显式参数一路传进 `ConversationStore(profile=…)` → `Conversation(profile=…)`。两者的参数默认是「不带」。
- **IM 不传**：IM 的提问者是 `--allow-user` 里的他人，不是运行进程的人。IM 构造 `ConversationStore` 时不给这个参数，行为逐字不变。
- **`--reader` 不带**：reader 可能给多人用，宿主机主人的画像不能套在别人头上。
  - `--reader` 下忽略默认路径，不读、不提示。
  - `--reader --profile <路径>` 是用法错误，启动前拒绝（退出码 2）。
- 与 P5.5.1 D2 同理：把解析放在入口层，是为了让复用 `Conversation` 的其它宿主不会无意间带上画像。

### W2 来源：与 CLI 同一套规则

`guanlan web` 加 `--profile <路径>` / `--no-profile`（互斥），规则与 P5.5.1 D1 相同：

| 参数 | 画像来源 |
|---|---|
| `--profile <路径>` | 该路径 |
| `--no-profile` | 不带 |
| 都不给，`~/.guanlan/USER.md` 存在 | 默认路径 |
| 都不给，不存在 | 不带 |

**启动时先校验一次**，结果打在启动信息里（stderr，与端口、库路径等启动信息放在一起）：

- 生效：`提问者画像：~/.guanlan/USER.md（新会话带上；会话内 /profile 查看或关闭）`
- 默认文件不合格：`⚠ 默认画像未使用：<原因>（~/.guanlan/USER.md）`，照常启动，不带画像（同 P5.5.1 D4）。
- 显式 `--profile` 不合格：拒绝启动，`EXIT_USAGE`（同 P5.5 D4）。

启动信息每次启动都打。P5.5.1 D3「只打一次」针对的是每次提问都会运行的 CLI；Web 启动不频繁，启动信息本来就是一屏状态，不读写 `profile-notice`。

启动后，**每个会话构造时按同一规则重新解析一次**（W3），与 CLI「每次运行都重新解析」一致：

- 默认路径：启动后才建的 `~/.guanlan/USER.md`，对之后的新会话生效；启动时坏了、后来修好的，也对新会话生效。不必重启。
- 显式 `--profile`：路径在启动时定下并校验；之后每个会话按该路径重读。
- 启动信息只反映启动那一刻；运行中的实际状态以会话标记和 `/profile` 为准（W5）。

### W3 读取时机：会话构造时读一次，作为本会话的快照

- 新建会话和懒恢复会话都在 `Conversation.__init__` 里按 W2 解析来源、用 `load_profile` 读一次，经 `build_profile_instructions` 拼好，以 `project_instructions=` 传给 `build_from_environment`。之后本会话一直用这份。
- **改了画像文件，对新会话生效**，已打开的会话不变。与 Hermes「会话开始时读取、作为会话快照」一致。
- **不每轮重读**：项目指令是系统提示的第一段，内容一变，提示缓存的前缀就全部失效；每轮重读还要每轮做一次文件校验。收益只是「改画像后已开会话立即生效」，新开一个会话即可做到。
- **懒恢复读的是当前文件**：系统提示不落盘（§1），恢复时只能重新读。所以恢复后的会话可能带的是改过的画像，甚至原来带、现在不带（文件被删了）。画像与姿态无关（W4），恢复成什么姿态都照样带。`/profile` 显示的是恢复后的实际状态。
- **运行中文件坏了**：某次会话构造时读取失败（不论是启动时就生效的默认路径还是显式路径），该会话不带画像，`info()` 带上警告原因（W5），不拒绝建会话。启动时显式路径已校验过；运行中才坏的，拒绝建会话会让整个 Web 对话不可用，代价过大。

### W4 可写姿态下画像照常生效

画像与姿态无关：会话在只读和 `workspace-write` 下都带画像，`/mode` 切换不动 `project_instructions`。要在某个会话里不带画像，用 `/profile off`（W6）。

- **用户决定（2026-11-23）**：接受画像影响可写轮。首稿推荐「可写时暂停」，未采纳。
- **与 CLI 的不一致，需要明说**：CLI 回填（P5.5 D4、P5.5.1 D5）和 Web 回填作业（W8）都不带画像，理由是写进共享 `wiki/` 的内容不应受个人画像影响。Web 对话的可写轮则会带着画像改 `wiki/`（以及 `SCHEMA.md`、`workspace/`）。区别在于：
  - 回填是「一键把答案沉淀进库」的批量入口，用户不逐字看；
  - Web 可写轮是人在对话里逐轮发起、看得见每一轮的写入，并有「撤销本轮写」（P4.5）。画像对写法的影响在用户眼前。
- **缓解**：
  - 会话标记在可写姿态下显示为「画像（可写）」（W5），提醒这一轮的写入带着画像；
  - 用户想让某次写入不受画像影响时，先 `/profile off`；
  - 用途句不变：画像只管切入角度、详略和术语，事实和引用以库内资料为准，与库规约冲突时以库规约为准。写进 wiki 的事实仍须有引用，写门禁（check）照常把关。
- `/goal` 续跑同样带画像。
- **好处**：`/mode` 不再牵动系统提示，切姿态不会让提示缓存失效，`agentao.log` 也不会因切姿态重记画像段；实现比「暂停」少一条状态分支。

### W5 看得见：会话状态 + `/profile`

- `Conversation.info()` 增加 `profile` 字段：

  ```json
  {"state": "active", "path": "~/.guanlan/USER.md", "warning": null}
  ```

  - `state` 取值：`none`（本会话无画像来源）、`active`（本轮会带上）、`off`（本会话用 `/profile off` 关了，W6）、`failed`（构造时读取失败，原因在 `warning`，W3）。
  - 前端结合已有的姿态字段显示标记，不另设字段。
  - **不返回画像正文**：前端不需要；`info()` 的结果也会进日志和调试工具，少一处明文。
- 进程级 `/api/info` 增加 `profile: {"source": "default" | "explicit" | null, "path": …}`。新会话要到首次 `POST /api/chat` 才创建，首轮之前前端拿不到会话的 `info()`，靠这一项先显示「新会话将带画像」。
- 前端：
  - 会话头部与姿态、模型并列显示一个小标记：「画像」/「画像（可写）」/「画像已关」/「⚠ 画像未加载」。`state` 为 `none` 时不显示。
  - 斜杠命令 `/profile`：显示上面的状态与路径，以及「改画像文件后对新会话生效」。
  - 文案进 `i18n.js`，中英两套。

### W6 单会话关闭：`/profile off`、`/profile on`

- `POST /api/chat/{id}/profile`，请求体 `{"enabled": false|true}`。**照抄 `/mode` 端点的前置处理**：冷会话 409、未知会话 404；取 `conv.lock` **之前**先 `_reject_if_writable_active()`，否则 Agent 在可写轮里 curl 本端点会自死锁（`/mode` 评审时修过的同一问题）。然后持 `conv.lock` 执行，与在飞的一轮串行。
- **做法**：会话构造时算好两份项目指令：
  - `base`：`load_project_instructions(kb)`，与 agentao 不带画像时自己读到的逐字一致；
  - `with_profile`：`build_profile_instructions(kb, profile)`。

  `off` 把 `agent.project_instructions` 设为 `base`，`on` 设回 `with_profile`。不重建 agent，不丢对话历史。生效规则：`state = active` 当且仅当有来源 ∧ 构造时读取成功 ∧ 未关闭。
- **依据**：agentao 每轮开头按 `agent.project_instructions` 重建系统提示（§1），所以改属性下一轮即生效。端点持 `conv.lock`，与在飞的一轮串行，不会落在一轮中间。
- **风险**：`project_instructions` 是 agentao 的公开属性名（无下划线），但「运行期改写它」不是文档化用法。加一条 `tests/test_agentao_contract.py` 契约测试，**跑真实的两轮**：真实 Agentao、猴补 LLM 客户端截获请求，第一轮后改属性，断言第二轮**实际发出的** system 消息随之变化（设为空串时 Project Instructions 段消失）。只调 `_build_system_prompt()` 不够：`_runner.py` 已有按脏标记跳过重建的逻辑，上游若把这类缓存扩展到跨轮，直接调函数的测试仍会绿，`/profile off` 却会静默失效。
- **代价**：开关时系统提示第一段变化，提示缓存前缀失效一次；开关不频繁，可以接受。历史里已有按画像写的回答，`off` 之后模型仍看得到。
- `state` 为 `failed` 或 `none` 时 `on` 返回 409：没有可放回的内容，要重新读需新开会话。
- **关闭状态不落盘**：懒恢复的会话回到「带画像」。会话落盘只存 `messages`，为一个开关加一份 sidecar 不值得；`/profile` 会显示恢复后的实际状态。
- `--reader` 下不注册这个端点（reader 本来就不带画像）。
- **理由（用户决定首版就给）**：W4 让画像也作用于可写轮，`off` 是用户让某次写入不受画像影响的唯一入口；否则只能带 `--no-profile` 重启整个 Web。

### W7 落盘与留痕

- **会话快照不含画像原文**：系统提示不在 `messages` 里。测试锁定：带画像的会话落盘后，快照文件不含画像中的标记词（模型回答没有复述它时）。
- **但画像会间接进入库内**：按画像写的回答常会复述画像（如「考虑到您是…」），这些回答随会话快照落在 `<库>/.agentao/sessions/`，也就是**库目录内**。CLI 不落会话，这是 Web 新增的留痕路径，与 P5.5.1 §2「画像不进库」有张力。本稿不做过滤（无法可靠识别复述），只如实写明：`zip` 不打包 `.agentao/`，但直接复制库目录会带走；不想留痕可用 `--no-session-persist`。
- **`agentao.log`**：非 reader 的 Web 默认写库根 `agentao.log`（P4.9-15），画像会以明文出现在日志里，与 CLI 相同（P5.5 D6）。日志首次请求记完整系统提示，之后只记变化，所以每次开关画像（W6），画像段都会以差异的形式再记一遍（切姿态不会，W4）。可用 `--no-agent-log` 关闭会话日志。
- 启动信息和 `--profile` 帮助写明以上两点。
- 画像文件仍在库外，观澜不复制、不缓存（内存里的会话快照除外）、不改写。

### W8 不受影响的路径

Web 里这些路径不带画像：回填作业（`run_query(backfill=True)`）、上传入库与 `ingest`/`heal`/`audit` 等子进程作业、体检、MCP 诊断、wiki 浏览。只有对话会话带画像。
