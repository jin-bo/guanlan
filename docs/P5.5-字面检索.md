## 0. 为什么要第二条召回路

`search` 的分词把非 CJK 段切成 `[a-z0-9]+`（[`search.py:72`](../guanlan/search.py)），于是：

| 查询 | 实际参与打分的词 |
|---|---|
| `bge-m3` | `bge` + `m3` |
| `P4.22` | `p4` + `22` |
| `v0.1.23` | `v0` + `1` + `23` |
| `claude-opus-5` | `claude` + `opus` + `5` |

**召回不丢**（query 与文档同一 `tokenize`，决策P5.0-3），丢的是**精度**：一条标识符查询实际退化成"其中最稀有的那一段"，数字段在真实库里是高频噪声、被 IDF 压到近乎无贡献。而观澜自己的语料**恰恰塞满这类标识符**——决策编号、阶段号、版本号、模型名、slug。

实测（两页微库，一页含 `bge-m3`、另一页只分别含 `bge` 与 `m3`）：

```
$ guanlan search bge-m3
query「bge-m3」· 检索 2 页 · top 2：
  [0.724528] wiki/entities/bge-m3.md  «bge-m3»（entity）
  [0.391324] wiki/entities/other.md   «其他页»（entity）     ← 这页根本没有 bge-m3

$ guanlan grep bge-m3
字面「bge-m3」· 扫描 2 页 · 命中 2 处（1 页）：
  wiki/entities/bge-m3.md:9
      bge-m3 是一个嵌入模型，决策P4.22-14 提到过它。
  wiki/entities/bge-m3.md:10
      bge-m3，还有 BGE-M3 大写形式。
```

**为什么不改 `tokenize` 反而新开一条路**：让 `tokenize` 保留复合标识符、再额外吐拆分片段、还要给扩展词降权——这三件事里第三件根本不是分词改动。观澜的打分数据流是 `tokenize(text) → list[str] → DocBag.tf: dict[str, int]`，**词项来源在数据结构里根本不存在**；要支持"扩展词命中弱一档"得改 `tf`/query 词项的表示、改 `score()` 的累加，波及 P5.3 反链重排与全部黄金集。而合并 token 还会抬高 `|d|`、让 BM25 长度归一化令**全库分数整体漂移**。相比之下本阶段**不动 `tokenize` 一个字节、不碰 BM25、不影响任何既有黄金集**——它是新增的第二条路，不是改动第一条路的口径。

## 1. 命令契约（新增 `guanlan grep`，无新退出码）

```bash
guanlan -C my-wiki grep "bge-m3"
guanlan -C my-wiki grep "决策P4.22-14" --json
guanlan -C my-wiki grep "[[某实体]]" --limit 200
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `pattern` | — | 要找的**字面**串（**不是正则**） |
| `--limit` | 50 | 全库命中上限（须 ≥ 1） |
| `--json` | 关 | 输出 JSON 契约 |

退出码沿用既有集合：成功 `0`、用法/库根错 `1`（`EXIT_USAGE`）。**无新码**（同决策P5.0-6）。

## 2. 模块与归口

新增 [`guanlan/grep.py`](../guanlan/grep.py)，**内核 / 命令壳分立**（仿 P5.0）：

- `grep_pages(wiki, pattern, *, limit) -> GrepResult` —— 内核，纯读、无状态、可被将来的 Web/MCP 直接复用；
- `grep_result_dict(result) -> dict` —— JSON 契约**字段单一归口**（同决策P5.1-4），CLI/Web/MCP 三处不再各写一份映射；
- `run_grep` / `grep_entrypoint` —— 打印壳与库根校验，错误输出口径与 `search` 一致（`--json` 出 `{"ok":false,"error":…}` 到 stdout，否则 stderr 纯文本）。

`GrepHit` **不带分数**：本路不排序，加一个假分数只会误导消费侧去比较它。

## 3. 决策

- **决策P5.5-1（另立命令、另立契约，不并入 `search`）**：字面扫描没有分数、没有排序、没有分词，塞进 `SearchResult` 会逼出一个假的 `score` 字段。两条路**并列、互不替代**：`search` 管"按含义找"，`grep` 管"按原文字面找"。二者扫的是**同一批页**，故用户可以拿 `grep` 的结果直接回去看 `search` 为什么没排上来。

- **决策P5.5-2（匹配口径钉死为「字面 + 大小写不敏感」，无旋钮）**：三件事各有理由。
  ① **字面**：输入过 `re.escape`，**永不当正则**。本路唯一的承诺是"你打的这个串字面出现在这一行"，接受正则会让这句话变成假的（`.*` 会"命中"一切），还会引入灾难性回溯。代价是查正则的需求落空——那种需求该用真的 `grep`/`rg`，观澜不做半个正则引擎。
  ② **大小写不敏感**：经 `re.IGNORECASE` **直接在原行上匹配**，故 `m.start()` 是**原文偏移**、片段窗口有效。刻意不用"先 `.lower()` 再 `find`"——`'İ'.lower()` 是两个字符，那条路上的偏移会静默错位。
  ③ **不做 NFKC / 全半角 / CJK 归一**：归一过的"命中"在文件里**并不字面存在**，会让"页:行号 + 片段"这条证据链失真；且 `search` 对正文同样不归一，两条路不因此分叉。测试里带**正对照**（全角原样查得到、半角查不到），否则"查不到"这条断言什么也证明不了。
  **不给旋钮**：`--case-sensitive` / `--regex` / `--normalize` 一个都不加。口径是契约，可调的口径等于没有契约。

- **决策P5.5-3（扫描面 = `iter_pages`，即 `wiki/` 非 config 页；不扫 `raw/`）**：与 `search` 同一批页，复用同一个归口，config 三件套（`index.md`/`log.md`/`overview.md`）自动排除——否则 `index.md` 会把几乎所有查询都命中一次。**`raw/` 明确不在范围内**：那是另一个问题（源审计），需要另一套口径（原件不可变、体量大、非 markdown 单格式），本阶段不含它，记在 §5。

- **决策P5.5-4（双封顶 + 触顶必须说出来）**：单页至多 `MAX_MATCHES_PER_PAGE`（5，常量、非旗标）、全库至多 `--limit`（默认 50）。单页封顶是防"一张把某编号重复几十次的页把整个回执吃光"。**触顶时 `truncated=True`**，文本侧多一行说明、JSON 侧多一个字段——**绝不静默丢**。截断文案报的是**两道闸各自的值**（单页 5 / 全库 `limit`，后者随回执一起出在 `GrepResult.limit` 与 JSON 契约里），**不报 `len(hits)`**——单页闸先拦住时后者会让人误以为 `--limit` 就是 5。反向也钉死：没触顶就**不许**报 `truncated`（多报会让这面旗子失去意义、用户学会无视它），恰好等于上限的边界同样不报。
  另：截断只截**命中列表**，`pages_searched` 照实数全——回执自己不能先失真。

- **决策P5.5-5（正文限定匹配，但行号按原文件计）**：frontmatter 不参与匹配（命中 `origin:`/`tags:` 会让"第 N 行有这个串"指到一行配置上），但行号必须指回**原文件**，否则带 frontmatter 的页整体偏移若干行、照着行号跳过去是错行。实现取 `len(text) - len(body)` 这段前缀里的换行数作偏移——`split_frontmatter` 的 `body` 是 `text` 的**逐字后缀**，故这个算法是精确的而非估算。

- **决策P5.5-6（不建索引、不落任何派生物）**：整库扫一遍文本，与 P5.0 的 stateless 边界一致。观澜库的体量是"人能读完的 markdown"，一次全扫的成本远低于维护一个倒排索引的成本与一致性风险（markdown 唯一真相：索引一旦落盘就成了要维护的第二真相）。若将来真撞上性能墙，先按 P5.4 的办法做**进程内 memo**，仍不落盘。

## 4. 确定性

页序取 `iter_pages` 的稳定排序、页内按行号升序，无时间戳/随机/盘上派生物——**同库同串两次调用字节一致**（有专测）。

## 5. 边界（明确不做）

- **不扫 `raw/`**（决策P5.5-3）。源审计是另一个问题，要另立口径。
- **不接 Web / MCP**。仿 P5.0 → P5.1 的分期：内核 + CLI 先落，宿主接入另作半阶段（内核与 `grep_result_dict` 已按可复用写好，接入成本是几十行）。
- **不做正则、不做模糊匹配、不做同义扩展**（决策P5.5-2）。
- **不与 `search` 混排**：两条路各自出各自的回执，不做加权融合——融合需要一个把"分数"和"有没有"放在同一标尺上的理由，目前没有。
- **不改 `tokenize`**（§0）。复合分词与扩展词权重仍属暂缓项，证据留在反向评审笔记 §1.C。

## 6. 测试要点（`tests/test_grep.py`，34 例）

- **口径**：大小写不敏感；字面不当正则（`.*`/`[abc` 既不匹配任意内容、也不报错，**且正对照证明字面就查得到**）；`[[某实体]]` 这种形状查得到；不做 NFKC（**带正对照**）。
- **行号**：带 frontmatter 的页行号指回原文件（断言里回读原文件那一行核对）；无 frontmatter 从 1 起；未闭合 frontmatter 按"无块"处理。
- **扫描面**：config 三件套一页不扫（`pages_searched == 0`）；frontmatter 里的串不命中；`raw/` 里的串不命中。
- **双封顶**：单页超限截断且报 `truncated`；全库 `--limit` 截断且报；**恰好等于上限不报**；没触顶不报；截断不扭曲 `pages_searched`；截断文案报的是两道闸各自的值（单页闸先拦住时仍说得出 `--limit` 的真实值）。
- **入参**：空/纯空白串与 `limit < 1` 抛 `ValueError`。
- **确定性**：两次调用 JSON 字节一致；命中按 (页, 行) 升序。
- **容错**：坏字节页照扫不抛（`errors="replace"`，同决策P5.0-16）。
- **CLI 壳**：文本/JSON 两侧回执形状、错误形状、非库根拒绝、无命中文案。
