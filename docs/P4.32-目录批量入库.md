# P4.32 — 目录批量入库（`guanlan import <目录>`：一个目录 = 一个一键入库任务）（草案）

> **状态**：已实现（2026-11-13）。§10 已裁定、评审意见已改入正文（见 §10「评审」「复审」行）；实现中的补充标「实现说明」。
> 改动集中在 `guanlan/oneclick.py`（任务清单、准备、预检、回执）与 `guanlan/cli.py`（参数），新增目录扫描函数；
> Web 只做到「能显示、能继续、能放弃」CLI 发起的批量任务（§8）。
>
> **定位**：`guanlan import ./dir/` 把目录里的多份原件排成**一个**一键入库任务：逐份准备（①–④），全部准备好后
> **统一确认一次**，再逐份落 `raw/`、逐篇串行入库。P4.30 的任务模型不变：一个库同时只有一个任务、整个任务是
> JobQueue 里的一个作业、篇与篇串行、任一篇失败即停（决策P4.30-7）。
>
> **首版取舍（已定，2026-11-12）**：
> 1. **全部准备完再统一确认**，不做「准备一份入一份」的流水线；
> 2. **准备阶段任何一份失败 → 整批失败**，一篇都不入，没有「部分可入」状态；
> 3. **不递归**，只收目录第一层的文件；
> 4. **只做 CLI 入口**；Web 不新增发起入口。
>
> **不推翻既有决策**。确认关口（决策P4.30-8）、库级写锁（决策P4.30-15）、续跑判定（§6.4）、首版不做整书替换
> （决策P4.30-12）原样沿用；本期只把「一份原件」扩成「一组原件」。

## 0. 动机

P4.30 解决了**一本书**从原件到入库的全流程，但入**多本**时仍要写 shell 循环：

```bash
for f in dir/*.pdf; do guanlan -C kb import "$f" --yes || break; done
```

这个循环能用（每个任务结束后才开下一个，不违反「唯一任务」约束），但缺三样：

1. **没有整批确认**：要么每本交互确认一次（几十本就得守在终端前），要么 `--yes` 全部跳过，开跑前看不到整批的拆分结果和冲突。
2. **没有整批预检**：第 8 本才发现 `raw/` 里有冲突，前 7 本已经入库；同目录里 `报告.pdf` 与 `报告.md` 落到同一个
   `raw/报告…`，要跑到第二个才报错。
3. **没有整批进度与续跑**：进度只到「本书第几篇」；中断后要人自己判断循环跑到哪本、哪本已完成。

## 1. 用户流程（CLI）

```bash
guanlan -C <kb> import ./dir/              # 扫描 → 逐份 ①–④ → 打印整批确认摘要 → 交互确认 → ⑤⑥
guanlan -C <kb> import ./dir/ --dry-run    # 只扫描 + 逐份 ①–④ + 打印摘要；零 LLM（目录审校除外，同 P4.30）、不写 raw/、不建任务
guanlan -C <kb> import ./dir/ --yes        # 跳过交互确认（非交互终端必须给）
guanlan -C <kb> import ./dir/ --overwrite  # 对整批的「可覆盖」项背书（§6）
guanlan -C <kb> import --resume / --status / --cancel   # 不变：作用于本库唯一的未完成任务，单份或批量都一样
```

- 位置参数是目录时进入批量模式，是文件时行为与现在完全一样。**不新增子命令或开关**。
- `--model` / `--thinking` / `--backend` / `--no-toc-review` / `--json` 对每份原件统一生效。
- 进展日志格式：准备阶段 `① [3/12] 解析 报告.pdf …`；入库阶段沿用 P4.30 的 `[17/85] 入库 raw/…`（全批篇数统一编号）。
  顶部进度行加原件维度：`入库 17/85 篇 · 第 3/12 份原件 · 已用 …`。

## 2. 目录扫描（零 LLM、确定性）

扫描在**取锁后、准备开始前做一次**，结果写进任务清单后固定，之后不再重扫。锁约束不了外部对目录的修改，
多扫几次也保证不了之后目录不变；准备时某份读不出、不存在或内容变了，按 §4「一份失败即整批失败」处理即可。

**收：** 目录第一层、常规文件（不跟符号链接）、扩展名（不分大小写）在下列白名单内：
`.pdf .docx .pptx .xlsx .html .htm .md` 与图片（`.png .jpg .jpeg .gif .webp .tiff .tif .bmp`）。
白名单与网址导入的格式表同源（决策P4.31-3），抽到 `guanlan/formats.py` 共用，不另立一份。

**跳过（不算错误）：** 子目录、符号链接、白名单外的扩展名、空文件——列入摘要的「已跳过」；隐藏文件（含网址导入的出处记录
`.<名>.source.json`、`.DS_Store`、上传临时文件）**静默跳过**，不列出。
实现说明：隐藏文件不列——`.DS_Store`、出处记录都是正常伴生物，列出来只是噪声。`.markdown` 不在白名单：网址导入会把它改名成 `.md`，
而一键入库内核只按 `.md` 认 Markdown，本地的 `.markdown` 收进来会被送去转换器（`formats.BATCH_IMPORT_EXTS`）。

**拒绝（以用法错误退出，提示原因，什么都不做）：**
- 收到的文件为 0 份；
- 超过单批上限 `BATCH_MAX_FILES = 50`（§10 Q1）；
- **准备产物路径相撞**。只比样本名不够：每份原件准备时会写下面这组路径（`_prepare_steps` 现状），样本名不同也可能撞，
  例如 `A.pdf` 的 `parsed/A.origin.md` 恰好是 `A.origin.pdf` 的整本产物 `parsed/A.origin.md`：

  | 产物 | 路径 | 种类 |
  |---|---|---|
  | 整本 | `parsed/<s>.md` | 文件 |
  | 解析原样 | `parsed/<s>.origin.md` | 文件 |
  | 目录审校 | `parsed/<s>.toc.json` | 文件 |
  | 分卷与目录索引 | `parsed/<s>/` | 目录 |
  | 解析图片 | `parsed/images/<s>/` | 目录 |
  | 落盘目标 | `raw/<s>.md`、`raw/<s>/`、`raw/images/<s>/` | 文件 / 目录 |

  扫描时对每份算出这组路径，两份之间**任一文件路径相等、或一方落在另一方的目录之下**即相撞。比较前统一做 `casefold()`：
  macOS 默认文件系统不分大小写，`A.pdf` 与 `a.PDF` 在这里同样相撞（区分大小写的文件系统上会多拒一些，宁可多拒）。
  再按 NFC 规范化（#197）：只差 NFC / NFD 写法的名字在 macOS 上也是同一个文件；批内 slug 检查（§5）同口径。
  命中 → 以用法错误退出、什么都不做，列出相撞的文件组和撞在哪条路径上，请用户改名或挪走。不做自动改名、不另建隔离目录。

  `<s>` 的计算从 `prepare` 里抽成一个函数（UTF-8 字节截短、空名兜底 `import`、`images → images-doc`），扫描与准备共用，
  保证扫描时检查的就是准备时实际写的路径。分卷文件名由拆分决定、扫描时还不知道，它们只落在 `parsed/<s>/`、`raw/<s>/` 之下，
  目录级的检查已经覆盖。

**顺序**：按文件名的 Unicode 码位排序（与 `sorted()` 一致，不依赖平台的本地化排序），排好后写进任务清单，
续跑与 Web 显示都按清单顺序，**不再重新排序**。顺序有意义：后入的书常补上先入的书留下的断链（决策P4.30-16）。
想要别的顺序，就给文件名加序号前缀。

## 3. 任务清单

### 3.1 形状

单份任务的清单**格式不变**（Web、`--json` 消费方、历史清单都不受影响）。批量任务在此基础上加 `kind` 与 `docs`，
每份原件的准备期字段从顶层挪进 `docs[i]`；`items` 仍是扁平的一条列表，每项加 `doc` 指回原件：

```json
{
  "task_id": "20261112-101500-年度报告-批量",
  "kind": "batch",
  "sample": "年度报告",
  "upload": "../报告集/年度报告",
  "origin": "cli",
  "state": "awaiting_confirm",
  "stages": {"confirm": "pending", "land": "pending"},
  "docs": [
    {"upload": "../报告集/年度报告/2023.pdf", "upload_sha256": "…", "sample": "2023", "split": true,
     "stages": {"parse": "done", "normalize": "done", "split": "done"}, "warnings": []},
    {"upload": "../报告集/年度报告/2024.pdf", "upload_sha256": "…", "sample": "2024", "split": false,
     "stages": {"parse": "done", "normalize": "done", "split": "done"}, "warnings": []}
  ],
  "skipped": ["../报告集/年度报告/notes.txt（不支持的格式）"],
  "prepared_sha256": {"parsed/2023/2023-01-….md": "…", "parsed/2024.md": "…"},
  "normalized": {"headers_removed": 212, "page_numbers_removed": 180, "sentences_joined": 96},
  "warnings": ["2023-03-….md：图片 fig.png 找不到，原样保留"],
  "precheck": {"status": "ok", "details": [], "docs": [{"status": "ok", "details": []}, {"status": "ok", "details": []}]},
  "items": [
    {"doc": 0, "raw": "raw/2023/2023-01-….md", "parsed": "parsed/2023/2023-01-….md", "land": "pending", "state": "pending"},
    {"doc": 1, "raw": "raw/2024.md", "parsed": "parsed/2024.md", "land": "pending", "state": "pending"}
  ]
}
```

- 顶层 `sample` 是目录名的 slug，只用于任务号和日志文件名；它**不对应**任何 `parsed/` / `raw/` 路径。
- 顶层 `upload` 记目录路径（口径同 `_origin_label`）；没有顶层 `upload_sha256`（目录无哈希，各份的哈希在 `docs[i]`）。
- 顶层 `normalized` / `warnings` 是整批合计（#198）：各份的整理统计逐项相加（只加计数项，`toc_applied`、`toc_source`
  这类逐份性质不进顶层）、图片警告按原件顺序拼接。**派生数据，只在准备结束时写一次**，之后不变；各份明细仍在 `docs[i]`。
  这样摘要、Web 任务卡、`--json` 与单份任务读同名字段，不必各自去 `docs[*]` 里合计。
- 任务号后缀 `-批量`，与同名单份任务区分。
- `prepared_sha256` 本就以 `parsed/` 相对路径为键，各份路径不相交，直接合并成一张表。

### 3.2 代码如何同时支持两种形状

**写：批量包装层逐份传入普通字典，完成后归并。**`_prepare_steps` 会直接改传入字典的 `stages`、`items`、`split`、
`prepared_sha256`、`precheck`、`warnings`、整理统计等字段，所以不给它只读视图或可写代理，而是：

1. 包装层为第 i 份新建一个与今天单份任务同形的普通字典（`task_id` 用批量任务的号，`sample` / `upload` /
   `upload_sha256` 是这一份的）；
2. **沿用单份 `prepare` 的出处记录读取**：算出这一份的哈希后调 `read_source_record(src, sha256=…, discard_stale=not dry_run)`，
   有效时把去凭据的 `source_url` 写进这份字典，并把记录作为 `source=` 传给 `_prepare_steps`。漏了这一步，网址下载来的文件
   出处会退回本地路径，Markdown 里的相对图片也会被当成本地附件去找（P4.31 §2.5、§4.4）。这段逻辑从 `prepare` 抽成一个
   小函数，单份与批量共用；
3. 调 `_prepare_steps`；
4. 返回后把它归并进批量清单：准备期字段（`upload`、`upload_sha256`、`sample`、`split`、`stages` 前三项、`source_url`、
   `warnings`、整理统计、`precheck`）进 `docs[i]`；`items` 每项加 `doc: i` 后追加到批量清单的 `items`；`prepared_sha256` 合并进总表；
5. 归并后落一次批量清单。逐份字典用完即弃，不落盘。

`_prepare_steps` 本身**不改**；它在最后顺带做的逐份预检结果照常进 `docs[i].precheck`，批内检查与汇总在全部归并后由包装层做（§5）。

**读：一个小辅助函数兼容单份。**`_doc_entries(task) -> list[dict]`：批量任务返回 `docs`；单份任务从顶层字段拼出一项。
只给摘要、回执、`--status`、Web 任务卡、`upload_in_use` 这些**只读**用途用，返回的字典不写回。

**不改写**旧清单、也不把单份任务改成 `docs` 形状：历史清单只被 `_owned_by_other_tasks` 读 `items`，`items` 的形状没变；
单份任务保持原样，Web 端单份的路径一行不用动。

## 4. 准备阶段（①–④）

- 持库级锁（决策P4.30-15）、先查有没有未完成任务，与单份相同。
- **逐份**执行现有的 `_prepare_steps`（解析 → 整理 → 拆分，传入方式见 §3.2），每份写自己的 `parsed/<sample>…`。整理、拆分、
  目录审校、图片处理的规则**一条不改**。每份开始前现算原件哈希；文件已不存在或读不出，按准备失败处理。
- 每份完成后落一次清单（`docs[i].stages`），所以 `--status` 能看到准备到第几份。
- **任何一份失败（转换失败、整理后为空、图片超容量…）→ 整批记 `failed`**，原因写明是哪一份、什么错误，
  一篇都不落 `raw/`（决策P4.32-2）。已准备好的份数的 `parsed/` 产物留着，由下次准备覆盖；重新导入时 MinerU 有解析缓存，
  已解析过的份不会重新付出解析时间。
- **停止**（Ctrl+C / 将来 Web 的「停止」）：整批记 `cancelled`，语义同 P4.30 #173——准备阶段只停不续。
- 全部完成后：做整批预检（§5），进入 `awaiting_confirm`，释放锁。

**锁时长**：准备阶段全程持锁，30 份 PDF 可能占锁一两个小时，这期间其它写操作立即失败（不排队）。这是决策P4.32-1 的已知代价：
- 开始前摘要先打印「将准备 N 份原件，准备期间本库的其它写操作会被拒绝」；
- 用单批上限（§10 Q1）兜住最坏情况；
- 真需要更大规模时，把目录分成几批跑。

## 5. 预检

在 P4.30 §5 的逐份预检之外，加**批内**检查：

1. **逐份预检**：对每份原件按现有 `precheck` 规则跑一遍（以该份的视图为输入：`sample`、`split` 与它自己的 `items`）。
   现有规则只看盘上 `raw/`，看不到同批其它份**将要写**的文件，所以还需要第 2 步。
2. **批内 slug 冲突**：全批所有目标 `raw/…md` 的 `raw_slug(stem)` 两两不得相同（沿 `ingest._reject_source_slug_collision`
   的口径）。样本名在扫描时已经保证不重，这一步兜的是分卷名与另一份的样本名相撞这类少见情况
   （例如 `A.pdf` 拆出 `A-01-B.md`，而目录里恰好另有 `A-01-B.pdf`）。命中 → 冲突。
3. **汇总**：任一份 `conflict` 或批内冲突 → 整批 `conflict`；否则任一份 `overwritable` → 整批 `overwritable`；否则 `ok`。
   清单的 `precheck.docs[i]` 保留每份的明细，确认摘要按份列出。

**接入方式：`precheck(root, task)` 仍是唯一入口。**现有 `confirm`、`resume`、`_land` 都直接调它，而它按顶层 `sample`
检查——对批量任务那是目录名，复检结果会错。所以：

- 现有单份逻辑原样提为 `_precheck_doc(root, doc) -> dict`，输入是一个单份形状的字典（`task_id`、`sample`、`split`、
  这一份的 `items`）。`_self_owned` 本就只遍历传入字典的 `items`，按份传入后自然只看这一份的篇目；
- `precheck(root, task)`：单份任务直接调 `_precheck_doc(root, task)`，返回值与今天逐字段相同；批量任务按 `items[*].doc`
  筛出各份篇目、配上 `docs[i]` 的 `sample` / `split` 拼成单份字典，**每次都重新逐份检查**（不复用准备时存下的结果），
  再做批内 slug 检查并汇总，返回 `{"status", "details", "existing", "docs": [...]}`；
- 准备结束时、`confirm`、`resume --overwrite`、`_land` 全部走这一个入口，**一处都不改调用方**；`_prepare_steps` 内部那次逐份调用
  只服务于单份流程，批量包装层在归并后用 `precheck` 重算一次整批结果写进清单；
- `_precheck_signature` 对批量结果把 `docs[i]` 的状态与明细按序纳入，任一份变化都使旧确认失效（P4.30 §5「写锁内复检」照旧）。

## 6. 确认摘要与覆盖

CLI 摘要按原件分组，最后一行是整批合计：

```
批量入库：../报告集/年度报告（12 份原件，跳过 2 份）
  [1/12] 2023.pdf → 拆 7 份（3.1–4.8 万字），raw/2023/
  [2/12] 2024.pdf → 不拆（3.6 万字），raw/2024.md   ⚠ 可覆盖：已由旧任务写入，目标相同
  …
已跳过：notes.txt（不支持的格式）、草稿/（子目录，不递归）
合计 85 篇，预计入库约 14 小时（按本库历史平均每篇 10 分钟）
```

- **整批要么都开始、要么都不开始**：有任何不可覆盖的冲突，只能放弃整批，处理后重新导入。不提供「跳过冲突的那几份、其余照入」——
  这会让用户确认的范围和实际入库的范围不一致（决策P4.32-3）。
- `--overwrite` 对整批所有「可覆盖」项一并背书；摘要逐份标出哪些会被覆盖，背书前看得到。
- 交互确认只问一次。

## 7. 落盘、入库、暂停、续跑、放弃

全部沿用 P4.30 §5–§6，因为 `items` 仍是一条扁平列表：

- ⑤ 先把整批所有篇落 `raw/`，再 ⑥ 按清单顺序（原件顺序 → 分卷顺序）逐篇入库。与单份书「先全部落盘再逐篇入库」同构。
- 任一篇非 0 退出 → 整批 `paused`，继续时从这一篇重试；暂停 = 本篇入完后停；续跑判定同 §6.4。
- 断链统计（决策P4.30-16）对整批只在 ⑥ 开始前与全部完成后各做一次，不按原件分别统计。
- `--cancel` 放弃整批；已落盘、已入库的篇不撤回（与单份相同：撤回走 `guanlan remove`）。
- `--status` / 回执 / `--json` 多给 `kind`、`docs`（每份的上传路径、样本名、份数、入库进度）与 `skipped`。

---

## 8. Web

不新增发起入口（决策P4.32-4），但 P4.30 已承诺「CLI 发起的任务可在 Web 里继续」，并且未完成任务会挡住 Web 的新导入，
所以 Web 必须能**认出并处理** CLI 发起的批量任务：

- 任务卡标题显示「批量入库：<目录名>（N 份原件）」，篇目列表按原件分组；
- 「继续」「暂停」「放弃」照常可用（后端走同一套 `resume` / `cancel`）；
- 批量任务处在 `awaiting_confirm` 时，Web 只提示「请在终端确认，或放弃」，**不在 Web 上确认**——Web 确认页是按单份设计的，
  首版不为批量重做。**后端一并限制**：`POST /api/oneclick/{task_id}/confirm` 遇到 `kind == "batch"` 的任务直接返回 409，
  提示「批量入库任务请在终端用 `guanlan import --resume` 确认」，不调 `confirm`。只藏按钮不够，接口仍能被直接调用；
- `GET` 任务状态的返回加上 `kind` 与 `docs`；`upload_in_use`（#172）对批量任务按 `docs[*].upload` 逐个比对。

---

## 9. 决策（草案）

- **决策P4.32-1（全部准备完再统一确认）**：确认关口（决策P4.30-8）要求用户在写 `raw/` 之前看到整批结果。
  流水线（准备一份入一份）只能在 `--yes` 下成立，等于把确认关口变成可选项；首版不做，代价是准备阶段占锁时间长（§4）。
- **决策P4.32-2（准备一份失败即整批失败）**：沿决策P4.30-7「失败即停」。准备是零 LLM 的（目录审校除外）且有解析缓存，
  重来便宜；引入「部分可入」需要新状态与「用户确认的范围 ≠ 实际入库范围」的解释，不值得。
- **决策P4.32-3（冲突按整批处理）**：不跳过冲突项、不部分开始，理由同上。
- **决策P4.32-4（只做 CLI 发起；Web 只显示、继续、放弃）**：批量的主要使用场景是一次性的大量导入，终端更合适；
  Web 多选上传与批量确认页的交互设计留到有真实需求时再做。
- **决策P4.32-5（不递归、文件名排序、顺序入清单）**：递归会让子目录里的同名文件撞车更常见，也说不清子目录名该不该进 `raw/` 路径；
  顺序影响断链补全，必须确定且可复现。
- **决策P4.32-6（单份任务的清单形状不变，批量任务只加字段；逐份传普通字典再归并）**：避免迁移历史清单、避免 Web 单份路径返工。
  `_prepare_steps` 原地改字典，所以写路径用「逐份普通字典 → 归并」，不引入视图类或可写代理；读路径用 `_doc_entries()` 兼容单份。
- **决策P4.32-7（扫描白名单与网址导入的格式表同源）**：一键入库能处理什么格式只有一处定义。
- **决策P4.32-8（按准备产物路径查撞车，扫描只做一次）**：撞车的判据是「两份会不会写到同一个文件或目录」，不是样本名是否相同；
  样本名算法与准备共用一个函数。扫描在取锁后做一次并固定，之后原件出问题按准备失败处理，不做前后两次扫描比对。

## 12. 测试要点

- **扫描**：白名单内外、大小写扩展名、隐藏文件、出处记录 `.x.source.json`、子目录、符号链接、空文件都按 §2 分到收 / 跳过；
  0 份与超上限拒绝。
- **准备产物撞车**（被拒且什么都不做，提示指明撞在哪条路径）：`报告.pdf` + `报告.md`（样本名相同）；
  **漏报用例**——样本名不同、只在附属产物上撞：`A.pdf` + `A.origin.pdf`（`parsed/A.origin.md`）、`A.pdf` + `A.toc.pdf`
  不撞（`A.toc.json` ≠ `A.toc.md`，确认不误报）；`A.pdf` + `a.PDF`（`casefold`）；`images.pdf` 改名为 `images-doc` 后与
  目录里的 `images-doc.pdf` 相撞；两个长中文文件名按 UTF-8 字节截短后才相撞（在 Linux CI 上跑）。
- **样本名一致**：扫描算出的路径与准备实际写下的路径逐一相同（同一函数，防两边各算一套）。
- **顺序**：清单顺序 = 码位排序；续跑时目录里新增文件不影响清单顺序和范围。
- **准备失败**：第 3 份转换失败 → 整批 `failed`、原因指明第 3 份、`raw/` 无任何写入；重新导入成功。
  扫描后、准备到第 3 份前把它删掉 → 同样整批 `failed`。
- **归并**：逐份准备后批量清单的 `docs[i]`、`items`（含 `doc`）、`prepared_sha256` 与逐份结果一致；某份的字段没有覆盖
  批量清单顶层的 `task_id` / `sample` / `upload` / `stages`。
- **停止**：准备到第 2 份时 Ctrl+C → 整批 `cancelled`。
- **预检**：某份 `conflict` → 整批不可开始；某份 `overwritable` 无 `--overwrite` → 拒绝，有 → 只覆盖标出的项；
  批内分卷 slug 与另一份样本名相撞 → 冲突（**漏报用例**：逐份预检各自都是 ok，只有批内检查能报出）。
- **预检接入**：单份任务的 `precheck` 结果与改动前逐字段相同；批量任务确认前在 `raw/` 放入与第 2 份目标同名的文件 →
  `confirm` 复检报冲突、旧确认失效（**漏报用例**：只看顶层 `sample`（目录名）时这里会报 ok）；某份已落盘后被手工改动 →
  `resume` / `_land` 报出的是这一份；第 1 份已写入的文件在续跑时不被当成第 2 份的冲突。
- **出处记录**：目录里放一份带 `.<名>.source.json` 的网址下载 Markdown（含相对图片）→ 批量准备后 `docs[i].source_url`
  是去凭据的网址、`raw/` frontmatter 的 `origin` 是网址而不是本地路径、相对图片转成指向网址的链接而不是去本地找附件；
  哈希不符的出处记录照旧作废。
- **入库**：篇目全批连续编号；第 k 篇失败 → 整批 `paused`，`--resume` 从第 k 篇重试，已 `done` 且指纹一致的篇跳过。
- **兼容**：历史单份清单（无 `kind` / `docs`）照常被 `--status` / `--resume` / 归属判定读取；单份 `import <file>` 的清单
  与回执与改动前逐字段相同。
- **Web**：CLI 发起的批量任务在 Web 显示为分组任务卡、可继续 / 暂停 / 放弃、不显示确认按钮；直接调
  `POST /api/oneclick/{task_id}/confirm` 确认批量任务 → 409、任务仍为 `awaiting_confirm`；批量准备中，Web 上传覆盖
  `docs` 里的任一原件被 `upload_in_use` 拦下。
- **`--dry-run`**：逐份 ①–④、打印整批摘要、不建任务记录、不写 `raw/`；有未完成任务时拒绝。

## 13. 不做 / 以后

- **递归子目录**：不做（决策P4.32-5）。需要时先把文件平铺到一个目录。
- **流水线（准备一份入一份）**：不做（决策P4.32-1）。如果真实使用里准备阶段占锁成了主要痛点，再考虑「仅 `--yes` 时流水线」。
- **跳过冲突、部分开始**：不做（决策P4.32-3）。
- **Web 多选发起、Web 批量确认页**：以后（决策P4.32-4）。
- **glob / 文件列表参数**（`import a.pdf b.pdf`、`import 'dir/*.pdf'`）：首版只认一个目录；需要挑选文件时先放进一个目录。
- **多个批量任务排队**：不做，「一个库同时只有一个任务」不变。
