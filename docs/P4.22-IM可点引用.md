## 0. 起点：一条被撤回的支线，和一条至今未决的前提

### 0.1 决策P4.21-76 撤了什么

P4.21 实现期把「显式给了 `--web-base-url` 就把 wikilink 转真链接」这条支线**无条件撤回**了，理由是核实出来的
事实：**Web 宿主没有按页面名打开某一页的路由**（SPA 只认 `?raw=<源文件名>` 与 `?c=<会话 id>`；`/api/page?path=`
要相对路径且回 JSON）。任何由页面**名**拼出来的 URL 都是死链，而「一个 404 比一段可读的 `[[甲实体]]` 更误导」。

那条论证今天仍然成立——**它否掉的是"把名字拼成 URL"，不是"让引用可点"**。本相位走的是另一条路：点击的目标
不是某个 URL，而是**机器人自己**；机器人手里有那张 `link_resolution_index` 解析表，按名开页对它是零成本的。
于是决策P4.21-76 的前提（"没有可以指向的东西"）被消解，而它的判据（"不承诺一个不存在的东西"）被继承：
**按钮只在能解析到页时才出**（§6.1）。

### 0.2 ★ 曾经的阻断项：卡片回调走哪种帧，证据是**矛盾的**（已由兼容层化解）

本相位的地基是「点击能到达我们的进程」。这件事**至今未决**。排期过程里我对它下过两次结论——先是
"被 Python SDK 堵死、走不通"，随后翻案成"CARD 帧是红鲱鱼、其实是通的"——**两次都错在同一处：拿源码形状
替代真机事实**。这一轮把两边证据摊开，结论是**先跑探针，再定稿**。

**支持「走 EVENT 帧、开箱即用」的一侧**

Python 1.7.2 与 Go 双 SDK 在同一处都对 CARD 帧早返回（`lark_oapi/ws/client.py:342`；
`oapi-sdk-go/ws/client.go:626`），而 Go 的 **EVENT 分支**响应组装里写着：

```go
if rsp != nil { // for cardCallback
    resp.Data, err = json.Marshal(rsp)
```

即**至少有一类回调是以 event 帧回来的**。Python 侧路径也接得上：`_do_without_validation` 同时查
`_callback_processor_map`（`dispatcher_handler.py:159`），返回值经 `resp.data` 写回 WS——这条路只对
"需要同步应答"的回调才有意义。两条旁证：官方 Python 示例 `samples/ws/sample.py` 就在 `lark.ws.Client`
上注册 `register_p2_card_action_trigger`；飞书《使用长连接接收回调》把 Python 列进四种支持的 SDK。

**反对的一侧（更重，因为它来自真机）**

上游 issue [larksuite/oapi-sdk-python#126](https://github.com/larksuite/oapi-sdk-python/issues/126)：
1.6.4 上点击卡片按钮报 **200340（超时）**，报告者指认的正是 CARD 帧早返回——处理函数从不触发、响应帧也
写不回去。**200340 恰恰就是「平台发了 CARD 帧、SDK 丢弃、3 秒内没有任何应答」的表征**。该 issue 已关闭，
但**无维护者答复、无修复版本号**，且 1.7.2 仍原样保留那条早返回分支。

**怎么读这个矛盾**：两侧可以同时为真——**旧版（1.0）卡片的回调走 event 帧**（Go 那句注释的由来），
而**卡片 2.0 的 `card.action.trigger` 走 CARD 帧**。若如此，官方文档说的"Python 支持长连接接收回调"
指的是前者，而本相位要的是后者。**这是一个自洽的假说，不是结论。**

**实现期的处置：不选边，两边都接住**（★ 决策P4.22-21）

原计划是"先跑探针再定实现"。实际落地时选了另一条：**让这个问题不必先有答案**。
`_card_aware_ws_client()` 子类化 `lark.ws.Client`，在 `_handle_data_frame` 里把 CARD 帧的帧头
**就地改写成 EVENT** 再 `super()` 委回父类——父类那 40 行分包合并 / 响应回写逻辑一行不抄。于是：

| 真实情况 | 行为 |
|---|---|
| 回调以 **EVENT** 帧下发（假说 1） | 兼容层**一次都不触发**，走 SDK 原生路径 |
| 回调以 **CARD** 帧下发（假说 2） | 兼容层改写帧头 → 落进 `_do_without_validation` → 命中 `_callback_processor_map` |

**它是纯粹的超集**：不改变任何既有路径，非 CARD 帧一个字节不动（有反向用例守着）。代价是吃了
`_handle_data_frame` 这个私有名，故按决策P4.21-29 的同款姿态处置——**探不到就退回原类并告警**
（降级不拒启），并配一条真 SDK 形状探针用例（`test_real_sdk_still_exposes_the_card_seams`）。
**上游哪天把 CARD 帧接进 EVENT 分支，这个函数即可整段删除。**

剩下两种情况与代码无关，仍按原判据处理：**连帧都没有** → 多半是「回调」订阅方式没配（§6.4），
先查配置不是先改代码；**配置无误仍无帧** → 退回 §1 表里的表情回复方案，或改做 Web 按名开页路由。

> **诚实分级**：兼容层化解的是"实现要不要选边"，**不是**"回调一定能到达"。后者仍需真机核对
> （§9 #1），只是它现在决定的是**能不能用**，而不再决定**怎么写**。

### 0.3 诚实的前置（三条，全部会改变可用性）

1. **长连接接收回调仅支持企业自建应用**，且每应用最多 50 个连接；**推送是集群模式、不广播**——同一 `app_id`
   起多个实例，只有随机一个收到。这与 P4.21 §8.5 已有的「飞书单实例本机锁」同向，不构成新约束。
2. **回调与事件是两套订阅配置**（§6.4）。只配了「事件订阅 → 长连接」而没配「回调 → 长连接」，表现是
   **卡片发得出去、点了没反应**，且**没有任何错误日志**。这是本相位最可能的现场故障，运维步骤必须写死。
3. **3 秒响应上界**（飞书硬约束）。这不是性能建议，是协议：回调处理函数必须在 3 秒内返回，**故它里面绝不能
   有磁盘、网络或 LLM**（§5.4）。

## 2. 全链路

```
用户提问
  └─▶ [现状不变] intake 五道闸 → delivery edit 档 → 占位消息原地改写 → 终稿 post 消息
                                                             │
                                   ┌─────────────────────────┘
                                   ▼  ★ 新增：终稿之后
      extract_wikilinks(★ 实际送达的正文片段，非完整 answer) ──▶ 去重 / 保序 / 截到 max_actions
                                   │  （空 或 caps.supports_actions=False → 什么都不做，链路到此为止）
                                   ▼
      adapter.send_actions(chat_id, "本答案引用的页面：", [Action(label="甲实体", command="/page 甲实体"), …])
                                   ▼
      飞书：一条 interactive 卡片（2.0），每个按钮 behaviors[0].value = {"c": "/page 甲实体"}
                                   ▼
      用户点击 ──▶ 飞书服务端 ──▶ 【同一条 WS 长连】──▶ card.action.trigger
                                   ▼
      _on_card_action()（SDK 线程）：① 立即 return toast「已收到」  ② call_soon_threadsafe 投队列
                                   ▼
      map_card_action() ──▶ InboundMessage(text="/page 甲实体", origin="action", mentioned_me=True,
                                           chat_type=★ 查会话事实缓存（未知 → 整条丢弃）, msg_id="card:<event_id>")
                                   ▼
      【原路返回】adapter.inbound() → intake 五道闸（去重/白名单/@/合并/分流 + ★ action 来源只读白名单）
                                   ▼
      delivery._page()：解析表按名开页 → 剥 frontmatter → split_for 分片 → 发出
```

**这张图的要点只有一个**：★ 之后的所有箭头，核心侧走的都是**已经存在的**代码路径。适配器把点击变成一条消息，
之后核心分不清它是用户打的还是点出来的——这正是本相位能做到「核心零平台分支」的原因。

## 4. `/page`：本相位真正的服务端动作

**这是本相位的地基，且它与卡片正交**——先落地它，卡片没通电也已经交付了价值（决策P4.22-1）。

### 4.1 解析口径：复用，不新造

```python
# guanlan/im/pageview.py
def open_page(kb: Path, name: str) -> PageView | None:
    """名字 → 可发送正文 + **页内可解析引用的「键 → 拥有页」表**；未命中 → None。
    **一行都不自己写解析逻辑**。"""
    idx = link_resolution_index(kb / "wiki")     # ← 本次调用**唯一**的一次全库解析
    rel = resolve_owner(name, idx)
    ...
    links = {}
    for c in extract_wikilinks(body):
        owner = resolve_owner(c, idx)
        if owner is not None and owner != rel:   # 排除指向本页自身的引用（含经别名绕回来的）
            links.setdefault(link_stem(c), owner)
```

**表的值（owner）不是冗余**：出按钮时要按**拥有页**去重，不是按名字。`extract_wikilinks` 的去重键是
`link_stem`，而同一页有多个合法写法——别名（`[[甲方]]` vs `[[甲实体]]`，P3.1）与 fold variant
（`[[multi_head_attention]]` vs `[[multi-head-attention]]`，P3.8）的解析键各不相同、拥有页却是同一张。
只按名字去重的下场是：一句同时提到别名与本名的答案出**两个点开同一页的按钮**——既是噪音，又白占
`max_actions` 的名额、还把"另有 N 个"的告示算多。答案那条路（`resolve_many`）同理，两者共用
`_dedupe_by_owner`。

`resolve_owner` 是 P3.8 确立的**单一 owner 归口**（`check` / `graph` / `heal` / Web 全复用同一张表），自带
「精确 stem → 别名 → 安全 fold variant」三段语义。IM 侧另写一套按名查找，等于给这个系统开第五个口径——
P3.8 的整个动机就是消灭这种漂移。

**索引成本**：`link_resolution_index` 要遍历 `wiki/` 读 frontmatter，是同步磁盘 + CPU ⇒ **必须
`anyio.to_thread.run_sync`**（决策P4.21-35 的卸线程通则，判据是"会不会去拿一把别人可能长期持有的锁"，
这里是"会不会长时间占住事件循环"，同样成立）。v1 **不做缓存**：`/page` 是低频交互命令，而缓存要处理失效，
`CorpusCache` 那套是为高频 `/search` 建的，别照抄。

**但"不做缓存"≠"可以在同一次调用里建两遍"**（★ 决策P4.22-25）：页内引用的解析**与开页共用这一张表**，
故 `open_page` 回的是 `PageView(text, links)` 而不是一段文本。出按钮时只在 `links` 上做零盘 IO 的
过滤（`filter_resolvable`，同时按拥有页去重）。P3.8 那个 `loaded=` 参数就是为消掉 `build_graph` 的同款双解析而生的。

### 4.2 输出契约

```
甲实体　（entity）
wiki/entities/甲实体.md

<正文，已剥掉 frontmatter>
```

- **剥 frontmatter**：`load_page()` 已经把 `(meta, body)` 分好，直接用 `body`。YAML 头对 IM 用户是噪音。
- **首行给标题 + 页型 + 相对路径**：与 `/search` 的结果行口径一致（那里已经在显示 `hit['page']`）。
  相对路径无害且有用；**绝不显示绝对路径**（那是本机信息，且会经飞书服务端往返进日志）。
- **分片**：`split_for(text, caps.max_message_length, max_parts=caps.max_parts)`，与答案完全同一条路径。
- **截断告示不得承诺 URL**（继承决策P4.21-50）：`/page` 的截断文案是
  「⚠️ 本页还有约 N 字未发送。」——**不追加 Web 入口**。这里与答案截断的处境不同：那时被舍弃的内容"没有存在
  任何地方"，而这里内容明明在盘上，但**Web 宿主没有按名开页的路由**（§0.1），给出去的仍是死链。
  等 Web 补了路由，这一行再改，届时它才是诚实的。

### 4.3 未命中：降级为一次 `/search`，不空手而归

```
没有找到名为「甲实休」的页面。你也许想找：
1. 甲实体　wiki/entities/甲实体.md
2. …
```

按钮点出来的名字**理论上不会未命中**（名字是从答案正文里抽的，且出按钮前已经解析过一遍，§6.1）；未命中的现实
来源是**手打错别字**。这时把用户直接踢回"没找到"是最没用的答复，而 `/search` 的 BM25 + CJK 2-gram 召回恰好
擅长救错别字。上限 top-3（不是 `/search` 的 8）——这是**降级提示**不是检索结果，长了会喧宾夺主。

### 4.4 输入一律不可信

`/page` 的参数有两个来源：用户手打、卡片回调回传。**两者走同一条校验**，绝不因为"回调是我们自己发出去的卡片
回来的"就开后门（决策P4.22-8，P4.11 信任边界的同款口径）：

- **参数长度上限 200 字符**（页面名不可能更长），超限直接拒；
- **拒控制字符与换行**；
- **★ 只写一份校验器**（决策P4.22-18，v3 更正）：`pageview.validate_page_arg(arg) -> str | None` 在**核心**，
  手打与点击**共用同一次调用**——`classify()` 之后拿到的 `argument` 是什么来源，`/page` 处理函数并不关心。
  v2 稿在适配器侧也写了一条"≤200"，量的却是**整条命令串**：于是页面名在 194–200 字符之间时
  **手打能开、点按钮被丢**。适配器那侧只留**信封上界 256**（防畸形/超大 `value` 的平台级卫生检查，
  与"参数多长算合法"无关，故不构成第二份口径）。
- **不拼路径**：`resolve_owner` 返回的是**索引表里的值**，`../` 之类根本进不了表——路径穿越在这个设计里
  不是"挡住了"，而是**结构上不可达**。测试仍要有一条 `/page ../../etc/passwd` 的用例，守的是"日后有人图省事
  改成 `wiki / name` 拼路径"。

## 5. 点击 = 一条合成的入站消息（本相位的枢纽）

### 5.1 为什么在核心闭合

`Action` 携带的是 **`command` 文本**（`"/page 甲实体"`），不是"页面名"或"动作类型"：

```python
@dataclass(frozen=True)
class Action:
    label: str    # 按钮上显示的字
    command: str  # 点击后要合成的入站正文
```

**核心决定点击后会发生什么，适配器只负责把这句话塞进按钮、并在回调时原样取回**（决策P4.22-2）。这条边界
一划，三件事同时成立：

1. 适配器仍是"零业务判断"的——它不知道 `/page` 是什么，只知道有个字符串要往返；
2. 新增动作类型（将来的 `/graph <名字>`、`/related <名字>`）**适配器零改**；
3. 核心侧不需要为"点击"新开一条处理路径——五道闸原样复用，`tests/test_im.py` 那条"核心不许出现
   `== \"feishu\"`"的断言继续成立。

反面是把动作类型放进 value（`{"a": "page", "n": "甲实体"}`）再让适配器拼命令：那等于把"点了按钮该干嘛"的
知识切成两半，一半在核心一半在适配器，且每加一个动作两边都要改。

### 5.2 字段映射（`map_card_action`，与 §8.3 的 `map_event` 对称）

| `InboundMessage` | 回调字段 | 备注 |
|---|---|---|
| `tenant` | **`header.tenant_key`**（★ 决策P4.22-17） | **必须与 `map_event` 同源**（`adapters/feishu.py:161` 取的就是 `header.tenant_key`）。回调里**同时存在** `event.operator.tenant_key`，v2 稿误取了它——外部群 / 跨租户场景下两者可能是不同值，于是合法点击**查不到缓存**、被误判成"会话已过期"，表现为「按钮点了说过期，再问一次又好了」这种最难查的间歇故障 |
| `chat_id` | `event.context.open_chat_id` | |

| `user_id` | `event.operator.open_id` | 与消息事件同一命名空间，白名单可直接比 |

#### 5.2.1 `chat_type`：只认**见过的会话**，绝不由白名单反推（★ 决策P4.22-5，v2 改写）

回调不带 `chat_type`，`open_chat_id` 的前缀也区分不了单聊与群（都是 `oc_`）。**v1 稿的规则是错的**，
必须记下来防止有人凭直觉改回去：

> v1 写的是「在 `allow_chats` 里 → 群，否则 → 单聊」，并自称"取更严的一档"。**方向恰好反了**：
> 一个**未列入白名单的真实群**会被判成 DM，而 DM 分支只查 `user_ok`、**不查 chat_id、不要求 @**
> （`intake.py:60-64`）。于是"授权用户在一个未授权群里点了一张转发过来的卡片" ⇒ 页面被发进那个群。
> 卡片在飞书里是**可转发**的，这条路不是假想。

v2 的做法：**适配器为每条真实入站消息记一条 `(tenant, chat_id) → chat_type` 的事实缓存**，回调只查这张表：

```python
# adapters/feishu.py —— 事实，不是策略：适配器本来就是 chat_type 的产地
self._chats: OrderedDict[tuple[str, str], str] = OrderedDict()   # LRU，上限 4096
# map_event() 成功映射一条消息时写入；map_card_action() 只读
#
# ★ 键的两半都必须与 map_event **同源**（决策P4.22-17）：
#   tenant  ← header.tenant_key      （**不是** event.operator.tenant_key，两者可能不同值）
#   chat_id ← event.context.open_chat_id  vs  message.chat_id （待实证 #6 要比的是**整个键**）
# 键取错的后果不是"报错"，是**查不到**——合法点击被当成"会话已过期"，且只在跨租户/外部群才复现。
```

- **未命中 → 整条丢弃**，不投队列。fail-closed 是这里唯一可接受的默认：我们只会把卡片发进**回答过问题的
  会话**，所以正常点击必定命中；命不中只有两种来源——**卡片被转发到别处**，或**进程重启后点了旧卡片**
  （卡片可交互期 14 天）。前者必须挡，后者挡掉只是失效一次。
- **未命中时 toast 换成「会话已过期，请重新提问」**（而不是「已收到」）。这是**事实层判断**——适配器
  确实没见过这个会话——所以放在适配器里不破分工，且它把 fail-closed 从"点了没反应"变成一句可行动的话。
- **`allow_chats` 一个字都不进适配器**：授权仍然只在 `AccessPolicy` 里判一次（§5.3）。
- **卡片显式禁转发**（若 2.0 `config` 支持该开关）作为**纵深防御**，但**绝不作为安全依据**——真正的闸是
  这张缓存表。

> **实证任务**（§9 #6）：真机比对**整个键** `(header.tenant_key, chat_id)` 在消息事件与回调两侧是否逐字节
> 相等——单聊、群聊、以及**外部群 / 跨租户**各一次。只比 `chat_id` 不够：v2 稿正是在 `tenant` 那一半上取错了源。
> 若飞书日后在回调里补了 `chat_type`，直接改用真值、缓存降级为兜底。

### 5.3 五道闸逐条复核

| 闸 | 对合成消息成立吗 | 说明 |
|---|---|---|
| ① 去重 | ✅ **但只挡重推** | `card:<event_id>` 只能挡**平台对同一次点击的重投**（§9 #4）。**两次独立点击 = 两个 event_id = 跑两次**，这是既有语义、也是对的，见下 |
| ② 白名单 | ✅ **必须** | 群里的卡片是**共享**的，任何看得见消息的人都能点。`AccessPolicy` 原样生效，未授权者静默丢弃 |
| ③ @ 前缀剥除 | ✅ 空操作 | 合成正文没有 @ 前缀 |
| ④ 分片合并 | ✅ 被跳过 | `classify()` 认出 `/page` → 命令路径先 `_flush()` 再直投，不进 debounce 桶（既有行为） |
| ⑤ 斜杠分流 | ✅ | `"/page 甲实体"` → `("page", "甲实体")` |
| **⑤′ action 来源白名单**（★ 新增，§5.5） | ✅ **必须** | `classify()` 对**未知**斜杠命令是**当普通提问送进 LLM**的（`intake.py:100-115`）——只校验"以 `/` 开头"挡不住 `/foo` 变成一次 LLM 花费 |

**连点两次会发两次页面，这是有意的**（★ 决策P4.22-19，v3 更正）。v2 稿声称去重"让重推与用户连点两次都只跑
一次"——**错的**：两次点击是两个 `event_id`，闸① 放行两条。实际发生的是：

- **两次点击有重叠**（第一次还没答完就点了第二次）→ 撞 `Delivery` 的**单飞**（`_inflight`，同一 `session_key`），
  第二条收到「上一个问题还在处理，请稍候。」——既有机制，无需新东西；
- **两次点击不重叠** → **老老实实发两次**。`/page` 是零 LLM、毫秒级的读盘，重复一次的代价约等于零。

**明确不加"短期点击幂等键"**（评审建议的方案）。那正是决策P4.21-34 已经**删掉过一次**的东西——内容指纹去重
无法区分「平台换 id 重投」与「用户合法重复」，而"用户就是想再看一遍那一页"在 IM 里完全正常。
**静默吞掉一次合法点击，比偶尔多发一页糟得多**：前者的表现是"按钮有时候点了没反应"，用户无从察觉、也无从复现。
故 `tests/test_im_feishu.py` 要有一条**反向用例**：同一按钮、两个不同 `event_id` → **两条都被处理**，
守着这个决策不被后人好心"优化"掉。

**toast 不过白名单**（决策P4.22-7）。回调必须在 3 秒内同步作答，而白名单判定在核心、异步之后。方案是
**回一个中性 toast「已收到」**（唯一例外是会话未见过 → 「会话已过期，请重新提问」，那是**事实层**判断而非
授权判断，见 §5.2.1），未授权者点完看到 toast 但收不到任何页面。这看起来像信息泄露，实际不是：
**卡片本身就在那个群里、对所有人可见**——"这里有个机器人且它在听"这件事早已公开，toast 的信息量为零。反过来，
把 `AccessPolicy` 下放到适配器以便"未授权就不回 toast"，代价是白名单有两份实现——那才是真的风险。
（对比：决策P4.21-28 的 `im-identify` 之所以"绝不回复"，是因为在那个场景里机器人的**存在本身**还是秘密。）

### 5.4 3 秒契约怎么满足

```python
def _on_card_action(self, data: object) -> dict:      # 回 dict，理由见决策P4.22-22
    """**在 SDK 线程里跑，且必须 3 秒内返回**（§0.3 第 3 条）。

    故这里有且只有两步：映射（纯 CPU、微秒级）+ 投队列（call_soon_threadsafe）。
    **绝不**在此做磁盘 / 网络 / LLM——`/page` 要读整个 wiki 建解析表，放这里必然超时。
    """
    tenant, chat_id = callback_chat_key(data)                 # 与 map_event 同源（决策P4.22-17）
    chat_type = self._known_chat(tenant, chat_id) if chat_id else None
    if chat_type is None:
        return _toast(TOAST_EXPIRED)      # 会话没见过：转发来的 / 重启后的旧卡片
    msg = map_card_action(data, chat_type=chat_type)
    if msg is None:
        return _toast(TOAST_BAD)          # 会话认识、信封不合规（决策P4.22-23）
    loop = self._loop
    if loop is not None:
        with contextlib.suppress(RuntimeError):
            loop.call_soon_threadsafe(self._queue.put_nowait, msg)
    return _toast(TOAST_ACK)
```

线程边界与 `_on_message`（`adapters/feishu.py:414`）**逐字同构**——这不是巧合，是把"回调"归一成"入站消息"
之后的必然结果。真活儿由队列另一端的既有流水线接手，慢多久都不影响这 3 秒。

### 5.5 `origin` 事实字段与 action 来源白名单（★ 决策P4.22-14，v2 新增）

v1 稿只要求回传串"以 `/` 开头"，**这守不住红线 1**（§7：`Action` 只能承载零 LLM 只读命令）。因为
`classify()` 对**未知**斜杠命令并不拒绝，而是**当普通提问返回 `(None, text)`**：

```python
# intake.py:110-115（既有行为）
if stripped.startswith("/"):
    head, _, rest = stripped[1:].partition(" ")
    if head.strip().lower() in COMMANDS:
        return name, rest.strip()
return None, stripped          # ← 未知斜杠命令 = 普通提问 = 一次 LLM 花费
```

于是一个被改动过的 `value`（回传串是经飞书服务端往返的**外部输入**，决策P4.22-8）里塞
`/foo 帮我写一篇…`，就成了一次不该发生的 LLM 调用——红线在**构造端**声明了，却在**接收端**没有闸。

**做法**：`InboundMessage` 加一个**事实字段** `origin`（`"user"` | `"action"`，适配器只做事实映射，
同决策P4.21-36 的姿态），核心据此判**策略**：

```python
# intake.py
ACTION_COMMANDS = ("page",)          # ⊂ COMMANDS；v1 只有一个

# offer() 内，闸⑤之后：
if msg.origin == "action" and command not in ACTION_COMMANDS:
    self.dropped_unauthorized += 1   # 静默丢弃，绝不落进 LLM 分支
    return
```

三条理由说明这个位置是对的：白名单是**策略**故留在核心（适配器仍不认识 `/page`）；`origin` 是**事实**
故由适配器给（它确实知道这条消息是点出来的）；红线 1 从"构造端的自觉"变成**接收端可测的闸**——
测试直接构造一条 `origin="action"` + `text="/help"` 的消息断言被丢，不必去遍历所有 `Action` 构造点。

## 6. 飞书侧细节

### 6.1 卡片 JSON 与按钮

```jsonc
{
  "schema": "2.0",
  "config": {"update_multi": true, "enable_forward": false},
  "body": {
    "elements": [
      {"tag": "markdown", "content": "本答案引用的页面："},
      {"tag": "button",
       "text": {"tag": "plain_text", "content": "甲实体"},     // ★ 文本是**对象**，不是裸串
       "behaviors": [{"type": "callback", "value": {"c": "/page 甲实体"}}]},
      {"tag": "button",
       "text": {"tag": "plain_text", "content": "乙概念"},
       "behaviors": [{"type": "callback", "value": {"c": "/page 乙概念"}}]}
    ]
  }
}
```

> **v1 稿把 `text` 写成了裸串**（`"text": "甲实体"`）。官方 1.0 与 2.0 的按钮文本都是
> `{"tag": "plain_text", "content": …}` 对象形态——这条不必等真机就能订正，v2 已改。
> 仍待真机确认的只剩组件键是 `tag` 还是 `type`、以及 `behaviors` 的确切位置（§9 #2）。

- **★ 抽取输入 = 实际送达的正文片段，不是完整 answer**（决策P4.22-13，v2 新增）：`split_for` 会在超限时
  **丢掉后缀**（决策P4.21-31 的"不静默截断"只保证有告示，不保证内容都发出去）。若从完整 answer 抽，
  一个**只出现在被丢弃后缀里**的页面名会被印在卡片上——群里所有人都看得到一个**正文里根本没出现过**的
  页面名，红线 6（"卡片上只有正文里已经印出来的东西"）当场破掉。故两条投递档都在**发完正文之后**调
  `_offer_actions(parts)`，输入是 `"\n".join(parts)`（edit 档的 `parts` 同理，含被 `edit` 写回占位消息的首片）。
  附带好处：按钮与用户**看得见的文字**一一对应，点击语义也更直白。
- **★ 正文没发出去就不发按钮**（决策P4.22-20，v3 新增）：`parts` 只是**打算**发的东西。`_safe_send()`
  把出站异常吞成一条 WARNING（`delivery.py:197-202`，那是对的——一条消息发不出去不该杀死主循环），
  edit 档的 writer 也整段 `suppress(Exception)`。于是"正文全挂、卡片发成功"是可达状态，用户会看到一排
  指向**他没读到的文字**的按钮。做法：`_safe_send` 返回 `bool`，`_offer_actions` 只吃**确认送达**的片；
  一片都没成功 → 整张卡片不发。
  **定级要诚实**：这一条**不是越权泄露**——群与用户都已过 `AccessPolicy`，那些页面名本来就要发给这同一批人看，
  评审自己也把它从 P1 降了级。它是**一致性**保证（红线 6 的后半条），值得做是因为**成本近乎为零**，
  不是因为它挡住了什么攻击。真正属于安全面的是**截断**那一半（决策P4.22-13）：那才是"未送达内容"
  在群里被首次公开。
- **抽取口径**：`WIKILINK_RE`（`pages.py:87`）+ `strip_html_comments()`，与 `check` / `graph` **同一条正则**，
  不再各写一份（否则"answer 里算引用"与"check 里算断链"两处会漂移）。
- **出按钮前先解析一次**：`resolve_owner` 命中才出按钮（决策P4.22-3）。断链的 `[[丙实体]]` 出个按钮、点了回
  "没有找到"，正是决策P4.21-76 判据里"承诺一个不存在的东西"的翻版。**代价是每轮答案多一次解析表构造**——
  同 §4.1 卸线程，且只在"有引用 且 平台支持"时才跑。
- **去重保序**：同名只出一个按钮，按首次出现顺序。
- **上限 `max_actions = 8`，超出不静默**（继承决策P4.21-31）：卡片末尾追一行
  「另有 N 个引用未列出，可直接发送 `/page <名字>` 打开」。正文里的 `[[…]]` 原文本来就还在——这正是
  决策P4.21-76「保留原文」在本相位继续成立的用处（决策P4.22-9）：**按钮是叠加层，不是替换**。
- **`value` 里只放命令文本**，不放路径、不放 KB 位置。页面名本来就已经印在卡片上给人看了，不构成新泄露；
  而路径是本机信息，不该经飞书服务端往返。

### 6.2 ★ 为什么按钮承载在"追发的第二条消息"上（决策P4.22-6）

现状：飞书走 edit 档，正文是 `post` 富文本消息，流式期用 `PUT /messages/:id`（`UpdateMessageRequest`）原地改写。
卡片是 `interactive` 消息，**msg_type 不可中途变**，且卡片的原地更新是另一套 API。三条路：

| 方案 | 代价 |
|---|---|
| (i) 正文不动，**按钮独立成一条追发消息** ← **v1 选这条** | 一次问答最多两条消息（且仅当有引用） |
| (ii) 全程卡片：占位卡 → patch 流式 → 终稿卡带按钮 | 要重写 P4.21 §6.2 那段单写者 / 节流 / `finalize` / `_clip`——**全仓最脆弱、竞态最密**的一段；且卡片 markdown 组件对围栏块的渲染未知，§8.4 那个"md 元素吞掉围栏之后内容"的坑要重打一遍 |
| (iii) 终稿时把 post 换成卡片 | msg_type 不能变，做不到 |

选 (i) 的判据不是"简单"，而是**风险隔离**：本相位的新东西（卡片、回调、合成消息）全部落在一条**新的、独立的、
可以整条不发**的消息上；已经过一轮真机验证的流式路径**一个字不动**。

**这是可回退的取舍**：日后若做流式卡片（cardkit 的 `create_card` + 流式更新），按钮并回正文即可，
`send_actions` 退化成 `edit(..., finalize=True, actions=[...])`，**核心契约与 `Action` 一个字不用改**。

### 6.3 回调注册

```python
builder = lark.EventDispatcherHandler.builder("", "").register_p2_im_message_receive_v1(self._on_message)
if not self.caps.supports_actions:
    pass                                    # 本次部署不要可点面（im-identify，决策P4.22-24）
elif hasattr(builder, "register_p2_card_action_trigger"):
    builder = builder.register_p2_card_action_trigger(self._on_card_action)   # ★ 新增
else:
    self.caps = replace(CAPS, supports_actions=False, max_actions=0)          # 降级，不拒启
    _logger.warning("…本次不提供可点引用（[[引用]] 仍原样保留，可手打 `/page 名字`）")
handler = builder.build()
ws_cls = _card_aware_ws_client(lark) if self.caps.supports_actions else lark.ws.Client
```

**SDK 签名探针**（与决策P4.21-29 的 `extra_ua_tags` 探针同姿态）：启动时 `hasattr(builder, "register_p2_card_action_trigger")`，
缺则**降级而非拒启**——卡片是叠加层，没有它宿主照常工作。降级时 `supports_actions` 就地置 False 并记一条 WARNING。
（`extra_ua_tags` 那条是拒启，因为缺了它**群消息会静默收不到**，那是主功能。档次不同，处置不同。）

**降级只关可点面**：有一条用例断言 `supports_edit` 不受牵连——"降级"是很容易顺手降过头的那种改动。

**能力位落在实例上**（`self.caps`，不是类属性）：核心每次分派都读 `self._adapter.caps`，故就地降级立刻生效、
装配处（`server.py` 在 `start()` **之前**就构造了 `Delivery`）无须任何配合。

### 6.4 运维前提（必须写进 `docs/guide/`）

```
开发者后台 → 事件与回调 →
  ① 事件订阅   → 订阅方式：长连接      ← P4.21 已要求
  ② 回调       → 订阅方式：长连接      ← ★ P4.22 新增，漏配则「卡片发得出、点了没反应、无日志」
  ③ 添加回调：卡片回传交互 card.action.trigger
```

**漏配是静默的**，故 `send_actions` 首次成功时记一条 INFO：

> 已发出可点引用卡片。若点击无响应，请检查开发者后台「事件与回调 → 回调」的订阅方式是否为长连接。

这条日志是"静默失败必须留一句可执行线索"的最小成本实现（同 P4.21 §15.6/§15.7 首连看门狗与启动横幅的动机）。

## 7. 红线

1. **按钮永不承载写操作。** v1 只有 `/page` 一种命令进 `Action`。**闸在接收端，不在构造端**（§5.5）：
   `origin == "action"` 的消息，命令必须 ∈ `ACTION_COMMANDS`，否则静默丢弃——**未知斜杠命令会被
   `classify()` 当普通提问送进 LLM**，只在构造端自觉是挡不住的。测试直接构造 `origin="action"` +
   `text="/help"` / `"/foo …"` 断言被丢。否则日后"点一下就 ingest"会显得很自然——那一步就把 IM 宿主
   从只读叠加层变成了写入面。
2. **零监听端口不变。** 回调复用 P4.21 已建的 WS 长连；不起 HTTP 回调服务（那还需要公网可达/内网穿透，
   对本地知识库根本不成立）。
3. **KB 零字节写不变。** `/page` 只读盘。P4.21 的零写契约测试原样覆盖本相位。
4. **核心零平台分支不变。** 一切分派只读 `caps`；`tests/test_im.py` 既有断言继续守。
5. **`value` 不含本机路径 / 凭据 / 会话 id。** 只放核心生成的命令文本。
6. **群内卡片是公开面。** 两条，**分量不同、别混为一谈**：
   **(a) 安全不变量**——卡片上**绝不**放页面摘要或正文，且**绝不**出现只存在于被截断丢弃部分里的页面名
   （决策P4.22-13）。这两种都会把"只有授权者问得到的内容"变成群内公开展示。
   **(b) 一致性保证**——正文实际发送失败时不发按钮（决策P4.22-20）。这条**不涉及授权边界**
   （收件人本来就该看到这些名字），做它是因为成本近零，不是因为它挡住了攻击。
7. **回调只认见过的会话**（决策P4.22-5）。未命中会话事实缓存的点击一律丢弃——卡片可被转发，
   而"卡片出现在哪里"不是授权依据。
8. **`im-identify` 期间不存在任何出站面**（决策P4.22-24）。决策P4.21-28 的"绝不回复任何消息"
   **包括 toast**：identify 模式下卡片回调**根本不注册**，故这条红线是结构上的，不靠自觉。

## 8. 决策清单

- **决策P4.22-1（`/page` 先行、可独立交付）**：本相位的地基是"按名开页"这个服务端动作，卡片只是它的一个
  触发面。先落 `/page`，卡片没通电也已交付价值；且它可用 `FakeAdapter` 决定性地测到，不依赖任何 SDK。
- **★ 决策P4.22-2（`Action` 携带命令文本，点击在核心闭合）**：适配器只负责把核心生成的一句话塞进按钮、
  回调时原样取回，**不知道 `/page` 是什么**。新增动作类型时适配器零改；核心不为"点击"新开处理路径。
- **决策P4.22-3（出按钮前先解析，断链引用不出按钮）**：继承决策P4.21-76 的判据——不承诺一个不存在的东西。
- **决策P4.22-4（合成消息 `mentioned_me` 恒 True）**：点击即寻址；群里点按钮不可能再 @ 一次机器人。
- **★ 决策P4.22-5（`chat_type` 查适配器自持的会话事实缓存，未命中即丢弃；**绝不**由 `allow_chats` 反推）**：
  v1 稿的"在群名单里 → 群，否则 → 单聊"**方向反了**——未列入白名单的**真实群**会被判成 DM，而 DM 分支
  只查 `user_ok`、不查 chat_id、不要求 @（`intake.py:60-64`），转发出去的卡片因此能把页面发进未授权群。
  改为只认**真实入站消息见过**的 `(tenant, chat_id)`，未命中 fail-closed。连带好处：适配器不再需要
  `allow_chats`，「`server.py` 零改」重新成立（§3 注）。
- **★ 决策P4.22-6（按钮承载在追发的独立消息上，不改流式路径）**：把本相位的全部新东西隔离在一条可以整条不发的
  消息里；P4.21 §6.2 那段单写者/节流/finalize 竞态代码一个字不动。**可回退**：日后做流式卡片，`Action` 契约不变。
- **★ 决策P4.22-7（toast 恒回中性文案，不过白名单）**：卡片本身在群里公开可见，"有机器人且它在听"早已不是
  秘密，toast 信息量为零；而把 `AccessPolicy` 下放适配器会让白名单有两份实现。与决策P4.21-28（`im-identify`
  绝不回复）不矛盾——那里机器人的**存在本身**才是要保护的东西。
- **决策P4.22-8（回调回传的参数与手打参数走同一条校验）**："这是我们自己发出去的卡片回来的"不构成信任依据
  （P4.11 口径）。长度 / 控制字符 / 前导 `/` 三项校验，不合规整条丢弃。
- **决策P4.22-9（按钮是叠加层，`[[原文]]` 继续保留）**：决策P4.21-76 在本相位**继续成立**——正文里的
  wikilink 一个字不改。故按钮超限、平台不支持、卡片发失败三种情况下，用户仍看得到引用并可手打 `/page`。
- **决策P4.22-10（缺 `register_p2_card_action_trigger` → 降级不拒启）**：卡片是叠加层，与
  决策P4.21-29 的 `extra_ua_tags`（缺则群消息静默收不到，属主功能）档次不同，故处置不同。
- **决策P4.22-11（`/page` 未命中降级为 `/search` top-3）**：未命中的现实来源是手打错别字，而 BM25 + CJK 2-gram
  正擅长救它。top-3 而非 8：这是降级提示，不是检索结果。
- **决策P4.22-12（`/page` 截断告示不附 Web 入口）**：内容在盘上，但 Web 没有按名开页的路由，给出去仍是死链。
  等 Web 补了路由这一行再改。

### v3 复审新增（★★★）

- **★★★ 决策P4.22-17（会话缓存键的两半都取 `map_event` 同源字段：`header.tenant_key` + `chat_id`）**：
  v2 稿在 `tenant` 那一半误取了 `event.operator.tenant_key`（回调里两个字段**同时存在**）。外部群 / 跨租户下
  两者可能不同值 ⇒ 合法点击查不到缓存、被回成"会话已过期"。**这类 bug 不报错、只在特定租户形态下复现**，
  是最贵的一种。待实证 #6 相应改为比对**整个键**。
- **★★★ 决策P4.22-18（参数长度只有一个口径，校验器只写一份在核心）**：v2 稿在适配器侧也量了一次"≤200"，
  量的却是**整条命令串** ⇒ 页面名 194–200 字符时"手打能开、点按钮被丢"。核心 `validate_page_arg()` 是唯一
  语义校验；适配器只留信封上界 256（平台级卫生检查，不构成第二份口径）。
- **★★★ 决策P4.22-19（连点两次就发两次页面；**明确不加**点击幂等键）**：v2 稿声称去重能挡"连点两次"——
  错的，两次点击是两个 `event_id`。重叠点击由既有单飞挡（`_inflight` + BUSY_HINT），不重叠就照发两次
  （零 LLM、毫秒级）。加"短期点击幂等键"等于把决策P4.21-34 删掉过的内容指纹去重请回来——**静默吞掉一次
  合法点击**（表现为"按钮有时点了没反应"）比多发一页糟得多。配反向用例守着。
- **★★★ 决策P4.22-20（正文未确认送达则不发按钮；但定级为一致性、非安全）**：`_safe_send` 吞出站异常
  （`delivery.py:197-202`，这本身是对的），故"正文全挂、卡片成功"可达。让 `_safe_send` 返回 `bool`、
  `_offer_actions` 只吃确认送达的片。**收件人本来就该看到这些页面名，故这不是越权泄露**——做它是因为
  成本近零。安全面在决策P4.22-13（截断）那一半。
  > 实现补充：edit 档的**首片是编辑回占位消息的**，故它的送达回执来自 writer 的 `final_ok`，
  > 不是 `_safe_send`——writer 整段 `suppress(Exception)`，不置这个标志就等于把"编辑挂了"当成"发出去了"。

### 实现期新增（★★★）

- **★★★ 决策P4.22-21（CARD 帧兼容层：不选边，两边都接住）**：把 §0.2 那条**证据矛盾**的前提从
  "先实证再实现"改成"实现对两种假说都成立"——子类化 `lark.ws.Client`，把 CARD 帧头就地改写成 EVENT
  再委回父类。**纯粹的超集**：假说 1 成立时它一次都不触发。代价是一个私有方法名，故探不到即降级告警、
  并配真 SDK 形状探针；上游修好即可整段删除。**这不等于"回调一定能到达"**——那仍需真机核对（§9 #1），
  只是它现在决定的是**能不能用**，不再决定**怎么写**。
- **★★★ 决策P4.22-22（toast 回普通 `dict`，不构造 SDK 的 `P2CardActionTriggerResponse`）**：
  处理函数的返回值被 SDK 直接交给 `JSON.marshal`，而那个模型 marshal 出来的**就是这个形状**——
  **线上的形状才是契约**。回 dict 换来三件事：不必在 SDK 线程里 import 模型、假件测试不必伪造模型模块、
  模型改名也炸不到我们。
- **★★★ 决策P4.22-25（`/page` 的输出也出按钮——推翻 §1「不纳入」里的同名条目）**：原顾虑是
  "把一次问答追发一张卡变成**可无限下钻的浏览态**"。复盘下来，那三条顾虑里只有一条是真的：
  - **"点击链没有天然终点"** —— 不成立。每一跳都是**用户显式点的**，没有任何自动递归；
    浏览器就是这么工作的。A→B→A 的来回也只是导航，不是循环。
  - **"每一跳多一条群内可见的卡片"** —— 成立但不是新问题：`/page` 的**正文**本来就发进同一个
    会话、可见性完全一样，而卡片上**只有页面名**（红线 6(a) 不变）。
  - **"每一跳多一次解析表构造"** —— **真问题，且必须一起修**。照搬答案那条路的话，一次 `/page`
    会把全库 frontmatter 解析**两遍**（开页一次、出按钮又一次），而 `/page` 号称毫秒级零 LLM。
    故 `open_page` 改回 `PageView(text, links)`：**一次建表把页内引用也判完**，出按钮时只
    在已备好的「键 → 拥有页」表上做零盘 IO 的过滤（`filter_resolvable`）。P3.8 那个 `loaded=` 参数就是为消掉
    `build_graph` 的同款双解析而生的，这里不该再犯。配一条**计数用例**守着——双解析不会让任何
    功能用例变红。

  另两处必须跟上、否则是退步：**① 引导语**说"本页引用的页面"而不是"本答案…"（照抄就成了假话）；
  **② 自引用不出按钮**，判据是**解析到的 owner** 而非名字——只比名字会漏掉 `[[甲方]]` 经别名绕回
  本页那一路。决策P4.22-13（只从**实际送达**的片抽）对页面输出**同样成立**，长页被截断时尾巴里的
  引用不上卡片，有独立反向用例。
- **★★★ 决策P4.22-24（`im-identify` 连卡片回调都不注册：`actions_wanted=False`）**：实现期才浮出来的
  一条**红线冲突**。`im-identify` 的安全性**整个建立在「绝不回复任何消息」上**（决策P4.21-28：对方只看到
  "发了没人理"，与机器人不存在无异），而卡片回调**必须同步回一个 toast**——上一次 `guanlan im` 发出的卡片
  在这 300 秒里被点一下，就等于告诉对方**机器人此刻正活着**。会话缓存是空的、于是回的是"会话已过期"，
  **这照样是一次回复**。做法：加一个与 `group_wanted` 同款的**平台无关部署意图** `actions_wanted`，
  identify 传 False ⇒ **连注册都不做**，"绝不回复"于是是**结构上的**而非自觉的。
  > 教训记在这里：本相位一路在说"叠加层、可回退、不碰既有路径"，而这条冲突恰恰出在**另一个命令**上——
  > 「新增的是叠加层」并不蕴含「它只影响新增的那条路」。
- **★★★ 决策P4.22-23（会话缓存未命中与载荷不合规回**两种不同的 toast**）**：前者是「会话已过期，请重新
  提问」（卡片被转发 / 进程重启后点旧卡片），后者是「这个按钮无法识别」（信封校验没过）。合成一句会让
  现场排查在两条完全不同的路之间盲猜；两句话的成本是零。**两者都不泄露授权信息**——卡片本身就在那个
  群里公开可见（决策P4.22-7）。

### 评审期新增（★★★）

- **★★★ 决策P4.22-26（CARD 帧改写**必须在写出回执前还原**）**：决策P4.22-21 的兼容层有一处自伤，
  是复审才看出来的——父类 `_handle_data_frame` 末尾是
  `frame.payload = ...; await self._write_message(frame.SerializeToString())`：**回执复用的就是入站
  那个帧对象**（1.7.2 `ws/client.py` 已核）。于是 CARD 假说成立时，应答会带着**我们伪造的
  `type=event`** 回去；平台若按帧型路由应答，那颗 toast 就没了。页面照样会到（入队发生在应答之前），
  症状恰好是「点了、页面来了、但没有任何反馈」——本相位最难排查的那一种，**绝不该由我们自己制造**。
  父类在方法内部就完成了序列化，事后还原来不及，故在**写出那一刻**再拦一道：还原帧头、拿同一个帧
  重新序列化。传递用 `ContextVar` 而非实例属性——帧派发是并发的，实例属性会串台（两帧同飞时后进的
  覆盖前一个，还原落到错的帧上），且**单帧用例对此全绿**，故专门有一条并发用例。
  还原挂在第二个私有名 `_write_message` 上：**探不到就整层不启用**——宁可回到"CARD 帧被父类丢弃"
  （按钮不工作，但没有伪造的帧头流出去），也不留一个我们收不了尾的改写。
  > 一般化的教训：**一个"只读改写"如果落在被下游复用的对象上，它就不是只读的**。
- **★★★ 决策P4.22-27（`Intake` 在 `adapter.start()` 之后重读一次 caps）**：`Intake` 在**装配期**
  构造（`serve_im`），而适配器**会在 `start()` 里就地降级**能力位（飞书探不到卡片注册面即如此）。
  `Delivery` 每次派发现读 `self._adapter.caps`、天然跟得上；`Intake` 攥的是构造期快照。今天恰好
  无害——降级只动 `supports_actions`/`max_actions`，而 `Intake` 只读长度与节流阈值——但"下一个会在
  `start()` 里降级、且恰好被 `Intake` 读到的能力位"会**静默用陈旧值**，且没有任何用例会红。
  一行 `intake.set_caps(adapter.caps)` 把这一类 bug 一次性掐掉，并配一条会红的用例。
- **★★★ 决策P4.22-28（`/page` **不**另设 config 页黑名单：`index`/`log`/`overview` 照常可开）**：
  复审指出 `/page log` 会把 Agent 操作日志原样发进会话，而 `/search` 走 `iter_pages`、天然排除 config 页。
  查证后**维持现状**，理由三条：**①** 决策P3-6 已经裁过——config 页**不建节点、不受校验，但是合法的
  链接目标**；`/page` 就是"跟着链接走"，拒绝跟一个全系统都认的链接等于开**第五个口径**（P3.8 的整个
  动机就是消灭口径漂移）。**②** Web 宿主是**同一形状**：`/api/pages` 列表经 `iter_pages` 排除 config，
  `/api/page?path=wiki/log.md` 照读——IM 若单独禁掉，反倒是它成了例外。**③** `/search` 排除是因为
  它是**语料召回**（`iter_pages` 口径），与"按名开页"不是一回事。
  **边界仍在白名单，不在页面集**：能跑 `/page` 的人本来就能跑 `/search`、`/new` 并对同一个库自由提问。
  唯一要写给运维的是一句事实——`/page` 能打开 `wiki/` 下**任何**页（含那三张 config 页），群里放行前
  自己掂量；已加进 `docs/guide/` 的命令表旁注。

### 已知成本（评审记录，**非缺陷**，不改）

- **每答一次重建一次解析表**：`_offer_actions` 为了判"哪些引用能解析到页"要 `link_resolution_index`，

  别名藏在 frontmatter 里），而那是一条独立的设计题、不该顺手塞进本相位。
  `/page` 那条路已经**不吃**这笔（决策P4.22-25 的 `PageView` 一次建表两用）。
- **控制字符判据在两层各有一份**（`pageview.validate_page_arg` 与 `feishu._callback_command`）：

  在 `anyio.to_thread.run_sync` 上装哨兵；被调即失败）。
- **线程边界**：断言投队列走的是 `call_soon_threadsafe`，不是直接 `put_nowait`。
- **卡片 JSON 构造**：按钮数、`value` 结构、**`value` 里不出现任何本机路径**（反向用例，守红线 5）。
- **真 SDK 探针**（仅在装了 `im-feishu` extra 时跑，与既有 `extra_ua_tags` 探针并列）：
  `EventDispatcherHandler.builder("","")` 上存在 `register_p2_card_action_trigger`。SDK 变形时这条先红。
- **降级路径**：探针缺失 → `supports_actions` 置 False、记 WARNING、**宿主照常启动**（决策P4.22-10），
  且**只关掉可点面**（断言 `supports_edit` 不受牵连——"降级"很容易顺手降过头）。
- **★ CARD 帧兼容层**（决策P4.22-21，实现期新增）：喂一个 CARD 帧 → 父类看到的是 `event`；喂
  `ping`/`event` 帧 → **一个字节不改**（反向用例，守"纯粹的超集"这条性质）。另有一条真 SDK 形状探针
  （`_handle_data_frame` / `_write_message` / `MessageType.CARD` / `HEADER_TYPE` 四个接缝都在）。
- **★★★ 回执帧头还原**（决策P4.22-26，评审期新增，三条）：① 单帧——派发时看到 `event`，而**写回去的
  串是 `type=card`** 且帧对象已还原干净；② **并发两帧各还原各的**（`ContextVar` 的存在理由——实例属性
  在这条上串台，而**单帧那条对此全绿**）；③ 探不到 `_write_message` → **整层不启用**并告警（宁可回到
  "CARD 帧被丢弃"，也不留一个收不了尾的改写）。假件的 `_handle_data_frame` 为此照抄了真 SDK 末尾那两行
  （回执复用入站帧对象）——不照抄就是在测空气。
- **★ 卡片被拒不回退纯文本**（有别于正文的 post→text 降级）：断言只发了一次 `interactive`。
- **★ 两种 toast 分开**（决策P4.22-23）：未见过的会话 → 「会话已过期」；会话认识但信封不合规 →
  「这个按钮无法识别」。合成一句会让现场在两条完全不同的排查路之间盲猜。
- **★ `im-identify` 不注册卡片回调**（决策P4.22-24，两条）：① 适配器侧——`actions_wanted=False` 时
  `handler.card_callback is None` 且 `supports_edit` 不受牵连；② **装配侧**——`run_identify` 真的传了
  `actions_wanted=False`。**只测①等于只证明适配器听得懂这个参数**，而漏掉的正是"没人传"这种沉默失效。

### 不测

真实飞书网络、真实点击（属 §9 待实证，人工）、卡片在客户端的渲染效果。
