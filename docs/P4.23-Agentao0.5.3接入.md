## 1. 版本与现有接入

- 上游最新正式版为 [0.5.3（2026-09-19）](https://github.com/jin-bo/agentao/releases/tag/v0.5.3)，[PyPI](https://pypi.org/project/agentao/0.5.3/) 也已发布。本机相邻 Agentao 仓库 main 已有发布后改动，故回归使用 `v0.5.3` 标签导出的源码。
- GuanLan 的 `pyproject.toml` 声明 `agentao[cli]>=0.4.17`，`uv.lock` 与本机 `.venv` 都是 **0.4.17**。没有上界意味着新安装可能已解析到 0.5.x，而当前锁文件 CI 仍在验证旧版本。
- `guanlan/runtime.py`：`agentao run --format json --interaction-policy reject`，解析退出码和 JSON 信封；服务 ingest/query 等单次任务。
- `guanlan/web/conversation.py`：`build_from_environment()` + `arun()` + `build_compat_transport()`；提供确认、提问、流式文字、取消、会话和 goal。IM 的 `delivery.py` 复用 `Conversation.turn()`，因此共享嵌入路径的改动。
- `PolicyFileSystem`、写后检查、撤销、单写者锁、AGENTAO.md 恢复仍是 GuanLan 的职责。新版 Agentao 不会自动替代这些宿主逻辑。

22 处生产代码中的 Agentao `from … import …` 已在 0.5.3 源码下逐项导入成功——但**导入成功只证明名字还在，不证明签名没变**，真正的把关是 §5 的真实工厂契约测试。Python 下限仍为 3.10。

### 2.1 `copies_to_subagents`（升级引入的行为反转）

本条是逐版本对比确认的，不是推测：`git grep` 显示 `v0.4.23` 无此机制、`v0.4.24` 起有。

- **0.4.17（当前）**：`agents/tools/_wrapper.py:461-465` 把 `self._all_tools` 里每个工具（仅受 agent 定义的 `tools` 白名单约束）直接 `scoped_registry.register(tool)`，**共享父 Agent 的同一实例**。`guanlan_search` 因此会进子 Agent。
- **0.5.3**：未声明 `copies_to_subagents` 的宿主工具一律不进子 Agent（默认且静默，`_wrapper.py:213`）；声明了也只得到一份 `copy.copy` 浅拷贝，且拒绝 `__copy__` 返回 `self` 或改名的副本。

即"父 Agent 注册了、子 Agent 就有"在 0.5.3 不再成立。**但在标准知识库里当前不可达**，原因见 §3.4。

## 3. 需要处理的行为缺口

> 本节混着两类事，§5 会按这条线重排顺序：**3.1 / 3.4 在 0.4.17 上就能做，不必等升级**；**3.2 / 3.1 的 goal 续跑部分必须在升级之后**（0.4.17 没有对应机制可对齐）。

### 3.1 使用 `last_turn` 判定是否获得答案（优先）

`Conversation.turn()` 当前在 `await agent.arun(...)` 后直接保存并返回文本（`conversation.py:610-620`）。Agentao 可以正常返回 `[LLM API error: …]`、空响应占位符、截断或循环终止提示；没有 Python 异常并不等于模型成功回答。

> **这不是 0.5.x 的新能力，本机 `.venv` 的 0.4.17 里 `runtime/outcome.py` 已有 `status` / `incomplete_reason` / `tool_count` / `error` / `is_answer`。** 0.5.x 只多了一个 `finish_reason_missing` 字段。所以本节**可以、也应该先在当前锁定的 0.4.17 上单独交付**：diff 小、出问题好定位，且不必等升级验收。读 `finish_reason_missing` 一律用 `getattr(outcome, "finish_reason_missing", False)`，判定代码就不会绑死在 0.5.x 上。

建议在 `arun` 返回后读取公开的 `agent.last_turn`：

- `is_answer` 为真才按正常答案处理。
- 将 `status`、`incomplete_reason`、`error` 映射成宿主错误/未完成结果；已流出的文字可以保留，但不能发正常完成语义。**"未完成"必须是结构化返回，不能是抛异常**——理由见下面的"未完成 ≠ 异常"。
- Web、IM 一处归口（IM 的 `delivery.py:438/472` 直接复用 `conv.turn()`，改 `turn()` 一处即覆盖两个宿主）；无论成功失败，可写 turn 的 `finally` 仍执行检查、还原和释放锁。
- `finish_reason_missing` 单独作为诊断，不应直接等同失败：部分兼容服务始终不提供它。

#### 失败轮契约（必须写死，不能只说"映射成宿主错误"）

**若**把 `turn()` 的失败实现成抛异常，它就会落进 `run_goal` 的通用异常路径——而那条路径**与两条中断路径不等价**（本节据此推出的契约要求，对结构化返回同样成立；最终方案见下面的"未完成 ≠ 异常"）：

| | `AgentCancelledError` / `CancelledError`（`conversation.py:1064-1078`） | 通用 `except Exception`（`conversation.py:1105`） |
|---|---|---|
| 累计本轮耗时 `time_used_seconds` | ✅ | ❌ |
| 出 `turn_done` 帧（带 `turn_meta`） | ✅ | ❌ 只 `_pause_active_goal()` 后重抛 |

于是"**已写文件、随后 API 失败**"这一幕的后果是具体的：`_finalize_writable` 照常生成了 check 结果与撤销 token，但 `turn_meta` 不出帧，用户拿不到撤销入口；本轮真实墙钟也丢失，反复 resume 会让 `--for` 预算永不 trip。因此须明确：

1. **失败轮照样累计 `time_used_seconds`**，与两条中断路径同口径。
2. **失败轮照样带 `turn_meta`（`check` / `undo` / `immutable_mutated`）出帧**，失败不等于没写盘。
3. **明确失败轮是否落盘。** `conversation.py:614` 的注释写"仅成功轮落盘"，但今天 API 错误文本一样会被 `_save()` 保存——占位文本已经进了 `agent.messages`。存或不存都要选一个并写进注释：不存则重启后丢掉用户那条消息，存则历史里留下 `[LLM API error…]`。**注意与"落盘本身失败了怎么办"是两个问题**——后者是既有降级契约，保持不变，见下面"未完成 ≠ 异常"的第二条。
4. 测试须覆盖"**工具写入之后才失败**"，不能只测一上来就失败。

#### goal 续跑：镜像上游现成规则，不要自拟

上游 0.5.3 在 `cli/input_loop.py:695-860` 已有成文规则（0.4.17 **没有**，属升级后才能对齐的部分）：

- 无进展原因集合 `_NO_PROGRESS_REASONS = {"no_output", "reasoning_only", "llm_error"}`；
- 连续无进展达上限即 `mark_blocked()` 并落盘，且**由宿主设置的 block 与 agent 自陈的 block 在回执里分开呈现**；
- 本轮调过工具算有进展（`tool_count > 0`）——**但 `llm_error` 不享受这条豁免**：`tool_count` 按轮累计而非按迭代重置，一次成功工具调用会让此后每轮都重置计数，goal 会在已失效的 provider 上永远空转。

GuanLan 的 `run_goal` 现在对任何返回都执行 `turns_used += 1`（`conversation.py:1084-1089`）。P4.16 的既定原则就是对齐 agentao，故照搬这套规则，并**在注释里点名 `llm_error` 这条例外**，否则后人极易"顺手"把它也加进豁免。

#### 未完成 ≠ 异常（两条规则的衔接，第三轮复审补）

上面两小节有一处会互相打架，必须显式衔接：**若"未完成"实现为从 `turn()` 抛异常，"连续无进展达阈值才 blocked"就永远无法成立**——首次 `no_output` / `llm_error` 一抛，就落进 `run_goal` 的通用 `except`（`conversation.py:1105`）暂停并重抛，计数根本攒不起来。上游之所以能计数，正是因为这些结果**正常返回**，由 goal 循环在返回后读 `last_turn` 再分类（`input_loop.py:725` 的 `getattr(cli.agent, "last_turn", None)`）。

所以定成：

- **未完成轮结构化返回**，携带 `incomplete_reason`，由 `run_goal` 在返回后分类计数——与上游同构；
- **真正的运行异常**（传输中断、取消等）仍走现有异常路径：暂停目标并传播；
- **会话持久化失败不在此列，保持现有降级**（第四轮复审订正）。`conversation.py:613-619` 明确捕获 `_save()` 的任何异常、只记 warning 并照常返回答案，注释写明"绝不让它冒泡把已成功的 arun 答案翻成 error（失败不毁答案，同 §4.4 降级精神）"。**磁盘满或只读目录不该中断一次本来成功的问答，更不该打断 goal 续跑。** 故须把两类失败分开：*运行失败*（拿不到答案）传播，*持久化失败*（答案有了、只是没存住）降级。若将来确实要改这条，必须显式列为行为变更并补测试，不能顺手夹带进本次改动；
- 若坚持用异常表达未完成，则必须是**专用异常类型**，且由 `run_goal` 单独捕获、转成计数后继续循环，绝不能混进通用 `except Exception`。
- 测试须覆盖三种：**连续达到阈值**、**中途有进展则重置**、**工具已执行但最后 LLM 失败**（即 `tool_count > 0` 且 `llm_error`，验证它不吃豁免）。

#### 测试替身

`tests/` 目前**没有任何一处**引用 `last_turn`，现有 fake agent 全都没有这个属性。上游自己用 `getattr(cli.agent, "last_turn", None)` 并要求 `tool_count` 是真正的 `int`，正是为了防 `MagicMock`（它对任何属性都返回真值）和"从不填 `last_turn` 的宿主"。GuanLan 须采用同样的降级约定——**`last_turn is None` 时按旧行为处理**，否则这个 PR 会牵动大量既有用例。新增的正面用例则应构造真实 `TurnOutcome`，不能只用返回字符串的 fake agent。

### 3.2 恢复历史时清理模型专属推理数据（启用新协议前）

`ConversationStore.restore()` 直接执行 `conv.agent.messages = messages`，并有意使用当前配置的模型；`load_session()` 本身不清理历史。`_lean_messages()` 仅去掉图片内容，保留其他字段。

0.5.3 上游 CLI 恢复会话时还会清理：

- `reasoning_content`；
- `anthropic_thinking_blocks`；
- `openai_reasoning_items`；
- tool call 本身及其 `function` 上的 `thought_signature`。

这些数据与生成它们的模型/协议有关。GuanLan 跳过清理，恢复到不同模型或服务时存在请求失败风险；这是源码审查发现，未做真实服务复现。

**本节必须排在依赖升级之后**：0.4.17 既没有 `purge_thinking_artifacts` 也没有 `WIRE_CARRIER_KEYS`，无从对齐。

上游辅助函数目前位于私有的 `agentao.runtime.model.purge_thinking_artifacts`。建议向上游提出公开的恢复/清理入口；GuanLan 短期用一个集中适配函数承担此规则，测试跨模型、跨协议恢复，并保留普通文字与工具调用配对。**只在恢复/切换边界清理，不应每轮删掉活跃会话的推理数据。**

短期方案在两条路里**明确选"直接 import 私有函数"**，而不是自己抄一份字段清单：

- 抄清单有隐患——上游新增 wire 时只需往 `WIRE_CARRIER_KEYS`（`llm/_stream_response.py`）加一项，GuanLan 的副本会悄悄漏掉它，而**漏清理是沉默的，正向用例测不出来**。
- 直接 import 并配一条契约测试，断言它确实清掉了 `WIRE_CARRIER_KEYS` 里的**每一项**；上游一旦改名或挪窝，这条测试立刻报错，而不是等到线上换模型才炸。
- 依赖私有模块在本仓已有先例与惯例：`safe_load_dotenv` 就是"私有 import + docstring 写明理由"。

### 3.3 收敛内部 API 依赖（可后续独立实施）

- `policy_fs.py` 的 `FileSystem` 类型改从公开的 `agentao.host.protocols` 导入；`LocalFileSystem` 实现仍可使用 `agentao.capabilities`。
- 当前通过 `transport._ask_user = …` 替换私有回调。可改为 `SdkTransport(on_event=…, confirm_tool=…, ask_user=…)`，保留现有确认和提问行为。

### 3.4 子 Agent：后台与前台是两件事，必须分开处理

> **订正（第三轮复审）**：本节先前把"传 `bg_store=None`"当成能一并关掉子 Agent 的单一决策，**这是错的**。`bg_store=None` 只关后台执行面，前台子 Agent 照常注册。§2.1 不会被它自动关闭。以下是订正后的结论。

**`bg_store=None` 到底关了什么——只关后台，不关子 Agent。** `agents/manager.py:160-166` 的 docstring 写得很明确：

> When `bg_store` is `None` the background-agent surface is disabled: each wrapper drops `run_in_background` from its parameter schema and the trailing `CheckBackgroundAgentTool` is not appended.

`create_agent_tools` 里 `wrappers = [AgentToolWrapper(...) for defn in ...]` 这个列表**无条件**按 agent 定义逐个建。所以传 `None` 之后，`agent_<name>` 工具照样注册，只是少了 `run_in_background` 参数——**前台执行完全可用**。

**而且没有"一键关全部子 Agent"的开关。** `AgentManager._load_definitions()`（`manager.py:36-44`）分两步：第 1 步扫内建定义，受 `include_builtin_agents` 门控；**第 2 步无条件扫 `<kb>/.agentao/agents/*.md`**。`enable_builtin_agents=False`（两版的默认）只挡得住第 1 步。构造器没有第二个旋钮能挡第 2 步。理论上只能靠 `enabled_tools` 允许清单（`agent.py:657-660` 的最后剪枝）逐名剪掉，但那是允许清单，要枚举全部想留的工具，**脆且易漏**，不适合作为不变量的承载方式。

**因此两个口子必须分开办：**

| 口子 | 关闭方式 | 说明 |
|---|---|---|
| **生命周期**（子任务在父轮收尾后继续写盘） | 传 `bg_store=None` | 一行、零成本，确实关死 |
| **工具继承**（§2.1，`guanlan_search` 进不了子 Agent） | 给 `guanlan_search` 声明 `copies_to_subagents` | `bg_store=None` **管不着**，前台子 Agent 仍在 |

**决策：两件都做。** 传 `bg_store=None` 守住写门禁的生命周期边界；同时给 `guanlan_search` 声明 `copies_to_subagents`，让前台子 Agent 仍有确定性召回入口——否则 `query.py:22` 那条"先用可用的 search 入口"对子 Agent 就成了死指令（正是 §1.2 要治的病）。并发这关已查清可以直接用：`copy.copy` 浅拷贝、副本与父实例共享同一个 `CorpusCache`，而 `CorpusCache` 自带 `threading.Lock`（`search.py:441`，锁只护纯字典短临界区，glob + stat 在锁外），**共享安全**。落地时须验副本满足 0.5.3 的两条校验——`copy.copy` 不返回 `self`、`copied.name` 不变（`_GUANLAN_SEARCH_NAME` 是常量，天然满足）。

**验收必须用"已配置 agent 定义的知识库"**，不能用标准库：标准库里 `guanlan init` 不生成 `.agentao/agents/`，两条路径都跑不到，绿了也说明不了任何事。

**定性一则：后台任务不是 0.5.3 引入的。** `factory.py` 默认 `overrides["bg_store"] = BackgroundTaskStore(persistence_dir=wd)`，这行在 **0.4.17（223-224 行）与 0.5.3（267-268 行）逐字相同**，GuanLan 两版都没传 `bg_store`。所以这是既有缺口，不是升级阻塞项——但既然一行能关，就该关。

**后果边界（第三轮订正，原先说窄了）。** 子 Agent 继承父的文件系统（`_wrapper.py:1018` `filesystem=self._filesystem`，即 GuanLan 的 `PolicyFileSystem`）：

- **`raw/` 与 `AGENTAO.md` 的不可变判定不受影响**——它在 capability 实例级做（`policy_fs.py:127-128`），与轮次无关，后台写照样 `PermissionError`。这条仍然成立。
- ~~"check 不会真的漏，下一轮会检出"~~ —— **这条是错的，撤回**。三个理由：① 可能根本没有下一轮；② 下一轮可能是只读轮，`run_check` 只在 `_finalize_writable` 里跑，只读轮不跑；③ 即便有下一个可写轮，呈现是按 `before_check` 基线做差、只 surface **本轮新增**的 violation（`conversation.py:683-684`），后台写造成的问题会在下一轮起跑时**被收进基线**，从此静默。所以应表述为：**后台写可能脱离本轮的检查与撤销范围**。
- ~~"走 shell 的写会躲过本轮 `raw/` 快照"~~ —— **这条也是错的，撤回**。Web 可写轮**根本不拍 `raw/` 快照**：`conversation.py:573` 的注释是"层②……**只拍 AGENTAO.md 一个文件（近免费）；`raw/` 树不扫**"。`gate.py:104` 的 `snapshot_raw` 服务的是 CLI 子进程路径（`ingest`/`query`），不是嵌入式 Web 轮。所以 shell 直写 `raw/` 在 Web 路径上是**既有的、未封堵的边界**，与后台任务无关，不能说成"绕过了已有快照"。
- 真正破掉的是三点：① **脱离本轮检查范围**（即上一条的结论：可能没有下一轮、下一轮可能只读、或被收进基线从此静默）；② **撤销失效**（写发生在 `end_journal()` 之后，拿不到 token）；③ **日志归属错乱**（混入下一轮的 per-turn 写日志）。

## 4. 新版能力怎么启用

**原生协议不需要 GuanLan 自己实现 HTTP 适配。** factory 和 CLI 都读取 `{PROVIDER}_API_FORMAT`，现有配置路径可直接承接：

```dotenv
# 已有同一 provider 的 API_KEY、BASE_URL、MODEL 配置时，再显式选择协议
OPENAI_API_FORMAT=openai-responses
```

另一种取值是 `anthropic-messages`；不设置仍走 `openai-completions`。应按实际 `LLM_PROVIDER` 的前缀配置，并确保服务端支持该协议。Responses 的请求组织、工具 schema、推理数据和重试由 Agentao 处理。

可选后续能力：

- 用 `llm.usage_snapshot()` 展示输入、输出、缓存读取、缓存写入用量，区别于当前上下文占用统计。
- 子 Agent 用量已经计入父级总量；`SubagentLifecycleEvent.usage` 用于归因，不能再加一次。缓存 token 是 prompt token 的子集，也不能重复相加。
- 原生 Anthropic 的温度行为与 Chat Completions 不同；若增加参数 UI，应按协议显示实际生效能力。
