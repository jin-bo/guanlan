# P4.18 — MCP 2.0 迁移（官方 SDK v2 + 协议 `2026-07-28`，可选叠加层）

> P4.10 把只读核心搬进任意本地 Agent（MCP **stdio**），P4.17 补第二种传输（**Streamable HTTP**）。两者都建在官方
> `mcp` Python SDK **v1.x**（`mcp.server.fastmcp.FastMCP`）之上、extra 钉 `mcp>=1.27,<2`（决策P4.10-14 / 决策P4.17-4）。
> 2026-07-28 官方同日发布 **协议修订 `2026-07-28`** 与 **Python SDK `2.0.0`（stable）**，并宣布 **v1.x 转入只收安全修复
> 的维护态**——那条 `<2` 上界从"防将来破坏性升级"变成了"钉在维护态分支上"。P4.18 把底座迁到 SDK v2 并对齐新协议修订。
>
> **定性：一次「等价迁移」半阶段**——**命令契约零变更、工具集零变更、只读/零写契约零变更、退出码零变更**（决策P4.18-1）；
> 改的是**依赖契约**（extra 上下界）、**三处 import**、**一段 http 配置写法**、**测试面口径**。协议 `2026-07-28` 的新能力
> 绝大部分是"白拿"（我们本就是无状态只读服务端），需要写代码的两项（cache hints / tasks 扩展）**显式不进本半阶段**（§5）。
>
> **状态：已实现**（`guanlan/mcp/{server,tools,__init__}.py` + `cli.py` 降级提示 + `pyproject.toml` extra 硬切 +
> `tests/test_mcp.py` 迁移与三条新用例）。§2 的事实基线**已在沙箱实测**（Python 3.10 + `mcp==2.0.0`，复现步骤见 §2.0）
> 并已转成常驻断言；`uv run pytest` 全绿（643 通过 / 3 skip，其中 `tests/test_mcp.py` 59 例）。

## 0. 定位：为什么是 P4.18

- **为什么不是 P4.17.1**：`.1` 子半阶段（P4.6.1 / P5.2.1）的定性是「补漏 + 不改任何既有契约」。P4.18 的**用户可见契约
  确实零变更**（这点像 `.1`），但它**换掉整个底座 SDK 的大版本**并改**依赖契约**（`[mcp]` extra 的上下界 = 安装面破坏性
  变更：`mcp 1.x` 环境将不再满足）。依赖契约是契约，故不用 `.1`。
- **为什么不是新里程碑 / P6**：仍是「可选宿主层」同一主题下对**既有能力**的底座迁移，挂 P4 家族、接在 P4.17 之后为
  **P4.18**，不新开顶层。
- **为什么不是直接 E2**：协议 `2026-07-28` 的授权硬化（RFC 9207 `iss` 校验、DCR 废弃转 CIMD、凭据绑定 issuer）**全在
  OAuth 面**，而 P4.10/P4.17 已把完整 OAuth / 多租户 source 级 scoping 显式推给 **E2**。P4.18 **不碰**这条线：仍是
  localhost-first + 单 bearer token 闸（决策P4.17-2/8 逐字保留）。

### 0.1 「MCP 2.0」两义之辨（本文的口径）

用户口中的「MCP 2.0」实际是同日落地、但**必须分开决策**的两件事：

| | 内容 | 本半阶段的处理 |
|---|---|---|
| **协议** `2026-07-28` | 无握手/无 session 的无状态核心（SEP-2575/2567）、MRTR 取代 elicitation/sampling 反向流（SEP-2322）、`Mcp-Method`/`Mcp-Name` 路由头（SEP-2243）、可缓存 list 结果（SEP-2549）、tasks 转 `io.modelcontextprotocol/tasks` 扩展（SEP-2663）、roots/sampling/logging + legacy HTTP+SSE 废弃（≥12 月窗口，SEP-2577） | **主体白拿**（我们本就无状态只读）；两项需写代码者不做（§5） |
| **SDK** `mcp 2.0.0` | `FastMCP` → `MCPServer`、`mcp.server.fastmcp.*` → `mcp.server.mcpserver.*`（**无 alias**）、wire 类型拆到 `mcp-types`、Python 属性转 snake_case（wire 仍 camelCase）、传输参数从构造期移到 `run()`/app 工厂、lowlevel handler 统一 `(ctx, params)`、同步 handler 自动卸 worker thread、HTTP 客户端换 `httpx2`、默认发 OpenTelemetry span | **本半阶段的主体工作量** |

> **口径**：本文标题写「MCP 2.0 迁移」以对齐外部说法，但正文一律区分「协议 `2026-07-28`」与「SDK `2.0.0`」，不混用。

### 0.2 同名反向陷阱（沿用 P4.10 §0.1 / P4.17 §0.2）

仍是 **guanlan 作 MCP 服务端**把 wiki 只读暴露出去，**不是** DESIGN §1.22「Tool 注入」（Agentao 作 MCP 客户端消费外部
工具）。P4.18 只换服务端底座，方向不变。**但**本半阶段第一次让两个方向在**依赖层面相撞**：一个环境里只能装一个 `mcp`
发行版，而 agentao 正是"客户端方向"的消费者——故 §4 的硬切决策必须以 agentao 的双大版本兼容实测为前置（决策P4.18-10）。

## 1. 命令契约：零变更（硬约束）

```bash
guanlan -C <kb> mcp                              # stdio，七工具，与 P4.10/P4.17 字节等价
guanlan -C <kb> mcp --transport http             # Streamable HTTP，默认 127.0.0.1:8766，默认六工具
guanlan -C <kb> mcp --transport http --host 0.0.0.0 --allowed-host kb.example.internal --auth-token-env GUANLAN_MCP_TOKEN
guanlan -C <kb> mcp --transport http --allow-ask
```

**决策P4.18-1**：旗标集、默认值（`--transport stdio`/`--host 127.0.0.1`/`--port 8766`/`--allow-ask` 默认关）、门控公式
`allow_ask=(transport=='stdio' or --allow-ask)`、绑定红线与拒启条件、退出码（`EXIT_OK` / `EXIT_USAGE`）、七工具名与信封
形状、`page`/`path` 口径（相对库根带 `wiki/` 前缀）——**全部逐字保留**。已注册在 `~/.claude.json` / `mcp.json` 里的
stdio & http server 条目**不需要改一个字**（§2 实测：v2 服务端在两种传输上都仍服务旧协议握手客户端）。

用户可感知的变化**恰好两处**，都记在册：

1. **安装面**：`[mcp]` extra 要求 `mcp>=2`（§4）。
2. **`initialize` 响应里的 `serverInfo.version`**（B8 / 决策P4.18-12）：v1 实测回**所装 mcp SDK 的版本**（`1.29.0`
   ——这本来就是个把 SDK 版本当服务端版本的错值），v2 默认回**空串**。故本半阶段**显式传 guanlan 自己的版本**，把这处
   身份元数据一次性钉正。**不宣称此处字节等价**——v1 的值从来就不是 guanlan 的版本。

## 2. 事实基线（实测，不是文档推断）

### 2.0 复现步骤

```bash
uv venv /tmp/mcp2 --python 3.10 && uv pip install --python /tmp/mcp2/bin/python "mcp==2.0.0"
# ① in-memory：TypedDict 输出 schema / ToolError in-band / 越界入参 / stdout 洁净
# ② 真 uvicorn：streamable_http_app(stateless_http=True, transport_security=…) + 我们的 bearer middleware
#    → 无 auth 401 / 有 auth 200 / 坏 Host 421 / 缺 Mcp-* 头 200 / initialize(2025-06-18) 200
# ③ 真 stdio 子进程：mcp.run(transport="stdio") + 手写 JSON-RPC 帧喂 stdin、逐行解析 stdout
#    → 旧握手 era 全程可用 / 现代信封 era 可用 / stdout 只承载合法帧、stderr 空
```
（沙箱脚本是一次性探针、不入仓；实现期把结论转成 `tests/test_mcp.py` 的常驻断言，见 §7。）

> **实测方法论的一条教训（写进来免得实现期重踩）**：v2 的 lowlevel `run` 是 `serve_dual_era_loop` 的薄壳——**「客户端
> 首帧决定本连接的 era」**。第一版探针在**同一连接**里先发现代信封 `tools/call`、再发旧 `initialize`，收到
> `-32022 connection is serving the 2026-07-28 protocol; the initialize handshake is not accepted`，一度被误读成
> "v2 stdio 不再支持旧客户端"。换成全新连接、首帧即旧 `initialize` 后**完全正常**（见 §2.1）。故 §7 的两个 era 断言
> **必须各起一条连接**，不得在一个连接里混测（决策P4.18-7）。

## 3. 代码改动面（约 10 行 + 测试面）

```
guanlan/mcp/
  server.py     # B1（import + 构造）、B3（_build_http_app 改 kwargs）；serve_mcp/CLI 分派逻辑零改
  tools.py      # B2 一行 import（+ 注释里"已核对 SDK 1.27"改口径）；七个工具函数逐字节不动
  __init__.py   # 文档串里 `from mcp.server.fastmcp …` 措辞
  cli.py        # 仅降级提示补版本口径（决策P4.18-9）；旗标/透传零改
```

**B1 + B8（server.py:38、103、123、292、313）**——`FastMCP` 这个名字在 server.py 出现在**五个语法位置**，一次改净
（漏掉类型注解会让 mypy/pyright 报未定义名，漏掉 tests 的 monkeypatch 会红——见 §7）：

```python
- from mcp.server.fastmcp import FastMCP          # :38  import
+ from mcp.server.mcpserver import MCPServer
+ from .. import __version__                      # B8：版本单一来源 guanlan/__init__.py
...
- ) -> FastMCP:                                   # :103 build_mcp 返回注解
+ ) -> MCPServer:
- mcp = FastMCP("guanlan", instructions=_INSTRUCTIONS, log_level="WARNING")               # :123
+ mcp = MCPServer("guanlan", version=__version__, instructions=_INSTRUCTIONS, log_level="WARNING")
...
-     mcp: FastMCP,     # :292 _build_http_app 形参注解 / :313 _serve_http 形参注解
+     mcp: MCPServer,
```

构造签名不变（`instructions` / `log_level` 均在 `MCPServer.__init__`），唯一新增实参是 `version=`（**决策P4.18-12**：
v1 在这里回的是 mcp SDK 自己的版本，v2 默认回空串；两者都不对，故显式传 guanlan 版本一次钉正，并在 §7 落断言）。
另有若干**文档串/注释**里的 `FastMCP` 措辞（:22、:104、:121、:126、:323）一并改，`tools.py:8`/`:26-29` 同理。

**B3（server.py:291-309 `_build_http_app`）**——从"settings 后置赋值"改为"app 工厂 kwargs"。注意决策P4.17-11 曾把落点
写成"经 `mcp.settings` 后置赋值（已核对 `Settings` 有这些字段）"——那句在 v2 下失效，须改口径（§9）：

```python
- mcp.settings.stateless_http = True
- mcp.settings.transport_security = _http_security(host, allowed_hosts)
- app = mcp.streamable_http_app()
+ app = mcp.streamable_http_app(
+     stateless_http=True,                                    # 决策P4.17-7：无 Mcp-Session-Id、无事件重放
+     transport_security=_http_security(host, allowed_hosts),  # 决策P4.17-5：白名单派生自 --host/--allowed-host
+     host=host,                                               # 仅用于 SDK 的"环回自动开 rebinding 防护"分支
+ )
  if token is not None:
      app = _BearerTokenMiddleware(app, token)
```

> `host=` 只影响"`transport_security=None` 且 host 环回时 SDK 自动补默认白名单"这条兜底路径；我们**总是显式传**
> `transport_security`，故该兜底不生效——传 `host` 只为不与 SDK 语义打架，行为等价。`_http_security` / `_host_label` /
> `_allowed_host_patterns` / `_BearerTokenMiddleware` / `_serve_http` **全部逐字节不动**。

**保留手写 `to_thread`（决策P4.18-5）**：v2 会把同步 handler 自动卸到 worker thread，使 server.py 里七处
`anyio.to_thread.run_sync`（决策P4.10-15）在语义上变成冗余。**不改**——① 显式 async + 显式卸载是零行为风险的现状；
② `ask` 的子进程仍值得我们自己控（一次慢 `ask` 不饿死并发 `search`）；③ 改它会把"等价迁移"变成"顺手重构"，与本半阶段
定性相悖。`anyio>=4.1` 的直接依赖声明（现状注释：server.py 直接 import anyio）因此保留。

**决策P4.18-9（降级提示补版本口径）**：`cli.py:162-170` 的 ImportError 守卫会把「装了 mcp 但是 1.x」误报成「没装
extra」（v2 缺 module 抛的正是 `ModuleNotFoundError`，落进同一 `except`）。提示语须补一句"需要 `mcp>=2`（v1.x 不再
支持）"，否则用户按提示重装 extra 仍失败、无从自救。

## 4. 依赖契约：硬切 `mcp>=2,<3`

**决策P4.18-2（硬切，不做双大版本 shim）**。两条路线对比：

| | A. 硬切 `mcp>=2,<3`（**取**） | B. 双支撑 `mcp>=1.27,<3` + 探针 shim（否） |
|---|---|---|
| 服务端代码 | 单一路径，改完即净 | 新增一层 `_sdk.py` 收敛 import 与 http 配置两种写法（约 +20 行） |
| 测试 | 一套 | B5/B6 的约 30 处须按 major 探针取字段，且**必须 CI 双 job 才算诚实**（否则等于声明支持但从不验证） |
| 代价 | 环境里若有别的包钉 `mcp<2`，则装不上 `guanlan-wiki[mcp]` | 长期背两套分支；每次 SDK 变更要在两个 major 上核 |
| 收益 | v1.x 已只收安全修复，早切早了 | 只在"共存旧钉版"这一个场景兑现 |

取 A 的三条理由：① `guanlan mcp` 是**可选叠加层**，多数用户装在专用环境 / `uvx` 里，共存冲突概率低；② 服务端真实
差异只有两处 import + 一处 kwargs（§3），双支撑的成本几乎全在测试矩阵，性价比倒挂；③ **最可能冲突的那个依赖已经不
冲突了**——`agentao` 已自带探针式双大版本兼容（§2.1 末行）。

**决策P4.18-10（agentao 双兼容是硬切的前置条件，不是巧合）**：guanlan 的核心依赖 `agentao[cli]` 自身依赖
`mcp>=1.26,<3` 并作 MCP **客户端**（Tool 注入方向）。同一环境只能装一个 `mcp`，故"把 guanlan 的 extra 抬到 `>=2`"
等价于"把 agentao 也推到 mcp 2.x 上跑"。实现期须**实测复验**（不只读代码）：装 `mcp 2.x` 后 agentao 的 MCP 客户端
路径仍可用；若将来 agentao 回退掉 `_compat.py` 的双兼容，本决策须重新评估。

**足迹变化**（`mcp 2.0.0` 的运行时依赖，实测自 PyPI 元数据）：新增 `httpx2>=2.5`、`opentelemetry-api>=1.28`、
`jsonschema>=4.20`、`mcp-types==2.0.0`、`pyjwt[crypto]>=2.10.1`、`typing-inspection>=0.4.1`、`sse-starlette>=3`；
下界抬升 `pydantic>=2.12`、`anyio>=4.9`（py3.14 上 `>=4.10`）。**仍随 SDK 到位**：`starlette`、`uvicorn>=0.31.1`、
`python-multipart` → 决策P4.17-4 的"ASGI 栈随 `[mcp]` extra 到位、无独立 http 依赖门"结论**继续成立**，`_serve_http`
里的 `import uvicorn` 不动。我们 extra 里的 `anyio>=4.1` 声明保留（表达"我们直接 import 它"），实际会被 SDK 抬到
`>=4.9`。`opentelemetry-api` 是 **api-only、无 exporter** → 与决策P4.10-13 的 stdout 洁净红线不冲突（§2.1）。

```toml
mcp = [
    # 官方 SDK v2.0.0（2026-07-28）为当前 stable；v1.x 同日转入只收安全修复的维护态，故下界抬到 2、
    # 上界 <3 防下一次大版本破坏（决策P4.18-2）。v2 同时服务协议 2026-07-28 与握手时代旧修订，
    # 已注册的 stdio/http 客户端零改（决策P4.18-7 实测）。
    "mcp>=2,<3",
    "anyio>=4.1",   # server.py 直接 import（to_thread 卸 ask 子进程/读盘），显式声明而非靠 mcp 传递
]
```

## 5. 协议 `2026-07-28`：白拿什么、不做什么

**白拿（零代码）**
- **无状态核心**：协议层删掉 `initialize`/`initialized` 与 `Mcp-Session-Id`，每个请求自描述（`_meta` 携协议版本/客户端
  身份/能力）。我们 http 侧本就 `stateless_http=True`（决策P4.17-7）、stdio 侧本就"客户端自持对话、零服务端会话"
  （决策P4.10-1），**姿态天然对齐**——P4.17 §3.1 里"无 `Mcp-Session-Id`、无事件重放"的解释性绕弯可以简化为"协议已如此"。
- **`server/discover`**、**标准错误码**（未知方法 `-32601`、头不匹配 `-32020`）：SDK 内建，我们不注册任何自定义方法。
- **`Mcp-Method` / `Mcp-Name` 路由头**：规范要求客户端在 Streamable HTTP 上带，便于网关/WAF 不解 body 就能路由与计量。
  **实测 v2 服务端不强制**（不带头的 `tools/call` 照样 200）→ 我们无需改任何代码；值得在 P4.17 §5 的反代片段补一句：
  前置 nginx/caddy 可按这两个头做限流/计量（对 `ask` over http 的成本面尤其有用，决策P4.17-6 的自然延伸）。

**不做（决策P4.18-8）**
- **cache hints（SEP-2549）**：`MCPServer(cache_hints={...})` 可给结果挂 `ttlMs`/`cacheScope`（`mcp.server.caching.CacheHint(ttl_ms:int, scope:'public'|'private')`）。
  它**很便宜但边界必须说清**：实测 `CacheableMethod` 只含 `prompts/list`、`resources/list`、`resources/read`、
  `resources/templates/list`、`server/discover`、`tools/list`——**`tools/call` 不在其列**。也就是说它能省掉客户端反复拉工具表，
  **救不了** `list_pages`/`graph` "无分页、大库上可能几十 MB"那个老问题（P4.10-10 附 / P4.17 §3.1 的载荷上限）。
  收益小且与本半阶段"等价迁移"定性不同轨 → 单列后续（连同"给 `list_pages`/`graph` 上真分页"一起评估）。
- **tasks 扩展（SEP-2663）**：概念上正对 `ask` 的痛点（几十秒同步调用，现靠 to_thread 不饿死并发；tasks 让它立即返
  task handle、客户端轮询 `tasks/get`）。**两条实测理由推后**：① Python SDK `2.0.0` **未随包提供 tasks 实现**
  （`mcp/server/` 下只有通用 `extension.py` 扩展框架，无 tasks 模块）→ 等于自己手写一个扩展；② 任务态需要服务端存储，
  与决策P4.17-7 的无状态姿态**直接冲突**（同 EventStore 的推后理由）。列为**观察项**：待 SDK 内建 + 客户端支持面变厚
  再评估。
- **MRTR / elicitation / sampling / roots**：只读服务端不需要向用户/客户端反向要输入或采样，本就未用（决策P4.10-3
  "不注册任何写工具"的自然延伸）。roots/sampling/logging 的废弃（SEP-2577，≥12 月窗口）对我们**零影响**。
  ⚠️ 口径澄清：`build_mcp` 里的 `log_level="WARNING"` 是 **Python logging 级别**（压 FastMCP/MCPServer 每请求 INFO
  到 stderr），**不是**被废弃的**协议** `logging` 能力——不要因"logging 废弃"去动它。
- **OAuth 面全部**（RFC 9207 `iss` 校验、DCR 废弃转 CIMD、凭据绑 issuer、`application_type`）：仍属 **E2**
  （决策P4.17-2/8 边界不变）。P4.18 的鉴权面**逐字保留**单 bearer token 闸。
- **legacy HTTP+SSE**：协议已正式废弃，与决策P4.17-10（"绝不回头实现"）同向，无动作。

## 6. 边界（明确不做）

- **不改任何命令契约 / 工具集 / 信封形状 / 退出码**（决策P4.18-1）——这是本半阶段的定性，不是顺手。
- **不做双大版本兼容层**（决策P4.18-2）。
- **不顺手重构** `to_thread` 卸载（决策P4.18-5）、不动 `tools.py` 七个工具函数的逻辑、不动 `search`/`report_dict`/

- **不引入 OTel exporter / 不接可观测性后端**：v2 默认发 span，我们只让它保持 no-op（api-only）。真要观测是独立议题
  （且须先过 stdout 洁净红线的审）。
- **不动 Web 宿主**：`guanlan/web/` 与 `mcp` SDK 无关（fastapi/uvicorn 自有 extra），P4.18 不碰它一行。
- **不做 cache hints / tasks / 分页**（§5，单列后续）。
- **不放宽只读契约**：`require_kb_root(writable=False)`、不注册写工具、`raw/` 不可写、`ask` 的 KB 零写探问（决策
  P4.10-3）全部照旧，且须在 v2 下**复测**（§7）。

## 8. 决策清单（沿用仓库 `决策PX-N` 体例）

- **决策P4.18-1（等价迁移：命令契约/工具集/只读契约/退出码零变更）**：用户可见变化**恰好两处**——`[mcp]` extra 的版本
  要求（§4），与 `initialize.serverInfo.version`（B8/决策P4.18-12，主动钉正、不宣称字节等价）。已注册的 stdio/http
  客户端条目不需改一个字。
- **决策P4.18-2（硬切 `mcp>=2,<3`，不做双大版本 shim）**：v1.x 已只收安全修复；服务端差异仅两处 import + 一处 kwargs，
  双支撑的真实成本全在"必须 CI 双 job 才诚实"的测试矩阵。
- **决策P4.18-3（零契约变更项按实测承接，不重新设计）**：结构化输出（TypedDict → output schema → `structuredContent`
  + 文本兜底）、in-band error 总壳、路径越界红线、DNS-rebinding 白名单派生、bearer 闸、`ask` 子进程姿态——**全部逐字
  保留**，实测已证 v2 上语义同形（§2.1）。
- **决策P4.18-4（http 配置改走 app 工厂 kwargs）**：`stateless_http`/`transport_security`/`host`/`port` 在 v2 的
  `Settings` 里**已不存在**（实测字段清单见 §2.2 B3）→ `_build_http_app` 改 kwargs；这**推翻**决策P4.17-11 里"经
  `mcp.settings` 后置赋值"的落点描述（§9 连带更新）。传输/绑定/鉴权仍全部收在 `serve_mcp`，`build_mcp` 单一职责不变。
- **决策P4.18-5（保留显式 async + `anyio.to_thread`）**：不依赖 v2 的"同步 handler 自动卸 worker thread"隐式行为；
  显式卸载零风险，且 `ask` 的慢子进程仍须我们自己控（决策P4.10-15 逻辑不变）。
- **决策P4.18-6（stdio 洁净红线在 v2 下重新实证）**：v2 默认发 OTel span，但只依赖 `opentelemetry-api`（无 exporter）
  → no-op。**须作常驻断言**，不接受"应该没事"。
- **决策P4.18-7（旧协议客户端回归必测）**：v2 服务端同时服务协议 `2026-07-28` 与握手时代旧修订（实测 `2025-06-18`
  握手 200）。这是"零用户可见变更"的硬证据，测试常驻。
- **决策P4.18-8（cache hints / tasks 不进本半阶段）**：cache hints 只覆盖 list/read/discover 类方法（**`tools/call`
  不在其列**，救不了大 payload），收益小；tasks 在 SDK `2.0.0` 里**无现成实现**（只有 extension 框架）且与无状态姿态
  冲突 → 观察项。MRTR/roots/sampling/logging 废弃与 OAuth 硬化对我们零影响（后者仍属 E2）。
- **决策P4.18-9（降级提示补版本口径）**：`mcp 1.x` 环境下 `from mcp.server.mcpserver …` 抛 `ModuleNotFoundError`
  会落进"缺 extra"守卫 → 提示须明示"需要 `mcp>=2`"，否则用户按提示重装仍失败。
- **决策P4.18-10（agentao 双大版本兼容是硬切前置）**：同环境只能一个 `mcp`；agentao 作 MCP 客户端已自带探针式
  1.x/2.x 兼容层。实现期实测复验；若 agentao 回退该兼容，本决策重评。
- **决策P4.18-11（测试面口径：in-memory 双 mode，不许静默降覆盖）**：旧 `create_connected_server_and_client_session`
  已删除，但**默认 `Client(mcp)` 走 `DirectDispatcher` 直调——无流、无 JSON-RPC 帧、无握手**（B10）。故：① 既有全套
  语义回归改挂 **`Client(mcp, mode="legacy")`**（内存流 + 真 JSONRPCDispatcher，与 v1 覆盖等价）；② **另加**默认
  `Client(mcp)` 的并行用例覆盖 2026 现代 per-request 路径；③ 真 JSON-RPC 帧的**最终**证据是决策P4.18-6 的 stdio 子
  进程测试。另：**Python 属性读 snake_case、wire 断言仍 camelCase**——两套口径不可混，混了会写出"看起来通过其实没测到
  wire 契约"的断言。
- **决策P4.18-12（显式传 guanlan 自己的版本）**：`MCPServer("guanlan", version=__version__, …)`，来源
  `guanlan/__init__.py`（版本单一来源）。理由：v1 在 `serverInfo.version` 回的是**所装 mcp SDK 的版本**（实测
  `1.29.0`），v2 默认回**空串**——两者都是错值，趁本半阶段一次钉正，并在 §7 落断言。此处是本半阶段**唯一**主动引入
  的 wire 变化，须写进 CHANGELOG（§9）。
