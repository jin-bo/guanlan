## 1. 现状

| 按钮 | 接口 | 查什么 | 性质 |
|---|---|---|---|
| 校验 | `GET /api/report/check` | frontmatter、`sources`、断链 | frontmatter / sources 阻断（写门禁增量追究）；**断链只是警告**（`gate._WARNING_KINDS`） |
| 健康 | `GET /api/report/health` | 桩页、`index.md` ↔ 磁盘、源页无 raw、重名、目录与 type 不符、overview 过大 | 建议性 |
| 巡检 | `GET /api/report/lint` | 孤页、断链、高频缺失实体、hub / 桥边 / 割点 / 孤立社区 | 建议性 |

三者共用一个前端渲染 `renderReport`：只有「通过 / ✗ N 条」和一张平铺列表。

**真实库实测**（一个 1743 页的真实库，2026-11-14）：

| 报告 | 耗时 | 条数 | 构成 |
|---|---|---|---|
| check | 1.5 s | 3015 | 全部 `wikilink.broken`（**0 条阻断**） |
| health | 0.35 s | 1 | `overview_large` |
| lint | 1.1 s | 2814 | `broken_link` 2210、`missing_entity` 560、`hub_node` 44 |
| heal worklist | 0.8 s | 560 | 与 lint `missing_entity` 同源 |
| audit 预览 | 0.26 s | 0 组 | — |
| 待入库 raw | ≈0 s | 0 / 157 | — |
| quotes | 12 s | 1104 | — |

**问题**：
1. 「校验」把一个没有任何阻断问题的库报成「✗ 3015 条」，用户读到的是「库坏了」。
2. 断链在校验、巡检各报一遍（同一张图，决策P3-6：`graph.broken ≡ check.wikilink.broken`；check 按出现次数计 3015 条，lint 按「页 + 折叠后目标」去重为 2210 条），
   巡检又把被多页引用的断链目标另聚成「缺失实体」——同一批断链出现三次。
3. 3000 条平铺，看不出主次，也没有「怎么修」的入口；补全（heal）、审计、补录各在自己的浮层里，体检结果不指向它们。

## 2. 方案

顶栏三个按钮合成一个 **「体检」**。浮层分三段，每类一行「类别 · 条数 · 修复入口」，点开看明细（默认只展开第一段）：

### 2.1 必须修

| 来源 | 说明 | 修复入口 |
|---|---|---|
| `gate.partition_violations(check.violations)` 的 **blocking** 部分 | 与写门禁同一口径：凡不在 `gate._WARNING_KINDS`（目前只有断链）里的都算——现有 `frontmatter.*`、`sources.unresolved`、`aliases.duplicate`、`aliases.collides_stem`、`page.not_utf8`、`wiki.missing`，以及以后新增的阻断类型 | 只有 `sources.unresolved` 可一键修：另有有效来源的摘掉失效项（§6.3），全部失效的内容页整页删进回收区（§6.4）；其余无自动修复，明细给页名，点击打开页面 |

不在体检里另维护阻断类型白名单：check 新增阻断类型时体检自动跟上，不会显示「没有阻断性问题」而漏报。

全部为零时这一段只剩一行「✓ 检查了 N 页，未发现阻断性问题」——措辞说「未发现」而非「没有」：体检只报已有检测查得出的问题。

### 2.2 建议处理

| 类别 | 来源 | 修复入口 |
|---|---|---|
| 高频缺页 | lint `missing_entity`（= heal worklist，被 ≥2 页引用的断链目标） | 「补全」→ `openHealPreview()` |
| 其余断链 | lint `broken_link`（已按页 + 目标去重）减去目标已列入「高频缺页」的；check 的 `wikilink.broken` 不再单列 | 「补全」→ `openHealPreview(min_refs=1)`；明细按目标聚合（「[[X]] ← 3 页」），不再逐条平铺 |
| 待入库资料 | `_list_raw` 中 `ingested=false` | 「补录」→ `openIngestPicker()` |
| 漂移源 | `audit_preview` 的 `groups + postponed`（预览默认只把前 `DEFAULT_LIMIT`=10 组放进 `groups`，体检全量计数、全量列出） | 「审计」→ `openAuditPreview()`（一批审几组仍由原浮层的 limit 决定） |
| 索引不同步 | health `index_missing_page` / `index_dangling` | 「修复」→ `openReindexPreview()`（§6.2；首版只提示可用 `guanlan reindex`） |
| 页面质量 | health 其余 kind、lint `orphan` | 无；明细给页名 |

### 2.3 结构提示（默认折叠）

lint 的 `hub_node` / `bridge_edge` / `cut_vertex` / `isolated_community` / `thin_intercommunity_link`。只是「图谱上值得看一眼」，不是问题；
给「打开图谱」入口。

## 3. 接口

- 新增 `GET /api/doctor`：线程池里依次跑 check / health / lint / audit 预览 / heal worklist / raw 列表，返回
  `{"sections": [...], "counts": {...}, "pages_checked": N, "elapsed_s": …}`。分组与去重在**服务端**做（一处实现、可测），前端只渲染。
  实现为一个只读聚合函数（`guanlan/doctor.py` 的 `run_doctor(root)`，零 LLM），端点只做线程池调用与序列化。
  - **命名**：接口与模块叫 `doctor`，界面中文仍叫「体检」、英文 Checkup。兑现 [`finding-因果排序.md`](finding-因果排序.md) 里「跨命令统一根因视图
    候选并入未来 `doctor` 聚合」的伏笔；也与 gbrain 的 doctor（知识库内容体检）同义。将来若加运行环境检查（agentao、模型配置、技能安装），
    并进同一个 doctor 作为单独一段，不另起名字。本期不加 CLI；真要加 `guanlan doctor`，打印同一份聚合结果。
  - **断链的结构化来源**：不解析 lint finding 的中文 `detail`。聚合层直接取 `graph.build_graph(wiki).broken`（`Edge.source` / `Edge.target`，
    target 已是 `link_stem` 折叠后的键）与 `lint.missing_entities(wiki)`（`target` / `ref_pages`），据此按目标聚合、排除已列入「高频缺页」的目标。
    明细项形如 `{"target": …, "ref_pages": [...], "detail": <lint 原文案>}`：结构化字段供分组，原文案照样展示。
    实现上只建一次图：`lint.py` 拆出 `lint_from_graph(g)`（`run_lint` = 建图 + 它）与 `missing_entities_from_graph(g)`，体检在同一张图上取 lint 发现、
    断链边与缺失实体；断链文案用 lint 同一个 `broken_link_detail()`，不两处拼。`run_lint` 的对外契约不变。
  - 其它条目保留各子报告原样的 `kind` / `page` / `detail`，分组只加 `category`，不改写文案；旧接口 `/api/report/{name}` 的契约不变。
  - **计数按最终展示项算**：断链按聚合后的目标数、缺页按目标数、漂移源按组数、待入库按文件数；不沿用子报告的原始条数（check 的 3015 不会出现在体检里）。
    总数 = 必须修 + 建议处理各类之和，**不含结构提示**。
  - 全量约 4 s（1743 页）。不缓存：结果随写入变化，缓存失效规则比多跑几秒更贵。
- `GET /api/report/{name}` **保留**（CLI `--json` 字节对齐的红线，决策P4-7；外部脚本可能在用），前端不再调用。
- `--reader` 部署：沿用决策P4.9-10——**隐藏体检按钮**（维护诊断对只读读者无用，体检还会列出待入库文件名、漂移源等维护信息），`/api/doctor` 只读、照常注册（同 `/api/report/*`，隐藏是 UX、非安全边界）。前端另兜一层：reader 下修复入口里的写入口不渲染。

## 4. 前端

- 顶栏：去掉校验 / 健康 / 巡检三个按钮，加一个「体检」，省出两个位置。
- 浮层顶部一行总评：「✓ 检查了 N 页，未发现阻断性问题」或「✗ 检查了 N 页，发现 3 处必须修」；下一行「另有 X 项建议处理（见下）· 用时 Y 秒」。
- 明细超过 50 条时只显示前 50 条 + 「还有 N 条」，不一次渲染几千个节点。
- 修复入口只是打开既有浮层（`openHealPreview()` / `openAuditPreview()` / `openIngestPicker()`），不在体检里直接提交写任务——提交仍走原浮层的预览与确认。
- 中英文按现有 i18n 约定（`t()` 首参字面量）。

## 5. 能力上限与失效规则

- **不新增规则**：体检的每一条都来自已有检测；它们的误报 / 漏报原样继承。
- 断链取 `graph.broken`：依赖决策P3-6 的 `graph.broken ≡ check.wikilink.broken`。加一条测试钉住「check 断链的 (页, `link_stem` 折叠后目标) 集合 = lint `broken_link` 的集合」，
  两边将来分叉时体检不会悄悄漏报（在该真实库上实测两者一致；直接比 detail 文本会因大小写折叠误判出 122 个「差异」）。
- 结构提示在小库上几乎总是空，大库上总是有；它不参与总评。
- 体检不进写门禁、不进 CI，结果不落盘。

### 6.1 深查·引文核对（已实现，2026-11-15）

体检浮层末尾加一段「深查（可选，点击才跑）」，目前只有引文核对一项。

- **跑什么**：`doctor.run_doctor_quotes(root)` = 全库 `quotes.run_quotes`（默认参数、非 strict，同 `guanlan quotes`），按三类分组：
  - `strict`：计入 `--strict` 的那一档（altered ∧ 无 OCR 提示 ∧ 非标签形态），默认展开；
  - `review`：其余 altered 与 unsupported，要人判断；
  - `unchecked`：`no_source` / `source_unreadable` / `scan_incomplete`，核对没做成。
  `misattributed` 与 CLI 默认一样只计数。汇总（候选、逐字通过、strict 条数）与 `quotes --json` 的 `summary` 同口径，测试钉住。
  每条带原因**代号**（`quotes._REASONS` 的键），前端按代号取中英文案，不转发中文原文；代号表由 `_REASONS` 反查生成，测试钉住与 i18n 两份齐全。
- **怎么跑**：`guanlan/web/deepcheck.py` 的 `DeepCheck`——进程内单飞的后台线程。`POST /api/doctor/quotes` 起跑（在跑则原样返回状态，
  不排队、不报 409），`GET /api/doctor/quotes` 取 `{state: idle|running|done|failed, started_at, finished_at, running_s, result, error}`；
  前端在跑时每秒轮询。结果只留最近一次、只在内存：关掉浮层再打开，进行中的接着显示进度，做完的直接显示；服务重启即没了。
- **返回截断**：每类 `items` 只带前 50 条（= 前端每类渲染上限），`count` 仍是全量。实测 1741 页的库「需人判断」1001 条，全量返回 706 KB、
  截断后 47 KB；其余提示用 CLI `guanlan quotes --json` / `--page`。与 `run_doctor` 的「`count == len(items)`」不同，是有意的。
- **reader**：两个端点都不注册（体检按钮本就隐藏；也不让匿名读者反复触发全库扫描）。
- **实测**：上述库服务端单跑 12.4 s，Web 内（与体检本身前后脚）14.3 s；逐字通过 95.7%，strict 0、需人判断 1001、未能核对 103。
- **能力上限**：不取写锁，核对期间库若被写入，结果反映读到时的样子；不能中途停止（十几秒，停止的价值抵不上停止机制的成本）；
  不落盘、不进写门禁与 CI；不新增规则，误报漏报原样继承 P3.14。

### 6.2 索引一键修复（已实现，2026-11-15）

「索引与磁盘不同步」一行的修复入口（`action: "reindex"`）打开预览浮层，确认后作为后台任务执行。

- **预览**：`GET /api/reindex/preview` == `guanlan reindex --prune --dry-run`（零 LLM、不写盘）。一次算出两样：将登记的漏登页
  （分区、整行）与可删除的悬空行（被 HTML 注释包住的行受 P3.4 的保护，不在其中）。悬空行**默认不删**，与 CLI 默认一致；
  勾选「同时删除 N 条悬空条目」才带 `prune: true` 提交。只有悬空行又没勾选时，按钮置灰（提交了也什么都不做）。
- **执行**：`POST /api/reindex {prune}` → 任务类型 `reindex`（`TASK_KINDS`），走 `_submit_task`：层③ 423、查重、上限、写锁排队、
  前像（取消即回滚）、重启恢复、重试（`ReindexBody` 重建），与其他任务同一条路。作业**执行时服务端重算** `run_reindex`，
  预览只给人看（同 heal 的 worklist，决策P4.3-3）：排在长时间 ingest 后面时，ingest 期间新登记的页不会被重复登记。
  写入用 `atomic_write_text`，回执是 CLI 同一份 `format_result` 文案。完工回调按写 wiki/ 处理（bump 代际）。
- **修不了的单列**：体检「索引」一项里有、reindex 却修不了的——不在四个分区目录下的页、沾 HTML 注释或与有效链接同行的悬空条目——
  预览另返回 `manual_pages` / `manual_links`，界面列出并提示手动编辑 `index.md`；只有这些都为空时才显示「已同步」，免得预览与体检互相矛盾。
- **作业 = CLI 的单一落地**：直接调 `reindex_entrypoint(root, prune=…, dry_run=False)`（算 → 写 → 回执），不在 Web 里另抄一份。
- **撤销**：前像只在任务完成前有效（取消即回滚）；reindex 毫秒级就跑完，完成后前像已删，没有撤销。界面文案据此写「开始执行前可取消，完成后没有撤销」。
- **不变**：仍是 P3.4 的契约——零 LLM、只写 `wiki/index.md`、不过写门禁、不写 `log.md`（决策P3.4-6）；一句话摘要留空待补。
- **reader**：两个端点都不注册。
- **实测**：1741 页的库上 `run_reindex` 0.09 s，前像 1.7 s（1745 个文件）——前像远比修复本身贵，但仍在秒级，换来与其他写任务一致的
  排队、取消回滚与记录。真浏览器冒烟：预览 → 勾选删除 → 切英文保留勾选 → 提交 → 任务中心完成 → `index.md` 登记新页、删掉悬空行 → 重开体检该类消失。
- **评审中识别、有意不改**：
  - 前像对只写一个文件的任务偏重（整份 wiki/ 副本 + fsync + check 基线），且 `wiki/` 里有目录符号链接或特殊文件时 `preimage.take` 会拒绝，
    Web 修复失败而 CLI 能跑。轻量前像要改 `preimage` / `tasks.py` 的统一流程，等真遇到再说。
  - 预览调 `run_reindex` 时，分区目录外的每一页都会往服务端 stderr 打一行「跳过 …」。界面已经单列这些页；根治要让 `run_reindex` 返回跳过的页而不是打印，留待下次动 `reindex.py`。
  - 代际递增的测试直接调完工回调，不跑真作业：完工回调在信封转终态之后才执行，等任务结束再断言会时序偶发。
- **没做**：CLI `guanlan reindex` 本身仍不取库级锁（`require_kb_root(writable=False)`），与 Web 的写任务同时运行时可能互相覆盖 `index.md`；
  Web 这一侧已经排在写锁之后。CLI 是否取锁另议，不在本节范围。

### 6.3 摘除失效来源（已实现，2026-11-23）

**来路**：撤回（P3.9）时只有被撤回那一个来源的页按决策P3.9-3 原样保留、只报孤儿；之后再入库补上新来源，ingest 只追加、不清旧项——
`sources` 里那条失效项就一直挂着，体检报 `sources.unresolved`（阻断）。撤回当时页面若已有其它来源，`remove` 会当场摘掉（`drop_slug`），
所以问题只出在「先撤回、后补源」这个顺序上：没有任何一步会回头再摘。真实库上撤回一篇新闻后再入库另一篇同人物报道即复现。

- **判据**（`guanlan/deadsrc.py`，零 LLM）：一页 `sources` 里有解析不到 `wiki/sources/<slug>.md` 的项（`check.source_resolves`，
  与 `sources.unresolved` 同一函数），**且同页另有能解析的来源** → 可摘。全部来源都失效的页不摘（摘完 `sources` 为空，等于抹掉出处，
  要从回收区恢复、删页还是补源由人定）；`sources` 不是字符串列表的页不碰（归 frontmatter 校验）。
- **check 提示**：`sources.unresolved` 的文案在可摘时补一句「该页另有 N 个有效来源，此项可直接摘除（Web 体检一键处理，或手改 frontmatter）」。CLI 看得到；写门禁的基线比对（`gate._vkey`）、自愈回喂与失败回执、Web 对话「本轮新增」都截掉这句（本次新引入的失效项多半是笔误 slug，提示会诱导摘源了事）；
  类型与退出码不变。
- **体检**：可摘的阻断条目带 `fix: "dropsrc"`；有一条以上时「阻断性问题」一行的 action 为 `dropsrc`，显示「修复」。同页的失效项要么全可摘、
  要么全不可摘，按页标记，不解析 `detail`（D8 的原则）。
- **预览**：`GET /api/sources/drop-dead/preview` → `{droppable: [{page, dead, live}], manual: [...]}`，不写盘。`manual` 列出全部失效的页并提示
  回收区恢复 / 删页 / 补源。
- **执行**：`POST /api/sources/drop-dead {drops: {页: [失效 slug]}}` → 任务类型 `dropsrc`，走 `_submit_task`（层③ 423、查重、写锁排队、前像、重试），
  与 reindex 同一条路；作业**执行时重算**，只摘「预览里列出」∩「执行时仍失效」的 slug：排在撤回后面时新失效的页或 slug 人没看过，不碰（同 §6.4 删页）。写入复用 `remove._drop_slugs_from_page`：只重出 frontmatter、正文逐字不动、原子写、非 UTF-8 页跳过并列入回执。
  完工回调按写 wiki/ 处理（bump 代际）。
- **不改正文**：正文里对失效来源的 `[[slug]]`、`raw/<slug>.md:N` 不动，之后照常报断链 / 引文找不到出处（警告）——来自被撤回资料的事实是否留着，
  是内容判断，留给人或下次修订。界面文案写明。
- **不变**：不写 `log.md`、不过写门禁（同 reindex，决策P3.4-6）；任务记录即审计。不加 CLI 子命令：CLI 用户看到 check 提示后手改 frontmatter。
- **任务类型命名**：任务 id 形如 `<日期>-<时间>-<kind>-<hex4>`，kind 段只认小写字母，故类型名用 `dropsrc` 而非 `drop_sources`
  （后者建得出信封、却查不到任务）；加了一条测试钉住所有 `TASK_KINDS` 都符合 id 格式。
- **能力上限**：失效 slug 也可能是笔误或来源页改名，而非撤回——摘掉会丢掉这条线索。预览逐页列出失效 slug 与保留的有效来源，由人确认后才执行。
- **与回收区恢复的关系**：恢复只按撤回 manifest 的 `slug_dropped_from` 补回来源，而「先撤回、后补源」的页撤回时是独源页、不在那张清单里——
  摘掉之后再恢复那篇原文，这页不会自动重新挂上它。不因此拒绝摘除（那等于本功能不可用），预览对回收区里仍可恢复的 slug 逐项标出（`in_trash`），由人决定。

### 6.4 删除失源页（已实现，2026-11-23）

§6.3 摘不了的另一半：**全部来源都失效的内容页**（撤回时的独源孤儿，决策P3.9-3 一期只报不删、删除降为后续 `prune-orphans`）。
这里在体检里补上「人逐页确认后删」，不做自动级联。

- **范围**（`deadsrc.prunable`）：`plan_dead_sources` 里 `live` 为空、且不在 `wiki/sources/` 下的页。全部失效的**摘要页**不在此列——
  摘要页随原文走，归撤回 / 恢复；预览里单列为「这里不处理」，体检条目也不标修复入口。
- **预览**：与 §6.3 同一个浮层（`GET /api/sources/drop-dead/preview` 多返回 `prunable: [{page, dead, live, index_lines, backlinks}]`，
  `deadsrc.preview_prune`）。逐页复选框、默认全选。每页各带自己的 index 登记行与入链，**入链不排除同批其它可删页**：前端按勾选现算——
  将删的 index 行 = 勾选页各自行的并集，删后断链的页 = 勾选页的入链去掉同样被勾选的页（取消勾选 B 而只删 A 时，B 链向 A 要报出来）。
  执行时的记录仍按实际删的那批排除。入链复用 `graph.build_graph` 的解析边（别名 / fold 变体同样算数），同 stem 多页时宁可多列。
- **执行**：`POST /api/pages/prune {pages: [...]}` → 任务类型 `prune`。作业**执行时重算**，只删请求清单里**当时仍全部来源失效**的页；
  清单外的页一律不碰（排在长 ingest 后面时新出现的失源页，人没看过），清单里已不可删的（补了来源、已被删）列为跳过。
- **怎么删**（`deadsrc.prune_pages`）：建 `.trash/prune@<ts>/`，**先写记录文件 `prune.json`**（`format`、`kind: "prune"`、`pruned_at`、
  `moved`、`dead_sources`、`index_lines_removed`、`backlinks`），再把页按原相对路径移进去，最后删 index 里指向它们的登记行
  （`remove._prune_index_targets`，与撤回同一个函数）。不改其它页、不写 `log.md`、不过写门禁（同 remove / reindex）。
- **回收区**：记录文件名特意不用撤回的 `manifest.json`——旧版本只会把它认作「未知」，不会误当撤回去恢复。`trash.py` 认出新种类
  `prune`（界面「删页」）：状态判定同撤回（只看归档侧，页还在原处 = 未完成）；但未完成**不受删除保护**——删页没有续跑步骤要用这份记录，
  仍在原处的页本来就没丢，保护反而让取消回滚后（页已放回原处）的条目永远删不掉；`moved` 只接受 `wiki/` 下、非摘要页、
  非 config 页的 `.md`，其余标不合规。可查看、可彻底删；**不支持自动恢复**（`restore_block` 给出原因：按 `prune.json` 手动移回、
  补回 index 行）——用户选定先只做看与删，恢复等真有需要再做。
- **前像**：照拍（只覆盖 `wiki/`）。毫秒级任务里取消回滚的窗口极小；真回滚了，页与 index 恢复原样，回收区那份副本留着、可彻底删。
- **能力上限**：删的是 Agent 生成的内容页，被删页里有价值但未被别处转述的内容随之离开 wiki/（在回收区里还能看到）；链向它的页之后报断链，
  不自动改写（决策P3.9 的「断链是生长信号」）。不加 CLI 子命令。

评审中识别、本期有意不改（有实际问题再处理）：

- **重复扫描 wiki**：check / health / lint 各扫一遍，一次体检约 3 s。合成一次扫描要改三个模块的入口，眼下耗时可接受。
- **lint 建议项经出参字典带回**：内部接口，不影响行为；改成正常返回值留待下次动 lint 时顺带。
- **接口返回全量、界面只显示前 50 条**：负载目前不大；条目多到影响加载再改为服务端截断。
- **既是桩页又是孤立页的页面计两次**：两个类别各自成立、修法不同，按类别计数是有意的；总数可能略高于去重页数。
- **单项扫描出错整体失败**：几项扫描都是确定性的，出错就是缺陷，直接报错比返回残缺结果更容易发现；不做部分结果。
- **「其余断链」的补全范围包含高频目标**：它以 `min-refs=1` 打开 heal 预览，清单里会带上高频缺页；预览中可见、可取消，不另做排除。

## 7. 决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | 合并只在 Web；CLI 三命令不动 | 退出码被写门禁与 CI 使用，合并会破坏契约 |
| D2 | 新增 `/api/doctor`，分组去重在服务端 | 一处实现、可测；前端只渲染 |
| D3 | 断链在「建议处理」，不在「必须修」 | 与写门禁口径一致（`wikilink.broken` 是警告） |
| D4 | 修复入口只打开既有浮层，不直接提交 | 写任务的预览与确认不重复实现 |
| D5 | quotes、reindex 修复推后 | 一个慢且要人判断，一个是写操作（均已落地：quotes 见 §6.1 / D12，reindex 见 §6.2 / D13） |
| D6 | 保留 `/api/report/{name}` | 字节对齐红线；可能有外部调用 |
| D7 | 阻断判定复用 `gate.partition_violations()` | 与写门禁同一口径，不维护第二份白名单 |
| D8 | 断链去重用 `graph.broken` 与 `missing_entities` 的结构化字段 | 不解析中文 `detail`；旧接口契约不动 |
| D9 | 计数按最终展示项；总数不含结构提示 | 去重后仍报原始条数会重现「✗ 3015 条」的误导 |
| D10 | 顶栏「补全」「审计」按钮收进体检，只从「高频缺页」「漂移源」的修复入口打开；「补录」保留 | 补全、审计只处理体检报出的那两类，没问题时按钮只会打开空清单；补录还能重录已收录的源，是主动操作，入口不依赖体检。代价是多一步（先体检，真实库约 3 秒）。浮层与接口不动。「其余断链」也带「补全」入口，以 min-refs=1 打开 heal 预览——否则只有单页引用的断链时到不了 min-refs=1（原顶栏 heal 浮层可调） |
| D11 | reader 部署隐藏体检按钮，接口保留 | 沿用决策P4.9-10（原三个诊断按钮 reader 下就隐藏）；合并后不应悄悄改变这条取舍 |
| D12 | 深查·引文核对用体检内的单飞只读作业（`DeepCheck`），**不进任务中心**（§6.1） | 任务中心按写任务设计：取写锁排队、拍整库前像、取消即回滚、重启判「可能已写入」。只读核对放进去会排在长时间入库后面、反过来挡住可写会话 12 秒，还要在前像 / 回滚 / 恢复 / 抽屉各处加只读分支。§6 原文「走后台任务」的本意（不占住请求、关浮层不丢结果）由进程内后台线程 + 轮询满足 |
| D13 | 索引修复进任务中心（`reindex` 任务类型），预览只看、执行时重算；悬空行默认不删（§6.2） | 它是写操作：要排在在途 ingest 之后（两者都写 `index.md`），并能取消回滚、留记录——正是任务中心的职责（与 D12 相反的理由）。前像 1.7 s 的代价可接受。悬空行删除默认关，与 CLI 一致，删前逐条列出 |
| D14 | 失效来源只在「同页另有有效来源」时可一键摘，全部失效的页只列出、不改；只改 `sources`、不改正文；进任务中心（§6.3） | 有有效来源时摘掉失效项与 `remove` 当场摘 `drop_slug` 同一语义，只是补上「先撤回、后补源」的顺序；全部失效时摘了就没有出处，属于决策P3.9-3 留给人的那一步。正文里的事实是否保留是内容判断，宿主不做 |
| D15 | 全部来源失效的内容页可在预览里逐页勾选、整页移入回收区；只删请求清单 ∩ 执行时仍失效的页；回收区只看与彻底删，不做自动恢复（§6.4） | 补上决策P3.9-3 推后的「删独源孤儿」，但保持「人确认后才删」：不做撤回时的自动级联。进回收区而不是直接删，误删能手动找回；自动恢复要扩 restore 的识别、冲突与续跑，用户选择先不做 |

## 8. 分期

本期一个 PR：`run_doctor` + `/api/doctor` + 前端浮层 + 测试——分组；阻断项覆盖 check 全部非警告类型（含 `aliases.*` / `page.not_utf8` / `wiki.missing`）；
漂移源超过 10 组时全量计数；断链按结构化目标去重与聚合；计数按展示项、总数不含结构提示；reader 下隐藏体检按钮（接口照常）；断链口径钉子。

## 9. 实现说明

- **返回形状**：`{ok, pages_checked, total, elapsed_s, categories: [{key, section, count, items, action}]}`，`categories` 按展示顺序：
  `blocking` / `missing_entity`（action=heal）/ `broken_link` / `pending_raw`（ingest）/ `drift`（audit）/ `index` / `quality` / `topology`（structure，action=graph）。
  按目标聚合的项为 `{target, ref_pages, detail, suggestion?}`；其余项沿用子报告的 `{page, kind, detail}`；漂移源项沿用审计预览的组形状。
- **实测**：一个 1743 页的真实库，原「校验」报「✗ 3015 条」，体检报「✓ 检查了 1740 页，未发现阻断性问题」「另有 1075 项建议处理」（高频缺页 560、其余断链 514 个目标、页面质量 1），
  全量 2.9 s。
- **前端**：顶栏三个按钮换成一个「体检」（`#doctor-btn`）；每类一行可折叠（必须修默认展开），明细每类最多 50 条；页名可点、跳到页面并关浮层；
  修复入口调 `openHealPreview()` / `openIngestPicker()` / `openAuditPreview()` / `openGraph()`，reader 下只保留「打开图谱」。
  旧的 `/api/report/{name}` 保留，前端不再调用。
- **测试**：`tests/test_doctor.py`——类别顺序与计数口径、阻断项与 `partition_violations` 一致（含 `aliases.duplicate`）、断链去重与按目标聚合、
  check 与链接图断链集合一致（含大小写折叠、`#节`、`|别名`）、漂移源超过 10 组全量计数、待入库、索引 / 质量 / 结构分组与总数、端点在个人与 reader 模式下可用、reader 前端隐藏体检按钮、
  旧报告接口保留、页面上不再有三个旧按钮。真浏览器冒烟（不入仓）：总评、类别、修复入口、reader 下体检按钮隐藏且无前端错误、点补全打开 heal 预览、点页名跳页、英文重渲染、无前端错误。
