## 0. 缺的不是埋点，是出口

`guanlan/im/` 一路埋着 DEBUG，而且埋的正是真机排障要问的那几件事：

| 位置 | 已有的 DEBUG 行 | 对应 P4.22 §9 的未决项 |
|---|---|---|
| [`adapters/feishu.py:381`](../guanlan/im/adapters/feishu.py) | 「卡片回调以 CARD 帧下发，已并入 EVENT 分支处理」 | 飞书把卡片回调投在哪种帧上 |
| [`intake.py:206`](../guanlan/im/intake.py) | 「丢弃未授权消息：chat_type=…」 | 未授权点击路径 |
| [`intake.py:217`](../guanlan/im/intake.py) | 「丢弃越权的合成消息：command=…」 | 转发卡片路径 |

但**宿主从不配置 `logging`**（[`server.py:390`](../guanlan/im/server.py) 自己注明过），于是 INFO/DEBUG 没有任何 handler 接（`logging.lastResort` 只兜 WARNING+），这些记录默认一个字也不出现。

想看它们，此前唯一的办法是**改源码插 `print` 再跑一次真机会话**——而真机会话要人拿着手机点，成本不在代码在人。**埋点早就写好了，缺的只是出口。**

## 1. 命令契约

```bash
guanlan -C my-wiki im --platform feishu --allow-user <id> --log-level debug
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `--log-level` | `warning` | `warning` / `info` / `debug`。**只作用于 `guanlan` 自己的日志** |

**无新退出码**。默认档 `warning` **不改变"看得见什么"**：此前无 handler 时 `lastResort` 也只兜 WARNING+。它只改变"长什么样"——多了时刻、级别与 logger 名。

## 2. 决策

- **决策P4.21.1-1（作用域即安全边界：handler 只挂 `guanlan` 树，绝不碰 root）**。这是本阶段唯一真正重要的设计。第三方 SDK（`lark_oapi` / `httpx`）的 DEBUG 会把**消息正文**打出来，而观澜的日志姿态是「只打事件、ID 形状、计数与结果」（P4.21 §9.1，启动横幅那条「只打数量、绝不打 ID」是同一条纪律）。把 handler 挂在 `guanlan` 上、级别也只设在它上面，于是 `--log-level debug` **在结构上不可能**打开第三方 DEBUG——它们的记录属于别的 logger 树，永远到不了本 handler。
  **用作用域代替黑名单**：SAG 的做法是逐个把 `httpx`/`openai`/`LiteLLM` 压到 WARNING。那是**黑名单**——列漏一个就把用户私聊写进日志文件或 journal，而且每加一个依赖就要想起来补一行。作用域是"默认关"，列漏了也不会泄。
  **副作用是好的**：不碰 root 意味着第三方的 WARNING+ 仍照旧走 `lastResort`，与加本阶段之前**逐字节相同**。

- **决策P4.21.1-2（级别设在 logger 上，不是设在 handler 上）**：`logging.getLogger("guanlan")` 默认 `NOTSET`、生效级别继承自 root（WARNING）。只调 handler 级别的话，DEBUG 记录**在 logger 那一层就被丢掉、根本到不了 handler**。这是 `logging` 最常见的一个坑，值得写死在注释里。

- **决策P4.21.1-3（安装点在 `serve_im` 的最前面，早于每一道闸）**：`.env` 加载、只读门、白名单、凭据锁——每一道失败时都可能带日志。装晚了那条路上的记录就看不见，而**拒启恰恰是最需要日志的时刻**（P4.21 §9.1 的白名单死锁就是这么来的）。有专测用"白名单全空拒启"当探针钉住这个顺序。

- **决策P4.21.1-4（幂等安装）**：handler 起名 `guanlan-im-stderr`，装之前先按名摘掉自己上一次装的。测试会连装几次；将来若别的宿主复用同一函数同理。不幂等的代价是同一条记录打两遍，而排障时重复行比没有行更误导。

- **决策P4.21.1-5（只开三档，且显式映射级别名）**：`warning`/`info`/`debug`。再细的档对一个长驻宿主没有使用场景，多一档就多一种要解释的状态。映射用显式 dict 而非 `logging.getLevelNamesMapping()`（3.11+，本包要 3.10），也不用 `getattr(logging, …)`（那会让任意大写属性名成为合法输入）。

- **决策P4.21.1-6（只给 stderr，不给 `--diag-log <file>`）**：落文件是另一档承诺——轮转、留存期限、误传风险都要一并回答。真机排障有 `2>im.log` 就够。SAG 的"设置页一键导出 JSON"更是 Web 产品形态，与命令行宿主无关。

- **决策P4.21.1-7（不复用 `mcpdiag` 的脱敏器）**：观澜确有一套很强的脱敏归口（P4.19，遮 URL 的 userinfo / query / 路径段），但它是**为 MCP 配置写的**——对象是结构化配置里的已知字段。IM 日志面对的是任意文本，两者不同构。本阶段的姿态是**不打消息正文**，而不是"打了再遮"。

## 3. 与硬退出路径的关系

决策P4.21-59 要求第二次中断信号那条路**完全绕开 logging**（`os.write(2, …)` 后 `os._exit(5)`，因为 `logging.shutdown()` 会逐个 `handler.acquire()`/`flush()`，后台线程正持锁时主线程到不了 `os._exit`）。本阶段只在启动时装一个 handler，**不触碰那条路**；硬退出仍**不承诺刷完缓冲**，文档口径一字不改。

## 4. 测试要点（`tests/test_im_logsink.py` 17 例 + `tests/test_im.py` 1 例）

- **出口通不通**：`debug` 档下 DEBUG 出得来；默认档 WARNING 出、DEBUG 不出；`info` 档居中；一律走 stderr 不串 stdout；格式里时刻/级别/logger 名三者俱在。
- **作用域关不关得住**（安全断言）：`debug` 档下 `httpx`/`httpcore`/`lark_oapi`/`websockets`/`openai`/`agentao` 六个第三方 logger 的 DEBUG **一条都不出现**；root logger 的 handlers 与 level **逐字节不变**；同前缀的别的树（`guanlanx`）不被带上。
- **幂等与入参**：连装三次仍只有一个 handler、记录只打一遍；CLI `choices` 里的每一档都真的装得上；未知级别抛 `ValueError`；默认值必须在 `choices` 之内。
- **安装顺序**：用"白名单全空拒启"当探针，钉住 sink 早于第一道闸（挪到 `adapter.start()` 之后即红）。
