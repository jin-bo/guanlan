# P4.36 — 回收区管理（CLI + Web）

> **状态**：定稿（2026-11-24，经五轮评审）。T1、T2 均已实现（实现记录见 §11）。
> 范围：浏览 `.trash/`、单条彻底删除、恢复撤回条目。CLI 新增 `guanlan trash`，Web 在任务中心加「回收区」页签。
> 目标：兑现 P3.9 的「反悔窗」。撤回之后能看到东西去了哪、能放回原处，也能腾出空间。
> 本文承接 P3.9 决策P3.9-10 降为后续项的 `restore` 与 `trash purge`，以及 P4.35 §8「`.trash/` 浏览与恢复界面」。`--cascade` / `prune-orphans` 不在本期。

## 1. 现状

`.trash/` 下目前有三种条目，都由宿主确定性写入：

| 来源 | 目录名 | 记录文件 | 内容 |
|---|---|---|---|
| 单源撤回（CLI `remove`、Web `scope=one`） | `<slug>@<YYYYmmddTHHMMSS_ffffff>[-n]` | `manifest.json`：`slug`、`removed_at`、`moved`、`slug_dropped_from[{page, dropped_slug, before_sources}]`、`orphaned`、`backlinks`、`index_lines_removed`，可能带 `pending_legacy_raw` | 按原相对路径存放的 raw、图片目录、摘要页 |
| 整批撤回（Web `scope=all`） | `<原件目录名>@<ts>[-n]` | `manifest.json`：上述字段，另有 `group`（成员、`identity_keys`、`shared_pages`）和 `slug_dropped_from[].resolved_to` | 同上，多卷 |
| 任务回滚（P4.33 T2） | `job-<task id>@<YYYYmmddTHHMMSS>` | `manifest.jsonl`：首行 `{meta}`，之后每行 `{path, action, saved_as}`（先记录、后移动） | 回滚时移走的、任务新建或改动过的条目 |
| 删失源页（P4.34 §6.4，2026-11-23 新增） | `prune@<YYYYmmddTHHMMSS_ffffff>[-n]` | `prune.json`：`format`、`kind: "prune"`、`pruned_at`、`moved`、`dead_sources`、`index_lines_removed`、`backlinks` | 按原相对路径存放的内容页；`kind=prune`，可看、可彻底删，不支持自动恢复 |

另外，用户也可能手动往 `.trash/` 里放东西，可能是普通子目录、单个文件，没有记录文件，或者记录文件解析不了。

几处与恢复相关的现状限制：

- 单源 manifest 的 `moved` 只记路径，不记内容指纹；`before_sources` 是排序去重后的结果（`remove.py` `_scan_derivatives` 用 `sorted(frozenset)`），原顺序已丢。整批 manifest 的 `before_sources` 保留原顺序。
- P4.35 整批中断后续跑会**新建**一个回收目录，只归档剩余成员（P4.35 §3.5「每次执行各建一个回收目录」）。所以一次整批撤回可能分散在多个目录里，末次目录本身齐全，却只含原批次的后半段。
- 回滚中途服务重启后，信封回到 `rollback_from`（通常是 `interrupted`），前像还在时可以再次回滚，并复用信封里的 `rollback_trash`，写进**同一个**回收目录（`web/tasks.py` `recover`、`_rollback_and_record`）。

现在的恢复方式全靠人工：按 manifest 把文件移回原处，再跑 `guanlan reindex`，再把 slug 逐页补回 `sources`（P3.9 §129）。清理也要手动删目录。Web 端完全看不到 `.trash/`。

## 2. 入口

- **Web**：任务中心抽屉顶部分成「任务 | 回收区」两个页签。理由：
  - 回收区条目几乎都是任务产生的，任务回执里本来就写着 trash 路径。
  - 恢复是写操作，要作为后台任务执行。从发起、看进度到看结果，都在同一个抽屉里完成。
  - 只读部署（reader）下任务中心整个不显示，回收区跟着隐藏，接口也不注册。

  任务详情里的 `.trash/…` 路径做成链接，点了切到回收区页签并展开对应条目；条目恢复后保留（§5.5），链接仍能打开。
- **体检**（P4.34）：信息区加一行「回收区：N 项，共 X MB」，每次体检都显示，空时显示 `0 项`，**不设阈值**，也不计入问题数，保持体检「问题计数」的口径。点了跳到回收区页签。reader 模式不显示这一行。
- **CLI**：`guanlan trash list | show <条目> | purge <条目> | restore <条目>`。`purge` 和 `restore` 默认只预览，加 `--yes` 才执行，与 `remove` 一致。

**列表一律扫描 `.trash/` 得出**，不从任务记录反查。CLI 撤回不产生任务记录，任务记录也可能已被保留策略清掉。

## 3. 列表与详情（T1，只读）

### 3.1 目录安全与条目识别

两件事分开判断，各用自己的条件：

- **目录安全**（先判，不过就整体不扫）：`.trash` 本身须是真目录（不是软链接），解析后位于库根下。每个条目须是 `.trash` 下的直接子项，且本身不是软链接。扫描与删除**都不跟随条目内部的任何链接**：遍历用 `os.scandir` + `follow_symlinks=False`，链接只按自身计数、按自身删除。
- **条目识别**（只决定种类，不决定能不能看到）：
  - 目录名匹配系统条目的时间戳形态（`^[^/\\]+@\d{8}T\d{6}(_\d{6})?(-\d+)?$`），且有能解析的记录文件 → 按记录文件识别为 `remove` / `remove_batch` / `rollback`。
  - 其余一切（手动放进去的普通目录、单个文件、名字不合形态、记录文件缺失或损坏）→ `unknown`。照样列出、能看大小、能彻底删除，只是不给恢复。

### 3.2 条目字段

`trash.scan(root) -> list[TrashEntry]` 是纯函数，零 LLM，不写盘。每个条目包括：

- `name`：条目名；`kind`：`remove` / `remove_batch` / `rollback` / `prune`（P4.34 §6.4）/ `unknown`。
- `when`：取记录文件里的时间，没有就取目录名里的时间戳，再没有就取 mtime。
- `size`、`files`：大小与文件数，按 §3.1 不跟链接。
- `subject`：单源为 slug，整批为原件目录与卷数，回滚为任务 id 与任务标题（任务记录还在时才有标题）。
- `origin`：整批条目是首次撤回还是续跑产生的（§5.1）。
- `state`：
  - 撤回条目：
    **只看归档侧**判断完整性，原位置只在有缺项时参考：
    - `complete`：`moved` 里的每一项都在条目里。原位置上有没有同名文件不影响——完整撤回后重新入库是正常操作，不能因此把旧归档锁住；首次恢复时的原位占用由 §5.2 按冲突拒绝。
    - `incomplete`：有 `moved` 项不在条目里，且该项的原位置仍在。撤回没有完成，P3.9 续跑或 P4.35「重新预览」还要用到这份 manifest。
    - `partial`：有 `moved` 项不在条目里，原位置上也没有（已由续跑归档到别的目录，或被人动过）。
  - 回滚条目：**看归档侧**，即每条记录的 `saved_as` 是否仍在条目里。全在为 `complete`，否则 `partial`。同一路径有多行记录时（回滚崩在「记录」与「移动」之间、重跑再以新序号移一次），只要其中一行已归档就算这一项在。不看原位置：回滚的后续步骤会把前像内容写回同一路径，原位置有东西是正常的。
  - `restoring`：有 `restore.json` 且没有 `finished_at`，恢复做了一半（§5.3）。
  - `restored`：已恢复（§5.5）。
  - `unknown`：见 §3.1。
- `protected`：当前是否受删除保护，附原因（§4.2）。

详情把记录文件翻成人能读的清单：移了哪些文件、从哪些页摘了哪些 slug、删了哪些 index 行，回滚条目则列出移走了什么。只展示，不允许编辑。

### 3.3 manifest 不可信

记录文件在库内，Agent 也能写。凡是会被读、会被写的路径都先校验：相对路径、没有 `..`、各级都不是软链接、位于允许的前缀下。

- 撤回条目：`moved` 限于 `raw/`、`wiki/sources/`；`slug_dropped_from[].page` 限于 `wiki/` 下的内容页 `.md`，排除配置页 `index.md`、`log.md`、`overview.md`。
- 回滚条目：`path` 限于前像范围（`wiki/`、`AGENTAO.md`、`SCHEMA.md`），`saved_as` 须落在本条目内。

核对不过的那一项标为 `invalid`，整个条目不给恢复，但仍可浏览与删除。只要路径本身是合规的相对路径，`invalid` 项照样参与状态判断：原位置还在（库侧目录是链接也跟过去看）就算撤回未完成、受保护；归档侧途经链接的不认作已归档。不能因为记录看不清，就把续跑要用的 manifest 当成完整的删掉。

## 4. 彻底删除（T1）

### 4.1 行为

`purge` 递归删除一个条目，**不可恢复**，一次一条。

- CLI 预览列出条目、大小、文件数，加 `--yes` 才删。
- Web 在详情里放「彻底删除」按钮，点了在浮层里二次确认，写明条目名与「不可恢复」。不弹浏览器的 `confirm()`。
- 本期不做按时间批量清理（`--older-than`），见 §8。

删除只碰 `.trash/`，所以**不进任务中心**。CLI 与 Web 都在**库级写锁内**做 §4.2 的检查并删除；拿锁非阻塞，库被占用时 CLI 报错退出，Web 返回 423（层③）或 409（写锁），不排队。

**必须真正拿到库级锁。** Web 的 `KBWriteLock` 在库级锁文件打开失败（`OSError`，如只读介质）时会退化为只有进程内锁（`web/jobs.py`）。`purge` 不接受这种退化：直接调 `kblock.acquire`，拿不到（忙或 `OSError`）一律失败退出、什么都不删，否则 CLI 与 Web 的互斥只是纸面承诺。`kblock.acquire` 在祖先写运行持锁时会返回 `nested=True` 的嵌套放行，这时调用方并未独占持锁，同样视为失败。T2 的恢复登记与执行沿用这条规则。

### 4.2 删除保护

在写锁内按**实际续跑条件**判断，以磁盘上的任务信封为准（CLI 也读 `workspace/jobs/`，不依赖 Web 进程是否在跑）。

**匹配与删除都用扫描到的实际目录名。** 先在 `.trash` 的目录列表里找到与请求名对应的条目（大小写不敏感的卷上，另一种拼写也能打开同一目录），之后的保护检查（如与 `rollback_trash` 比较）和删除都用这个实际名字，不用请求里的字符串。找不到返回 404。

以下情况拒绝删除，返回 409 并写明原因：

1. **撤回未完成**：`state == incomplete`。续跑要读这份 manifest（P3.9 `_pending_legacy_raw` 读的就是 `.trash/<slug>@*/manifest.json`）。
2. **回滚还可能续跑**：有任务信封的 `rollback_trash` 正好等于这个条目路径，且该任务满足以下任一：
   - 状态为 `rolling_back`，或排队、等锁中的回滚作业；
   - 状态为 `interrupted` / `rollback_failed` 且前像目录仍在（与 `has_preimage` 同一判据）。下一次「回滚」会并入这个目录。
   用户在任务中心对该任务选「保留现状」或删除记录后，保护自动解除。
3. **恢复未完成**：条目有 `restore.json` 且没有 `finished_at`（§5.3）。不看任务记录——任务中断或记录被删了，这份进度仍要保住。
4. **正被恢复任务引用**（T2）：有 `restore` 任务处于排队、等锁或运行中，目标是这个条目。

T2 接入时，**恢复登记与删除检查须用同一把跨进程锁互斥**，否则会出现「删除刚检查完、恢复就入队」的竞态（恢复入队时还没拿写锁）。`TaskStore` 的锁只在 Web 进程内生效，挡不住 CLI `purge --yes`。做法是复用库级锁（`kblock`，同样不接受退化）：

- Web 提交恢复：在库级锁内核对条目可恢复、落盘任务信封（含目标条目名），然后释放；worker 之后照常排队取写锁执行。锁忙返回 409。
- 删除：在库级锁内读磁盘上的任务信封，按 §4.2 第 4 条判断有没有引用该条目的恢复任务，再删除。

这样「登记」和「删除」都发生在库级锁内，CLI 与 Web 之间也不会交错。

## 5. 恢复（T2）

### 5.1 范围

- **单源撤回条目**：可以恢复，但只恢复首次执行留下的、`format >= 2` 的条目。单源中断后续跑也会拆成多个目录，续跑目录单独恢复会放回残缺的源、补不回图片和引用。两种已验证的拆分：
  - 先移走图片、摘掉引用后中断，续撤目录只剩 raw 和摘要页。删掉前一个目录后，续撤目录看起来是完整的，却补不回图片和引用。
  - 旧名摘要页移走后中断，再用 raw 的新名续撤：slug 变了，raw 路径没变，按 slug 找不到前一个目录。
  - **新条目判定续跑按实际路径，不按 slug**，判定规则见下文「续撤判定」，单源与整批共用。
  - **旧单源条目（没有 `format`）一律只展示**，与旧整批相同。上面两种拆分在旧记录上都无法可靠识别。
- **整批撤回条目**：只恢复**一次撤回留下的完整批次**，即首次执行的目录，且它的 `group.members` 全部在本条目内归档。整批作为一个整体恢复，不支持只恢复其中一卷。
  - 续跑产生的条目只展示、不给恢复，交人工处理。即使它自身齐全，也只含原批次的后半段，单独恢复会让共享页和跨卷引用补不全。
  - 为此，整批 manifest 新增 `format: 2` 与 `origin`，判定见下文「续撤判定」。这是 T2 的前置改动，写进 `remove_batch.py`。
  - **改动前的整批条目（没有 `origin`）一律只展示。** 旧续跑目录的 `group.members` 本来就只列剩余卷，「成员齐全」会让它冒充完整批次，靠成员判断不可靠。
- **续撤判定**（单源与整批共用，写在执行函数里、manifest 落盘之前）：本次计划的待移路径里，只要有一项出现在回收区某个旧撤回条目（单源或整批）的 `moved` 里、而那个旧条目的归档侧缺这一项（即旧条目 `incomplete`），本次就记 `origin: {"kind": "resume", "from": [<命中的旧条目名>, …]}`。整批从任务中心续跑时另记 `from_task`，并且一律记 `resume`：能走这个入口的旧任务都已开始写，本次必定只含原批次的一部分，不靠路径命中判断。其余情况都不命中才记 `{"kind": "first"}`。
  - 不按入口区分，因为跨入口会拆：单源撤回移走 A 卷的摘要页和图片后中断，再从 B 卷发起整批撤回，整批计划仍含 A、B 两份 raw，却缺 A 的摘要页、图片和已摘引用。按路径判定，这次整批会命中 A 的单源旧条目，记为 `resume`，不会冒充完整批次。
  - 判定只读回收区、不写，执行函数在写锁内调用。
- **回滚条目**：本期不恢复。恢复它就等于撤销一次回滚，而回滚之后库里很可能已有新写入。详情里展示清单，需要时由人工取回。
- **`unknown` / `partial` / `incomplete` / 含 `invalid` 项的条目**：不恢复，详情里说明原因。含 `invalid` 项的，原因逐条写出路径和不合规之处（如 `wiki/sources/x.md：路径途经软链接（wiki/）`），并提示按 manifest 手动恢复。`partial` 的意思是有些文件已经不知去向，按 manifest 补回引用会指向不存在的源。

### 5.2 预览

`GET /api/trash/restore/preview?name=` 与 CLI `trash restore <条目>` 用同一个纯函数 `plan_restore(root, entry) -> RestorePlan`：

1. **放回文件**：列出 `moved` 中每一项的去向。
   - **首次恢复**（没有 `restore.json`）：原位置只要被占用就是冲突。占用包括同名文件、目录、软链接，**悬空链接也算**。有冲突时整个条目拒绝恢复，列出所有冲突路径。不做合并、不覆盖、不改名。
   - **续跑**（有未完成的 `restore.json`）：见 §5.3。
2. **补回 `sources`**：先把 `slug_dropped_from` 按页分组，**一页一次比较、一次写回**（整批里同一页可能摘了多个 slug）。对每一页：
   - 页面不在了：跳过，列为提示。
   - 本页要补的 slug 都已在 `sources` 里：跳过（幂等）。
   - 当前 `sources` 等于 `before_sources` 去掉本页被摘的 slug：按 `before_sources` 原位补回，算**干净补回**。可恢复的条目都是 `format >= 2`，`before_sources` 保留了原顺序。
   - 其他情况：说明页面在撤回后被改过，把缺的 slug 追加到末尾，列为「页已改动，请核对」。
   - 整批里 `resolved_to.raws` 含多卷的条目（共享摘要页）：只有该页和这些卷都在本次恢复范围内才补回（P4.35 §3.6）。按 §5.1 只恢复完整批次，所以这个条件总是成立。
3. **补回 index**：复用 `reindex` 的登记逻辑，但把候选**限定为本次恢复出来的摘要页**，不顺手登记库里其他未登记的页。不重放 `index_lines_removed`，因为撤回后 index 可能被改写过，这份字段只在预览里展示。
4. **提示**：manifest 里的 `orphaned` 页恢复后会重新有来源，`backlinks` 页的链接也会重新可达，两者都列出来供核对。这些页在撤回时没有被改动，所以不用写。
5. **与撤回冲突**：库里还有 `remove` 任务在排队、运行，或者是 P4.35 定义的待续任务，而且涉及同一个 slug 或同一原件时，拒绝恢复。

恢复预览同样计算 `plan_digest`，覆盖条目内容哈希、各目标位置的现状、各待补页的当前 `sources`。执行时在写锁内重算并核对，不一致就什么都不写（与 P4.35 §3.4 同理）。

T2 前置改动：单源撤回的 `before_sources` 改为记录页面原列表（不再排序去重），并写 `format: 2`。没有 `format` 的旧条目按 §5.1 只展示，不进入这套补回逻辑。

### 5.3 执行与续跑

任务种类 `restore`，与 `remove` 一样**不拍前像**。恢复要往 `raw/` 里写，而前像不覆盖 `raw/`（P4.35 §2）。所以它同样运行中不可取消，没有「回滚 / 保留现状」，中断后靠重新预览向前收敛。`NO_PREIMAGE_KINDS` 加入 `restore`。重启恢复与重试照搬 P4.35 §3.5：用 `restore_writes_began` 区分 `cancelled` 和 `interrupted`，通用重试返回 409。

执行顺序是撤回的逆序，每一步都幂等：

**移动只用同一文件系统内的原子重命名**（`os.replace`）。预览时比较条目与各目标父目录所在的设备，跨文件系统（如 `wiki/` 链到别的卷）报冲突，不退回「复制后删除」。这样中断后每一项只可能在两侧之一，不会两侧各有半份。

**首写前校验**（首次恢复与续跑都做，在 `restore.json` 写入或续跑第一次移动之前完成，不过就整体拒绝、零写入）：

- 清单来自通过 §3.3 校验的 manifest `moved`，`restore.json.items` 与它**逐项对应**。续跑时 `items` 只用来确认进度，不能增删项：两者不一致（项数、路径不同）判冲突。
- 目标之间不能重复，也不能重叠（一项是另一项的祖先路径）。
- 每个目标的父路径要么已是真目录，要么可以逐级创建：途中不能有文件、软链接或特殊文件挡路。
- 归档侧逐项检查类型：单文件须是普通文件；图片目录整棵树里只能有普通文件和真目录，**出现软链接或特殊文件就拒绝**。
- 指纹在类型检查通过之后再算。现有 `path_digest` 用 `is_file()` / `rglob` 会跟随指向文件的链接，恢复侧另写一个不跟链接的版本（遇到链接直接报错），不复用它。
- **`sources` 与 index 也在首写前检查**，沿用撤回的处理（`remove.py` `_drop_slugs_from_page`：非 UTF-8、无 frontmatter 块、块不是映射都不动）：
  - 衍生页缺失、不是普通文件、编码或 frontmatter 无法安全编辑：预览列为「跳过」，不阻止恢复，回执照列。执行时同样跳过，不会崩在中途。
  - 顺序：**先确认 `index.md` 可以安全读取**（普通文件、不是链接、UTF-8 可解码），再据此判断恢复出来的摘要页是否已登记。读不了就无法判断，直接在首写前报冲突、零写入。
  - 需要补登记时，再确认 `index.md` 可写；不可写同样首写前报冲突。确认无需补登记时，省掉写入检查。

① **在第一次移动前**原子写入 `restore.json`：`{started_at, task_id?, plan_digest, items: [{path, kind: file|dir, sha256 | tree_digest}]}`，逐项记下每个待放回项的路径和内容指纹（文件取 sha256，目录取上述不跟链接的树摘要）。写入失败就不动任何文件。
② 放回文件，**raw 先放**：raw → 摘要页 → 图片目录。raw 是定位源的锚，先放回之后，中断再重跑时，后面的步骤都能按 slug 找到它。
③ 补回 `sources`。
④ 补回 index。
⑤ 在 `restore.json` 写上 `finished_at`。

**续跑判定**（有 `restore.json`、无 `finished_at`）：对每一项，

两侧都核指纹，以首次写入的 `restore.json` 为准：

- 归档侧还在、原位置空、**归档内容指纹与记录一致**：待放回。指纹不符说明中断后归档被改过，判冲突，不把改过的内容放回去。
- 归档侧已消失、原位置内容指纹与记录一致：**已放回**，跳过。
- 其他情况（归档侧还在且原位被占，或归档侧消失而原位指纹不符、或原位为空）：冲突，拒绝续跑，列出明细交人工处理。

只有 `restore.json` 能做逐项核对：撤回 manifest 的 `moved` 只有路径，`plan_digest` 只能整体判断「变没变」，不能判断「哪一项是自己放回去的」。

未完成的恢复始终可以重新预览、提交续跑，并且持续受删除保护（§4.2 第 3 条），不论任务是中断了还是记录已被删除。

### 5.4 回执

- 放回了多少文件、干净补回几页、追加补回几页（要核对）、跳过几页、补了几条 index。
- 恢复不会重新 ingest。撤回期间如果别的页已经改写过（比如失源页被人重写），恢复不处理，回执提示可跑 `guanlan check` / `audit`。

### 5.5 恢复后

条目目录保留，里面只剩 `manifest.json` 和 `restore.json`，列表上显示「已恢复」，详情里给出恢复时间和任务 id。用户可以手动彻底删除。任务详情里指向它的链接继续可用。

## 6. 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/trash` | 列表，按时间倒序，含 `protected` |
| GET | `/api/trash/{name}` | 详情 |
| POST | `/api/trash/purge` | `{name}`，同步执行；409 / 423 见 §4 |
| GET | `/api/trash/restore/preview?name=` | 恢复预览（T2） |
| POST | `/api/restore` | `{name, plan_digest}` → `restore` 任务（T2） |

reader 模式下这几个接口都不注册。`{name}` 只按「是 `.trash` 的直接子项、不含路径分隔符、不是 `.`/`..`」校验，不合规返回 400；不要求时间戳形态，否则 `unknown` 条目删不掉。

## 7. 能力上限与失效规则

- **只恢复撤回留下的东西。** 不恢复撤回之后的改写，不撤销 ingest，也不撤销回滚。
- **只恢复首次撤回留下的新格式条目。** 续跑产生的条目、没有 `format` 的旧条目（单源、整批）、`partial` 条目只能看、只能删；需要时按 manifest 人工恢复。
- **只在同一文件系统内恢复。** 目标在另一个卷时报冲突，不做复制后删除。
- **`wiki/`（或 `raw/`）是软链接的库只支持手动恢复。** 按 §3.3，这类库的撤回记录里每条经过链接的路径都标 `invalid`，T1 照常列出、可删除，T2 不给恢复。恢复预览要写明具体原因（哪条路径途经哪一级链接），并提示按 manifest 手动恢复。不放宽顶层这一层链接：放宽就要另外判断「预览后链接目标有没有变」和「实际落点是否跨卷」，T2 只做同卷原子移动。
- **冲突就停。** 原位置被占用（含悬空链接）时不合并、不覆盖、不改名，交给用户先处理。
- **补回 `sources` 是尽力而为。** 页面被改过时只追加并提示核对，不推断用户本意。
- **index 文本不保证与撤回前相同。** 只保证恢复出来的摘要页都已登记。
- **本期不做按时间自动清理，也不做容量上限。** 回收区只会越来越大，靠体检那一行提醒。
- **识别靠记录文件。** 新的条目来源（比如将来的 `prune-orphans`）必须写记录文件，否则只会显示为 `unknown`。

## 8. 推后 / 非目标

- 按卷恢复整批条目、把续跑产生的多个目录合起来恢复：要处理共享摘要页与 `resolved_to` 跨卷的拆分，等有人需要时再做。
- 恢复回滚条目。
- `trash purge --older-than` 与自动 GC。
- 冲突时合并或改名恢复。
- `--cascade` / `prune-orphans`。

## 10. 测试要点

### T1

- 识别：三种条目各认出种类；手动放入的普通目录、单个文件、名字不合形态、记录文件损坏都显示为 `unknown`，可删除。
- 目录安全：`.trash` 是软链接时整体不扫；条目是软链接时不跟随；条目内部链接不跟随，删除只删链接本身，链接目标完好。
- 状态：撤回条目 `complete` / `partial` / `incomplete`（构造「撤回中断」）；回滚条目原位置已被写回时仍判 `complete`，归档侧缺项判 `partial`。
- manifest 校验：`..`、绝对路径、越界前缀、路径中间有软链接、`saved_as` 指向条目外，都标 `invalid`。
- 状态：完整撤回后同一路径重新入库，旧条目仍判 `complete`、可删除。
- 删除保护：
  - `incomplete` 撤回条目拒绝。
  - 回滚中途重启：信封回到 `interrupted`、前像仍在、`rollback_trash` 指向该条目 → 拒绝；选「保留现状」后 → 允许。
  - `rollback_trash` 指向别的目录时不误伤。
  - CLI 在 Web 未运行时同样按磁盘信封拒绝。
  - 有未完成 `restore.json` 的条目拒绝（T2 写入，T1 先按字段判断）。
- 锁：库被占用时 CLI 报错、Web 返回 423 / 409，不排队；**库级锁打不开（模拟 `OSError`）或只拿到嵌套放行时，删除失败、条目仍在**；reader 模式不注册。
- 实际目录名：在大小写不敏感的卷上用另一种拼写请求删除回滚条目，仍按实际目录名命中保护并拒绝。
- 体检：空回收区显示 `0 项`；不计入问题数。

### T2

- 单源往返：撤回后恢复，盘面一致；所有引用都补回、摘要页已登记。index 文本允许与撤回前不同，不做逐字比较。
- 整批往返：包括共享摘要页、双身份；同一页摘了多个 slug 时一次写回。
- **中断 → 续撤 → 末次目录不能单独恢复**：整批与单源各一例。首次目录 `partial`、末次目录 `origin.kind == resume`，二者都不给恢复。
- 旧条目：没有 `format` 的单源与整批条目都只展示、可删除。
- 单源续撤识别：「先移图片、摘引用后中断」与「旧名页移走后用新名续撤」两种拆分，续撤目录都记为 `resume`、不给恢复；后一种 slug 不同也能识别。
- **跨入口续撤**：单源撤回移走 A 卷的摘要页和图片后中断，再从 B 卷发起整批撤回，整批条目记为 `resume`（`from` 含 A 的单源旧条目），不给恢复。
- 冲突：首次恢复时原位有文件、目录、悬空链接都整体拒绝、零写入。
- 续跑：恢复中断后，已放回且指纹一致的项跳过；原位被替换成别的内容时判冲突；**中断后归档侧内容被改，判冲突、不放回**；任务记录删掉后条目仍显示「恢复中」、仍受删除保护、仍可续跑。
- 跨文件系统：目标在另一个卷时预览报冲突。
- 首写前校验：目标重复或互为祖先、父路径上有文件挡路、图片目录里有软链接或特殊文件、续跑时 `items` 与 `moved` 不一致，都在写任何东西之前拒绝。
- `sources` 与 index：衍生页缺失、非 UTF-8、frontmatter 坏时预览列为跳过、恢复照常完成；需要补登记而 `index.md` 被换成目录（或无法解码）时零写入。
- 摘要失配时零写入。
- index 只登记本次恢复的摘要页，库里另一张未登记的页保持未登记。
- 重启恢复按 `restore_writes_began` 区分；重试返回 409。
- 与待续撤回任务冲突时拒绝。
- 并发：CLI `purge --yes` 与 Web 提交恢复同一条目，只有一个成功；先登记恢复则删除被拒，先删除则恢复提交返回 404 / 409。
